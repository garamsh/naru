# Config

How a Node's configuration and network reach init in P0, and the shape of the files.

Claims about garamsh/gaon hold at commit `c2b42f91724cae39a4f6824517c278150cf4695f`, and about garamsh/mvmd at `b1a60cd649673a6db5fa72ca8cc23f088fd83639`, the pin the PM moved to for aurora#811 from `191326aca748a0e6e365578016ab87455107164e` ([ADR 0038](./adr/0038-the-host-api-stops-and-starts-a-microvm-and-restart-on-boot-brings-a-microvm-back-after-its-host-restarts-and-naructl-takes-the-os-forms-flags.md)); they promise nothing about later versions. Those about mvmd were read at `d189133bba8d842d2bcb20046f39fe03161efeb1`, and were not read again at the new commit. They were read at those commits when they replaced `d643b1cb6a6cc01ea587dd7c967bdfd07280fe0b` and `f08e9130c57c0d71e2bb21ac1deb048563ec3ef8`: gaon's `resource-api.md` §Common rules and mvmd's `runtime.md` §Network and `daemon/internal/app/config.go`.

## Current decisions

- **Delivery.** A cloud-init NoCloud drive: a block device with an ISO 9660 volume labelled `cidata` (either case), the form Proxmox's cloud-init drive takes. Init mounts it read-only and reads two files: `user-data`, which is `naru.yaml`, and `network-config`. `meta-data` is not read. It is not `fw_cfg`, and no ext4 `NARUCFG` disk is read.
- **Shape.** `apiVersion: naru.garam.sh/v1alpha1`, `kind: NodeConfig`, `metadata.name` the node name, and `spec`. There is no `status`. The shape follows gaon's resource rule, "Every resource has `apiVersion`, `kind`, `metadata`, `spec` and `status`" (gaon `docs/architecture/resource-api.md` §Common rules), minus `status`, which a file has no observer for.
- **`spec` holds:**

- **The network is `network-config`**, in the version 1 form Proxmox writes (qemu-server `src/PVE/QemuServer/Cloudinit.pm`, at commit `b0965eeba61248046f803a4995112f0ab8523843`). Init accepts only `version: 1`; `physical` cards, each with a `mac_address` or a `name` (the MAC wins when both are given, and init does not rename a link), a static IPv4 subnet (`address` with a dotted `netmask`, or in CIDR form) and at most one `gateway`, which lies inside the prefix; and one `nameserver` entry with `address` and `search` lists. A `dhcp4` subnet, which takes no address, netmask or gateway and must be the interface's only subnet, asks for DHCPv4 (at most one interface may); an absent or empty file is DHCPv4 on the first Ethernet link with a carrier. It refuses IPv6, bonds, VLANs, bridges, routes, an unknown field and a malformed value. Init sets each link up, adds its address and the default route through netlink, and writes the resolvers to `/run/naru/resolv.conf`, which `/etc/resolv.conf` links to.
- **Init validates before it acts.** An unknown `apiVersion` or `kind`, a field the shape does not name, a value that fails validation, or a file that does not parse, stops init before any service starts; the error names the field. The same holds for a `network-config` that is malformed or asks for what init does not apply, and for a drive that is missing, has no `user-data` or has no `network-config`. What init does next is in [init.md](./init.md).
- **Configuration has revisions.** The `user-data` is the base at revision 0; an apply stores revision N+1 on the data disk in `/var/lib/naru/config/store.yaml` with the SHA-256 of the base. At boot init uses the stored configuration only when that digest equals the current `user-data`'s and the configuration validates. An apply is a merge patch with keyed lists (RFC 7386, with `spec.services` and `spec.files` merged by `name` and `path`, `spec.storage` by `name`, `spec.network.routes` by `to`, and the two lists of `spec.pki` by `name`) or a whole replacement. The fields an apply may change (`spec.services`, `spec.files`, `spec.network.routes`, `spec.pki.certificates` and `spec.api` other than its `listen` and its presence), may change only by a reboot (`spec.controlPlane`, `spec.storage`, `spec.network.forwarding`, `spec.pki.authorities`, `spec.api.listen` and whether `spec.api` is present) and may never change (`metadata.name`, `spec.dataDisk`, `apiVersion`, `kind`) are in [ADR 0018](./adr/0018-a-nodes-configuration-is-a-base-and-numbered-revisions-stored-on-the-data-disk-and-changed-by-merge-patch.md); what init does with each is in [init.md](./init.md).
- **Restart policy.** `spec.services[].restartPolicy` is `always` (the default) or `on-failure`; with `on-failure` a service that exits with status 0 is left stopped ([ADR 0058](./adr/0058-a-host-boots-from-a-join-form-that-names-an-orch-and-an-enrollment-key-and-init-applies-the-configuration-hostd-brings-back.md)).
- **Restart backoff is fixed in P0.** A service that exits is restarted after 1 s, doubling to a cap of 30 s, reset after a run of 60 s. The file has no field for it.
- **Forwarding.** Init turns on `net.ipv4.ip_forward` and `net.ipv6.conf.all.forwarding` for the families `network` names, before it starts mvmd, since mvmd never sets it and refuses to start when a served family has it off (garamsh/mvmd#311).
- **mvmd's `network` section is required.** mvmd refuses, at load, a Firecracker or Cloud Hypervisor configuration without it (mvmd `docs/architecture/runtime.md` §Network, "A real Driver needs the `network` section"; `daemon/internal/app/config.go`, `Config.check`). The Node configuration tooling writes `network.ipv4_prefix`, `ipv4_gateway` and `resolvers` (`node.Config.MvmdJSON`), and `spec.network.forwarding` turns forwarding on, so both of mvmd's conditions hold.
- **mvmd's `network.no_masquerade` keeps a Machine's source address to another Node's Machines.** It is a list of CIDRs, empty by default, in the families the node serves; one accept for each sits in mvmd's postrouting chain ahead of the masquerade, matching on the destination, and a change of it takes an mvmd restart (mvmd `runtime.md` §Network, ADR 0049, at the commit above). Routes to those prefixes are not mvmd's, so they are `spec.network.routes`. `naructl gen node --peer` writes both, below.
- **mvmd's `supervision.dir` is left empty without storage, and is `/var/lib/naru/mvmd-storage/machines` with it.** mvmd refuses one that is the state directory, an ancestor of it, or inside it other than at `machines`; empty means `machines` under `state_dir` (`daemon/internal/app/config.go`, `sharesStateDir`), which `node.Config.MvmdJSON` relies on. With a storage disk the run directories go to the storage mount, outside `state_dir`, so that a snapshot taken in by rename stays on one file system; `state_dir` stays `/var/lib/naru/mvmd`, whose file system has fs-verity for the Image Store, and `conversions/` stays under it ([ADR 0073](./adr/0073-mvmds-disks-snapshots-and-run-directories-are-on-the-first-storage-disk-through-links-while-its-state-directory-stays-on-the-data-disk.md)).
- **naru knows no service's internals.** Name, binary and arguments come from this file.
- **gaon's certificates are `files`, or are issued from `spec.pki`, and an agent's pair comes from a signing request.** A Node that carries no CA key gets its certificates as `files`, as below. A control-plane Node whose `spec.pki` carries the CA and its key gets the API server's, scheduler's and controllers' pairs init issues at boot under `/run/gaon/`, in the same places, and the services name them with the same flags; a Node Agent there holds a bootstrap token instead of a pair and is issued one by `gaon-controllers` ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md); gaon ADR 0007 at gaon commit `c2b42f91724cae39a4f6824517c278150cf4695f`) ([ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md), which supersedes item 5 of ADR 0012). For `files`: a Node's CA, its agent's pair and, on the control-plane Node, the API server's, the scheduler's and the controllers' pairs are entries of `spec.files` under `/run/gaon/`, which the gaon services name with their `--tls-*` flags, as gaon's `deployment.md` §Certificates and §Config shape ask. The files' content is the tooling's input; init writes it and knows nothing of it ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)).

## Operator tooling: naructl

`naructl` is the operator's tool for a gaon cluster on naru Nodes. It writes the CA, each Node's user-data and `network-config`, and the operator's client certificate pair; it calls the gaon Node layout (services, `spec.pki`, the worker's files, mvmd's configuration, the data disk's paths), which is the module `lib/layout` that orch also calls, and which `tooling/qemu` runs through the binary and does not copy ([ADR 0015](./adr/0015-naructl-is-the-single-owner-of-the-gaon-node-layout-and-tooling-qemu-runs-it-as-a-binary.md), [ADR 0060](./adr/0060-the-gaon-node-layout-is-the-library-lib-layout-called-by-naructl-and-by-orch-when-it-builds-a-joining-hosts-configuration.md)). It is a static linux/amd64 binary, the release asset `naructl-<version>-linux-amd64`, and every file it writes is one `naru-init -validate` accepts. The example below is the release's example deployment, with `guest.json` the release's `naru-guest-<version>.json` and `$FIRECRACKER` the `firecrackerSha256` of its `naru-inputs-<version>.json`:

```sh
naructl gen ca --ca-dir ca                        # ca/ca.pem, ca/ca.key
naructl gen token --ca-dir ca --name node-2        # ca/tokens/node-2, once per Node before node-1's gen node
naructl gen node --ca-dir ca --name node-1 --control-plane \
  --address 192.168.0.40/24 --mac 02:00:00:00:03:e9 --gateway 192.168.0.1 --nameserver 1.1.1.1 \
  --api-server 192.168.0.40 --machine-prefix 10.200.1.0/24 \
  --guest guest.json --firecracker-sha256 "$FIRECRACKER" \
  --out node-1.user-data --network-config node-1.network-config
naructl gen node --ca-dir ca --name node-2 \
  --address 192.168.0.61/24 --mac 02:00:00:00:03:f4 --gateway 192.168.0.1 --nameserver 1.1.1.1 \
  --api-server 192.168.0.40 --machine-prefix 10.200.2.0/24 \
  --guest guest.json --firecracker-sha256 "$FIRECRACKER" \
  --out node-2.user-data --network-config node-2.network-config
naructl gen client --ca-dir ca --cn alice --out client   # client/client.pem, client/client.key
naructl gen etcd-client --ca-dir ca --out etcd-client    # etcd-client/ca.crt, tls.crt, tls.key
```

- **`gen ca --ca-dir <dir>`** writes `ca.pem` and `ca.key` (ECDSA P-256, valid ten years; the key `0600`) and refuses to replace an existing `ca.key`.
- **`gen token --ca-dir <dir> --name <name>`** makes the Node's bootstrap token, `[a-z0-9]{6}\.[a-z0-9]{16}` from `crypto/rand`, in `<dir>/tokens/<name>` (mode `0600`), and leaves an existing one as it is. It checks that `<dir>` holds a CA.
- **`token create --ca-dir <dir> --name <name> --config <client file>`** and **`token revoke`** add or revoke a Node's bootstrap token on the running control-plane Node, with no reboot ([ADR 0081](./adr/0081-a-bootstrap-token-is-added-or-revoked-by-a-live-patch-to-the-control-plane-nodes-token-list-file-from-the-operators-token-store.md)): `create` makes `<dir>/tokens/<name>` as `gen token` does, `revoke` deletes it (exit 1 when there is none), and each then patches `spec.files` of the Node the client file reaches with the list file `/run/gaon/bootstrap-tokens` (`0600`, `restart: [gaon-apiserver]`), whose content is every token of `<dir>/tokens` in the order of the names. `--kubernetes` patches `/run/kubernetes/bootstrap-tokens.csv` instead.
- **`gen node`** writes the Node's `user-data` (`--out`, mode `0600`) and, with `--network-config`, its `network-config`. It makes the Node's token if `<dir>/tokens/<name>` is missing; the token goes into the Node's `/run/gaon/bootstrap-token` (`0600`), and the Node Agent runs with `--tls-ca /run/gaon/ca.pem --bootstrap-token-file /run/gaon/bootstrap-token --cert-dir /var/lib/naru/gaon-node-agent`, so it creates a signing request with the token and keeps the pair it is issued on the data disk ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)). On the control-plane Node (`--control-plane`) `spec.pki` carries the CA and its key (the key also at `/run/gaon/ca.key`, `0600`), init issues the API server's, scheduler's and controllers' pairs at boot ([ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)), the API server gets `--bootstrap-token-file /run/gaon/bootstrap-tokens` (one token per line, every token file in `<dir>/tokens` at that time, a `spec.files` entry with `restart: [gaon-apiserver]`) and the controllers `--signing-cert /run/gaon/ca.pem --signing-key /run/gaon/ca.key`. `--pairs-as-files` is the operator's-pair form of any Node: it carries an agent pair, CN the Node's name, signed by the CA (certificates valid one year, never past the CA's), and the agent's `--tls-*` flags; a control-plane Node with it carries its pairs as files, and no CA key, token or signing flag. `--api-server` is the address every agent dials and the API server's serving certificate names; `--serving-address` (repeatable) adds more. `--time-server <host[:port]>` (repeatable, in the order asked) writes `spec.time`; without it the user-data has none. `--binary <service>=<path>`, `--disable <service>`, `--extra-nic <mac>=<cidr>` and `--search` are the other flags; `naructl gen node -h` lists all. `--name` must be a DNS label, since it is the Node's CN, its etcd name and its `metadata.name`. A flag given without what makes it apply is refused: `--mac`, `--gateway`, `--nameserver`, `--search` and `--extra-nic` need `--network-config`, and and `--serving-address` needs `--control-plane`. `gen node` refuses a Node it cannot make work: `--pairs-as-files` with a token, a token not in gaon's form, a token list on a worker or one without the control-plane Node's own token, and `--disable gaon-controllers` on a control-plane Node that signs. A file already at `--out`, or at a key's path, is replaced by one with the mode named here, never written into with the old file's mode. A CA whose certificate has expired is refused.
- **The command line is a cobra tree** ([ADR 0067](./adr/0067-naructl-is-a-cobra-command-tree-with-one-flag-name-per-concept-and-the-old-spellings-are-hidden-aliases-removed-in-v0-1-0-dev-13.md)). `naructl -h`, `naructl <command> -h` and `naructl completion bash|zsh` are generated, and `-h` exits 0. One flag has one name: `--ca-dir` is the directory of an authority and `--endpoint` the address of the API a command calls. `--ca`, `gen ca --out`, `--node` and `--host` are spellings v0.1.0-dev.13 removed: they are refused as unknown flags. `gen ca`, `gen api-ca` and `gen host-ca` share one implementation.
- **Signer commands take `--socket <path>` or `--config <client file> [--endpoint <ip[:port]>]`.** `operator add`, `operator revoke`, `ccm credential`, `orch issue`, `signer bundle`, `signer restore` and `signer reissue-root` need exactly one of the two, and `--endpoint` only with `--config`. `--config` is an admin's Node API client file (`gen api-client --role admin`) and the requests go to `/v1/signer/` of that Node, which forwards them to its signer ([init.md](./init.md), [ADR 0057](./adr/0057-an-operator-reaches-the-signer-through-the-node-apis-admin-role-which-forwards-v1-signer-to-the-signers-unix-socket-and-adds-no-authority.md)).
- **`naructl host drain <id>` and `naructl host undrain <id>`** are orch commands, taking the connection flags of `host label`. They `POST /v1/hosts/{id}/drain` or `/undrain` ([orch.md](./orch.md) §Drain), and print whether the host is draining. An operator's certificate is required; a reader's is refused by orch with 403.
- **`gen node --orch-host-ca <file>` and `--host-client-ca <file>`** make orch reach the hosts: the first writes `spec.orch.hostCA` (the host authority, `<ca-dir>/host/ca.pem`), the second, with `--host-region`, adds the authority orch's certificate chains to (the file of `--orch-ca`) to `/run/naru-hostd/client-ca.crt` after the host authority's, so hostd verifies orch's certificate. Each is refused when its file holds no PEM certificate. `--host-revocation-public-key <file>`, with `--host-region` and `--host-orch-url`, writes `spec.host.revocationPublicKey`, the key naru-hostd checks its clients' certificates against the signed list with (ADR 0062); a host that enrolls is configured up front and gets no key at admission.
- **`gen node --extension <name>=<sha256>`**, repeatable, writes a `spec.extensions` entry; the SHA-256 is the `sha256` field of the release's `naru-orch-ext-<tag>.json`. `--signer` and the orch flags are refused without `--extension naru-orch=...`, since the daemons are in that extension ([ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)). **`extension add <file>`**, **`extension list`** and **`extension remove <sha256>`** are client commands over `PUT`, `GET` and `DELETE /v1/extensions`: `add` hashes the file, streams it under its digest and prints the `spec.extensions` entry to write.
- **`gen node --orch-join <url>`** writes `spec.orch.join`, the client URL of a running member, in place of `--orch-member`: the Node takes the initial cluster from that member, so `--orch-member`, `--orch-restore` and `--orch-state new` are refused with it, and without `--orch-peer-url` it has no effect.
- **`gen node --storage <name>=<label, /dev/path or serial:NUMBER>`**, repeatable, writes a `spec.storage` entry of `form` `xfs` that finds its disk by `device` when the value starts with `/dev/` (a blank disk has no label), by `serial` when it starts with `serial:` ([ADR 0079](./adr/0079-a-blank-storage-disk-is-named-by-its-serial-number-which-init-reads-from-sysfs-and-the-xfs-label-takes-over-after-the-first-boot.md)) and by `label` otherwise; the first one's `mountPoint` is `/var/lib/naru/mvmd-storage` (`wire.MvmdStorageMount`), which holds mvmd's disks, snapshots and run directories while its `state_dir` stays on the data disk, and the others take the default mount point; only this release's `naructl` writes it, and user-data from an earlier one keeps the old mount point and mvmd's refusal until it is written again ([ADR 0073](./adr/0073-mvmds-disks-snapshots-and-run-directories-are-on-the-first-storage-disk-through-links-while-its-state-directory-stays-on-the-data-disk.md)). A name that is not a DNS label of at most 12 characters, an empty label or a name given twice is refused. The device or serial is used only to find a blank disk at the first boot: at every later boot init finds the disk by the XFS label it gave it, wherever the kernel names it ([ADR 0032](./adr/0032-a-storage-disk-is-found-by-the-xfs-label-init-gives-it-and-device-names-only-a-blank-disk.md)). Init formats a blank disk and never any other ([ADR 0027](./adr/0027-a-node-offers-an-extra-disk-as-xfs-storage-for-mvmds-disks-formatted-when-blank-mounted-hardened-and-grown-at-boot.md)).
- **`gen node --peer <address>=<machine-prefix>`**, repeatable, names another Node of the cluster: its address, which must be an IPv4 address on this Node's network and neither this Node's own nor another peer's, and the IPv4 prefix its mvmd gives its Machines, in canonical form, not the default route, and overlapping neither this Node's network, its own `--machine-prefix` nor another peer's. For each peer the user-data gets a `spec.network.routes` entry to the prefix `via` the address, and mvmd's `network.no_masquerade` gets the prefix, so the Node's Machines reach the peer's with their own source address. A Node with no `--peer` has neither, and the Machine prefixes of a cluster must be pairwise disjoint ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)).
- **`gen node --no-masquerade <prefix>`**, repeatable, adds an IPv4 prefix in canonical form to mvmd's `network.no_masquerade` and writes no route to it: the Machine prefixes of the hosts a WireGuard tunnel reaches, which the tunnel carries and mvmd's masquerade would otherwise rewrite to a source the peer's allowed IPs refuse. Its prefixes follow the `--peer` prefixes in the list.
- **The registry serves the data disk's test image.** A Node runs `registry` by default, and mvmd trusts its certificate through a `spec.registries` entry for `127.0.0.1:5000` that carries its authority (`--registry host=127.0.0.1:5000,ca=<file>`), so the data disk's image is pullable by digest; the release's `naru-data-<version>.qcow2` carries it. The Node that orch builds for a joined host (`HostOnly`) runs no registry: it has no inputs tree to stage the binary from and pulls from its profile's registries ([ADR 0061](./adr/0061-a-host-certificate-names-the-host-id-and-orchs-host-client-accepts-the-address-or-the-host-id.md)). `--disable registry` leaves the service out, and an operator who pulls from elsewhere gives `--registry` for that host instead.
- **`gen node --registry host=H[,ca=FILE][,username=U,password=P][,helper=NAME]`**, repeatable, writes a `spec.registries` entry; `ca=FILE` is a PEM file read when the user-data is written. It refuses a credential that is a helper and a username together, a username without a password, an unknown key and a `ca` file that is not there. mvmd's `registry` section gets `credentials_file`, `ca_file` when some registry has a CA, and `credential_helpers` for the hosts that name a helper, and mvmd's `PATH` is `/bin:/run/bin`. **`--aws-region`, `--aws-trust-anchor`, `--aws-profile` and `--aws-role`**, all four or none, write `spec.aws` with the Node Agent's `node-agent.pem` as certificate and key, and the `aws-credentials` service after the Node Agent's, with mvmd's `AWS_EC2_METADATA_SERVICE_ENDPOINT` and `AWS_REGION` ([ADR 0029](./adr/0029-aws-credentials-is-a-service-serving-the-instance-metadata-endpoint-to-mvmd.md)). mvmd's `HOME` is `/run/naru/registry/home`, whose `.ecr/log/ecr-login.log` `naructl logs mvmd` shows. The Node Agent's service carries `keptPair` for that file with `gaon:nodes` ([ADR 0026](./adr/0026-a-node-takes-registry-credentials-and-trust-as-configuration-an-ecr-credential-comes-from-iam-roles-anywhere-and-an-agent-pair-without-the-required-organization-is-set-aside.md)).
- **`gen client`** writes `client.pem` and `client.key` for an operator, CN as given, signed by the CA, for gaon's CLI (`--tls-ca ca/ca.pem --tls-cert client/client.pem --tls-key client/client.key`).
- **`gen etcd-client`** writes `ca.crt`, `tls.crt` and `tls.key` (`0600`) for gaon's etcd snapshot writer, the keys of the Secret it mounts: a pair with CN `gaon-etcd-snapshot` and `clientAuth`, signed by the CA that signs the members' etcd certificates, which every member accepts on 2379 ([ADR 0024](./adr/0024-the-control-plane-is-three-etcd-members-with-tls-on-both-ports-and-a-virtual-address-held-by-naru-vip-behind-a-fence-on-etcds-ports.md) item 7). A control-plane Node's fence admits its own MicroVMs to port 2379 (`naru-fence -allow-machines <the Node's machine prefix>`), by their own address to its own member and, to another member, as the Node's address once masqueraded; a worker's address is refused. The rule names port 2379 only: the peer port 2380 is refused to the prefix by a TCP reset at the sending Node, in its output and forward hooks, before the masquerade.
- **The token handoff is a file per Node in the CA's directory.** `naructl` keeps each Node's token in `<ca-dir>/tokens/<name>` and writes it into that Node's user-data; the control-plane Node's user-data lists every token that exists when it is written. To **add a Node later**: run `naructl token create --ca-dir ca --name node-3 --config admin.yaml`, which adds the token to the running control-plane Node by a patch (no user-data again, no reboot), then `naructl gen node --ca-dir ca --name node-3 ...` for the new Node and start it ([ADR 0081](./adr/0081-a-bootstrap-token-is-added-or-revoked-by-a-live-patch-to-the-control-plane-nodes-token-list-file-from-the-operators-token-store.md), which supersedes the procedure of regenerating the control-plane Node's user-data). To **revoke** a Node's token, run `naructl token revoke` for it; a Node that already holds a pair keeps it. The patch carries every token of `<ca-dir>/tokens`, so keep one store. `naructl` does not renew a token.
- **The CA key goes only into the control-plane Node's user-data and the operator's secret store.** `naructl` writes it to `ca.key` and to `spec.pki` of the control-plane Node (`--pairs-as-files` excepted: that Node has no `spec.pki`), and nowhere else: a worker's user-data holds none, and no operator's CA is written into a release asset. Whoever holds `ca.key` can issue a certificate the API server accepts, so keep it out of version control, and treat the control-plane Node's user-data (and the NoCloud drive it is on) as holding it. The release's `naru-node-1.test.yaml` is different: it carries the build's throwaway test CA, key included, which is published ([image.md](./image.md#release-assets), [ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)).

- **`gen api-ca --ca-dir <dir>`** writes the Node API's authority, `<dir>/api/ca.pem` and `<dir>/api/ca.key` (ECDSA P-256; the key `0600`), and refuses to replace one. It is separate from gaon's CA, needs none, and works on a directory that holds no `ca.key` ([ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md)).
- **`gen node` adds `spec.api` when `<ca-dir>/api/` exists** and nothing otherwise: `clientCA` is the authority's certificate, and `certificate` and `key` are a serving pair it issues for the Node, naming the Node's address, its `--serving-address` values and `127.0.0.1`. No Node carries the authority's key, and `listen` is left to init's default. A `<ca-dir>/api/` that holds no authority is refused. The release's test user-data is made without `<ca-dir>/api/` and carries no `spec.api`.
- **`gen api-client --ca-dir <dir> --role admin|reader --endpoint <ip[:port]> --out <file>`** writes the client file (`0600`, a file already there is replaced): `endpoints` (port `50000` when none is given), `ca`, and a `certificate` and `key` issued by the API authority with the Organization `naru:admin` or `naru:reader`. `--cn` names the caller in a Node's request log and defaults to `naru-<role>`.
- **`gen host-ca --ca-dir <dir>`** writes the host API's authority, `<dir>/host/ca.pem` and `<dir>/host/ca.key`, and refuses to replace one. **`gen host-client --ca-dir <dir> --role provisioner|reader --endpoint <ip[:port]> --out <file>`** writes the client file (`0600`; port `7443` when none is given; `--cn` defaults to `naru-host-<role>`) with a certificate of the Organization `naru:host-provisioner` or `naru:host-reader`. **`gen node --host-region <region> [--host-label k=v]...`** reads the host authority from `<dir>/host`, writes `spec.host`, the serving pair for the Node's addresses and `--serving-address`es, the client CA at `/run/naru-hostd/`, and the `naru-hostd` service after mvmd, with `--machine-gateway` set to the first address of the Node's Machine prefix, the gateway of the seeds hostd writes ([ADR 0035-the-host-api-creates-a-microvm-of-an-os-form-from-a-boot-set-with-a-data-disk-and-a-nocloud-seed-and-the-iso-9660-writer-is-a-library-module.md](./adr/0035-the-host-api-creates-a-microvm-of-an-os-form-from-a-boot-set-with-a-data-disk-and-a-nocloud-seed-and-the-iso-9660-writer-is-a-library-module.md)); the authority's key is not written. `--host-label` needs `--host-region`. **`naructl host`** and **`naructl microvm create|get|list|stop|start|delete`** call the host API with `--config <client file>` and optional `--endpoint <ip[:port]>`, or with `--identity <person file> --passphrase-file <file> --host-ca <host authority PEM> --endpoint <address> [--server-name <h-id>]` for a seed-joined host (exactly one of the two forms; [ADR 0080](./adr/0080-a-seed-joined-host-accepts-an-operator-certificate-the-signer-issued-and-takes-its-role-from-the-certificates-organizational-unit.md)); `create` takes `--name --image --cpu --memory --root-disk --disk name=bytes[,ro]` (the image form), or `--name --boot-set --seed FILE --data-disk [--cmdline] [--pod-prefix] [--cpu] [--memory]` (the OS form, whose flags are not mixed with the image form's), or `-f <request.json>`, not both; `--fenced` gives the microVM a fence of its own; `stop` and `start` take the microVM's name. The calls the harness once made through its own client are commands too: `microvm snapshot <name> --name <snapshot>`, `microvm fence get <name>` and `microvm fence renew <name> --length <seconds> --renewal <n>`, `snapshot list|get|delete <name>` and `snapshot resume <name> --name <microvm> [--network] [--pod-prefix]`, `host network put <name> --prefix <cidr> [--api-endpoint] [--remote-member <cidr>]...|get <name>|list|delete <name>`, `host peers get|set -f <peers.json>` and `host tunnel`; `naructl network` is the management plane's ([host.md](./host.md), [ADR 0038](./adr/0038-the-host-api-stops-and-starts-a-microvm-and-restart-on-boot-brings-a-microvm-back-after-its-host-restarts-and-naructl-takes-the-os-forms-flags.md)).
- **`--server-name <name>`** is a flag of every command that calls the Node API or the host API (`version`, `services`, `logs`, `get config`, `apply`, `reboot`, `upgrade`, the signer commands with `--config`, `host`, `microvm`, `snapshot` and `host network|peers|tunnel|boot-set`). It names what the server's certificate is verified against in place of the address in `--endpoint`; the client files keep their authority as the only root. A host that joined from an install seed has a certificate that names only its host ID `h-<id>`, so its operator gives `--server-name h-<id>` and the address; the certificate has no IP SAN because a DHCP address can change within its lifetime ([host.md](./host.md)).
- **The client commands** `version`, `services`, `logs <service> [-f]`, `get config` and `apply -f <file> [--mode no-reboot|staged|reboot] [--dry-run]`, `reboot` and `upgrade` each take `--config <client file>` and `--endpoint <ip[:port]>` (the file's first endpoint when absent), and speak TLS 1.3 to the API with the file's CA as the only root. `get config` prints one YAML document, the configuration as the Node returns it, redacted, with the Node's `status` beside `spec` (`version`, `bootId`, `slot`, `lastUpgrade`, `revision` and each service's `state` and `restarts`); `status.version` is what `version` prints, and an apply that names `status` is refused with 422 ([ADR 0047](./adr/0047-a-nodes-state-is-served-as-a-status-block-of-its-configuration-document-an-apply-naming-it-is-refused-and-a-node-has-no-login-path-and-no-port-its-configuration-does-not-name.md)). `apply` reads the Node's current revision, then posts the patch (a YAML or JSON mapping) against it; `--mode` defaults to `no-reboot`; `reboot` stores the change as `staged` does, including a reboot-only field, and the Node then reboots on the new revision. `reboot` asks the Node to reboot (`POST /v1/reboot`) and prints the action it accepted: the answer comes before the Node stops, and the client reads `bootId` from `version` to see the new boot. A refusal (403, 409, 422, or a failure after the revision was stored) is one line with the Node's reason, and the exit code is 1. `upgrade --bundle <file> --sums <SHA256SUMS>` finds the bundle's line in the sums file, hashes the file, refuses a mismatch before it sends anything, then streams the file to `POST /v1/upgrade` with the digest as the query parameter `sha256` and prints the actions the Node accepted; `upgrade --status` prints the version, the boot ID, the slot and the outcome of the last upgrade, and sends no bundle. `version` does not print the slot or the outcome. The commands never print a key.
- **`group apply -f <file>|get <name>|list|delete <name>`** and **`events [--group <name>] [--limit <n>]`** (orch's newest events, 50 by default) and **`network apply -f <file>|get <name>|list|delete <name>`** talk to orch with the flags every orch command takes (`--orch-url`, `--orch-ca`, `--identity`, `--passphrase-file`) and need the operator role to write and the reader role to read. A group's file is its `GroupSpec` and a network's is `name`, `prefix` and optionally `apiEndpoint`, in YAML or JSON; a field the type does not have is refused before anything is sent. A group template's network policy is the key `policy` and its virtual network the key `network` ([ADR 0049](./adr/0049-orch-keeps-the-networks-and-allocates-each-members-pod-prefix-by-compare-and-swap-and-the-leader-tells-every-host-its-networks-members-and-peers.md)).
- **To operate a Node by its API:** (1) `naructl gen api-ca --ca-dir ca`; (2) regenerate each Node's user-data with `gen node` as before, and give each Node its new user-data; (3) `naructl gen api-client --ca-dir ca --role admin --endpoint 192.168.0.20 --out admin.yaml`; (4) `naructl get config --config admin.yaml` reads the redacted configuration and the Node's status, whose `status.revision` is the revision; (5) `naructl apply --config admin.yaml -f patch.yaml --dry-run` lists what a patch would do, and without `--dry-run` applies it.

### Kubernetes ([ADR 0031](./adr/0031-a-node-runs-kubernetes-as-init-services-containerd-and-runc-are-static-and-pods-get-routed-prefixes-from-one-pod-network.md))

`lib/layout` holds a second layout, the Kubernetes Node's, beside gaon's: `Node.Kube` selects it, and a Node with no `Kube` is written as before.

```sh
naructl gen ca --ca-dir ca
naructl gen kubernetes --ca-dir ca --endpoint 192.168.0.40 [--admin-address 127.0.0.1:6443]
naructl gen kubernetes-node --ca-dir ca --name node-1 --role control-plane --address 192.168.0.40/24 --endpoint 192.168.0.40 \
  --pod-network 10.64.0.0/12 --pod-prefix 10.64.1.0/24 --peer 192.168.0.41=10.64.2.0/24 --out node-1.user-data
naructl gen kubernetes-node --ca-dir ca --name node-2 --role worker --address 192.168.0.41/24 --endpoint 192.168.0.40 \
  --pod-network 10.64.0.0/12 --pod-prefix 10.64.2.0/24 --peer 192.168.0.40=10.64.1.0/24 --out node-2.user-data
naructl topology kubernetes
```

- **`gen kubernetes --ca-dir <dir> --endpoint <ip>`** writes into the CA's directory what a cluster has besides its authority: the front-proxy authority (`front-proxy/ca.pem`, `ca.key`), the ServiceAccount key pair (`sa.key` mode `0600`, `sa.pub`; ECDSA P-256) and the administrator's kubeconfig `admin.conf` (mode `0600`, certificate and key inline, CN `kubernetes-admin`, Organization `system:masters`). `--admin-address host:port` names the server `admin.conf` dials in place of the endpoint on port 6443, for a forward. Files that exist are kept, except `admin.conf`.
- **`gen kubernetes-node`** writes a Node's user-data (`--out`, mode `0600`) and, with `--network-config`, its network-config. `--role control-plane` runs etcd, the API server, the controller manager and the scheduler besides the Node's own programs and needs what `gen kubernetes` wrote; `--role worker` runs containerd, the kubelet and kube-proxy only. `--peer <address>=<pod-prefix>` routes to another Node's Pod prefix through its address (`spec.network.routes`); naructl refuses a Pod prefix outside `--pod-network`, one that overlaps another's, the Service range `10.96.0.0/16`, or the Node's own network. `--disable`, `--binary`, `--time-server`, `--extra-nic`, `--local-registry`, `--registry-ca` and `--sandbox-image` are as `gen node`'s, or ADR 0031's. It sets `spec.dataDisk.formatBlank: true`, because a Kubernetes Node may be a microVM whose host gives it a blank data disk (a labelled one is left as it is, [init.md](./init.md)).
- **`gen kubernetes-node` adds `spec.api` the same way `gen node` does** when `<ca-dir>/api/` exists, and `gen kubernetes-bootstrap-rbac` prints the manifest a cluster that takes bootstrap tokens needs ([ADR 0081](./adr/0081-a-bootstrap-token-is-added-or-revoked-by-a-live-patch-to-the-control-plane-nodes-token-list-file-from-the-operators-token-store.md)).
- **Add-ons.** Every Kubernetes Node imports the add-on images into containerd's `k8s.io` namespace and pins them, with one one-shot service per image (`addon-image-<name>`: `ctr images import --digests --base-name naru.local/<name> --label io.cri-containerd.pinned=pinned`, `restartPolicy: on-failure`), which names the archive's tag and its digest image and pins both, and the kubelet configuration sets `clusterDNS` `10.96.0.10` and `clusterDomain` `cluster.local`. A control-plane Node also runs the one-shot service `addons`: `kubectl apply --server-side --force-conflicts --field-manager=naru-addons` of `/usr/lib/naru/addons/manifests/<name>.yaml` for each enabled add-on, with the pair `naru:addons` in `system:masters` (`addons.conf`), which retries until the API server answers. `gen kubernetes --disable-addon <name>` (repeatable; the names are `dns` and `volumes`) writes `<ca-dir>/disabled-addons`, which `gen kubernetes-node` reads (a later `gen kubernetes` without the flag removes the file, so every add-on is on again): a disabled add-on is not applied, and so is never pruned, and a control-plane Node with none enabled has no `addons` service. naructl refuses an unknown name. [ADR 0083](./adr/0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) decides this; no removed-objects list exists yet, because no add-on has been dropped. The `volumes` add-on is the exception to the path: its manifest and image archive are in the system extension `naru-volumes` (`spec.extensions` with no digest, so init resolves it to the image built for its version), read from `/usr/lib/naru/extensions/naru-volumes/addons/`, and enabling it adds that entry and the service `addon-image-volumes`. A Node with `spec.storage` (`gen kubernetes-node --storage <name>=<label, /dev/path or serial:NUMBER>`, whose first disk holds the local volumes, class `naru-local`) or `--block-serial` disks (offered whole, class `naru-block`) also gets `/run/kubernetes/naru-volumes.json` (the driver's state directory `/var/lib/naru/volumes`, that storage directory and the serials) and the kubelet label `naru.garam.sh/volumes=true`, which selects the driver's DaemonSet; naructl refuses a block serial that is empty, repeated or a storage disk's (init does not check the list; the driver refuses a disk the Node uses, below). The provisioner runs as a sidecar of the DaemonSet's Pod on each Node that has the label (`--node-deployment`, `--strict-topology`), so the Node holding the disk creates the volume, and a Node with only block disks has the driver too; there is no Deployment ([ADR 0090](./adr/0090-a-volume-is-made-where-its-disk-is-by-a-provisioner-per-node-a-disk-the-node-uses-is-never-handed-out-and-an-operator-frees-a-retained-disk-by-deleting-its-volume.md)). **Delivering the extension.** A Node that is built with the volume add-on enabled gets the entry `{name: naru-volumes}` from `gen kubernetes-node`; the image reaches the Node's extension store by the upgrade bundle, which carries it (ADR 0084), or, for a new Node or one upgraded before the add-on existed, by `naructl extension add naru-volumes-ext-<tag>.sqfs` (`PUT /v1/extensions`, the admin role) before the Node is booted with the entry: an entry with no stored image refuses the boot. **Freeing a disk.** A claim of `naru-block` is released when its claim is deleted and the volume stays `Released`; the operator frees the disk by setting the volume's `persistentVolumeReclaimPolicy` to `Delete` (`kubectl patch pv <name>`), which makes the provisioner call `DeleteVolume`; the driver forgets the claim and never wipes the disk. A disk that holds a mounted file system, a partition that is mounted or a device mapped over it is not handed out, so the Node's own disks are never a claim's. A disk a previous tenant left with a device mapped over it (device-mapper or LVM) is refused the same way, with the device named; the mapping lives in the kernel only, so rebooting the Node (`naructl reboot`) or a privileged Pod on that Node running `dmsetup remove` for the device clears it. A block volume is not published read-only, since a read-only bind of a device does not stop writes.
- **Only the control-plane Node's user-data carries the cluster CA's key**: init issues its pairs from `spec.pki` (ADR 0013), and the controller manager signs with the key. A worker has no `spec.pki`: `gen kubernetes-node` issues its kubelet client and serving pairs and kube-proxy's from the CA and writes them with the CA's certificate as files under `/run/kubernetes/pki` (keys `0600`), the form of `--pairs-as-files`. They are not renewed at the Node; delivering new user-data renews them. The kubelet's client pair is `system:node:<name>` in `system:nodes`, which the API server's node authorizer names.
- **`topology kubernetes`** prints the Kubernetes topology as `topology` prints gaon's, with no signer.

### Joined hosts ([ADR 0059](./adr/0059-orch-admits-a-host-that-boots-from-an-install-seed-allocates-its-machine-prefix-and-builds-its-configuration-from-one-fleet-profile.md))

- **`naructl host install-seed --orch-url --orch-ca-sha256 --enroll-key <file> [--name] --out`** writes the install seed, an ISO 9660 `cidata` volume (0600) whose `user-data` is the join form only and which has no `network-config`.
- **`naructl gen host-profile`** writes the fleet's host profile, from gen node's flags for what every host shares, with `--machine-pool`, `--orch-url`, `--orch-ca-sha256`, `--storage <name>=<label, /dev/path or serial:NUMBER>` and `--extension <name>=<sha256>`; the file is 0600 when it carries a registry password. `naructl host profile set -f` keeps it in orch; `host profile get` prints orch's answer, in which every secret is `<set>`, and a file with `<set>` where a password belongs is refused by `set` before it is sent.
- **`naructl host remove <id>`** removes a host and frees its Machine prefix. It does not revoke the host's certificate; `naructl operator revoke` does, and the command says so. `host pending` shows each host's hardware.
- **`naructl host list`** shows each host's region, address, Machine prefix, last report and labels (orch's `GET /v1/hosts`); **`naructl signer ca`** and **`naructl orch ca`** print the authorities, with the SHA-256 a seed carries ([ADR 0061](./adr/0061-a-host-certificate-names-the-host-id-and-orchs-host-client-accepts-the-address-or-the-host-id.md)).
- **`lib/layout`'s `HostOnly` mode** is the host Node of a joined host: no gaon, so no CA, bootstrap token or Node Agent pair; `metadata.name` is the host ID; the serving key is `spec.api.keyFile`; the AWS pair is `/run/naru-hostd/tls.crt` and that key file.
