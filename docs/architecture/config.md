# Config

How a Node's configuration and network reach init in P0, and the shape of the files.

Claims about garamsh/gaon hold at commit `c2b42f91724cae39a4f6824517c278150cf4695f`, and about garamsh/mvmd at `d189133bba8d842d2bcb20046f39fe03161efeb1`; they promise nothing about later versions. They were read at those commits when they replaced `d643b1cb6a6cc01ea587dd7c967bdfd07280fe0b` and `f08e9130c57c0d71e2bb21ac1deb048563ec3ef8`: gaon's `resource-api.md` §Common rules and mvmd's `runtime.md` §Network and `daemon/internal/app/config.go`.

## Current decisions

- **Delivery.** A cloud-init NoCloud drive: a block device with an ISO 9660 volume labelled `cidata` (either case), the form Proxmox's cloud-init drive takes. Init mounts it read-only and reads two files: `user-data`, which is `naru.yaml`, and `network-config`. `meta-data` is not read. It is not `fw_cfg`, and no ext4 `NARUCFG` disk is read.
- **Shape.** `apiVersion: naru.garam.sh/v1alpha1`, `kind: NodeConfig`, `metadata.name` the node name, and `spec`. There is no `status`. The shape follows gaon's resource rule, "Every resource has `apiVersion`, `kind`, `metadata`, `spec` and `status`" (gaon `docs/architecture/resource-api.md` §Common rules), minus `status`, which a file has no observer for.
- **`spec` holds:**

  | Field | Meaning |
  |---|---|
  | `services` | a list; each has a name, a binary path, args, env, and `controlPlane: bool`, which marks a service started only on the node that runs the control plane |
  | `controlPlane` | `bool`; whether this node runs the control plane |
  | `dataDisk` | `device` or `label` (exactly one), and `mountPoint` |
  | `network` | `forwarding`: the families, `ipv4` and `ipv6`, for which forwarding is turned on. `routes`: optional, each `to` (an IPv4 prefix in canonical form, not the default route) and `via` (an IPv4 unicast address outside `to`), no `to` twice; init installs each as a static route ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)) |
| `files` | a list of files init writes before any service starts; each has `path` (absolute, under `/run/`, and not `/run/naru` or below it), `mode` (octal, at most `0777`; `0644` when absent), `content` and `restart` (optional; services of `spec.services` that init restarts when an apply changes the file's `path`, `mode` or `content`). No path is another's directory |
| `api` | optional. `listen` (`host:port` with a port other than 0; `0.0.0.0:50000` when absent), `clientCA` (PEM CA certificate), `certificate` (PEM) and `key` (PEM, matching `certificate`). Without it a Node has no Node API. Init validates it and serves the Node API from it, as [init.md](./init.md) describes ([ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md)) |
| `time` | optional. `servers`: a non-empty list of `host[:port]` SNTP servers (port 123 when absent, an IPv6 address with a port in brackets), none repeated once the port is filled in. Init sets the clock from them before it issues certificates and keeps it, as [init.md](./init.md) says. Without it init does not synchronise the clock and logs so. A change applies live ([ADR 0021](./adr/0021-init-keeps-time-from-spec-time-servers-over-sntp.md)) |
| `pki` | optional. `authorities`: each has `name`, `certificate` (PEM), `key` (PEM, optional), `certificatePath` and `keyPath` (optional, and only with a `key`). `certificates`: each has `name`, `authority` (one that carries a `key`), `certificatePath`, `keyPath`, `commonName`, `organization` (optional), `usage` (`server` or `client`), `dnsNames`, `ipAddresses`, `nodeAddresses` (adds the addresses of `network-config`, and `127.0.0.1` to a server certificate), `validity` (a duration from `1h` to `87600h`, `720h` when absent; a certificate lives no longer than its authority's certificate) and `restart` (services of `spec.services` that init restarts when it renews the certificate). Every path follows the rules of a `files` path and is no file's of `files`, nor another's of `pki`. Init issues the certificates at boot and renews them ([init.md](./init.md), [ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)) |

- **The network is `network-config`**, in the version 1 form Proxmox writes (qemu-server `src/PVE/QemuServer/Cloudinit.pm`, at commit `b0965eeba61248046f803a4995112f0ab8523843`). Init accepts only `version: 1`; `physical` cards, each with a `mac_address` or a `name` (the MAC wins when both are given, and init does not rename a link), a static IPv4 subnet (`address` with a dotted `netmask`, or in CIDR form) and at most one `gateway`, which lies inside the prefix; and one `nameserver` entry with `address` and `search` lists. It refuses DHCP, IPv6, bonds, VLANs, bridges, routes, an unknown field and a malformed value. Init sets each link up, adds its address and the default route through netlink, and writes the resolvers to `/run/naru/resolv.conf`, which `/etc/resolv.conf` links to.
- **Init validates before it acts.** An unknown `apiVersion` or `kind`, a field the shape does not name, a value that fails validation, or a file that does not parse, stops init before any service starts; the error names the field. The same holds for a `network-config` that is malformed or asks for what init does not apply, and for a drive that is missing, has no `user-data` or has no `network-config`. What init does next is in [init.md](./init.md).
- **Configuration has revisions.** The `user-data` is the base at revision 0; an apply stores revision N+1 on the data disk in `/var/lib/naru/config/store.yaml` with the SHA-256 of the base. At boot init uses the stored configuration only when that digest equals the current `user-data`'s and the configuration validates. An apply is a merge patch with keyed lists (RFC 7386, with `spec.services` and `spec.files` merged by `name` and `path`, `spec.network.routes` by `to`, and the two lists of `spec.pki` by `name`) or a whole replacement. The fields an apply may change (`spec.services`, `spec.files`, `spec.network.routes`, `spec.pki.certificates` and `spec.api` other than its `listen` and its presence), may change only by a reboot (`spec.controlPlane`, `spec.network.forwarding`, `spec.pki.authorities`, `spec.api.listen` and whether `spec.api` is present) and may never change (`metadata.name`, `spec.dataDisk`, `apiVersion`, `kind`) are in [ADR 0018](./adr/0018-a-nodes-configuration-is-a-base-and-numbered-revisions-stored-on-the-data-disk-and-changed-by-merge-patch.md); what init does with each is in [init.md](./init.md).
- **Restart backoff is fixed in P0.** A service that exits is restarted after 1 s, doubling to a cap of 30 s, reset after a run of 60 s. The file has no field for it.
- **Forwarding.** Init turns on `net.ipv4.ip_forward` and `net.ipv6.conf.all.forwarding` for the families `network` names, before it starts mvmd, since mvmd never sets it and refuses to start when a served family has it off (garamsh/mvmd#311).
- **mvmd's `network` section is required.** mvmd refuses, at load, a Firecracker or Cloud Hypervisor configuration without it (mvmd `docs/architecture/runtime.md` §Network, "A real Driver needs the `network` section"; `daemon/internal/app/config.go`, `Config.check`). The Node configuration tooling writes `network.ipv4_prefix`, `ipv4_gateway` and `resolvers` (`node.Config.MvmdJSON`), and `spec.network.forwarding` turns forwarding on, so both of mvmd's conditions hold.
- **mvmd's `network.no_masquerade` keeps a Machine's source address to another Node's Machines.** It is a list of CIDRs, empty by default, in the families the node serves; one accept for each sits in mvmd's postrouting chain ahead of the masquerade, matching on the destination, and a change of it takes an mvmd restart (mvmd `runtime.md` §Network, ADR 0049, at the commit above). Routes to those prefixes are not mvmd's, so they are `spec.network.routes`. `naructl gen node --peer` writes both, below.
- **mvmd's `supervision.dir` is left empty.** mvmd refuses one that is the state directory, an ancestor of it, or inside it other than at `machines`; empty means `machines` under `state_dir` (`daemon/internal/app/config.go`, `sharesStateDir`), which `node.Config.MvmdJSON` relies on.
- **naru knows no service's internals.** Name, binary and arguments come from this file.
- **gaon's certificates are `files`, or are issued from `spec.pki`, and an agent's pair comes from a signing request.** A Node that carries no CA key gets its certificates as `files`, as below. A control-plane Node whose `spec.pki` carries the CA and its key gets the API server's, scheduler's and controllers' pairs init issues at boot under `/run/gaon/`, in the same places, and the services name them with the same flags; a Node Agent there holds a bootstrap token instead of a pair and is issued one by `gaon-controllers` ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md); gaon ADR 0007 at gaon commit `c2b42f91724cae39a4f6824517c278150cf4695f`) ([ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md), which supersedes item 5 of ADR 0012). For `files`: a Node's CA, its agent's pair and, on the control-plane Node, the API server's, the scheduler's and the controllers' pairs are entries of `spec.files` under `/run/gaon/`, which the gaon services name with their `--tls-*` flags, as gaon's `deployment.md` §Certificates and §Config shape ask. The files' content is the tooling's input; init writes it and knows nothing of it ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)).

## Operator tooling: naructl

`naructl` is the operator's tool for a gaon cluster on naru Nodes. It writes the CA, each Node's user-data and `network-config`, and the operator's client certificate pair; it owns the gaon Node layout (services, `spec.pki`, the worker's files, mvmd's configuration, the data disk's paths), which `tooling/qemu` runs as a binary and does not copy ([ADR 0015](./adr/0015-naructl-is-the-single-owner-of-the-gaon-node-layout-and-tooling-qemu-runs-it-as-a-binary.md)). It is a static linux/amd64 binary, the release asset `naructl-<version>-linux-amd64`, and every file it writes is one `naru-init -validate` accepts. The example below is the release's example deployment, with `guest.json` the release's `naru-guest-<version>.json` and `$FIRECRACKER` the `firecrackerSha256` of its `naru-inputs-<version>.json`:

```sh
naructl gen ca --out ca                        # ca/ca.pem, ca/ca.key
naructl gen token --ca ca --name node-2        # ca/tokens/node-2, once per Node before node-1's gen node
naructl gen node --ca ca --name node-1 --control-plane \
  --address 192.168.0.40/24 --mac 02:00:00:00:03:e9 --gateway 192.168.0.1 --nameserver 1.1.1.1 \
  --api-server 192.168.0.40 --machine-prefix 10.200.1.0/24 \
  --guest guest.json --firecracker-sha256 "$FIRECRACKER" \
  --out node-1.user-data --network-config node-1.network-config
naructl gen node --ca ca --name node-2 \
  --address 192.168.0.61/24 --mac 02:00:00:00:03:f4 --gateway 192.168.0.1 --nameserver 1.1.1.1 \
  --api-server 192.168.0.40 --machine-prefix 10.200.2.0/24 \
  --guest guest.json --firecracker-sha256 "$FIRECRACKER" \
  --out node-2.user-data --network-config node-2.network-config
naructl gen client --ca ca --cn alice --out client   # client/client.pem, client/client.key
naructl gen etcd-client --ca ca --out etcd-client    # etcd-client/ca.crt, tls.crt, tls.key
```

- **`gen ca --out <dir>`** writes `ca.pem` and `ca.key` (ECDSA P-256, valid ten years; the key `0600`) and refuses to replace an existing `ca.key`.
- **`gen token --ca <dir> --name <name>`** makes the Node's bootstrap token, `[a-z0-9]{6}\.[a-z0-9]{16}` from `crypto/rand`, in `<dir>/tokens/<name>` (mode `0600`), and leaves an existing one as it is. It checks that `<dir>` holds a CA.
- **`gen node`** writes the Node's `user-data` (`--out`, mode `0600`) and, with `--network-config`, its `network-config`. It makes the Node's token if `<dir>/tokens/<name>` is missing; the token goes into the Node's `/run/gaon/bootstrap-token` (`0600`), and the Node Agent runs with `--tls-ca /run/gaon/ca.pem --bootstrap-token-file /run/gaon/bootstrap-token --cert-dir /var/lib/naru/gaon-node-agent`, so it creates a signing request with the token and keeps the pair it is issued on the data disk ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)). On the control-plane Node (`--control-plane`) `spec.pki` carries the CA and its key (the key also at `/run/gaon/ca.key`, `0600`), init issues the API server's, scheduler's and controllers' pairs at boot ([ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)), the API server gets `--bootstrap-token-file /run/gaon/bootstrap-tokens` (one token per line, every token file in `<dir>/tokens` at that time) and the controllers `--signing-cert /run/gaon/ca.pem --signing-key /run/gaon/ca.key`. `--pairs-as-files` is the operator's-pair form of any Node: it carries an agent pair, CN the Node's name, signed by the CA (certificates valid one year, never past the CA's), and the agent's `--tls-*` flags; a control-plane Node with it carries its pairs as files, and no CA key, token or signing flag. `--api-server` is the address every agent dials and the API server's serving certificate names; `--serving-address` (repeatable) adds more. `--time-server <host[:port]>` (repeatable, in the order asked) writes `spec.time`; without it the user-data has none. `--binary <service>=<path>`, `--disable <service>`, `--extra-nic <mac>=<cidr>` and `--search` are the other flags; `naructl gen node -h` lists all. `--name` must be a DNS label, since it is the Node's CN, its etcd name and its `metadata.name`. A flag given without what makes it apply is refused: `--mac`, `--gateway`, `--nameserver`, `--search` and `--extra-nic` need `--network-config`, and and `--serving-address` needs `--control-plane`. `gen node` refuses a Node it cannot make work: `--pairs-as-files` with a token, a token not in gaon's form, a token list on a worker or one without the control-plane Node's own token, and `--disable gaon-controllers` on a control-plane Node that signs. A file already at `--out`, or at a key's path, is replaced by one with the mode named here, never written into with the old file's mode. A CA whose certificate has expired is refused.
- **`gen node --peer <address>=<machine-prefix>`**, repeatable, names another Node of the cluster: its address, which must be an IPv4 address on this Node's network and neither this Node's own nor another peer's, and the IPv4 prefix its mvmd gives its Machines, in canonical form, not the default route, and overlapping neither this Node's network, its own `--machine-prefix` nor another peer's. For each peer the user-data gets a `spec.network.routes` entry to the prefix `via` the address, and mvmd's `network.no_masquerade` gets the prefix, so the Node's Machines reach the peer's with their own source address. A Node with no `--peer` has neither, and the Machine prefixes of a cluster must be pairwise disjoint ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)).
- **The registry serves the data disk's test image.** A Node runs `registry` by default, and mvmd trusts its certificate through `SSL_CERT_FILE`, so the data disk's image is pullable by digest; the release's `naru-data-<version>.qcow2` carries it. `--disable registry` leaves both out, so an operator who pulls from elsewhere drops the registry and mvmd's `SSL_CERT_FILE` together.
- **`gen client`** writes `client.pem` and `client.key` for an operator, CN as given, signed by the CA, for gaon's CLI (`--tls-ca ca/ca.pem --tls-cert client/client.pem --tls-key client/client.key`).
- **`gen etcd-client`** writes `ca.crt`, `tls.crt` and `tls.key` (`0600`) for gaon's etcd snapshot writer, the keys of the Secret it mounts: a pair with CN `gaon-etcd-snapshot` and `clientAuth`, signed by the CA that signs the members' etcd certificates, which every member accepts on 2379 ([ADR 0024](./adr/0024-the-control-plane-is-three-etcd-members-with-tls-on-both-ports-and-a-virtual-address-held-by-naru-vip-behind-a-fence-on-etcds-ports.md) item 7). A control-plane Node's fence admits its own MicroVMs to port 2379 (`naru-fence -allow-machines <the Node's machine prefix>`), by their own address to its own member and, to another member, as the Node's address once masqueraded; a worker's address is refused. The rule names port 2379 only: the peer port 2380 is refused to the prefix by a TCP reset at the sending Node, in its output and forward hooks, before the masquerade.
- **The token handoff is a file per Node in the CA's directory.** `naructl` keeps each Node's token in `<ca-dir>/tokens/<name>` and writes it into that Node's user-data; the control-plane Node's user-data lists every token that exists when it is written. To **add a Node later**: run `naructl gen token --ca ca --name node-3`, then `naructl gen node --ca ca --name node-3 ...` for it, then `naructl gen node --control-plane ...` for the control-plane Node again with its original flags, and apply that new user-data (the API server reads its list at start, so the control-plane Node restarts with it). To **revoke** a Node's token, delete `<ca-dir>/tokens/<name>` and regenerate the control-plane Node's user-data. `naructl` does not renew a token.
- **The CA key goes only into the control-plane Node's user-data and the operator's secret store.** `naructl` writes it to `ca.key` and to `spec.pki` of the control-plane Node (`--pairs-as-files` excepted: that Node has no `spec.pki`), and nowhere else: a worker's user-data holds none, and no operator's CA is written into a release asset. Whoever holds `ca.key` can issue a certificate the API server accepts, so keep it out of version control, and treat the control-plane Node's user-data (and the NoCloud drive it is on) as holding it. The release's `naru-node-1.test.yaml` is different: it carries the build's throwaway test CA, key included, which is published ([image.md](./image.md#release-assets), [ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)).

- **`gen api-ca --ca-dir <dir>`** writes the Node API's authority, `<dir>/api/ca.pem` and `<dir>/api/ca.key` (ECDSA P-256; the key `0600`), and refuses to replace one. It is separate from gaon's CA, needs none, and works on a directory that holds no `ca.key` ([ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md)).
- **`gen node` adds `spec.api` when `<ca-dir>/api/` exists** and nothing otherwise: `clientCA` is the authority's certificate, and `certificate` and `key` are a serving pair it issues for the Node, naming the Node's address, its `--serving-address` values and `127.0.0.1`. No Node carries the authority's key, and `listen` is left to init's default. A `<ca-dir>/api/` that holds no authority is refused. The release's test user-data is made without `<ca-dir>/api/` and carries no `spec.api`.
- **`gen api-client --ca-dir <dir> --role admin|reader --endpoint <ip[:port]> --out <file>`** writes the client file (`0600`, a file already there is replaced): `endpoints` (port `50000` when none is given), `ca`, and a `certificate` and `key` issued by the API authority with the Organization `naru:admin` or `naru:reader`. `--cn` names the caller in a Node's request log and defaults to `naru-<role>`.
- **The client commands** `version`, `services`, `logs <service> [-f]`, `get config` and `apply -f <file> [--mode no-reboot|staged|reboot] [--dry-run]` and `reboot` each take `--config <client file>` and `--node <ip[:port]>` (the file's first endpoint when absent), and speak TLS 1.3 to the API with the file's CA as the only root. `get config` prints the revision and the configuration as the Node returns it, redacted. `apply` reads the Node's current revision, then posts the patch (a YAML or JSON mapping) against it; `--mode` defaults to `no-reboot`; `reboot` stores the change as `staged` does, including a reboot-only field, and the Node then reboots on the new revision. `reboot` asks the Node to reboot (`POST /v1/reboot`) and prints the action it accepted: the answer comes before the Node stops, and the client reads `bootId` from `version` to see the new boot. A refusal (403, 409, 422, or a failure after the revision was stored) is one line with the Node's reason, and the exit code is 1. The commands never print a key.
- **To operate a Node by its API:** (1) `naructl gen api-ca --ca-dir ca`; (2) regenerate each Node's user-data with `gen node` as before, and give each Node its new user-data; (3) `naructl gen api-client --ca-dir ca --role admin --endpoint 192.168.0.20 --out admin.yaml`; (4) `naructl get config --config admin.yaml` reads the revision and the redacted configuration; (5) `naructl apply --config admin.yaml -f patch.yaml --dry-run` lists what a patch would do, and without `--dry-run` applies it.

## Rationale

- [ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md): why `spec.network.routes` exists, that it applies live and is keyed by `to`, how `--peer` writes it with mvmd's `no_masquerade`, and the signs it was wrong.
- [ADR 0022](./adr/0022-a-node-is-rebooted-through-the-node-api-by-post-v1-reboot-or-the-reboot-apply-mode-and-init-answers-before-it-stops.md): why a Node is rebooted through the API, the `reboot` mode, and the reply before the stop.
- [ADR 0021](./adr/0021-init-keeps-time-from-spec-time-servers-over-sntp.md): why `spec.time` exists, and that it applies live.
- [ADR 0018](./adr/0018-a-nodes-configuration-is-a-base-and-numbered-revisions-stored-on-the-data-disk-and-changed-by-merge-patch.md): why the configuration is a base and revisions, and the boot choice.
- [ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md): why init serves the Node API from an authority of its own, and `naructl` is the client.
- [ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md): why a Node Agent gets its pair by a signing request with a token, how `naructl` hands the tokens over, and why the release publishes a test CA key.
- [ADR 0015](./adr/0015-naructl-is-the-single-owner-of-the-gaon-node-layout-and-tooling-qemu-runs-it-as-a-binary.md): why one tool owns the gaon Node layout, and why `tooling/qemu` runs it as a binary.
- [ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md): why `spec.pki` carries authorities and certificates, the validation, and the signs it was wrong.
- [ADR 0008](./adr/0008-a-node-reads-its-configuration-and-network-from-a-cloud-init-nocloud-drive.md): why a NoCloud drive, why `network-config` is read strictly, why the files field, and the signs it was wrong. It supersedes ADR 0005's delivery.
- [ADR 0005](./adr/0005-configuration-is-a-yaml-file-on-a-labelled-ext4-disk-in-the-shape-of-gaons-resources.md): why gaon's shape and the forwarding duty; its delivery by an ext4 disk is superseded.

- [ADR 0003](./adr/0003-naru-deploys-and-supervises-mvmd-builds-both-kernels-and-carries-mvmds-deployment-constraints.md): the forwarding obligation, and the other facts mvmd needs from a Node's configuration.

## Open questions

- **How a Node with no valid configuration accepts an operator.** [ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md) gives a Node an API only through `spec.api`, so a first Node with none has no way in; the reset and recovery follow-up ([target.md](./target.md)) decides it.
- **Fields beyond P0.** DHCP, IPv6, several addresses per card and routes in `network-config`, and the host network settings gaon will need for Nodes to connect, are not decided.
- **Configuration integrity.** Whether and how the file is signed is not decided.
