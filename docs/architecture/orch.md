# Orch

What `naru-orchd` is: the service of the control hosts that keeps the inventory of hosts (enrolled, admitted, in a region, with labels), elects the one member that acts, and answers the API through which operators and hosts reach it. The authorities' keys are not here: they stay with the signer.

## Current decisions

- **`naru-orchd` is a unit.** It is the module `orch/`, with one binary, `cmd/naru-orchd`, which is the composition site. Its types and Go client are the library module `lib/orchapi`, used by naructl and naru-hostd; the roles, the pairing code, the admission statement, the revocation list and the sealed box are `lib/identity`'s ([ADR 0041](./adr/0041-orch-is-a-cluster-of-members-with-an-embedded-etcd-one-elected-leader-and-an-mtls-api-that-enrolls-and-admits-hosts-and-the-signer-holds-every-key.md)).
- **Members.** Each control host runs one member: an embedded etcd v3.6 (peer and client URLs over mutual TLS from the orch certificate, the flags `--name`, `--data-dir`, `--peer-url`, `--client-url`, `--initial-cluster`, `--initial-cluster-state`, `--join`, `--restore`) and the API. With `--metrics-addr` the registry also counts the API's requests in `naru_orch_api_requests_total{route,code}`, by route pattern. Three members tolerate the loss of one.
- **One leader.** The members campaign on an etcd election with a session lease of 10 s. Reconcilers and state derived from the inventory run only while a member leads, with a context that ends when it stops leading. A stopped leader is replaced within about the lease; a member never resigns early. The groups engine (`orch/internal/groups/`, [groups.md](./groups.md)) and the network reconciler (`orch/internal/netrec/`, §Networks) are the `Reconciler`s orchd runs in that seam, each in its own goroutine.
- **The API** is HTTPS, TLS 1.3, port 7500 by default. A client certificate is verified against the authority and read with `lib/identity`; the role is its one OrganizationalUnit. A revoked serial is refused: the revocation list is the signer's, verified with the revocation public key (`--revocation-public-key`), kept 30 s and replaced only by a list whose `seq` is not lower. With no verified list yet every authenticated call is 503; with a list and a signer that stops answering, the last list stays in force for `--revocation-max-age` (default 10 minutes) from its last refresh, and after that every authenticated call is 503 until a refresh succeeds.
- **The revocation list is synced between the signers.** Each member stores the highest-sequence list it has seen in etcd at `/naru/orch/crl`, written with a compare-and-swap on the key's revision, and every `--revocation-sync-interval` (default 10 s) pushes it to its local signer with `POST /v1/crl` and stores what the signer returns when its sequence is higher. A lost swap is read again at the next sync. The list also carries the nonces of the signer's reissue requests, which orch stores and pushes as it does the serials ([ADR 0052](./adr/0052-a-reissue-nonce-is-signed-into-the-revocation-list-so-orchs-sync-carries-it-to-every-signer-and-a-peered-signer-refuses-a-reissue-until-it-has-taken-the-list-lately.md)). A revoke on one signer therefore reaches the others within a sync interval plus the member's list TTL; until then a signer that has not heard of it still issues for that operator.
- **What each role may do.**

  | Endpoint | reader | operator, automation | root | host | no certificate |
  | --- | --- | --- | --- | --- | --- |
  | `GET /v1/hosts`, `GET /v1/pending`, `GET /v1/events`, `GET /v1/microvms`, `GET /v1/groups`, `GET /v1/groups/{name}`, `GET /v1/networks`, `GET /v1/networks/{name}` | yes | yes | yes | 403 | 401 |
  | `POST /v1/admit`, `PUT /v1/hosts/{id}/labels`, `PUT /v1/groups/{name}`, `DELETE /v1/groups/{name}`, `PUT /v1/networks/{name}`, `DELETE /v1/networks/{name}` | 403 | yes | yes | 403 | 401 |
  | `POST /v1/enrollment-keys`, `DELETE /v1/enrollment-keys/{id}` | 403 | yes | yes | 403 | 401 |
  | `POST /v1/snapshot`, `GET /v1/snapshots/latest`, `PUT /v1/restore` (409 once the member runs) | 403 | 403 | yes | 403 | 401 |
  | `POST /v1/heartbeat` | 403 | 403 | 403 | yes | 401 |
  | `GET /v1/crl` | yes | yes | yes | yes | 401 |
  | `POST /v1/enroll`, `GET /v1/enroll/{hostID}` | n/a | n/a | n/a | n/a | key or proof, not a certificate |

- **Enrollment.** An operator creates an enrollment key (`naru-ek-` and 64 hex digits, shown once, valid at most 365 days); orch keeps the SHA-256 of it, never the key. A host sends the key, its ID, its public key and a certificate request to `POST /v1/enroll`; the request is refused with 403 for a key that is unknown, expired or revoked, and with 429 over a token bucket per source address (1 per second, burst 10) and per key (5 per second, burst 50). The buckets are in each member's memory. At most 1000 enrollments wait. The host shows its pairing code on its console every minute and polls `GET /v1/enroll/{hostID}` with a signature of the current time by its own key (five minutes of skew); orch answers a poll only for the holder of the enrolled key.
- **Admission.** `POST /v1/admit` is for an operator. Orch computes the pairing code from the key it stored and compares it with the request's code; it does not use a code a host sent. A mismatch is 403 and nothing reaches the signer. Otherwise the opaque admission statement and the host's certificate request go to the signer, which verifies the statement (role, revocation, expiry, the key's hash) and issues the host's certificate; orch checks that the certificate is for the enrolled key and stores it. The region and labels are fields of the request beside the statement. naructl's `host admit` takes the key from `GET /v1/pending`, compares the code against that key itself and signs locally with the operator's person file.
- **Region and labels.** A region is a DNS label; labels are Kubernetes keys and values, at most 64. `PUT /v1/hosts/{id}/labels` replaces both. Every enrollment, admission, refusal of a code and label change is an event, listed by `GET /v1/events`.
- **Heartbeat.** An admitted host presents its certificate to `POST /v1/heartbeat`; orch records the time as the host's `lastSeen`. After a restore the host reconnects with the same certificate.
- **Snapshots.** The leader's member takes an etcd snapshot every 6 hours, keeps the newest 8 and writes each sealed to the recovery public key (`--recovery-public-key`) with `lib/identity`'s sealed box; with no recovery key nothing is written, and an unsealed snapshot is never written. `POST /v1/snapshot` (root) takes one at once. The guest's snapshot directory is `/var/lib/naru/orch/snapshots`; an operator fetches the newest sealed snapshot with `GET /v1/snapshots/latest` (root, the sealed bytes, 404 with none), which `naructl orch backup --out <file>` does after taking one. [ADR 0053](./adr/0053-a-member-started-with-restore-serves-only-a-snapshot-upload-and-the-operator-sends-it-the-plain-snapshot-and-the-other-members-join-it-as-new-members.md)
  - **Restore.** `naructl orch restore` opens a sealed snapshot with the recovery key and its passphrase; `--out` writes the plain etcd snapshot, and `--push <orch URL>` (with `--orch-ca`, `--admin` and `--admin-passphrase-file`) sends it, with its SHA-256 in `X-Naru-Snapshot-Sha256`, to a member started with `--restore`. The plain snapshot is written to the operator's disk only with `--out`.
  - **A member that waits for a restore** has no etcd in its data directory and `--restore` set; it starts no etcd and serves only `PUT /v1/restore`, root only (other routes are 503). It refuses a body whose hash or etcd's own check fails (400), restores into this member's name, `--peer-url` and an initial cluster of itself alone, and starts; a second `PUT` is 409. With a member in the data directory `--restore` is ignored and logged.
  - **Order.** The first member restores alone. The second and third start with `--join <a running member's client URL>` and `--initial-cluster-state existing`, call `MemberAdd` themselves (retried for up to a minute while etcd calls the cluster unhealthy) and take the initial cluster etcd returns.
- **The signer** is a service on the control host that orch calls over a unix socket (`--signer-socket`), HTTP with JSON bodies. Orch makes three calls, which [the signer's document](./signer.md) fixes: `POST /v1/host` with `statement` and `csr`, answered with `certificate`; `GET /v1/crl`, answered with the signed list; `POST /v1/crl` with a signed list as the body, answered with the list the signer holds. A 401 or 403 is the signer's refusal; anything else that fails is a 502 to the caller. Orch does not ask for its own identity: the signer issues an orch certificate only for a request root signs, so root has the signer issue it (`POST /v1/orch`) and places it, with the key and the authority, at the paths orch is given; a member without them does not start. The revocation key's public half is a PKIX PEM, which `naru-signer init --revocation-public-key` writes.
- **The host's agent** in `naru-hostd` runs when `--orch-url` is set. It trusts orch by the SHA-256 of the authority's certificate (`--orch-ca-sha256`), which must be in the chain orch presents, and by orch's name, so a host's own certificate cannot stand in for orch. It reads the enrollment key from `--enroll-key-file`, keeps its key at `--host-key`, writes the certificate beside it and then heartbeats; with a valid certificate for the key it does not enroll again.
- **Groups.**
  - The API stores a group spec under `/naru/orch/groups/<name>` and the engine's member records under `/naru/orch/group-members/<id>`, each written with a compare-and-swap on its modification revision. A spec is validated before it is stored (400); `GET` shows the members with their phase computed from the hosts, or the stored phase and `observed: false` when no host list could be had. `DELETE` is 409 while the group has a member that is not gone: apply it with `count: 0` first.
  - The leader runs the engine over three adapters. The store is the etcd one. The events go to the inventory's event log as `group.<kind>`, a hold that repeats once per 10 minutes. The hosts are each admitted host's own API (`lib/hostapi`) at the address its enrollment recorded, over mutual TLS with the pair `--host-client-cert` and `--host-client-key` (orch's own pair by default, which init passes explicitly), trusting `--host-ca` (the authority by default; `spec.orch.hostCA` from init). The host takes that pair's OrganizationalUnit `orch` as the provisioner role ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md), note of 2026-11-14). `--group-interval` sets the pause between passes.
  - A host is ready while its `/v1/host` and `/v1/microvms` answer; its capacity is what `/v1/host` reports free, and the names of the kernels it offers are its node versions. It is never draining until the inventory has a drain.
  - A template maps to the host API as follows: the image form's `version` is the image (`repository@sha256:digest`) and its root disk is the template's `rootDiskBytes`, which must be above zero; the OS form's `nodeVersion` is the boot set, its first disk the data disk, and its seed the template's `userData`, or `#cloud-config` when that is empty. A template that names a `network` creates the microVM attached to it, with the member's Pod prefix when `podPrefixBits` is above zero.
  - `GET /v1/microvms` reports each microVM's image digest or boot set and its network, as its host reports them.
  - A stateful member is created fenced and not started. Renewing sets the host's per-microVM fence to the deadline the engine chose, its length rounded down to whole seconds and its renewal number that deadline in Unix nanoseconds; inspecting reads the time the fence has left, counted from the clock at the call, and `fenceLapsedAt`.
- **Networks** ([ADR 0049](./adr/0049-orch-keeps-the-networks-and-allocates-each-members-pod-prefix-by-compare-and-swap-and-the-leader-tells-every-host-its-networks-members-and-peers.md)).
  - The API stores a network, `{prefix, apiEndpoint?}`, under `/naru/orch/networks/<name>`. The name is a DNS label, the prefix an IPv4 prefix with its host bits clear, the endpoint an address inside it (400). `DELETE`, or an apply that changes the prefix, is 409 while a group's template names the network. Each apply and delete is an event, `network.applied` and `network.deleted`.
  - The leader's network reconciler runs one pass per `--network-interval` (default 10 s). For every admitted host that answers `GET /v1/tunnel` and `GET /v1/microvms` it declares every network on it with `PUT /v1/networks/{name}`, whose `remoteMembers` are the addresses (`/32`) and Pod prefixes of the network's microVMs on the other hosts, and puts the whole list of peers with `PUT /v1/peers`: each other host that answered, its tunnel's key, its endpoint at the host's address with the tunnel's port, and its Machine prefixes and the Pod prefixes of its members. It then lists the host's networks with `GET /v1/networks` and deletes with `DELETE /v1/networks/{name}` each that orch does not keep, so a network deleted on orch leaves every host. A host that does not answer is logged and skipped for the pass. Nothing is kept between passes, so a host that restarted, or orch after a restore, is brought whole again within one interval.
- **naructl** takes `orch init|backup|restore`, `host pending|admit|label`, `enroll-key create|revoke`, `group apply -f|get|list|delete` and `network apply -f|get|list|delete` ([config.md](./config.md)).
- **Deployment.** orchd runs as a configured service under the user `naru-orch`. Packaging it as an extension is not decided here (garamsh/naru#57).

## Rationale

- [ADR 0053](./adr/0053-a-member-started-with-restore-serves-only-a-snapshot-upload-and-the-operator-sends-it-the-plain-snapshot-and-the-other-members-join-it-as-new-members.md): why a restoring member serves only an upload, why the plain snapshot is sent by the operator, why the other members join as new members, and the signs it was wrong.

## Open questions

- `naructl orch init` writes the recovery key and its public half only. The root person file and the first control host's identities come from the signer's own commands, which this change does not have.
- The rate limits are per member, so an attacker who spreads requests over three members is allowed three times the rate.
- A fence's deadline as mvmd keeps it is the moment it receives the renewal plus the length, so it can be later than the recorded one by the call's latency; the engine's wait for a lapsed host is not extended for it.
- A group template carries no root disk size, no user-data and no host-API role. The root disk and the seed are fixed as above, and the host API still reads the role `naru:host-provisioner` from the certificate, not `lib/identity`'s roles, so orch's pair for the hosts carried that Organization until the host API took `lib/identity`'s orch role (see the ADR 0050 note).
- A host that stops answering is not ready after one failed probe; there is no grace period before the engine replaces its members.
