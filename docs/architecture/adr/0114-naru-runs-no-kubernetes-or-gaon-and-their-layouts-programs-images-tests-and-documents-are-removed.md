# ADR 0114: naru runs no Kubernetes or gaon, and their layouts, programs, images, tests and documents are removed

> Status: accepted
> Date: 2026-11-24

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for goal garamsh/naru#375, goal 2 of garamsh/naru#373. It supersedes by reference the ADRs listed under Decision item 6 and amends those under item 7; their bodies are not edited, and a superseded ADR's status names this one.

## Context

- **The direction changed.** On 2026-11-24 the owner decided that naru no longer builds Kubernetes and becomes the multi-host microVM Machine service (garamsh/naru#373). garam's own cluster moves to Talos Linux (#373 §1), so no cluster of ours depends on naru's Kubernetes.
- **gaon is gone too.** garamsh/gaon is archived (`gh repo view garamsh/gaon` reported `isArchived: true` on 2026-11-24). The host image still carried gaon's four services, and the "gaon Node layout" in `lib/layout` (the cluster authority, `spec.controlPlane`, etcd in the image, the bootstrap tokens, `/run/gaon`) and the public `naru-cluster` harness existed only to boot a gaon cluster. Kubernetes on naru reused exactly those parts (etcd, the control-plane Node, the cluster authority, `naru-vip`), so neither can go without the other. The coordinator of goal #375 decided on 2026-11-24 to remove both in this goal.
- **What stays is named.** #373 §2 lists what stays: the host OS, init, upgrades and rollback, extensions, kernels and guest initrds, enrollment, the signer and certificates, revocation, host networking, the Node API, the host API, orch's inventory, leader, prefixes, networks, exposures, snapshot and restore, groups, and naructl's host and orch commands.
- **Some shared mechanisms had one producer.** The boot-medium extension staging of ADR 0096 was built for, and only ever carried, the `naru-volumes` add-on. The XFS project quota on a storage disk, the `cpuset` and `hugetlb` controllers, the shared root mount, the seed's `meta-data`, `spec.network.bridgeNetfilter`, `mount` and `umount` in the initramfs, and the registry's sandbox image were each added for the kubelet, containerd, a Pod or a volume.

## Decision

**naru builds, ships and tests no Kubernetes, no gaon and no cluster on its Nodes. Everything that existed only for them is removed, in four pull requests into main (garamsh/naru#375), and what a kept part shared with them stays with only their use taken out.**

1. **Kubernetes.** The Kubernetes Node layout (`lib/layout`'s `Node.Kube`, the add-ons, the ServiceAccount issuers and keys, the front-proxy authority), `naructl gen kubernetes`, `gen kubernetes-jwks`, `gen kubernetes-node`, `gen kubernetes-bootstrap-rbac`, `topology kubernetes` and `token --kubernetes`, `node/`'s `naru-ccm` and `naru-volumes`, the image packages `kubernetes`, `kube-network-policies`, `containerd`, `libseccomp`, `cni`, `coredns`, `ccm` and `volumes` with `addon-image.sh`, the release's `naru-volumes-ext-<version>` assets and add-on images in the SBOM, and the Kubernetes QEMU tests are removed.
2. **Init's Kubernetes parts.** Init keeps no delegated `naru/kubernetes` cgroup and enables `cpu`, `memory` and `pids` only; it no longer makes `/` shared, reads the seed's `meta-data`, takes `spec.node` or `spec.network.bridgeNetfilter`, or mounts a storage disk with `prjquota`. `kubernetes` is no longer a reserved service name. A stored configuration that names `spec.node` or `bridgeNetfilter` was written for a Kubernetes Node and is refused, as any unknown field is: its trial boot rolls back (ADR 0025).
3. **The boot-medium extension staging (ADR 0096) is removed** with its only producer: `lib/init/bootmedia`, the stage before the extensions are mounted, `naru-disk -extension` and `-layout` with the ESP's `EXT/` index, the release's `extensionRoom` (`naru-esp.json`), and the Node initramfs's `/usr/lib/naru/boot-extensions`. The ESP is the room for kernels alone again (ADR 0037). Goal 3 may bring a staging path back when it has a real producer.
4. **The cloud controller's exposer, the Pod prefix, gaon and the cluster control plane** go in the later pull requests of #375: the `exposer` role and `naructl ccm credential` (operator exposures and address pools stay); the Pod prefix of a network member, of a group template and of the host API (a member keeps its address); gaon's services and package, the gaon modes of `lib/layout`, the bootstrap tokens, the cluster authority, `spec.controlPlane`, etcd in the image (orch's embedded etcd stays), `lib/vip`, `naru-vip`, `naru-fence` and the `naru-cluster` harness with its release asset.
5. **What stays.** The node image stays as a plain OS-form boot set of `naru-init`, with no Kubernetes content, and the host API's OS form, boot sets and a group's `os` form stay with it: goal 3 decides whether the OS form stays for Machines. The registry, `spec.registries`, `spec.aws` and the ECR credential stay for mvmd's pulls. The kernels' configurations are not changed by this decision.

## Options considered

- **Freeze the Kubernetes and gaon code in place.** Every kept change would keep building, vetting and documenting a path nobody runs, and the tree would not match the scope #373 sets.
- **Remove Kubernetes and keep gaon.** gaon is archived, and keeping it keeps etcd in the image, the control-plane Node, the cluster authority and `naru-vip` alive for nothing.
- **Keep the boot-medium staging with no producer.** A mechanism that no release exercises is kept working by tests alone (simplicity.md, "Delete, don't wrap"); history keeps it for a later producer.
- **Remove the node image and the OS form too.** The kept fleet tests of the host API, groups and snapshots boot it, and whether a Machine boots an OS form is goal 3's question, not this one's.

## Consequences

- A Kubernetes Node that upgrades to a release with this change refuses its stored configuration and rolls back to the release it ran (Decision item 2); a cluster on naru is replaced, not upgraded (#373 §4).
- The release carries no `naru-volumes-ext-<version>` asset; `make release` writes sixteen assets and `SHA256SUMS`, and the release workflow checks seventeen files. `fixture.ReadRelease` leaves the volume extension of an earlier release out of the store it builds.
- The ESP of a disk built after this change has no `EXT/` directory, and its manifest's `esp.bytes` is the whole partition.
- The kernels keep the options Kubernetes needed (`image/pkgs/kernel/`); trimming them is a kernel change that needs its own QEMU run.
- `docs/operate/install-kubernetes.md` and `docs/operate/reach-a-members-api-server.md` are deleted.

## Signs the decision was wrong

- A Machine of goal 3 needs a Kubernetes or gaon part removed here, such as a Pod network or the cluster authority: it would be brought back under goal 3's design, not restored from history as it was.
- A blank host cannot get an extension it needs at its first boot without a delivery by hand: the staging path removed in item 3 had a producer after all.
- A host that ran no Kubernetes refuses its stored configuration after an upgrade: a field the hosts' layout wrote was removed without the retired-field handling the later pull requests of #375 owe it.
