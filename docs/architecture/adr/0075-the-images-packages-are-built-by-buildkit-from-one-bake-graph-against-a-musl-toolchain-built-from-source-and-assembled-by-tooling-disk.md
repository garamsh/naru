# ADR 0075: the image's packages are built by BuildKit from one bake graph against a musl toolchain built from source, and tooling/disk assembles them

> Status: accepted
> Date: 2026-11-15

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#189, part of goal garamsh/naru#197. It carries out item 7 of [ADR 0063](./0063-the-image-is-built-inside-one-digest-pinned-builder-container-whose-toolchains-are-pinned-and-the-stage-2-direction-is-a-musl-toolchain-with-buildkit-built-packages.md) and records the whole of stage 2, the part built first (phase A) and the part built after it (phase B), so that phase B needs no ADR of its own. It supersedes [ADR 0006](./0006-the-host-kernel-is-built-from-the-pinned-longterm-6-18-tarball-and-the-image-inputs-live-in-image.md) in part (item 3's layout, a folder of inputs for each component, for the C components) and [ADR 0011](./0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md) in part (item 3, "the builder's `libc.a` is linked", and the script that built it). The facts about the old build are those of `docs/architecture/image.md` before this change.

## Context

- **The static links used glibc.** The builder's `libc.a` is glibc's. A link of `getpwnam`, `getaddrinfo` or `dlopen` warns that it needs the shared libraries of the glibc it was linked with, and the image has none, so ADR 0063 added a gate and an allow list. Three programs (nft, mkfs.xfs and util-linux's mount and umount) were on that list only because glibc cannot link them cleanly.
- **Each component had a script of its own,** with its own download, SHA-256 check, build directory and stamp. The scripts of the five C components repeated one shape, and a dependency (xfsprogs on util-linux, libuuid and libblkid; nftables on four libraries) was a build directory another script left behind.
- **The builder compiled every package.** A compiler of the builder's distribution is recorded in each binary's `.comment`, so the bytes of every C binary depended on the builder's package list as well as on the package.

## Decision

**The image's non-Go packages are built by BuildKit from one graph, `image/pkgs/docker-bake.hcl`, driven by `docker buildx bake`, against a `x86_64-linux-musl` toolchain that the graph builds from pinned source. Each package is an OCI image of only its installed files. `tooling/disk`'s `naru-pkg` unpacks them and the existing assembly scripts read the result.**

1. **One graph, BuildKit.** A package is `image/pkgs/<name>/Dockerfile` with its pins in `image/pkgs/<name>/pin.env`, which the Dockerfile copies in and sources, so one file holds a pin. A dependency is a named context of the bake file (`contexts = { toolchain = "target:toolchain" }`), so BuildKit builds the packages a package names first, shares their results and builds independent packages in parallel. The graph runs in the BuildKit of `image/builder/builder.env` (`BUILDKIT_IMAGE`, the docker-container driver). `image/pkgs/build.sh` runs on the host, because it needs the Docker daemon the builder container's own `run.sh` runs over, and builds the stage 0 image, the builder itself, as the first target, failing unless its config digest is `BUILDER_CONFIG_DIGEST`.
2. **Why BuildKit and not Talos `bldr`.** `bldr` is the tool Talos builds its packages with. Its README shows a frontend image on ghcr.io selected by a `# syntax=` directive, YAML `Pkgfile` and `pkg.yaml` specs with Go templates and Sprig, and `alpine` and `scratch` variants. It is a second tool and a second specification format beside BuildKit, which it runs on, for a graph of about twenty packages that bake already expresses with a Dockerfile each, and it adds a frontend image to pin and trust. The ADR chooses the smaller set of moving parts. What would change it: a graph that bake cannot express, or a need for `bldr`'s package-level reuse across repositories.
3. **The toolchain is built from source.** `image/pkgs/toolchain` is binutils 2.46.1, gcc 15.3.0 (C only), musl 1.2.6 and the Linux UAPI headers of the pinned kernel tarball (`image/common/kernel/pin.env`), with gmp 6.3.0, mpfr 4.2.2 and mpc 1.4.1 built in the gcc tree. The target is `x86_64-linux-musl`, the prefix `/toolchain` and the sysroot `/toolchain/x86_64-linux-musl`. Stage 0, the builder's gcc, builds it; no package is compiled by the builder's gcc. Archives are deterministic (`--enable-deterministic-archives`), and a check at the end of the build compiles a program with the toolchain and fails unless it is static, runs, and its `.comment` names no Ubuntu compiler. The recipe follows musl-cross-make's order (binutils, headers, a C-only gcc, libgcc, musl) with every tarball pinned in `pin.env` and checked by SHA-256; nothing is fetched unpinned.
4. **Provenance of the pins.** gcc 15.3.0 and binutils 2.46.1 were checked against the SHA-512 lists their projects publish (`sourceware.org/pub/gcc/releases/gcc-15.3.0/sha512.sum`, `sourceware.org/pub/binutils/releases/sha512.sum`) and pinned by SHA-256 of the same file. gmp, mpfr and mpc were fetched from a GNU mirror (`ftp.gnu.org` is not reachable from the machine that made the pins), and their detached signatures verify with `gpgv` against the GNU keyring from the same mirror (signers: Niels Moller, Vincent Lefevre, Andreas Enge); the SHA-256 is of the signed file. musl 1.2.6's `.asc` verifies against `musl.pub` from musl.libc.org (primary key `8364 8929 0BB6 B70F 99FF DA05 56BC DB59 3020 450F`); that key is not independently certified, so the check shows the file is the one the key's holder signed and does not show the key is the maintainer's by another route. The kernel pin was already SHA-256 checked. The five earlier components keep the pins and the provenance comments they had.
5. **musl's iconv CVEs do not reach the image.** 1.2.6 fixes CVE-2025-26519 (the EUC-KR out-of-bounds write, through 1.2.5). CVE-2026-6042 (a denial of service in the GB18030 decoder of `iconv`) is in 1.2.6, and CVE-2026-40200 (`qsort`) concerns 32-bit targets only. No program of these packages links `iconv`: every package builds with NLS off, and `image/pkgs/install-bin.sh`, which every shipped program passes through, fails the build when `nm` shows `iconv`, `iconv_open` or `iconv_close` in the linked program. If a package ever needs the path, the fix is an upstream patch applied by that package's Dockerfile and pinned there, not a newer musl by hand.
6. **Layout.** A package's last stage is `FROM scratch` and holds only the files it installs, under `/usr` (`/usr/bin`, `/usr/sbin`, `/usr/lib`, `/usr/include`), the toolchain under `/toolchain` and the root bundle at `/etc/ssl/certs/ca-certificates.crt`. A library a package needs is installed into the toolchain's sysroot by `COPY --from=<library> /usr /toolchain/x86_64-linux-musl/usr`, so the compiler finds it with no flag of the package's own. Every program goes through `install-bin.sh`, which strips it, and fails unless it is static and names no distribution compiler.
7. **Output and comparison.** bake exports each package as an OCI image tar, `build/pkgs/<name>.tar`, uncompressed and with timestamps rewritten to `SOURCE_DATE_EPOCH`, so the manifest digest names the bytes. `tooling/disk`'s `naru-pkg` unpacks a tar (layers in order, whiteouts applied, an entry kept inside the directory) and prints a package's manifest digest; no script parses OCI. `make image-repro` builds the packages twice with `--no-cache`, fails unless every package has the same manifest digest in both, and still compares `SHA256SUMS`.
8. **Phase A (garamsh/naru#189's first part) builds the toolchain, util-linux (mount, umount, libuuid, libblkid), e2fsprogs (mke2fs), xfsprogs with userspace-rcu and inih, nftables with libmnl, libnftnl and jansson, and cacert.** The initramfs scripts read their outputs, the five `image/common/<name>/build.sh` files and their stamps are deleted, and util-linux, nft and mkfs.xfs leave `image/nss-allow.txt`.
9. **Phase B (the rest of garamsh/naru#189) is decided here and built later.** Go programs become packages (`FROM` the toolchain's stage 0 Go, `GOFLAGS=-mod=readonly`, `-trimpath`), as do the host and guest kernels with their configuration, the guest initrds, the two initramfs archives and the `naru-orch` extension; each is a Dockerfile and a bake target under `image/pkgs/` and its output is unpacked the same way. The remaining `build.sh` files and `build_current` are removed when the last component is a package; the stamp's job is BuildKit's cache. `tooling/disk`'s assembly (ADR 0025), `run.sh`, the builder's digest and the `SHA256SUMS` comparison stay.

## Consequences

- **The static links are musl's.** No NSS warning is printed by these packages and the allow list holds the one program that needs a different explanation (`aws_signing_helper`).
- **The build needs two more things on the host:** the Docker daemon (as before) and `docker buildx`. `build.sh` creates a `docker-container` builder of the pinned BuildKit image and reuses it.
- **A change to a package rebuilds that package and the ones that name it,** and the cache is BuildKit's, which `make image-repro` bypasses on purpose.
- **The toolchain build is long** (gcc), paid once per cache.
- **musl is not glibc.** A program that needs `getpwnam` from `/etc/nsswitch.conf`, `dlopen` or locales behaves differently; the five programs here were checked by running them (the QEMU tests boot with them).

## Signs the decision was wrong

- Two builds of one commit differ in a package digest: the layer rewrite or a build input is not fixed.
- The graph grows past what a Dockerfile per package and named contexts express, and a second tool would cost less than the workarounds.
- A security advisory for musl or gcc reaches a program of the image faster than the pin moves.

## Erratum, 2026-11-16 (phase B, garamsh/naru#189)

Item 9 is carried out as decided. The cases it left open, settled here:

- **The version and the test root are bake variables, not files.** `NARU_VERSION`, `TESTROOT` (a named context holding `ca.pem`, empty for a release) and `REFUSE_LDFLAGS` are variables of `image/pkgs/docker-bake.hcl`; `build.sh` takes the first from the environment and refuses to run without it. The `upgrade` group adds the `-next` and `-refuse` initramfs and `bzImage` packages that `make image-upgrade` reads.
- **The kernel tree's `gen_init_cpio` is a target.** `gen-init-cpio` of `image/pkgs/kernel/Dockerfile` compiles it from the pinned tarball, and both initramfs packages take it by named context; the kernel build itself is one Dockerfile with a stage per kernel, so the tarball, its pin and the configuration merge are written once.
- **The root `.dockerignore` narrows the `src` context to the Go workspace** (`go.work`, `lib`, `host`, `node`, `orch`, `naructl`, `tooling`, no test files); every bake context names its own directory and so is not narrowed by it.
- **`libseccomp` is a package of its own** (`image/pkgs/libseccomp`), as the other libraries are, and `containerd`'s Dockerfile takes it by named context.
- **mvmd's `converter-initrd` downloads its build tools** (m4, autoconf, automake and libtool) from `ftp.gnu.org` with a fallback to `ftpmirror.gnu.org`, each checked against the SHA-256 in mvmd's script. The package build reaches the network for them as the old build did; the digests, not the host, decide what enters the initrd.
- **The `build/kernel/dl` and `build/containerd/dl` directories are gone.** They were local copies of pinned tarballs kept between builds; BuildKit's cache holds the downloads now.
- **The NSS gate and its allow list are removed with `image/lib.sh`.** Their one entry, `aws_signing_helper`, is built in its package against musl.
- **The build stamp is removed.** BuildKit's cache is the stamp of every package.
