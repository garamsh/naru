# ADR 0025: an upgrade is a bundle posted to POST /v1/upgrade, which init writes to the trial slot, and the trial boot promotes itself when healthy and is rolled back when not

> Status: accepted
> Date: 2026-11-13

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#67. It builds on [ADR 0020](./0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md) (the slots, the trial entry, the rename, the bundle) and [ADR 0022](./0022-a-node-is-rebooted-through-the-node-api-by-post-v1-reboot-or-the-reboot-apply-mode-and-init-answers-before-it-stops.md) (the reboot), and amends [ADR 0017](./0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md) (the endpoints) by reference: no body is edited, and what each says holds with this decision added.

## Context

- **ADR 0020 left the writing and the judging to #67.** It fixed the layout (two kernel files in the ESP's `\EFI\BOOT\`, a trial entry `Boot0100`, `BootNext`, promotion by one rename) and the bundle `naru-upgrade-<version>.tar`, and said that the running system performs the steps. It did not say which request carries the bundle, what makes a trial healthy, or what undoes a trial that is not.
- **The Node has no spare disk and no console an operator can be expected to have.** The upgrade has to complete, or undo itself, with no one at the Node, and a trial that never reaches init has to be undone by the firmware alone.
- **The ESP is not mounted at runtime.** The image mounts nothing from the boot disk after the kernel is loaded. A writable mount that stays is a writable FAT file system under a running Node.
- **A health check can be wrong in two directions.** One that is too quick promotes a kernel whose services were about to fail, and one with no bound leaves a Node that is up but broken on the trial slot for ever.

## Decision

1. **`POST /v1/upgrade`** needs `naru:admin`, takes the bundle as the request body (`application/x-tar`) and its expected SHA-256 as the query parameter `sha256` (64 hexadecimal digits, either case); a digest in the URL is visible to the caller only and carries no secret. Init streams the body into `TRIAL.EFI` on the ESP while it hashes it and while it reads the tar, and checks, before it writes any variable: the SHA-256 of the whole body is the one asked for; the tar holds `kernel.efi` and then `manifest.json`, and nothing else; the manifest's kernel `bytes` and `sha256` are those of the member written; and `TRIAL.EFI` is written, `fsync`ed and its directory `fsync`ed. The body is capped at 1 GiB (`413`). It then writes `Boot0100` and `BootNext=0100`, answers `202` with `{"actions":[{"action":"upgrade","target":"<version>"},{"action":"reboot","target":"node"}]}`, and reboots by the path of ADR 0022 (the reply is flushed first).
2. **Refusals touch nothing that boots.** A body that is not the bundle it was told (a wrong digest, a malformed tar, a manifest that disagrees with the kernel) is `400`; a body over the cap is `413`; an upgrade while another is being received, while this boot is a trial, or while one is staged and has not ended, is `409`; anything else is `500` with a message that names no path, the detail being in init's log. None of them writes `BOOTX64.EFI`, `Boot0100` or `BootNext`, and each removes a partial `TRIAL.EFI`. A Node without an upgrade (a build that gives the API none) answers `501`.
3. **The ESP is found by its partition GUID and mounted only while it is written or renamed.** Init reads `/sys/class/block`, takes the partition whose GPT partition GUID is `cb4162e7-9d1e-48df-b937-f5792071b950` (the one `image/disk/build.sh` sets, [ADR 0020](./0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)), mounts it as `vfat` (`nodev,nosuid,noexec`) at `/run/naru/esp` for the write, the rename or the removal, and unmounts it before it returns.
4. **A trial boot is the boot whose `BootCurrent` is `0x0100`.** Init mounts `efivarfs` at start and reads `BootCurrent`; any other value, and a machine with no EFI variables, is a default boot. `GET /v1/version` reports it as `slot`: `trial` or `default`.
5. **A trial is healthy when the boot sequence finished and every service it started has run for 30 s without a restart.** The boot finished when init did not refuse ([init.md](../init.md)). The 30 s (`Settle`) starts again whenever a service is not `running` or its restart count changes; a trial that started no service is healthy 30 s after the boot. Init looks once a second. A healthy trial is promoted by init: it renames `TRIAL.EFI` to `BOOTX64.EFI` in the one directory, `fsync`s the directory, deletes `Boot0100`, records the outcome and logs `upgrade promoted`. It does not reboot; the Node is already running the kernel that is now the default.
6. **A trial that is not healthy is undone by a reboot that does not promote.** A trial whose boot was refused gives up at once. One that is not healthy 180 s (`Bound`) after init started, or whose promotion fails, gives up then. To give up is to write the reason to the upgrade directory and reboot by the path of ADR 0022. `BootNext` was consumed by the firmware when it booted the trial, so the next boot is the default slot. A kernel that never reaches init is undone by the firmware alone: the kernel's `panic=-1` reboots it, and `BootNext` is one-shot.
7. **A default boot settles what a trial left.** If `TRIAL.EFI` or `Boot0100` is present on a boot whose `BootCurrent` is not `0x0100`, init removes both, and a stale `BootNext` that names the trial entry, and records the upgrade as `rolled back` with the reason the trial wrote, or `the trial boot did not reach a healthy state` when it wrote none, and logs `upgrade rolled back` with it. If the running version is the one the upgrade was to, only its bookkeeping was left, and it is recorded as `promoted`.
8. **The last outcome is stored on the data disk.** `/var/lib/naru/upgrade/last.json` holds `{from, to, result, reason, time}` (`result` is `promoted` or `rolled back`, `time` is RFC 3339 in UTC, `reason` is omitted when empty); `pending.json` holds an upgrade staged and not yet ended, and is written before `Boot0100` is. Both are written to a temporary file, `fsync`ed, renamed, and the directory `fsync`ed, as the configuration store is. `GET /v1/version` carries `slot` and, once an upgrade has ended, `lastUpgrade` with those fields.
9. **`naructl upgrade --bundle FILE --sums SHA256SUMS`** reads the line of the bundle's base name in the sums file (`sha256sum`'s format), hashes the file, refuses a mismatch with no byte sent, and calls the endpoint with the digest. It prints the actions the Node accepted. Whether the upgrade took is read afterwards: `naructl version` shows the version and the boot ID, and `naructl upgrade --status` shows the slot and the last outcome. `naructl version` does not show the slot or the outcome, since its client package is outside the scope of this change; the Node API does.
10. **What the tests do.** The QEMU tests boot a Node from the image's disk with its ESP writable and the Node API on. One upgrades it to a build of the same tree with another version and asserts the version, the boot ID, the slot after the promotion, the store revision and a file of the data disk. The other upgrades it to a build whose init cannot find its configuration drive and asserts that the Node comes back on the old version and reports `rolled back`, with nothing done to it by the test but starting QEMU again each time it ends, which a hypervisor does after a reboot.

## Consequences

- An upgrade is one command and its result is read from the Node. A Node that comes back on the old version after an upgrade says why in `lastUpgrade.reason`.
- A kernel that boots and runs its services for 30 s is kept, so an upgrade whose fault shows later (a service that fails after a minute, a fault in a feature no service uses at boot) is kept too. The health check says the new kernel started the Node's own services, not that the Node is correct.
- The `naru-bootnext` service of the QEMU test of ADR 0020 arms the trial entry on its own. Since a default boot now removes a trial slot it finds, the service arms only once, and the test waits on its third boot for init's `upgrade rolled back` line (the service and init run at the same time, so what the service reads is not fixed).
- The bundle passes through the Node API, so the API's mutual TLS, its roles and its 503 after an accepted reboot apply to it; a bundle of tens of megabytes holds a connection for as long as the transfer takes, and `naructl upgrade` allows 10 minutes.
- The ESP stays unmounted except for the length of a write, a rename or a removal, so a Node that loses power between them loses at most one of them; the rename is the single step that changes the default, and `fsync` of the directory makes it durable.

## Signs the decision was wrong

- A Node is promoted and then fails within minutes for a reason the settle time would have shown, for instance a service with a long start-up: the answer is a longer settle, or a check the service defines, not a different mechanism.
- A trial that is healthy by this definition is regularly bad: the health check is the wrong judge, and the Node should wait for the operator to confirm with a second request.
- The 180 s bound is too short for a Node whose services take long to start, so healthy trials are rolled back; or too long, so that a broken Node is unreachable for minutes before it recovers.
- `BootCurrent` is not set by some firmware, so a trial is taken for a default boot: init would then remove the trial slot the firmware booted from. The test machine's firmware sets it; a platform that does not needs another way to tell the boot.
- A bundle larger than 1 GiB is wanted, or the ESP is too small for two kernels and a bundle's worth of free space.
