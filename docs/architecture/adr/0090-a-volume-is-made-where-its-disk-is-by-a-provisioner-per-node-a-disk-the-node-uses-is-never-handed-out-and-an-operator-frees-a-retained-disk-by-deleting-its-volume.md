# ADR 0090: a volume is made where its disk is, by a provisioner per Node; a disk the Node uses is never handed out; and an operator frees a retained disk by deleting its volume

> Status: accepted
> Date: 2026-11-21

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#264, part of goal garamsh/naru#262, in the review of the pull request that builds [ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md)'s volume driver. It supersedes ADR 0083 in part: item 6's "as a Deployment (controller) and a DaemonSet on every Node that has a `spec.storage` disk (node plugin)", the one sentence of that item that the build found wrong. Everything else in ADR 0083 stands, and item 10's "an operator releases it" is given its procedure here. The driver's pairing with the extension delivery of [ADR 0084](./0084-an-upgrade-bundle-carries-the-extensions-the-hosts-configuration-names-and-an-entry-without-a-digest-is-resolved-by-init-to-the-image-built-for-its-version.md) is unchanged.

## Context

- **A central provisioner cannot create a volume on a Node.** ADR 0083 item 6 has a Deployment whose provisioner asks the driver for a volume. A `CreateVolume` call reaches one driver, on the Node the Deployment's Pod runs on, so the volume would be made on the wrong Node unless the driver forwarded the call. The external-provisioner has a mode for this, `--node-deployment`, in which each provisioner serves the claims scheduled to its own Node (the claim carries the `selected-node` annotation of `WaitForFirstConsumer`), and `--strict-topology` makes the volume's topology the Node's.
- **A Node with only block disks has no `spec.storage` disk.** ADR 0083 item 10 lets a Node offer whole disks and no storage disk, and the DaemonSet of item 6 would not run there.
- **A block volume is a whole disk, and the driver was told which by serial number only.** Nothing stopped the list from naming the disk that holds `/var/lib/naru` or the EFI system partition, or a disk with a device mapped over it, and a Pod given such a disk could destroy the Node.
- **"An operator releases it" had no procedure.** `naru-block` retains: the volume stays `Released` after its claim is deleted, and a retained volume is deleted only by an operator. Kubernetes calls `DeleteVolume` for a volume only when its reclaim policy is `Delete`.
- **The driver's bind mounts reach the kubelet only through a shared mount.** The DaemonSet mounts `/var/lib/naru/kubelet/pods` with `Bidirectional` and `/var/lib/naru/storage` with `HostToContainer`, and the container runtime refuses the first from a private mount. `LeaveRootfs` (`lib/init/linux/rootfs.go`) moves a tmpfs over `/` and the kernel leaves it private, so every mount init makes under it, the data disk among them, was private too.
- **The request's data is not trusted.** A volume id and a name arrive in a gRPC message, and the driver built a file path from the id.

## Decision

1. **There is one DaemonSet and no Deployment.** Its Pod has three containers: the driver, the external-provisioner with `--node-deployment`, `--node-deployment-immediate-binding=false` and `--strict-topology`, and the node-driver-registrar. It runs on each Node that has the kubelet label `naru.garam.sh/volumes=true`, which the Node's configuration writes for a Node with `spec.storage` or with block serials (ADR 0083 item 10). The sidecars run without privilege escalation, with a read-only root file system and no capabilities; the driver is the one privileged container.
2. **A volume id is `local-<name>` or `block-<name>`, parsed once.** `<name>` is the PersistentVolume's name, a lowercase DNS name that starts with a letter or digit. The driver parses the id of every request into a type before it builds any path, and a request whose id does not parse is `InvalidArgument`. A block volume's record names its disk's serial; the id no longer does.
3. **A record is written last.** `CreateVolume` of a local volume makes the directory and sets its quota, then writes the record. A directory with no record is what a crash left and nobody uses it, so a create removes it and makes it again. A record that cannot be read blocks the creation of volumes of its kind (it hides a project or a disk) and names the file; every other call is served.
4. **A disk the Node uses is never handed out.** A block volume is a disk of the Node's list that is not claimed, is large enough, and has no mounted partition, no mount of itself and no device in a `holders` directory of it or its partitions. The refusal names what uses it. The boot disk, whose partitions hold `/var/lib/naru` and the EFI system partition, is therefore never a claim's even when the list names it.
5. **A bind keeps what its source mount restricts.** The driver remounts a bind with the source mount's `nodev`, `nosuid` and `noexec`, and a directory is bound `nodev,nosuid`, read-only when the Pod asks; a remount with only the read-only flag would clear the others. A bind whose remount fails is unmounted before the call answers, since a retry would find the target mounted and report success for a mount that lacks the restrictions. A block volume is not published read-only (`InvalidArgument`): a read-only bind of a device node does not stop writes to the device, and the driver would otherwise report a restriction it does not keep.
6. **The driver refuses what it cannot keep.** A claim for a local volume larger than the storage disk's free space is `ResourceExhausted`; a volume content source and a StorageClass parameter are `InvalidArgument`, since the driver restores nothing and takes no parameter; a project identifier the file system does not keep whole (one without 32-bit project identifiers) is an error at the volume's creation; and a local volume is not published on a mount that has lost `prjquota`.
7. **An operator frees a retained disk by setting its volume's reclaim policy to `Delete`.** After the claim is deleted the volume is `Released`; `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Delete"}}'` makes the PV controller delete it and the provisioner call `DeleteVolume`, which forgets the claim and wipes nothing. The disk is then handed to the next claim of `naru-block`, with the bytes the last Pod wrote. No `naructl` command and no API of naru is added: the standard Kubernetes step is the only one, and an operator who wants the disk empty wipes it with the tool of their choice before freeing it. A disk that the last tenant left with a device mapped over it (device-mapper or LVM) is refused by the guard of item 4, whose message names the device (`<partition> is under the device dm-0`). The mapping exists in the Node's kernel only and the Node activates none at boot, so the operator removes it before the disk is claimed again by rebooting the Node (`naructl reboot`), or by a Pod with the privilege on that Node that runs `dmsetup remove` for the device named, and then the disk is handed out.
8. **The root mount is shared, once, at the first step of boot.** `LeaveRootfs` makes `/` and every mount under it shared (`mount(2)` with `MS_SHARED|MS_REC`) after it has moved the new root into place, before anything else is mounted, on every Node and every host. A mount made later under a shared one is shared, so the data disk, the storage disks and the mounts of the kubelet's tree are, and the Bidirectional and HostToContainer mounts of the DaemonSet work. Nothing in the layout signals it: the step runs before the configuration is read. The change is safe for mvmd, which also runs on the host: its supervisor starts each VMM in a mount namespace of its own (`CLONE_NEWNS`, `daemon/internal/supervisor/launch.go`) and its `buildRoot` makes that namespace private with `MS_REC|MS_PRIVATE` before it mounts anything and before `pivot_root` (`daemon/internal/supervisor/root.go`), the one operation the kernel refuses on a shared mount, so what it mounts never reaches the host and its pivot succeeds (read at mvmd commit ac22cbd099fa173e40d71b6e9acbdabc550b9f7f).

## Rejected alternatives

- **A Deployment with a controller that forwards to the Node.** A forwarding hop between Pods adds a protocol, a failure mode and a credential for nothing the sidecar mode does not already give.
- **A `naructl volume release` command, or an endpoint on the Node API.** It would be a second route to the same effect, reaching into the driver's records from outside, and the operator already has a tool that every cluster has. It would also be the one thing in naru that edits a driver's state.
- **The driver wipes the disk when the volume is deleted.** A mistaken delete would destroy data; ADR 0083 item 10 decided that the driver never wipes.
- **An id that carries the serial.** The id is the PV's name in the cluster's own records; a serial in it reaches a path and a log, and is no more useful than the name.
- **Sharing only the data disk's mount, or the kubelet's `pods` directory and the storage mount point bound onto themselves.** It leaves `/` private, but it needs a step after the data disk is mounted. `lib/init/boot` has none, and the one place left is a one-shot service on every Kubernetes Node that runs `/bin/mount --make-rshared /var/lib/naru` (the image has `mount`, ADR 0075). `Start` returns when a service is running, and init starts the services in list order without waiting for one to exit (`lib/init/boot/boot.go`), so the share could land after containerd and the kubelet have made mounts, and it adds a service to the topology, to `naructl topology kubernetes` and to their tests for what one call at the first step does for every mount.
- **Trusting the list.** The Node's configuration is the operator's, and a mistake in it is exactly the case a guard is for.

## Consequences

- A cluster with the add-on runs three small containers on each Node with the label, and no Pod elsewhere. RAM per Node is what ADR 0083 counted for the sidecars, with no Deployment's.
- A freed disk is handed out with its old content. A tenant that must not see the last tenant's bytes wipes it first; the Consequences of ADR 0083 about retaining stand.
- A driver that restarts finds its volumes: the records are on the state directory, outside the quota.
- Every mount of a Node is shared, so a mount or unmount in one mount namespace that is a peer of the host's reaches the others. Container runtimes put each container in a private root (runc's default `rprivate`), so only a volume that asks for `Bidirectional` or `HostToContainer` takes part; mvmd makes its VMM namespaces private (item 8).

## Signs it was wrong

- The provisioner of a Node creates no volume for a claim scheduled to that Node, or one creates the volume of another's: `--node-deployment` does not do what this record needs, and the Deployment returns.
- A Released volume cannot be deleted by changing the policy, because the provisioner of another Node ignores it: the release needs a command of naru.
- A disk is refused that nothing on the Node uses, because a `holders` entry or a mount is read wrongly.
- A publish fails with a propagation error although the mount is shared, or mvmd fails to start a VMM with `EINVAL` from `pivot_root`: sharing `/` at the first step is wrong, and the choice is the narrower share rejected above, with the step it needs in `lib/init/boot`.
- A Pod's mounts appear in the host's namespace or in another Pod's: a runtime that does not make a container's root private, so sharing `/` leaks.
