# ADR 0085: a Service of type LoadBalancer is fulfilled by a naru cloud-controller-manager that asks orch for an address from a pool, one host announces it on the LAN and forwards it to the Nodes' NodePorts

> Status: accepted
> Date: 2026-11-21

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#275, part of goal garamsh/naru#262. It carries out item 11 of [ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) and extends [ADR 0048](./0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md), [ADR 0049](./0049-orch-keeps-the-networks-and-allocates-each-members-pod-prefix-by-compare-and-swap-and-the-leader-tells-every-host-its-networks-members-and-peers.md) and [ADR 0042](./0042-the-groups-engine-plans-from-observation-alone-and-replaces-a-stateful-member-only-after-its-fence-has-passed.md) by reference. The API of `k8s.io/cloud-provider` the controller implements is `LoadBalancer` and `InstancesV2`; it is cited by those names, and the implementation pins the version.

## Context

- **A LAN client cannot reach a Node.** Nodes are microVMs on networks closed by default and carried between hosts over WireGuard ([ADR 0048](./0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md)). A Node's layer-2 announcement ends at its host, so an announcer inside the cluster (MetalLB in layer-2 mode, kube-vip) answers nobody on the LAN. The host is the only hop between the LAN and a network.
- **Orch owns the fleet.** It knows which host runs which member, holds a provisioner pair on every admitted host, and already allocates by compare-and-swap ([ADR 0049](./0049-orch-keeps-the-networks-and-allocates-each-members-pod-prefix-by-compare-and-swap-and-the-leader-tells-every-host-its-networks-members-and-peers.md) item 5).
- **The credential is a boundary.** Whatever runs inside the cluster can be compromised by the cluster's workloads. A host's provisioner role creates and destroys every microVM of every customer on it.
- **The LAN side is not naru's.** The addresses of the LAN belong to the network's owner (for aurora, its PM); naru can only be told a range and a link. aurora's PM accepted this ADR's layer-2 announcement and failover time, fixed the pool at 192.168.0.80 to 192.168.0.89, and required the client's source address (item 8).

## Decision

1. **The controller is `naru-ccm`, a cloud-controller-manager of the node unit (`node/cmd/naru-ccm`),** built on `k8s.io/cloud-provider` with its service controller and its node controller, as an add-on of [ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) (a Deployment of two replicas on the control-plane Nodes, with the standard Lease leader election). It holds no naru internals: it speaks orch's exposure API (item 4) and Kubernetes. It fulfils a Service of type LoadBalancer that has no `spec.loadBalancerClass`, or the class `naru.garam.sh/host`. A Service of any other class is left to the implementation that owns it.
2. **A customer replaces it by turning it off and running any implementation of the same interface** (item 12). The orch API is documented in `lib/orchapi`, so a customer's own controller may call it too; one that announces addresses itself (MetalLB in BGP mode against the customer's router, a cloud's controller) never calls it.
3. **The address pool is a fleet object kept by orch.** `PUT /v1/address-pools/{name}` (operator) takes `cidrs` (IPv4, the range the LAN's owner gave naru, none of them inside a network's prefix, no two pools overlapping) and `networks`, the names of the networks whose controller may draw from it. Orch alone assigns: the controller may ask for a specific address (`spec.loadBalancerIP` as `requestedAddress`), which orch grants if it is in the pool and free, and else picks the lowest free address. An assignment is a claim key `/naru/orch/exposure-claims/<pool>/<address>` created in the same etcd transaction as the exposure record, as in ADR 0049 item 5, so two leaders or two requests never hand one address out twice. A pool with no free address answers 409 and the Service stays pending with an event. IPv4 only, as the networks are.
4. **The controller asks orch, not the hosts.** Orch's API gains exposures: `PUT /v1/exposures/{id}` (the id is the Service's namespace and name and its UID's first 8 hex digits, so a delete and re-create is a new exposure), `GET /v1/exposures[/{id}]`, `DELETE /v1/exposures/{id}`, all under one network named by the certificate (item 7). The body is `network`, `pool`, `requestedAddress?`, `ports` (protocol, port, `nodePort`) and `backends`, the Nodes' InternalIP addresses. Orch refuses (422) a backend that is not the address of a live member of that network. The answer is the address, the announcing host's ID and the phase (`pending`, `announced`). Orch's other endpoints and the hosts are not reachable with this credential. The controller reconciles by listing its exposures and deleting those whose Service is gone, so an address is released when the Service is deleted even if the delete event was missed. Delete is idempotent.
5. **The answering host is chosen by orch and holds a lease, so failover has no second holder.**
   - Orch's leader reconciles exposures with the networks reconciler (ADR 0049 item 6) in the same pass. A candidate host is an admitted, answering host that runs a member of the exposure's network and has a LAN interface declared (`--lan-interface`, empty by default, where an unset flag makes every exposure unplaceable on that host). The choice is by rendezvous hashing of the address over the candidates, so addresses spread over hosts, a host's loss moves only its addresses, and a returning host takes back only its own.
   - `PUT /v1/exposures/{address}` on the host (provisioner; a new endpoint of the host API) carries the lease: the address, the ports and backends, a `leaseSeconds` (default 15) and the leader token. Orch renews every `leaseSeconds / 3`. A host that has not been renewed for `leaseSeconds` removes the address and its rules by itself, whether or not orch is reachable. Orch moves an address to another host only after the previous holder answered that it removed it, or after the lease deadline plus 2 seconds of skew has passed, as ADR 0042 does for a fenced member. So at most one host holds an address except for a clock skew beyond that margin.
   - The failover time is at most `leaseSeconds` + the renewal interval + the time to announce, which is under 25 s with the defaults.
6. **The host announces by owning the address, and forwards by DNAT.** hostd, on receiving a lease, adds the address as a /32 on the LAN interface, so the kernel answers ARP for it, and sends an unsolicited ARP reply (gratuitous ARP), to refresh neighbours' caches, when it acquires it and every 5 s for 30 s after. Removing the address is the release; a neighbour's cache entry ages out or is refreshed by the new holder's announcement. IPv4 only. In the `inet naru` table, a `prerouting` DNAT chain maps (address, port, protocol) to the backends with `numgen random`, each at its NodePort, and the forward chain accepts exactly that flow from the LAN interface to the backend and its replies, no other port and no other source. The lease lists only backends that run on the announcing host: the host refuses any other address with 422, checked against the microVMs attached on it, not the network's prefix, because a host has no address per network (ADR 0045), a remote host's forward chain accepts only its own network's sources, and WireGuard accepts only allowed IPs, so a flow to a remote backend has no source both ends accept (decided at https://github.com/garamsh/naru/pull/296#issuecomment-7055949000). Any NodePort reaches every endpoint through kube-proxy, and a failover moves the address to a host that has a backend. The forwarded flow is masqueraded for leased addresses only, so the reply returns through the same host. The address, ports and backends live in hostd's state file with the lease deadline, and a restarted hostd restores the table and removes an expired lease before it serves.
7. **The credential is a certificate of a new role scoped to one network.** The signer issues `naru:exposer` pairs whose CommonName is `exposer.<network>`; orch reads the role with `lib/identity` and takes the network from the name; every exposure call whose body names another network, a pool that does not list this network, or an exposure of another network is 403. The role cannot read hosts, microVMs or groups, nor write networks, pools or profile. The pair is valid at most 90 days, issued by an operator with `naructl` (`naructl ccm credential --network`) against a signed request, handed to the cluster as a Secret in `kube-system` by the operator and never created by a Node or orch, and revoked through the revocation list like any pair ([ADR 0062](./0062-every-naru-tls-peer-is-checked-against-the-signed-revocation-list-by-one-verifier-in-lib-identity-and-fails-closed-when-the-list-is-older-than-its-max-age.md)). The strongest thing a stolen credential does is to attract a pool's traffic for its own network to backends inside that network, or to exhaust the pool; orch caps one network's exposures (default 64) and ports per exposure (default 16).
8. **Traffic goes from the host to the Nodes' NodePorts, and a Service may ask for the client's address in a PROXY protocol v2 header.** The Service's `nodePort` is allocated by Kubernetes; kube-proxy on every Node already forwards it to the Pods, whatever the CNI, so the host needs no knowledge of Pods or endpoints. The announcing host reaches a Node on another host through the tunnel and that host's forward chain, which are already open for the network's members. `externalTrafficPolicy: Local` is not supported: a Service that sets `Local` is given the cluster behaviour with an event.
   - **Default:** the flow is DNATed and source-NATed (item 6), so the Node sees the host's address.
   - **Opt-in per Service:** the annotation `naru.garam.sh/proxy-protocol: "v2"` on the Service. Any other value, or none, is off. The controller sends it as `proxyProtocol: v2` in the exposure; orch passes it to the host's lease.
   - **Which hop writes the header:** the announcing host. For an exposure with it on, hostd does not DNAT its TCP ports; a TCP proxy in hostd accepts the client's connection on the address, connects to a backend's NodePort over the network and writes one PROXY protocol v2 header with the client's address and port as the first bytes, then copies both ways. The header is written before any payload, so it precedes a TLS ClientHello whether the listener terminates TLS or passes it through; the receiver (for aurora, Envoy's `proxy_protocol` listener filter, which aurora's PM sets on the listener) reads it before routing. It is TCP only: a UDP port of such a Service is refused (422), and the whole Service is on, since a receiver that expects the header on a port rejects a connection without it.
   - **Failover and state:** the proxy's listeners are part of the lease and of hostd's state like the DNAT rules, and go with the lease. An open connection resets when the address moves, as in every case.
   - **Limit:** a Pod that reaches the address from inside the cluster is short-circuited by kube-proxy to the Service's endpoints and sends no header; such a client uses the Service's cluster address.
9. **The node controller (`InstancesV2`) takes the Node's identity from orch's members.** A Node is a member of a group on a network, and the Node's name is the member's name (the implementation checks this against `lib/layout`'s hostname and, if it differs, adds the mapping to the cloud-config file). For its network the exposer role may read `GET /v1/networks/{name}/members`, not the fleet. `InstanceMetadata` returns provider ID `naru://<host-id>/<member-name>`, the member's address as the Node's InternalIP and the host's region and zone from the host's labels; `InstanceShutdown` is true for a stopped member; `InstanceExists` is false only for a member whose stored phase is gone or that the store no longer holds, never for a member whose host merely does not answer, so the node controller deletes a Node whose microVM is gone and does not delete one that is away. The kubelet runs with `--cloud-provider=external` when this add-on is on; the Node is then tainted until the controller initializes it. That flag is written by `lib/layout`, which garamsh/naru#264 owns, and its change is requested from that pull request and not made here.
10. **A fleet test needs a LAN.** The fleet test of this decision runs two hosts on a QEMU bridge with a third guest as the client outside the networks; it deletes the Service, stops the announcing host and checks that the address moves and is released. For the PROXY header it runs two Services with the annotation, each backed by a Pod that reports the source address in the header it read: one terminating TLS and one passing TLS through on 443. The client connects from outside and each Pod must report the client's own address and not the host's; the same Services without the annotation report the host's address. A unit test of `host/internal/network` checks the header's bytes (signature, version and command, family, addresses and ports) and that it is the first write on the backend connection, and fails if the proxy sends payload before it. It cannot run without that bridge, which `tooling/qemu` adds with the test.
11. **What aurora agreed to** (it owns the LAN side; naru does not implement the opposite):
   - the range 192.168.0.80 to 192.168.0.89 on the hosts' LAN segment, reserved for naru, with no DHCP in it and no other user (decided, and the pool the operator declares);
   - the hosts' LAN interface and that segment are layer 2 to the clients, and the switch accepts a gratuitous ARP from any host (no dynamic ARP inspection that blocks it);
   - one host answers an address at a time, and a failover takes under 25 s, during which new connections to it fail and open ones may reset (accepted);
   - ingress reads a PROXY protocol v2 header on the listeners of a Service with the annotation of item 8, for TLS-terminating and TLS-passthrough listeners alike (decided).
12. **Per cluster the controller can be turned off, or only its service controller.** The setting of `naructl gen kubernetes` is `addons: {cloudController: false}` (neither controller, no kubelet flag, since the flag with no controller leaves every Node tainted) and `addons: {loadBalancer: false}` (the node controller only). A disabled controller is neither applied nor pruned, as ADR 0083 item 12 says. Because the kubelet flag is a Node configuration, changing `cloudController` on a running cluster is a Node reconfiguration and reboot, which the documentation of the setting says.

## Rejected alternatives

- **An announcer inside the cluster (MetalLB or kube-vip in layer-2 mode).** Its announcement cannot cross the host to the LAN; it can serve only an address on the network, which the LAN does not route.
- **Each host's API as the controller's interface.** The controller would hold a pair for every host, and a host's provisioner role can create or delete any microVM on it, so a compromised cluster would own the host. Orch is the one that knows the whole fleet, which is also what the lease and the placement need.
- **A routed address announced by BGP from the hosts.** It is the final form for a large fleet, but it needs a router that peers with naru, which aurora has not decided; the exposure API does not change when an announcer of that kind is added beside layer 2, because the announcer is a host's setting.
- **Direct to Pods instead of NodePorts.** It saves a hop and keeps no NodePort, but then naru reimplements kube-proxy's Service semantics and watches EndpointSlices, and the Pod prefixes change with the members.
- **Several hosts answering one address.** It needs the router's ECMP or a switch that learns flapping addresses; with layer 2 only one answers, and failover is the lease.
- **Preserving the client address with a reply path through the host.** A Node's reply would have to return by the announcing host; the Nodes' default route is the machine gateway, so this needs per-flow routing on the Nodes. The PROXY header gives the address with no change to the Nodes.
- **PROXY protocol by default.** A receiver that does not expect the header rejects every connection, so it is off until a Service asks.
- **A credential per host or per cluster with every role.** A stolen Secret would reach more than its own network.

## Amendment: ARP probe and LAN-prefix requirement (garamsh/naru#296)

The original item 6 refused an exposure whose address is inside the host's management prefix. This was a defect: `spec.host.network.managementPrefix` is the host's LAN interface's subnet in a single-NIC deployment (aurora: `192.168.0.0/24`), and aurora's agreed pool (`192.168.0.80–.89`) is inside it. The check therefore refused every exposure in the only range naru can announce on that network. The QEMU fleet test reproduces the production topology (one NIC, management prefix equals the LAN subnet), and the failure confirmed it. Decided at https://github.com/garamsh/naru/pull/296#issuecomment-7079583563.

**Replacement rules (host side, item 6):**

1. **Drop the management-prefix refusal.** Hostd no longer refuses an exposure whose address falls inside `spec.host.network.managementPrefix`.

2. **Require the address inside the LAN interface's own prefix.** A layer-2 announcement cannot reach beyond the interface's subnet. An address not inside any prefix of the LAN interface is refused with 422.

3. **Probe with ARP before taking a new lease.** Before adding a new leased address, hostd sends one ARP request with sender IP 0.0.0.0 (RFC 5227 §2.1) and waits 500 ms for a reply. If any host answers — meaning another LAN host already holds the address — the PUT is refused with 409. Renewals do not probe: the host already owns the address and would answer itself.

The management prefix continues to govern the nftables rules (management traffic to network API endpoints) and is not removed from configuration.

## Consequences

- A Service has an address on the LAN within one reconciler interval of its creation and nothing in the cluster needs a privileged pod.
- The host API gains an endpoint and hostd's state gains the exposures; orch gains pools, exposures and the `exposer` role, and `lib/orchapi` and `lib/hostapi` gain their types and clients.
- Every host that is to announce needs a LAN interface in its configuration; a host without one holds no address, and an exposure with no candidate stays pending with an event.
- A Service with the annotation costs a userspace copy on the announcing host for each of its connections.
- The announcing host is a bottleneck and a single point for its addresses, bounded by the lease time.
- The address is lost for up to 25 s when its host is lost, and a connection through it is reset, since the new host has no conntrack entry.
- A cluster with the controller on runs two more Pods and one more image on the add-on budget of ADR 0083; the implementation's pull request reports the measured size.

## Signs the decision was wrong

- A listener needs the client address of a UDP port, or without a header: then a decision on `externalTrafficPolicy: Local` with a reply path (item 8's rejected alternative).
- Failover under 25 s is too long for the demonstrations: the lease is shortened, or the address is held by two hosts and a router steers.
- A pool is needed per host or per rack rather than per fleet: the pool takes a host label selector.
- Lease renewal at `leaseSeconds / 3` from the leader is lost under load and flaps an address: hosts renew by themselves from orch's record.
