# ADR 0077: the signer rotates a host's pair with the old serial revoked, registers offline pairs by serial, and hostd refuses a revoked key

> Status: accepted
> Date: 2026-11-16

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#237, part of goal garamsh/naru#235. It reads [ADR 0040](./0040-naru-signer-alone-holds-the-authority-keys-in-a-private-directory-and-issues-certificates-over-a-unix-socket-against-signed-requests-and-a-recovery-key-opens-the-bundle-that-restores-them.md) and [ADR 0062](./0062-every-naru-tls-peer-is-checked-against-the-signed-revocation-list-by-one-verifier-in-lib-identity-and-fails-closed-when-the-list-is-older-than-its-max-age.md) as they stand. Rotating an authority's own key is out of scope.

## Context

- **A host's key could be revoked but not replaced.** `operator revoke` puts a serial on the list, and a joined host's certificate comes from the signer only for an admission statement, which names the host's own key hash. A host with a leaked key had no operation that ended the old certificate and gave it a new one.
- **A pair `gen node` writes is invisible to the signer.** `gen node` issues the host's serving pair offline from the host authority `gen host-ca` wrote, which is not the signer's host authority. The signer never saw its serial, so the operator had no record to revoke it by.
- **Nothing on the host looked at its own key.** `naru-hostd` checks the clients' certificates against the revocation list (ADR 0062) and never its own serving certificate or the one stored beside its key, so a seed or a stored configuration that carried a revoked pair was served with.
- **The user decided that the signer issues and revokes.** Orch, hostd and naructl add no authority.

## Decision

1. **The signer keeps a registry of host certificate serials by host ID.** `hosts.json` in its directory (0600, optional) maps a host ID to the serials of its certificates. `IssueHost` records the serial it issues, and the registry is carried by the bundle, so a restored signer holds it. It is written in one commit with `issued.json` and the revocation list (`commitFiles`).
2. **A rotation is two signer calls with the delivery between them, and the old serial is revoked last.** Revoking first strands a running host: orch and the peers refuse its pair before it holds another. The order is:
   1. `POST /v1/reissue-host` (root or an operator) issues a further certificate for the new key's request (CN and DNS name the host ID, and the IP addresses the request carries, one year; naructl puts the host API's address in it, so a client that connects by address verifies it) and adds its serial to the host's registry entry. It revokes nothing; the old pair stays valid.
   2. naructl delivers the pair to the host with `PUT /v1/identity` on the host API, with the operator's own credential. The host heartbeats to orch with the new pair first, and only when orch accepts does it store the pair, use it toward orch and present it as the host API's serving certificate from the next handshake; it answers the serial it now reports with.
   3. naructl checks that serial is the issued one, and waits, up to 30 seconds, until a new connection to the host API is served that certificate.
   4. `POST /v1/retire-host` (root or an operator) names the host ID and the serial to keep. The signer puts every other serial of the entry that is not already revoked on the list at the next sequence and sets the entry to the kept serial, in one commit. A retry with nothing left to revoke changes nothing and publishes no sequence.
   A host the registry holds no serial for is refused at step 1 with 409 naming `register-host`; a kept serial the host does not hold is refused at step 4 with 409. Operators could already issue a host certificate through an admission statement and revoke a serial, so the calls add no authority.
3. **Each failure leaves the old pair valid.**
   - The signer refuses step 1: nothing was issued and the host was not contacted.
   - The host is unreachable, refuses the operator's credential (401, 403), has no orch to enroll with (409), refuses the pair (422) or orch refuses it (502): the new serial is in the registry, unused and unrevoked, and the old pair is the one in use. Rotating again retires it: step 4 of the next rotation revokes every serial but its own, the stranded one included.
   - Step 3 finds another serial, or the host API does not present the new certificate in time: naructl stops before step 4, with the same state.
   - Step 4 fails after the host took the pair: the host reports with the new pair and the old serials are still valid. naructl says so and to run `rotate-host` again, which issues once more and retires everything but its newest.
   A host never holds no valid pair: the old serial is revoked only after orch has accepted the new one and the host API presents it.
4. **naructl drives all four steps in one `naructl signer rotate-host`.** The key is made on the workstation, and the operator's signer credential and host client both live there; the signer cannot reach hosts, and a host that holds the signer's credential would add authority. Two commands would leave the order to the operator, which is the mistake the order exists to prevent. The key is written nowhere but the host: `--key-out` and `--cert-out` are gone. `--host-client` is a provisioner's `gen host-client` file, `--host` and `--host-server-name` override its endpoint and the name its certificate is checked against.
5. **`PUT /v1/identity` replaces the host's pair toward orch and its serving pair.** One certificate does both: the signer issues the host certificate for server and client use. The route takes the certificate and key as PEM in a JSON body (64 KiB at most, unknown fields refused) and is for the provisioner role, as every non-GET host route is. The certificate must be for the host's own ID and unexpired and the key an ECDSA key. The host sends orch a heartbeat with the pair; when orch refuses, nothing is written (502). It then writes the key and the certificate beside `--host-key`, each in one atomic rename, and swaps the pair its heartbeat loop uses. 200 answers the serial in hex; 409 answers a host that is not enrolled with orch; 422 a pair that is not its own. A crash between the two renames leaves a key and a certificate that do not match, and the host enrolls again on its next start. The same pair becomes the host API's serving pair: the listener takes its certificate from a callback (`tls.Config.GetCertificate`), so the next handshake presents the new one with no restart, and the pair is stored as one file `serving.pem` (certificate and key, 0600, one atomic rename) beside `--host-key`. Init writes `--cert` and `--key` to a tmpfs from user-data at every boot, so hostd cannot persist there; the stored file is what a restart serves. When the pair cannot be stored the route answers 500 and the old pair is still not revoked, because naructl stops on any failure of the call.
6. **`POST /v1/register-host`, root or an operator, registers an offline pair by serial.** The request names the host ID and the serial of a certificate another authority issued. The signer cannot verify that certificate: it takes the serial from the operator who signs, refuses a serial recorded as root's or any other role's, and does nothing for a serial already registered. A rotation then retires it like any other serial. `naructl signer register-host --cert` reads the serial from the certificate, and refuses a certificate whose CN is not `--host-id`. A `gen node` pair is registered by the operator after `gen node`, not by it: doing it from `gen node` needs a signer reachable while the user-data is made offline, which the pair's offline issue does not assume.
7. **`naru-hostd` refuses a revoked key.** At start it picks the serving pair: the stored `serving.pem` when it exists and is not revoked; else the seed pair `--cert`, `--key` when that is not revoked; else it logs the file, the subject and the serial and exits 1, and never serves. A revoked stored pair never falls back silently to a seed pair that is also revoked. Every minute while it runs it checks the pair it serves and the certificate beside `--host-key` against the list, and exits 1 the same way on a revoked one. That covers a seed (`spec.files`, `spec.host.certificate`) and a stored configuration, which both reach hostd as those files. A list that cannot be had yet is logged and the check retried, and the host's seed list (`--revocation-seed`) is what lets the first check run with no signer reachable. A revoked key stops `naru-hostd` only: init's boot and the Node API are not stopped.
8. **Which hosts delivery reaches.** The delivery is a call the operator's provisioner client makes to the host API as it stands: the route is added in `Handler` and no trust of the host API's clients changes. A host the operator's client already reaches is rotated. A host that joined from the install seed and whose host API does not yet trust the operator's client is not reached, and what it needs is the subject of garamsh/naru#238.

## Consequences

- **A leaked host key is ended in one command.** The old pair is refused by every peer within the list's TTL after the retire step, and the host keeps reporting with the new pair throughout.
- **A rotated host the signer never registered cannot be rotated.** The 409 says to register first. A joined host, whose certificate the signer issued, is already registered if the signer's directory was written by this version; one admitted by an earlier version is not, and is registered like an offline pair.
- **An offline serving pair registered by serial is replaced and revoked in one command.** The host serves the new pair at once and after every restart, though its seed still carries the revoked pair: the stored pair is chosen first.
- **A wiped data disk loses the stored pair.** The seed pair applies again, and when it is revoked hostd refuses to start; the operator then issues a new seed (`gen node`) for the host. The reset of the data disk (garamsh/naru#55) has to account for this, by keeping `serving.pem` or by taking a new seed with the wipe.
- **A replica holds the registry only as the bundle it was restored from carried it.** A host admitted through another replica since is unknown to this one, and `rotate-host` there is refused with 409 until the operator uses the signer that admitted it or registers the serial. The revocation list itself is shared as before.
- **hostd checks files, not what a peer sees.** A revoked key an attacker holds is refused by the peers as before; the host's own refusal is for the honest host that was handed a revoked pair.
- **A new serial can be left unused.** It sits in the registry until the next retire revokes it. It is valid for a year in that time, and nothing but the key that was never delivered can use it, which exists only in the failed command's memory.

## Signs the decision was wrong

- Operators register serials wrongly often enough that a rotation revokes nothing, or the wrong host: the signer should read the certificate itself, or `gen node` should register.
- Rotation is wanted where the signer is not reachable, which would need the key made on the host and a certificate request from it.
- A host that exits on a revoked key and is restarted by init in a loop hides the cause: the exit should be reported to orch.
- A client connects by a name or an address the rotated certificate does not carry: the request should carry every name the host API's clients use, and not only the address naructl connected to.
