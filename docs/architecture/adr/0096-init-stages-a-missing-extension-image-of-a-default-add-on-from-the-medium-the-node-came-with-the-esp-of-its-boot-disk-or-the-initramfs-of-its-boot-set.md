# ADR 0096: init stages a missing extension image of a default add-on from the medium the Node came with, the ESP of its boot disk or the initramfs of its boot set

> Status: accepted
> Date: 2026-11-23

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#332, part of goal garamsh/naru#262. It extends [ADR 0084](./0084-an-upgrade-bundle-carries-the-extensions-the-hosts-configuration-names-and-an-entry-without-a-digest-is-resolved-by-init-to-the-image-built-for-its-version.md) (an entry without a digest is the stored image built for init's version, and an upgrade bundle puts it there) and delivers what [ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) item 12 needs on a new Node. It uses the ESP of [ADR 0020](./0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md) and [ADR 0037](./0037-the-esp-has-room-for-a-trial-kernel-twice-the-size-of-the-one-it-was-built-with-and-a-release-refuses-a-kernel-the-previous-image-cannot-take.md) and the boot set of [ADR 0046](./0046-the-host-api-adds-and-removes-a-boot-set-on-a-running-host-through-mvmds-runtime-api-and-a-release-carries-the-node-boot-set-as-a-kernel-an-initramfs-and-a-manifest.md) and [ADR 0089](./0089-orch-adds-the-boot-set-a-group-needs-to-the-hosts-that-place-it-from-a-release-store-it-is-configured-with.md).

## Context

- **A new Node with the default volumes add-on refuses its first boot.** `gen kubernetes-node` writes the entry `{name: naru-volumes}` with no digest, init mounts the stored image built for its version, and a new Node's data disk is blank, so its store has none: `extension "naru-volumes": no image of "naru-volumes" is stored`. The only way today is to let the boot refuse, `naructl extension add` through the Node API that keeps serving, and reboot (install-kubernetes.md before this ADR). An upgrade has the bundle (ADR 0084); an install has nothing.
- **Two kinds of Node need it.** A Node that boots the disk image (`naru-host-<version>.qcow2`, Proxmox, the QEMU harness) comes with its ESP. A Node that orch places as a microVM (ADR 0089) comes with its boot set: a kernel and an initramfs mvmd boots, and a data disk hostd makes blank. The second is the Node of the clusters that matter, and has no ESP.
- **The initramfs of the host form is not a place for the image, and the Node initramfs, which the host form carries, is.** ADR 0083 and 0084 put the add-on in an extension because the initramfs of the host form is embedded in the kernel, which the ESP holds twice (ADR 0037), and because init copies the initramfs to a tmpfs (init.md step 1). The Node initramfs (`node-initrd.cpio.gz`) is booted by mvmd as the initrd of a microVM, but `image/pkgs/initramfs-host/Dockerfile` also copies it into the host initramfs as the built-in `naru-node` boot set, so whatever it carries rides in every host kernel too; item 5 and the Consequences count that.
- **The delivery must be one stage.** Init's boot order is a pipeline; a branch on the form of the Node inside the step that mounts extensions would be a second place to change for every form.

## Decision

1. **Init stages before it mounts.** A boot step runs between writing the registry files and mounting the extensions (init.md step 9a1). For each entry of `spec.extensions` with no digest whose name has no stored image built for init's version, it asks each **source** in order for an image of that name, and stores the first that offers one built for init's version, through the check the bundle's members get (`Manager.Stage`: the offered digest, the size cap, and a manifest with that name and version). The step refuses nothing: it logs why a source was skipped (`extension source failed`, `extension image from the source refused`, or that it offers another version) and `extension staged from the boot medium` for the image it took, and the mount that follows refuses the boot with the reason it always had when no image is there.
2. **A source is data passed in, not a branch of the step.** `extension.Source` is `Name()` and `Offer(name)`, which returns the image's digest, the naru version it was built for and its bytes, or `ErrNoOffer`. `lib/init/run` builds the list of sources the Node has; the step has no knowledge of which source is which, and a Node with no such place gets `ErrNoOffer` from it.
3. **What the stage never does.** It never replaces an image the store holds, and an image an operator put there (`PUT /v1/extensions`) or an upgrade bundle staged is the one found. It never provides a pinned entry: a digest is the operator's choice of an image and no source overrides it. It never takes an image built for another version: a Node upgraded in place keeps an ESP image of the release it was installed from, and that one is not offered to the new init, so the bundle's image (ADR 0084) is the only one for its version, as before.
4. **The source of the disk form is the ESP of the boot disk.** The disk builder (`naru-disk -extension <name>.json`, repeatable; `image/host/disk/build.sh` passes the volumes extension) writes `EXT/E<n>.SQF` for each image and `EXT/INDEX.JSN`, `{"extensions": [{name, version, sha256, bytes, file}]}`, in the ESP, whose files have 8.3 names that cannot carry an extension's name. It checks each image against the digest its description names, and makes the ESP larger by `ExtensionRoom` (the images, a 64th for the allocation tables, a MiB, whole MiB), so the room of the kernel slots is the room ADR 0037 gives; the manifest's `esp.bytes` is the ESP less that room, which `naru-disk -layout` writes beside the disk (`naru-esp.json`, `{"extensionRoom": N}`) for the release to read, so the check of the next release is made on the room a trial kernel has. Init finds the partition by `wire.ESPGUID`, mounts it read-only at `/run/naru/esp-extensions` and unmounts it when the image has been read.
5. **The source of the microVM form is the Node's own initramfs.** The Node initramfs carries the image as the file the release carries and its description, `/usr/lib/naru/boot-extensions/naru-volumes.sqfs` and `.json` (`image/pkgs/initramfs-node/initramfs.list`), and `bootmedia.Dir` offers the image the description names. It is a source in the same list as the ESP, so the host-form Node, which has no such directory, and the microVM, which has no ESP, take the same path. Once the stage is over init removes the directory, so the copy of the initramfs in tmpfs (init.md step 1) does not keep the image in memory; the image is the file itself, unpacked nowhere, so it is stored once in the initramfs and once in the Node's store. What a boot set cannot carry is mvmd's: at hostd's pin an added boot set is a kernel and an initrd (`AddBootSet`), and a disk made through the API has at most 1 MiB of contents (`CreateDisk`), so a third file or a volume of the boot set was not available for dev.14. The release refuses a Node initramfs larger than 256 MiB: ADR 0083's 256 MiB is a threshold on the growth of a Node's memory (its Signs), not a size of a file, and this check applies it to the initramfs file, which is the reading this ADR records; the image is 27,160,576 bytes and the initramfs before it 233,756,847 (the snapshot of 2026-11-23), 248.8 MiB together.
6. **Operators do nothing.** `install-kubernetes.md` drops the refuse-then-add step. `naructl extension add` stays: it is how an image is delivered to a Node whose medium has none, and the image a pinned entry names.

## Options considered

- **The ESP alone.** The disk form is the test of the harness and of Proxmox, but a microVM Node has no ESP, and goal #262's clusters are microVM Nodes placed by orch.
- **A third file of the boot set, or a volume hostd attaches.** mvmd at hostd's pin takes a kernel and an initrd in a boot set and at most 1 MiB of contents in a disk it creates, so neither can carry the image; they wait for mvmd.
- **The host serves the image over the Machine network.** It needs a listener a guest can reach and a trust anchor, since an unpinned entry has no digest to check what is served.
- **The extension in the Node initramfs.** Taken now, for the reason the options above give: the boot set takes only a kernel and an initrd (`AddBootSet`) and `CreateDisk` takes at most 1 MiB of contents, so the initramfs is the one place a microVM Node's medium can carry the image in dev.14. ADR 0083's 256 MiB holds at the measured 248.8 MiB (item 5).
- **The seed (`cidata`) carries the image.** Every builder of a seed (naructl, hostd, orch) would carry about 120 MiB for every Node, and the seed is configuration, not payload.
- **Init fetches the image from a release URL.** The Node would need a route out at boot, and the install procedure says nothing is fetched from the internet; a fleet that cannot reach the URL would refuse its first boot for it.
- **A branch inside the mount step for each form.** It would put the knowledge of each medium in the step that decides what to mount, and a third medium would be a third branch.

## Consequences

- **A blank Node of the disk form boots the first time with the default add-ons.** The QEMU test `TestNode_ABlankNodeWithTheDefaultVolumesAddOnBootsTheFirstTimeWithTheImageFromItsESP` boots one with no extension store, and its control spoils the index on the same disk and sees the refusal return.
- **The boot disk and its qcow2 are larger by the image** (the ESP holds it; the file is sparse, so the qcow2 grows by the image's bytes).
- **The ESP keeps the image of the release it was installed from for ever.** It is read only when the store lacks an image for init's version, and an in-place upgrade does not rewrite `EXT/`. A Node whose store was cleared by a reset (ADR 0082) and which runs a newer release than its ESP's finds no image there and refuses until the bundle's or an operator's image is put in the store.
- **Copies of the image.** A Node of the disk form holds it in its ESP and in its store, and in its kernel's initramfs too (below). A microVM Node holds it in the host's kernel (twice on the host's ESP when a trial slot is in use, and once in the host's tmpfs for good, since the host does not unpack its nested Node initramfs), in the Node's initramfs until the stage removes it, and in the Node's store.
- **The host kernel and every upgrade bundle grow by the image, and they still fit.** The snapshot of 2026-11-23 has a host kernel of 530,744,320 bytes; the image is a zstd squashfs that gzip does not shrink, so the kernel is about 557,904,896 bytes (computed, not built). The largest kernel a host installed from v0.1.0-dev.13 can take in place is 1,130,916,864 bytes (`TrialRoom` of its bundle's manifest: esp.bytes 1,538,260,992), so the upgrade fits with about 573 MB to spare and this release needs no `RECREATE`. The trial-slot room the release records is computed without the extensions' room on the ESP, so ESP growth by the image does not change it.
- **Headroom.** The Node initramfs is 248.8 MiB of 256 MiB, so about 7 MiB are left. The next add-on carried there needs room, or the boot-set route once mvmd takes a third file, and `make release` fails when the file passes the limit.

## Signs the decision was wrong

- **A third medium appears** that is neither the ESP nor the Node initramfs: the list of sources grows by a type, which is what the interface is for; if each new medium needs a change to the step, the interface was wrong.
- **The Node initramfs reaches the 256 MiB limit**, or the memory of a Node of 2048 MiB is short at the first boot, when init's tmpfs copy holds the image: the image goes to the boot set as a third file once mvmd takes one, and the initramfs loses it.
- **Nodes are reset often enough that the ESP's image for an old release matters** (the Consequences' third point): the stage would need to read the bundle's store of the host, or the ESP would need rewriting at upgrade.
