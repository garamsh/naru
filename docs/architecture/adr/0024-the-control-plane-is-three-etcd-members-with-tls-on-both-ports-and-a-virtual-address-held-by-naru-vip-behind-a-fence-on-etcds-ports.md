# ADR 0024: the control plane is three etcd members with TLS on both ports and a virtual address held by naru-vip, behind a fence on etcd's ports

> Status: accepted
> Date: 2026-11-13

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#59. It supersedes [ADR 0012](./0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md) item 2 by reference: 0012's body is not edited, and where item 2 says one etcd member, plain-HTTP client and peer URLs on the loopback and one API server, this decision says otherwise for a control plane of several members; a control plane of one Node keeps one member on the loopback, now over TLS. The gaon facts are read at garamsh/gaon commit `f431811565beb905ac859a78b126a47a734fdb27` (the pin of `image/gaon/pin.env`), and the etcd facts are the ones of tag v3.6.16, the pin of `image/etcd/pin.env`.

## Context

- **gaon's leader election is on by default at the pinned commit,** so the scheduler and the controllers of three control-plane Nodes run on all three and elect one; the API servers are all active and share one etcd.
- **etcd needs a majority.** Three members survive the loss of one. gaon's API server builds etcd's Go client without a keepalive, and that client keeps using a connection to a member that was powered off until TCP gives up, so a request sent on it waits for its deadline; in the QEMU test of this decision, with every member's URL listed, writes through a surviving API server failed for minutes after one Node stopped. This decision therefore gives each API server its own member's URL alone; etcd's members are the ones that talk to each other and see a peer's loss through their heartbeats.
- **Clients need one address.** Node Agents and `naructl` are configured with one `--api-server` address; if it were one Node's address, that Node's loss would end the control plane for them though two members serve.
- **Init holds no election** ([ADR 0002](./0002-gaon-depends-on-naru-one-way-through-the-node-api-and-naru-has-no-control-plane.md) item 6): whatever decides who answers at the address is a service the configuration starts.
- **etcd's ports are open to the Nodes' network.** Listening on a member's address instead of the loopback exposes 2379 (every key, so every resource) to any host that reaches it, so TLS with client certificates is the first layer and an address restriction the second.
- **spec.pki issues per-Node certificates** ([ADR 0013](./0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)): a server certificate with `nodeAddresses` names the Node's interface addresses and `127.0.0.1`; a client certificate with `nodeAddresses` names the interface addresses. etcd checks the address a peer dials from against the peer client certificate's SANs, so a peer's client certificate must carry IP SANs.

## Decision

**`naructl gen node --control-plane` takes `--member name=address` once per control-plane Node, in priority order, and `--api-server` is then the virtual address; each member runs etcd with TLS on both ports and client-certificate authentication, a service `fence` that closes etcd's ports to every address outside the control plane, and a service `vip` that holds the virtual address while it is the first member whose API server answers.**

1. **Members and URLs.** Every member's etcd has `--name <node>`, client URL `https://<own address>:2379` plus `https://127.0.0.1:2379` (listen), peer URL `https://<own address>:2380`, and `--initial-cluster node-1=https://<address>:2380,...` the same on every member (a static cluster, no discovery). `--initial-cluster-state` stays at its default, `new`. A control plane of one Node (no `--member`) listens on `https://127.0.0.1:2379` and `https://127.0.0.1:2380` and runs neither `fence` nor `vip`. `--api-server` stays required: it is the Node's address for one member and the virtual address for several. A member's address must not be the virtual address; the Node must be among its members.
2. **TLS on both ports, from spec.pki.** Three pairs are issued on every control-plane Node: `etcd-server` (server, `nodeAddresses`, restarts `etcd`), used for etcd's client and peer listeners; `etcd-peer` (client, `nodeAddresses`, restarts `etcd`), presented when etcd dials a peer; and `apiserver-etcd` (client, restarts `gaon-apiserver`), presented by the API server to etcd. etcd runs `--client-cert-auth` and `--peer-client-cert-auth` with `--trusted-ca-file` and `--peer-trusted-ca-file` the cluster CA. gaon-apiserver gets `--etcd-endpoints` with its own Node's member's `https://` URL alone (the Node's address; the loopback for a control plane of one), `--etcd-ca-file`, `--etcd-cert-file` and `--etcd-key-file`. Where the pairs are files and not issued (a layout with `files` credentials), the same names are files and `etcd-server` names the addresses etcd listens on. `naructl` has `(*CA).ClientAt` for the client certificate with IP SANs.
3. **The API server's certificate names the virtual address.** The API server's serving certificate carries the Node's addresses, `127.0.0.1` and the virtual address, so a client that dials the virtual address verifies it whichever member answers. Node Agents, the scheduler and the controllers and `naructl` dial the virtual address; `127.0.0.1` stays for the host forward of the QEMU tests.
4. **The holder of the virtual address is `naru-vip`, a binary of the new unit `controlplane/`, started by the configuration.** Every member's `naru-vip` dials every member's API server (`-member`, port `-port`, a TCP connection that is accepted within one second) once a second and counts consecutive misses. The holder is the first member in priority order, as listed by `--member`, that has answered and has missed fewer than three rounds; every member computes it from its own observations. The holder adds the address with netlink (`AddrReplace` on `eth0`) and announces it with a gratuitous ARP, and announces again every ten rounds; a member that is not the holder removes the address (`AddrDel`); a member whose own API server missed three rounds is not the holder and so releases it. Priority is fixed, so the address returns to the first member when it comes back. For the first five rounds after `naru-vip` starts no member takes the address, so that members started together do not pass it from the first whose API server answers to the first in priority.
5. **Why this holder.** Alternatives considered: keepalived (VRRP) is a C daemon with a build, a kernel-option and a configuration surface this image does not carry, and its advert is multicast on the Nodes' network, which a test that stops one Node can exercise but a static priority list expresses in fewer moving parts; kube-vip needs a leader lease from a Kubernetes API, and gaon's leader lease is held in the API server this address fronts, a cycle; a DNS name with several addresses leaves a client retrying a dead address and puts a resolver on the path of every agent; a load balancer in the image is one more process on every Node to keep alive. A small Go program in this repository takes the liveness signal that matters (the API server accepts a connection, not that the Node is up), is testable with a fake host, and keeps a decision of init's out of init. The cost is a split-brain window: two members that cannot see each other each consider themselves first and both hold the address until the partition heals; both announce, and the clients' connections go to whichever the network's ARP cache holds. etcd's quorum stops the minority's API server from writing, so the harm is bounded to a minority serving no writes. This is accepted for a priority list; a quorum-aware holder would read etcd's membership and is not decided here.
6. **The fence is nftables, in the image.** `naru-fence`, a binary of `controlplane/`, installs an `ip` table `naru-controlplane` with an input chain; for ports 2379 and 2380, a packet whose source is not in the set of the members' addresses, the virtual address and `127.0.0.1` is rejected with a TCP reset, and the program then blocks until it is signalled, because init restarts a service that exits. It is listed before etcd, but init waits for no service ([ADR 0012](./0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md) item 3), so etcd may accept connections for the milliseconds before the rules are installed; the client-certificate requirement is what holds in that window. The kernel options are `CONFIG_NFT_REJECT` and `CONFIG_NFT_REJECT_IPV4`; `NF_TABLES` and the other options it uses are in the image already. A worker, or any address that is no control-plane Node's, is therefore refused on 2379 with a reset before it reaches the TLS handshake, and a host in the set without a certificate is refused at the handshake.
7. **Where each lives.** `naructl/internal/layout` produces the services, flags and certificates (`controlplane.go`); `controlplane/` holds `internal/vip`, `internal/fence`, `cmd/naru-vip` and `cmd/naru-fence`, a module of `go.work`, built by `image/initramfs/build.sh` as static executables and listed in `initramfs.list`, and run by `make ci` with the other modules. init is not changed.
8. **The QEMU test.** Three Nodes, all control-plane, are booted by `tooling/qemu` with `ClusterSpec.ControlPlanes: 3` ([harness.md](../harness.md)). `naru-etcdprobe`, a test-only program in `tooling/qemu/cmd/` and in the test's user-data on node-3 only, adds an alias address to eth0, dials etcd from a member's address and from the alias with and without a client certificate, lists the members through etcd's Cluster service and dials the virtual address, and prints each result on the console for the test to read. It is not in the release's assets.

## Consequences

- **An API server depends on its own Node's etcd member:** if that member stops while the Node is up, the API server fails its requests though the other two members have a quorum, and `naru-vip` still sees its port accept connections. The liveness signal is the accepted connection, not a served request.
- **A control plane survives the loss of one member:** etcd keeps its two, the API server of each stays up, and the virtual address moves to the next live member in about three seconds plus the ARP announcement.
- **Losing two members stops writes;** the virtual address is then held by the survivor if its API server answers, which serves reads from etcd that has no quorum only as far as etcd lets it.
- **`naructl gen node` of an existing cluster of one Node gains TLS on etcd,** a change of its user-data: the three pairs are issued, and `etcd` and `gaon-apiserver` restart when they are renewed.
- **The VIP's address must be on the Nodes' subnet and free;** naru does not check it.
- **Every Node's initramfs carries two more small static executables** and every kernel two more options.
- **`gaon-workloads`, which exists at the pinned commit, is not wired,** and the plugins belong to garamsh/naru#57.
- **The fence blocks etcd's ports to every address but the members' and the virtual address,** so a monitoring host or a backup tool on another address is refused on 2379; adding one is a configuration change to `naru-fence`'s `-allow`, which `naructl` does not yet offer.

## Signs the decision was wrong

- Two members holding the address for longer than a partition: the observations are not symmetric enough for a static priority, and the holder reads etcd's membership.
- A release's user-data that needs a member count other than three: the static list is the wrong form, and discovery or a runtime member change replaces it.
- A client that needs a monitoring address on 2379: the fence becomes configuration of the operator's.
- A kernel without nftables: the fence is replaced by a listen address, and TLS stands alone.
- A client that needs the virtual address's ARP to be answered by a router, not by the Nodes' network: the announcement is replaced by a routed address.
