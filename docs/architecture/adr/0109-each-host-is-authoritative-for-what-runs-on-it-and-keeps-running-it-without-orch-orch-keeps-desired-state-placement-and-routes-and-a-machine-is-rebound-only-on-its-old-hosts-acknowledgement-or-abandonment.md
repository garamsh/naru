# ADR 0109: each host is authoritative for what runs on it and keeps running it without orch, orch keeps desired state, placement and routes, and a Machine is rebound only on its old host's acknowledgement or abandonment

> Status: accepted
> Date: 2026-11-24

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#373 (goal 3). It decides the state behind [ADR 0108](./0108-orch-serves-a-versioned-machine-api-that-names-machines-and-never-hosts-to-callers-holding-a-signer-issued-caller-certificate.md)'s API. It uses the leader token of [ADR 0071](./0071-an-orch-leader-fences-its-etcd-writes-and-its-host-calls-with-the-revision-of-its-election-key-and-a-host-refuses-a-lower-token.md), and the record-what-hosts-report rule of [ADR 0103](./0103-orch-records-the-machine-prefixes-every-host-reports-and-admits-a-joined-host-only-while-every-admitted-host-has-one-recorded.md) (#355). It does not use the per-microVM fence of [ADR 0042](./0042-the-groups-engine-plans-from-observation-alone-and-replaces-a-stateful-member-only-after-its-fence-has-passed.md) and [ADR 0043](./0043-the-host-api-snapshots-and-resumes-a-microvm-gives-it-a-fence-of-its-own-and-its-types-and-client-are-the-module-lib-hostapi.md) for Machines; Options considered says why.

## Context

- **What a host already holds.** mvmd records every Machine, disk and snapshot on its host and is the one writer of its state directory (garamsh/mvmd `runtime-api.md` at `2a07ba313c0a2c424ba9badf40ea9c36ec670e14`). hostd keeps its networks, peers and leases in its state file and restores them at start ([host.md](../host.md)). A host that restarts therefore knows what it runs without orch.
- **What orch already does.** Its leader observes hosts through the host API and plans from that observation alone ([groups.md](../groups.md)). It records what hosts report and never overwrites a host's report with its own belief: the #355 pattern, ADR 0103. It creates a stateful member fenced and replaces it only after the fence has passed. It fences its own writes and host calls with the leader token.
- **What keeps a host's microVMs running.** mvmd starts nothing without an armed fencing deadline for the whole host, and hostd renews it itself, every minute for 10 minutes ([host.md](../host.md) §Fencing), so a host whose orch is away keeps its microVMs running. hostd exits when the pair it serves or reports with is revoked (host.md §Its own key), and then nothing renews that deadline. A revocation reaches a host from orch's `GET /v1/crl`, which needs no client certificate ([orch.md](../orch.md)).
- **What orch's members tolerate.** Three members tolerate the loss of one ([orch.md](../orch.md) §Members). The first goal has two hosts.
- **Precedents.**
  - **Fly.io.** "Every worker is its own source of truth", in a BoltDB of its own. The scheduler `flaps` "doesn’t hold on to any state" and asks the workers for capacity at each request (fly.io/blog/carving-the-scheduler-out-of-our-orchestrator, read 2026-11-24). Routing state is Corrosion, a SQLite database gossiped between hosts, where "individual servers are the source of truth for their workloads" (fly.io/blog/corrosion; superfly/corrosion at `e7295ff0fd0a8b9712948c976e0758b7a26aa38c`).
  - **Fly.io's migration.** The Machine is stopped, its volume is forked to the destination ("an exact copy of that volume, including its data"), and it starts there. The Machine ID is kept, and "apps should never rely on 6PN addresses remaining static" (docs.fly.io/reference/machine-migration, read 2026-11-24).
  - **E2B.** The API records where each sandbox runs in Redis, the "source of truth for _running_ sandboxes", and the orchestrator on each node owns how it runs (e2b-dev/runtime `docs/ARCHITECTURE.md` at `30a39cf3364197c162576f3823bb7e927f6c82d5`).
  - **OpenNebula.** The hosts push their monitoring to the front-end, which keeps the desired state and the placement (docs.opennebula.io/7.4, monitoring system).

## Decision

1. **A host is authoritative for what runs on it, and keeps running it without orch.** What a host runs is what its mvmd records and hostd reports (`GET /v1/microvms`, `GET /v1/host`). Orch never takes a Machine to be running, stopped or gone because it asked for that; it reads the answer. Status in the Machine API is computed from the bound host's last report; a host that does not answer leaves its Machines `unknown`, and nothing is inferred about them. A host that loses orch, its quorum included, keeps every Machine it runs, under the host-wide deadline hostd renews itself. Every Machine is created with `restartOnBoot` true, a field fixed at create: a host that reboots without orch starts again each Machine that was running, and one stopped through the host API stays stopped (host.md, `restartOnBoot`). Losing orch stops creation, placement, moves and the push of new routes; it stops no Machine.
2. **Orch keeps what only it can decide, in its etcd.** The Machine record (caller, name, `id`, spec, desired state, `generation`; `/naru/orch/machines/<caller>/<name>`), written by the Machine API. The binding (host, epoch, microVM name), the move record (item 5) and the abandonment record of a host (item 6), written by the leader. The routes derived from them, read by the proxies (ADR 0112). Every leader write goes through `leader.Guard`, and every host call carries the leader token. Each rule below that decides whether a Machine may run elsewhere reads only these records and the hosts' answers, so a new leader applies it from the store.
3. **The microVM on a host carries no name of a caller.** It is `m-<id>-<epoch>`: `id` is the Machine's, and the epoch counts its placements. A host learns nothing of callers or names, and two placements of one Machine never share a microVM name.
4. **The leader's Machine reconciler is level-triggered.** One pass per `--machine-interval` (default 5 s), and at once after a Machine API write: it observes the Machines, bindings, move and abandonment records, and the microVMs of every admitted host that answers, plans from that observation alone, and applies it. On the bound host it creates the microVM if absent (with the Machine's volumes as disks), starts or stops it to the desired state, and deletes it once the Machine is deleted. A Machine whose microVM stopped on its own while desired `running` is started again at most once per minute, each attempt an event. A microVM it did not name (`m-` prefix) is outside its reach.
5. **A Machine is rebound to another host only on the old host's acknowledgement, and a move starts the target only after the commit.** The move record holds the source, the target, the step and the epoch, and each step is idempotent, so a new leader continues a move from its record:
   1. **Reserve** the target's capacity by placement ([ADR 0110](./0110-orch-places-a-machine-on-the-host-that-fits-its-shape-by-capacity-orch-accounts-for-itself-and-labels-and-spreads-machines-across-hosts-amending-adr-0042s-placement.md)); the phase becomes `moving`.
   2. **Stop** the microVM on the source with the Machine's grace period, and wait until the source reports it stopped. This answer is the acknowledgement; without it the move waits, and an operator may cancel it.
   3. **Copy** each volume from the source to the target, host to host over the mesh (ADR 0113): the target pulls it with a one-time grant orch obtained from the source and bound to the target's host ID, and the SHA-256 the source computed while streaming must equal the target's, or the copy fails and is retried. The move record marks each volume verified.
   4. **Create** the microVM on the target under the next epoch with the copied volumes, **not started**.
   5. **Commit**: in one transaction, rebind the Machine to the target, move the routes and mark the move committed.
   6. **Start** it on the target if the desired state is `running`, as the reconciler does for any bound Machine.
   7. **Clean up**: delete the source's microVM and its volumes once the target has reported the Machine running once (or, for a stopped Machine, at the commit), and once every proxy has the committed routes (ADR 0112).

   Before step 5 the source is still bound and the target has never run, so an abort deletes what was made on the target (or leaves a never-started microVM of an older epoch on a target that does not answer, for item 7) and starts the source again; no copy has run on the target. After step 5 the move completes forward. The root disk is not copied: it is made from the image on the target. A GPU Machine moves the same way; a move that keeps memory is a later capability ([ADR 0108](./0108-orch-serves-a-versioned-machine-api-that-names-machines-and-never-hosts-to-callers-holding-a-signer-issued-caller-certificate.md) item 8).
6. **A Machine on a host that does not answer is rebound only after an operator fences the host and abandons it.** Its Machines stay `unknown` with their volumes; orch never recreates them alone. Rebinding a Machine without its old host's acknowledgement is safe only behind a fence that stops the old host whatever it can still reach: a host cut off from orch but alive keeps renewing its own deadline and never fetches the revocation list, so revocation alone does not stop it. So the operator first fences the host outside naru, powering it off through its hypervisor or its BMC, or confirming that it is off, and then runs `naructl host abandon <id>` with `--fenced "<how it was fenced>"` (`POST /v1/hosts/{id}/abandon`, operator and root), which refuses a request without that attestation. In one guarded transaction it records the abandonment (host, time, the operator's identity and attestation, the Machines on it and their volumes), and then revokes the host's certificate at the signer and removes the host from every peer list and route. The attestation is the operator's, as STONITH's is a fencing device's; naru does not verify it, and its record says who made it. The attestation also commits the operator to bringing the host back only through a reset of its data (`POST /v1/reset` with `all`, or `data`, from maintenance mode) or a fresh install, never by powering it on as it was: a fenced host powered on again boots with the revocation list it held before its abandonment, so hostd's check before its first renewal passes, hostd renews the deadline, and mvmd starts every Machine that was running (all are created with `restartOnBoot`). Those copies are unreachable inbound, since the host is in no peer list or route, but their egress is live: until hostd fetches the newer list from orch and exits, and for up to 10 minutes after, if the host reaches orch; without limit, if it stays partitioned. Fencing through a hypervisor's or a BMC's API by naru itself is the later goal's (it needs a credential for each). The abandoned host's Machines are `lost`. For each, the use deletes it, or an operator moves it with `--abandon-volumes` (refused unless its host is abandoned), which starts it on another host with new, empty volumes and records an event naming the volumes left behind. If, against that commitment, the fenced host is powered on again and reaches orch, it fetches the revocation list, and hostd exits on its own revoked pair. hostd checks the pair it serves against the list it holds before its first renewal of the deadline at start, so init's restarts of it never renew the deadline again, and its Machines stop when the deadline lapses, within 10 minutes; meanwhile it is in no peer list and no route, so no use reaches them. The fence and its recorded attestation, not a deadline, are what let a Machine run elsewhere, and both are in the store.
7. **A disk is deleted only when another verified copy exists or its Machine is deleted.** On a host that answers, the reconciler stops a microVM of an older epoch, or of a Machine that no longer exists, and deletes it. It deletes that microVM's volumes only when the move record marks a verified copy of each committed elsewhere, or the Machine was deleted. The volumes of an abandoned epoch are kept and reported (`GET /v1/machines/abandoned-volumes` on the operator API, an event each pass it finds them) until an operator deletes them with `naructl machine abandoned-volumes delete`; a host that is re-admitted after an abandonment keeps them the same way.
8. **The disk stream is mvmd's.** mvmd's Disk adapter alone writes its disk directory, so hostd cannot copy a disk file itself. mvmd's runtime API gains a read of a disk no running Machine holds, or of a disk snapshot, as a stream, and a Create disk from a stream with its size and SHA-256; both are additions to `v1alpha2` (garamsh/mvmd#827). The host API gains an export (`POST /v1/disks/{name}/export`, provisioner, answering the grant) and an import (`POST /v1/disks/import`, provisioner, naming the source host, the grant, the size and the SHA-256). The source serves the stream only to the host certificate the grant names (role `host`), once, within 10 minutes: the one host-API route another host's certificate reaches.
9. **The first goal runs one orch member.** Two members would lose quorum with either host; one loses orch with its host, which stops placement and moves and, by item 1, no Machine. Three members come with the third host.

## Options considered

- **A per-microVM fence the leader renews (ADR 0042's, for every Machine).** It makes every Machine depend on orch: with orch's quorum lost, every Machine on every host stops when its fence lapses, which contradicts item 1. Fencing is needed only where a Machine could run in two places, and with the target started after the commit and an unreachable host rebound only after its abandonment, there is no such place. Rejected.
- **A fence armed only while a Machine might be rebound, with its deadline persisted.** A host that does not answer cannot be told to arm it, so it could not cover the lost host, the one case that needs it. Rejected for the operator's fence.
- **hostd stops renewing the deadline when its revocation list is older than a bound** (hours), and `--abandon-volumes` waits that bound plus 10 minutes. It fences a partitioned host without the operator, but an orch outage longer than the bound then stops every Machine on every host, which item 1 refuses, and a move waits hours. Rejected for the operator's fence, with an automatic fence through hypervisors and BMCs as the later goal's.
- **Abandonment on the revocation alone.** A host cut off from orch never fetches the list and keeps its Machines, and their egress, while the moved copy runs. Rejected.
- **Orch's etcd as the source of truth for what runs.** A host that ran while orch was away has state orch never wrote. Rejected; orch is the truth only for what should run and where.
- **No central state, as Fly.io's flaps.** A stateless scheduler cannot carry a move across a leader change, keep a desired state for a stopped host, or hold the routes proxies need. Rejected; the per-host truth is kept and orch adds the desired state.
- **Corrosion-style gossip in place of etcd.** Built for many regions where consensus is slow, and since split into regional clusters (fly.io/blog/corrosion). Orch's members are on the control hosts of one site, and etcd already holds the fleet and its fencing token. Rejected while naru runs one site; §Signs the decision was wrong names the measure that reopens it.
- **Orch relays the disk stream.** It would carry gigabytes through one member. Rejected for the host-to-host pull with a grant bound to the target.
- **Carry the root disk.** It needs mvmd to create a Machine on a disk it did not make from the image. Rejected: what survives a move is on a volume, as on Fly.io.
- **A memory snapshot as the first move.** It needs the same Driver, version and CPU model on the target, and mvmd's restore onto the snapshot's own disk identifiers. It is the later `snapshot` move kind.
- **Two orch members on the first goal's two hosts.** Either host's loss loses quorum, so two are less available than one. Rejected (item 9).

## Consequences

- A Machine is unavailable during a move for its stop, the copy of its volumes and its start; the copy dominates for large volumes. The fleet test records the time.
- A lost host's Machines stay down until an operator abandons the host; naru never trades a Machine's data for its availability on its own.
- mvmd gains the disk stream (garamsh/mvmd#827); nothing else in mvmd changes for this.
- The operator API gains `POST /v1/hosts/{id}/abandon` and the abandoned-volumes listing.
- A fenced host powered on again as it was runs a second copy of each of its Machines, with live egress, until it reaches orch and for up to 10 minutes after, or without limit while partitioned. Only the operator's commitment to a reset or a reinstall prevents it, until naru fences hosts itself (#397).

## Signs the decision was wrong

- A Machine runs in two places: on a host that came back and on its new host.
- Operators abandon hosts that were only slow, and lose data to it, often enough to want an automatic rule.
- An attestation proves false: an abandoned host is found running its Machines, which is the case for naru fencing through the hypervisor or BMC itself.
- Reconcile passes take longer than `--machine-interval` at the fleet's size, or etcd's write rate for Machines approaches its quota; either reopens per-site gossip in the manner of Corrosion.
- Moves fail more often at the copy than at any other step, which would argue for copying while the Machine runs and stopping only for the last delta.

## Errata

- **2026-11-28.** Item 6 says the abandonment's one guarded transaction also records "the Machines on it and their volumes". A list written once cannot stay correct: a Machine created, deleted or moved after the write, or a move's commit in flight at it, would leave the list wrong, and the host record holds no lock on the Machines. So garamsh/naru#384 writes the abandonment on the host record alone. The leader's reconciler derives `lost` for each Machine bound to the host and records the host, epoch and volumes on that Machine's record. From then on `lost` is the Machine record's own: it holds when the host's record or mark is gone, as after the host's removal and re-admission. The decision stands. [machines.md](../machines.md) §State has the shape as built.
- **2026-11-28.** Item 7's event for the volumes of an abandoned epoch is recorded once per microVM per leader, as `machine.unknown-microvm` is, and not on each pass. A pass runs every 5 seconds, and an event on each one would fill the fleet's event log.
