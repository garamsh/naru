# ADR 0086: Kubernetes NetworkPolicy is enforced on every cluster by kube-network-policies, an init service over the bridge Pod network that a cluster setting turns off

> Status: superseded by [ADR 0114](./0114-naru-runs-no-kubernetes-or-gaon-and-their-layouts-programs-images-tests-and-documents-are-removed.md)
> Date: 2026-11-21

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#266, part of goal garamsh/naru#262. It adds to [ADR 0031](./0031-a-node-runs-kubernetes-as-init-services-containerd-and-runc-are-static-and-pods-get-routed-prefixes-from-one-pod-network.md), whose Pod network enforces nothing, and settles what [ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) items 11 and 12 leave to garamsh/naru#266. The facts about naru are those of the base commit of this change. The facts about kube-network-policies are those of its release v1.1.3 (published 2026-11-02): the files `install.yaml`, `pkg/dataplane/controller.go`, `tests/README.md` and the release notes of `github.com/kubernetes-sigs/kube-network-policies`, read on 2026-11-21.

## Context

- **A NetworkPolicy object is accepted and ignored.** The Pod network is a bridge with host-local IPAM and a routed prefix per Node ([ADR 0031](./0031-a-node-runs-kubernetes-as-init-services-containerd-and-runc-are-static-and-pods-get-routed-prefixes-from-one-pod-network.md) item 6). Nothing reads the policies. aurora's workloads declare their reachability in policies (goal #262), so the silent default is a security defect.
- **The Node kernel has what a host firewall needs and not what a policy agent needs.** `image/pkgs/kernel/naru.config`, which the Node's own kernel (`image/pkgs/kernel/node/naru.config`, [ADR 0034](./0034-a-node-boots-as-a-microvm-from-a-guest-kernel-and-initramfs-the-image-carries-as-a-boot-set.md)) merges first, builds in nf_tables with the inet and netdev families, conntrack, NAT, `br_netfilter` and `veth`, for kube-proxy's nftables mode. It builds no queue to user space, no conntrack labels, and no BPF traffic control (`BPF_SYSCALL` and `CGROUP_BPF` are there, for the runtime's device filters).
- **Pod traffic crosses two Nodes' kernels.** A Pod's packet to a Pod on another Node leaves by a static route and reaches the other Node's bridge ([ADR 0023](./0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)). Between the two, hostd's `inet naru` table and the WireGuard tunnel ([ADR 0045](./0045-each-network-of-a-host-is-closed-by-default-by-an-nftables-table-hostd-writes-and-wireguard-carries-the-networks-between-hosts.md)) carry it as opaque host traffic, in a microVM that is a Node. Policy is therefore decided inside the Nodes; the host's table confines a network from other networks and does not know a Pod.
- **A policy must hold from the first Pod.** A Node's Pods are all recreated at every boot (the root and `/run` are memory). A policy engine that starts as a Pod starts beside them.
- **Customers have their own choices.** A customer runs Cilium, Calico or an admission-time policy engine of its own, and must be able to switch naru's enforcement off without patching the image ([ADR 0083](./0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) item 12).
- **The conformance run does not cover enforcement.** goal #262's criterion 2 is sonobuoy's certified-conformance run. Kubernetes' conformance set holds the NetworkPolicy API tests (create, read, update, delete), and the tests that send traffic between Pods are the `[sig-network]` NetworkPolicy and `Netpol` tests, outside it. The tests of this decision's item 8 are therefore a run of their own.

## Decision

1. **The enforcer is kube-network-policies, the SIG Network implementation of the NetworkPolicy API, over the bridge CNI of ADR 0031.** ADR 0031's bridge, host-local IPAM, static routes and kube-proxy in nftables mode stay. The agent evaluates each new connection's first packet in user space and records the verdict on the connection in conntrack, so later packets of an allowed connection do not return to user space. It enforces ingress and egress, `podSelector`, `namespaceSelector`, `ipBlock` and ports, and AdminNetworkPolicy and BaselineAdminNetworkPolicy beside them. It is the upstream program, with nothing naru-specific.
2. **It is an init service, not a Pod.** The service `kube-network-policies` is added to the Kubernetes topology of `naructl topology kubernetes` before `kubelet` on every Node, as `kube-proxy` is (ADR 0031 item 1): a static program built from the pinned source commit with `CGO_ENABLED=0`, its API credential a client pair of the `system:nodes` kind init issues, as for `kube-proxy`. Init has started it, and its rules and its queue exist, before the kubelet starts the first Pod, so no Pod runs unenforced. A Pod image, a privileged container, a host path mount and the image-import service of ADR 0083 item 3 are not needed, and the agent is not in the way of a customer's DaemonSets. The upstream manifest (`install.yaml`) is not applied.
3. **It fails closed.** The agent runs without its `--fail-open` flag, so the queue has no bypass: when the agent is not running or not yet synced, new connections of Pods are dropped and none is accepted unchecked. Init restarts the agent with its backoff. Established connections of an allowed flow survive the agent's restart on their conntrack verdict.
4. **Pod identity comes from the API server.** ADR 0031 item 10 disables containerd's NRI, so the agent's fallback of resolving a Pod by its address from the API server is the path used; the agent's local-Pod resolution through NRI (v1.1.3) is not enabled. If the implementation shows that v1.1.3 does not start without the NRI socket, the choice is made then between enabling NRI (its socket is under `/run`, which `/var/run` links to) and a build flag, and a new ADR records it.
5. **Kernel options.** `image/pkgs/kernel/naru.config` gains, and so the Node's kernel and the host's with it, `CONFIG_NETFILTER_NETLINK_QUEUE`, `CONFIG_NFT_QUEUE` and `CONFIG_NF_CONNTRACK_LABELS`, listed in `image/pkgs/kernel/node/required.txt` so a build that drops one fails. The expressions the agent writes (queue, conntrack state, direction and labels, `meta skuid`, payload and reject) are read from `pkg/dataplane/controller.go` at v1.1.3; the others it uses are already in the file. The bridge must pass the hooks (`CONFIG_BRIDGE_NETFILTER`, present), and init sets `net.bridge.bridge-nf-call-iptables` to 1, which the agent relies on to see Pod-to-Pod traffic on one Node. Whether the sysctl is set today is checked in the implementation, and a QEMU test fails when it is not. No eBPF option is added. The guest kernel of Machines (`guest-naru`) is unchanged.
6. **One cluster setting turns it off.** The cluster's configuration of ADR 0083 item 12 gains `networkPolicy`, on by default. With `networkPolicy: false`, `naructl` leaves the service out of the Node's topology and user-data, so no table, no queue and no agent exist, and the cluster is as ADR 0031 left it: a customer's own CNI or policy engine owns enforcement. The setting changes by `naructl apply` of new user-data and takes effect at the Node's next boot. It is not an add-on of ADR 0083 and the `addons` service does not apply or prune anything for it, because there are no objects: ADR 0083 item 11 expected an add-on of that kind and this decision does not build one, so that item's sentence on NetworkPolicy is settled here.
7. **Interaction with the rest of the Pod network.**
   - kube-proxy's nftables mode and the agent's table are separate tables with their own hooks, and the agent evaluates the destination a Service's DNAT chose, as a NetworkPolicy specifies.
   - The routed Pod prefixes and `--peer` routes (ADR 0031 item 6, ADR 0023) are unchanged; a Pod's source address stays its own, which is what a policy needs, and `ipMasq` stays off.
   - The host's `inet naru` table and the tunnel (ADR 0045) are unchanged. Both ends enforce: egress at the source Node, ingress at the destination Node, so the tunnel's closure and the cluster's policies compose and neither relies on the other.
   - A Node upgrade (ADR 0025) replaces the binary with the image. Policy state is in the API server, so the agent rebuilds from it at every start, and the Node's first boot of a release drops new connections until it has synced (item 3).
8. **How it is tested.**
   - A QEMU test in `tooling/qemu/tests` boots a two-Node Kubernetes cluster and shows, from Pods, that a default-deny ingress policy blocks a Pod on the other Node, that an allow rule for one port opens exactly that port, and that an egress policy holds; it fails when `networkPolicy: false` leaves the service out. A second case shows `networkPolicy: false` enforces nothing.
   - The Kubernetes e2e NetworkPolicy tests are run by sonobuoy, in a run of their own after the certified-conformance run, on the same 3-Node cluster, with a focus on the `[sig-network]` NetworkPolicy and `Netpol` tests and a skip of the SCTP ones: the Node kernel builds no SCTP, so the tests that need it do not apply. The focus, the skip and the number of tests run are posted with the result, and the exact regular expressions are fixed from the e2e binary's own test listing (`--dry-run`) in the implementation, not here. A test that fails for a reason other than SCTP is a fix in the implementation's pull request or an issue, not a skip.
   - The run belongs to the final check of goal #262, takes its turn under the build lock, and is not run per pull request.
9. **The release carries it.** The agent is built from a source commit pinned in `image/pkgs/` and listed in the SBOM and the sources tarball like every package ([ADR 0076](./0076-a-tag-publishes-once-and-a-release-is-signed-attested-and-carries-an-sbom-and-the-corresponding-source.md)); nothing is fetched at run time, and `make image-repro` is unchanged.
10. **RAM.** The agent is one program in the initramfs and no image, so the cost is its binary and its working set. The upstream manifest requests 50 MiB for the working set (`install.yaml` at v1.1.3). The binary is not measured here: it is a static Go program that links client-go and the nftables library, and an estimate of at most 70 MiB unstripped is an upper bound that the implementation's pull request replaces with the measured size. Alone it is under the 256 MiB threshold of ADR 0083's last section. Added to the 440 to 600 MiB of ADR 0083's add-ons it is not, and the agent cannot wait for an add-on's delivery since it must run before the kubelet: if garamsh/naru#265 makes system extensions the delivery of the add-ons, the agent is a payload of the same extension that init mounts before it starts any service ([ADR 0055](./0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)), and not a Pod image.

## Rejected alternatives

- **An enforcing CNI replacing the bridge (Cilium, Calico).** The final form for a cluster that wants a service mesh, observability or a CNI-level data plane, and the customer's choice then, by item 6. As naru's default it replaces ADR 0031's bridge, host-local IPAM and static routes, and brings the CNI's own agent, operator and (Cilium) eBPF options the kernel does not build, as Pods whose images, memory and upgrade naru owns; a policy engine that is also the CNI is a larger part of every Node than the question needs. Their sizes are not measured here: the rejection rests on the replacement of ADR 0031 and the added kernel and Pod surface, not on a figure.
- **The same agent as a DaemonSet from the upstream manifest.** It is the upstream's own way, and the standard add-on of ADR 0083 item 11. It starts as a Pod, beside the Pods it must constrain, so after every boot there is a window in which Pods run unenforced, and it needs a privileged Pod, host path mounts and an image imported into every Node. The window is the reason; it is a security boundary.
- **An nftables ruleset naru writes from the API itself, in init or a Node service.** It would run in the kernel with no queue. It is also a second implementation of the NetworkPolicy semantics (selectors, namespaces, `ipBlock` with `except`, named ports, AdminNetworkPolicy precedence) which naru would own and keep conformant, while SIG Network keeps one in the open. A hand-written enforcer of a security API with its own bugs is the less safe choice.
- **A policy engine at admission only (a webhook).** It validates objects and does not enforce traffic.
- **Fail-open.** The agent's `--fail-open` keeps traffic flowing when it is down. A policy that stops applying when its enforcer is down is not isolation, and a Node with an outage in enforcement has an outage in traffic that a restart ends; an operator who wants the other trade sets `networkPolicy: false` and brings an engine of their own.

## Consequences

- **Every cluster enforces NetworkPolicy by default, from the first Pod of every boot.** A cluster built with an earlier release enforces after the Node boots this one; its policies, which were ignored, then apply, and an existing allow-nothing policy stops traffic that flowed.
- **A new connection of a Pod is decided in user space once.** That adds latency to the first packet of a connection and CPU to a Node with many short connections; established connections do not return to user space. The agent exposes queue metrics; a measurement is not part of this decision.
- **The agent is on the path of every Pod's new connections.** Its crash drops them until init restarts it (item 3).
- **The Node's initramfs grows by the agent's binary** (item 10) and the kernels by three options.
- **A customer with its own CNI sets `networkPolicy: false` and owns enforcement.** naru then cannot say that a NetworkPolicy object is enforced.

## Signs the decision was wrong

- **The NetworkPolicy e2e tests fail for reasons the agent's design causes** (for example, a test whose Pods are on the bridge of one Node and are not seen by the hooks), and not for the agent's bugs: an enforcing CNI replaces the bridge.
- **The measured binary and working set pass the threshold of ADR 0083 on their own**, or the first-packet latency fails a workload of aurora's: the agent moves into the extension of item 10, or an eBPF CNI replaces the bridge.
- **The first boot's sync takes long enough that Pods wait noticeably:** the agent persists its last policy set to disk and applies it before the API server answers.
- **A customer needs a policy feature the SIG Network agent does not implement:** that customer sets `networkPolicy: false` and runs the CNI that does; naru's agent is not extended for it.

## Errata

- 2026-11-23: item 3 says the agent "runs without its `--fail-open` flag, so the queue has no bypass". The flag is on unless it is turned off: `pkg/cmd/cmd.go:42` of kube-network-policies at the pinned commit declares `fail-open` with the default `true`, so leaving it out gives the bypass item 3 rejects. The agent is started with `--fail-open=false` ([ADR 0094](./0094-the-network-policy-enforcer-is-a-user-of-its-own-whose-rbac-the-add-ons-service-applies-whenever-the-enforcer-is-on-and-it-is-started-without-nri.md) item 8). The decision stands.
