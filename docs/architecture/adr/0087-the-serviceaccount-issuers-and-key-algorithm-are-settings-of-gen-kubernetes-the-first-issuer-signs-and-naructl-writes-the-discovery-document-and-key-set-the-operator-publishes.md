# ADR 0087: the ServiceAccount issuers and key algorithm are settings of gen kubernetes, the first issuer signs, and naructl writes the discovery document and key set the operator publishes

> Status: accepted
> Date: 2026-11-21

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

Drafted for garamsh/naru#267, part of goal garamsh/naru#262. It amends item 4 of [ADR 0031](./0031-a-node-runs-kubernetes-as-init-services-containerd-and-runc-are-static-and-pods-get-routed-prefixes-from-one-pod-network.md), which fixes the ServiceAccount key as ECDSA P-256 and the issuer as the in-cluster one. The facts about naru are those of the base commit of this change. The facts about AWS are those of "Create an OpenID Connect (OIDC) identity provider in IAM" (https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html) and about OpenID Connect of "OpenID Connect Discovery 1.0" (https://openid.net/specs/openid-connect-discovery-1_0.html), both read on 2026-11-21. The facts about the API server are those of the flags of kube-apiserver in the Kubernetes release the image pins.

## Context

- **A workload that calls a cloud API presents its projected ServiceAccount token, and the cloud must be able to verify it.** aurora's workloads assume AWS IAM roles that way (goal #262). AWS federates with an OpenID Connect identity provider whose issuer URL it can fetch from. A cluster whose tokens say `iss: https://kubernetes.default.svc.cluster.local` has no URL another party can fetch from, and ADR 0031 gives the operator no way to set one.
- **What AWS requires of the issuer and the key set.** From the AWS page:
  - "The URL must begin with https://. Per the OIDC standard, path components are allowed but query parameters are not." and "The URL should not contain a port number."
  - The provider's discovery document is read from the issuer, and "jwks_uri: The JSON Web Key Set (JWKS) endpoint where IAM gets your public keys." is a field of it. The fields AWS lists as required are `issuer`, `jwks_uri`, `response_types_supported` and `subject_types_supported`.
  - "id_token_signing_alg_values_supported: RS256, RS384, RS512, ES256, ES384, ES512" names what AWS accepts.
  - "The JSON Web Key Set (JWKS) must contain at least one key and can have a maximum of 100 RSA keys and 100 EC keys."
  - A published key set must not carry a private parameter (RSA `d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`; EC `d`; `oct` `k`), and AWS treats a private key found there as compromised.
  - AWS verifies the TLS certificate of the key set's endpoint against its trusted root authorities.
- **OpenID Connect Discovery 1.0 sets the floor for any other provider.** "The algorithm RS256 MUST be included" in a provider's supported signing algorithms, `issuer` is a "URL using the https scheme with no query or fragment components", and `jwks_uri`, `response_types_supported` and `subject_types_supported` are required.
- **What the API server offers.** `--service-account-issuer` is repeatable: the first value is the `iss` of the tokens it issues and all of them are accepted when it validates. `--service-account-jwks-uri` sets the `jwks_uri` of the discovery document the API server serves itself, which otherwise names the API server's own address. `--service-account-key-file` may name a file with several public keys, and a token is accepted when any verifies it. The signing algorithm follows the signing key: an RSA key signs RS256, an ECDSA P-256 key ES256. A token's `kid` is the unpadded base64url of the SHA-256 of the signing public key's PKIX encoding.
- **Tokens outlive the key.** A projected token lives until its ServiceAccount's expiry (an hour by default, renewed by the kubelet), and a token a Pod has already presented to a cloud lives on there. A key that is replaced stops verifying the tokens it signed unless it is still listed.
- **The Nodes do not serve a publicly fetchable URL.** The API server answers `/openid/v1/jwks` only to an authenticated or an anonymous-allowed client, and the Nodes' addresses are private. The operator already publishes a static site for the cluster (aurora hosts one, garamsh/aurora#816), and a static file needs no running part of the cluster.

## Decision

1. **The issuers are a cluster setting of `naructl gen kubernetes`.** `--service-account-issuer <url>` is repeatable and written, in order, to `<ca-dir>/service-account-issuers`, as `--disable-addon` is written to `disabled-addons` (ADR 0083 item 12); `gen kubernetes-node` reads it. A later `gen kubernetes` without the flag removes the file, so a cluster returns to the in-cluster issuer alone, which is what ADR 0031 has.
2. **The first issuer signs and all are accepted, and the in-cluster issuer is always accepted.** `gen kubernetes-node` writes each issuer as a `--service-account-issuer` of the API server in the operator's order, then the in-cluster issuer `https://kubernetes.default.svc.cluster.local` last unless the operator named it. The in-cluster issuer therefore never stops validating, whatever the operator chooses, because the cluster's own components and Pods that were given a token before the change present it. When the operator names an issuer, `--service-account-jwks-uri` is set to the first issuer plus `/openid/v1/jwks`, so the discovery document the API server serves points at the file the operator publishes (item 5). With no issuer given, nothing changes from ADR 0031.
3. **An issuer is refused unless it is an `https` URL with a host, no query, no fragment, no trailing slash and not repeated.** This is the AWS rule and the Discovery rule together. The AWS rule on a port is not enforced: a URL with a port is accepted by naructl, and the AWS page's "should not" is left to the operator who federates with AWS.
4. **The key algorithm is RS256 or ES256, and the default is RS256.** `--service-account-algorithm` names it, and the key file decides it from then on: the layout has no algorithm field, because the API server reads the algorithm from the key. RS256 is the default because OpenID Connect Discovery requires every provider to support it ("MUST be included"), and AWS lists it, so it is the one a verifier beyond AWS is certain to have; an RSA key is 2048 bits. ES256 is listed by AWS too, makes smaller tokens and keys, and stays selectable. This changes ADR 0031's ECDSA default, and a cluster whose key exists keeps it: an existing key is kept, and a named algorithm that differs from the key's is refused, not silently replaced, because replacing the key voids every token in circulation.
5. **The discovery document and the key set reach the operator as files from an offline command.** `naructl gen kubernetes-jwks --ca-dir <dir> --out-dir <dir>` reads `sa.pub` and the issuers file and writes, under the first issuer's path, `.well-known/openid-configuration` and `openid/v1/jwks`. The discovery document has `issuer`, `jwks_uri` (the issuer plus `/openid/v1/jwks`), `response_types_supported` (`id_token`), `subject_types_supported` (`public`) and `id_token_signing_alg_values_supported` (the algorithms of the keys). The key set has one entry per public key in `sa.pub`, with `kid` computed as the API server computes it, `use` `sig` and the key's `alg`, and holds no private parameter, which is checked by a test. The operator publishes the two files unchanged at the issuer's URL over TLS with a certificate a public authority issued, and AWS then needs only the issuer URL. naructl does not host, upload or fetch.
6. **Rotation makes a new signing key and keeps the public key of the one before it.** `--rotate-service-account-key` makes a new key, writes it as `sa.key`, and sets `sa.pub` to the new public key followed by the previous signing key's public key. The previous key keeps verifying the tokens it signed, and the key set lists both, so a token that has not expired still verifies at the cloud. A second rotation drops the oldest key, so the set holds two keys at most, far under the 100 AWS allows. The operator republishes the key set (item 5) before the new user-data is applied, so no token signed by the new key is presented before the cloud can verify it. `naructl apply` delivers the new files, and the files carry the services that read them: `sa.key` restarts the API server and the controller manager, `sa.pub` the API server, so an apply takes effect without a reboot. The rotation may change the algorithm, which is the only way to.

## Rejected alternatives

- **Publishing from the running cluster: the operator points the cloud at the API server's `/openid/v1/jwks`.** It needs the Nodes' private addresses to be reachable by the cloud, anonymous access to a path (or a cluster role binding for `system:anonymous`), and a TLS certificate a public authority issued for the API server, which the cluster's own authority is not. It ties the verification of every token to the cluster being up. A file the operator hosts is fetchable when the cluster is down and exposes nothing of the cluster. Rejected.
- **A cluster-side publisher: a naru service that uploads the key set to a bucket.** It would need the operator's storage credentials in a Node's user-data for the life of the cluster, and a service per cloud. The operator's own pipeline, which already publishes a static site, does this better. Rejected.
- **An algorithm field in the layout.** The key file already decides the algorithm; a second source of the same fact can disagree with it and then the API server and the key set differ. Rejected.
- **Keeping ES256 as the default.** ECDSA is what ADR 0031 chose and is smaller, and AWS accepts it. It is not required of an OpenID Connect provider, and the first verifier that is not AWS decides the default for every cluster, so RS256 is the default and ES256 the choice. Rejected as the default, kept as an option.
- **Keeping every key ever used in the key set.** The set only grows, and a leaked old key stays trusted. Two keys cover the lifetime of a token across one rotation, as item 6 reasons, and an operator who needs a longer window rotates less often. Rejected.
- **Dropping the in-cluster issuer when the operator names one.** Every Pod holding a token with the old issuer, and the cluster's own components, would stop authenticating at the apply. Rejected.

## Consequences

- A cluster federates with AWS IAM (or any OpenID Connect verifier) by the operator running `gen kubernetes --service-account-issuer`, `gen kubernetes-jwks` and publishing two files. The tokens a Pod projects carry the issuer.
- The ServiceAccount key of a new cluster is RSA 2048 by default. A cluster made before this change keeps its ECDSA key and is refused `--service-account-algorithm RS256` unless it rotates.
- The issuers are a cluster-wide setting in the CA's directory like the disabled add-ons, so the operator who runs `gen kubernetes` again without the flag returns the cluster to the in-cluster issuer. The operator who rotates the key must pass the issuer flags again; the same holds for `--disable-addon`.
- The key set is the operator's to keep current: after a rotation, the files must be published before the apply. A missed publish breaks only the federation, not the cluster.
- A private key is never written by `gen kubernetes-jwks`, which reads only `sa.pub`.
- [config.md](../config.md) holds the flags.

## Signs the decision was wrong

- An operator needs different issuers for different parts of a cluster, which one cluster-wide list cannot say.
- A cloud that federates by a key set rejects the one naructl writes, on a field or an algorithm this decision did not read from its documentation.
- Operators publish the key set late or never after a rotation often enough that federation breaks in practice, which would argue for a command that checks the published copy.
- A rotation with tokens still in use after two rotations is common, which would argue for a longer list of keys.
