# Image

What the P0 image holds, where its inputs come from, and how a Node boots it.

Claims about garamsh/mvmd hold at commit `d189133bba8d842d2bcb20046f39fe03161efeb1`, and claims about garamsh/gaon at `c2b42f91724cae39a4f6824517c278150cf4695f`; they promise nothing about later versions. Claims about etcd hold for etcd-io/etcd v3.6.16, commit `0b065e61c679ea81f6862bb24c9815f7fc673966`. The claims about the QEMU tests, the release's user-data and the keys it publishes were checked against the code and the runs of this branch, not against the pinned commits alone.

## Current decisions

- **P0 is done when a QEMU VM boots the image and init, as PID 1, starts and supervises the services the configuration names.** The services are mvmd, gaon's Node Agent and optionally gaon's control plane.
- **One boot form.** The kernel and initramfs boot from a UEFI disk image, `naru.img`, which is the form Proxmox attaches ([ADR 0007](./adr/0007-the-proxmox-boot-form-is-a-uefi-disk-image-whose-efi-stub-kernel-loads-the-initramfs-from-the-esp.md)); the QEMU tests boot it, and none passes `-kernel` or `-initrd`. The disk has two slots for a kernel with its initramfs embedded and a trial slot is reached once by `BootNext` ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)). There is no installer. The system is the initramfs, which init copies to a tmpfs root at start and remounts read-only before it starts the first service ([Booting a Node](#booting-a-node)).
- **Three drives are attached.** The NoCloud drive (label `cidata`) carries the Node's configuration and network ([config.md](./config.md), [ADR 0008](./adr/0008-a-node-reads-its-configuration-and-network-from-a-cloud-init-nocloud-drive.md)). The boot disk is `naru.img`. The data disk holds mvmd's state directory, etcd's data directory and the test inputs, formatted ext4 with the `verity` feature.
- **Host kernel.** kernel.org longterm 6.18.63, built by naru from the release tarball with naru's configuration, the version and the tarball's sha256 pinned in `image/kernel/`. It meets the conditions table of [ADR 0006](./adr/0006-the-host-kernel-is-built-from-the-pinned-longterm-6-18-tarball-and-the-image-inputs-live-in-image.md).
- **Guest kernel and initrds.** The image carries the guest kernel `naru`, the Guest Agent's initrd and the converter's initrd, which a Machine boots on, under `/usr/lib/naru/guest/` (`kernels/naru/vmlinux`, `guest-initrd.cpio`, `converter-initrd.cpio`), with `guest.json` there naming each by its path and SHA-256 ([ADR 0010](./adr/0010-the-guest-kernel-and-initrds-are-image-components-built-at-the-pinned-mvmd-commit.md)). The kernel is built by naru from the host kernel's pinned tarball with its own configuration; the initrds are built by mvmd's Makefile at the pinned commit and checked against `image/guest/pin.env`. mvmd's configuration names these paths and digests, read from `guest.json`.
- **Non-Go inputs** are `image/kernel/` (configuration, pin and the build script), `image/guest/` (the guest kernels' configurations and `required.txt`, the kernels' names, the initrds' pin and the build scripts), `image/e2fsprogs/` (the e2fsprogs pin and the build script), `image/gaon/` and `image/etcd/` (each a pin and the build script), `image/initramfs/` (pin, the entry list and the build script), `image/disk/` (the disk and partition GUIDs and the build script) and `image/mvmd-checkout.sh`; `image/build.env` fixes the environment the scripts build in.
- **Binaries in the initramfs:**
  - naru-init as `/init`.
  - mvmd and mvmd-supervisor, built with Go (`CGO_ENABLED=0`) from the mvmd commit pinned in `image/initramfs/pin.env`, `d189133bba8d842d2bcb20046f39fe03161efeb1`, fetched with git into the build directory.
  - Firecracker, from the release that mvmd's `tooling/firecracker/fetch.sh` pins (v1.17.0 at the pinned commit), verified by that pin. The script is run from the pinned checkout as `fetch.sh --firecracker-only`, which downloads the Firecracker release tarball and verifies its digest and the binary's, and requests nothing from the Kata Containers release, writes no `vmlinux`, and writes an `inputs.env` that names only `MVMD_FIRECRACKER` and `MVMD_FIRECRACKER_SHA256`. It is still the only source of the Firecracker binary at that commit: mvmd's `make guest-initrd` and `make converter-initrd` fetch nothing and are unchanged between `3b37892f303a4d4dbd8e5360906d0f9c036b562e` and the pinned commit.
  - `mkfs.ext4`, mke2fs statically linked from the e2fsprogs release pinned in `image/e2fsprogs/pin.env` ([ADR 0011](./adr/0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md)), installed as `/bin/mkfs.ext4`, the path mvmd's `disk.mkfs` names.
  - `gaon-node-agent`, `gaon-apiserver`, `gaon-scheduler` and `gaon-controllers`, built with Go (`CGO_ENABLED=0`, `-trimpath`) from the gaon commit pinned in `image/gaon/pin.env`, `c2b42f91724cae39a4f6824517c278150cf4695f`, fetched with git into the build directory ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)).
  - `etcd`, the server binary only, built with Go (`CGO_ENABLED=0`, `-trimpath`) from the commit pinned in `image/etcd/pin.env`, v3.6.16 `0b065e61c679ea81f6862bb24c9815f7fc673966`, fetched with git.
  - `naru-standin`, the stand-in service of the P0 test (see [Booting a Node](#booting-a-node)).
  - Nothing is built or run in a container. There is no shell and no busybox.
- **Forwarding is set by init**, not by mvmd ([config.md](./config.md)).

## Building the image

- `make image` writes `build/image/bzImage` (the kernel with the initramfs embedded), `build/image/bzImage.bare` (the kernel before it), `build/image/initramfs.cpio.gz`, `inputs.env` (mvmd's name for Firecracker and its SHA-256, which the tests read) and `build/image/guest/`, which holds the guest files the initramfs carries and `guest.json`, `build/image/e2fsprogs/mke2fs`, which the initramfs carries as `/bin/mkfs.ext4`, `build/image/gaon/` (the four gaon binaries, and `gaon`, gaon's command line client, which the QEMU tests run on the host and the initramfs does not carry) and `build/image/etcd/etcd`. `build/` is not tracked.
- **The kernel.** `image/kernel/build.sh` downloads the pinned tarball, fails unless its SHA-256 is the pinned one, merges `image/kernel/naru.config` over the x86_64 `defconfig` with the kernel's `merge_config.sh`, runs `olddefconfig`, and then fails unless every line of `image/kernel/required.txt` matches a line of the final `.config`: kconfig drops an option whose dependencies are unmet without failing, so the file the build uses is what is checked. The unpacked source and the object directory are emptied before each build.
- **The guest files.** `image/guest/build.sh` builds each kernel `image/guest/kernels.env` declares with `image/guest/kernel.sh`: the host kernel's tarball (checked against its pin again) unpacked, `image/guest/kernels/<name>/naru.config` merged over x86_64 `tinyconfig`, `olddefconfig`, then a failure unless every line of that kernel's `required.txt` matches the final `.config` (it has a line for each condition of mvmd's guest.md §Kernel conditions, `CONFIG_VMGENID` and `CONFIG_ACPI` among them), and the uncompressed ELF `vmlinux`, everything built in. It then builds the two initrds with mvmd's `make guest-initrd converter-initrd` in the pinned checkout, fails unless each has the SHA-256 of `image/guest/pin.env`, and writes `guest.json`: `kernels` (name to `{path, sha256}`), `default_kernel`, `guest_initrd` and `converter_initrd`, the paths being the ones inside the image. A kernel name is 1 to 63 characters of `[a-z0-9-]`, the form mvmd's `kernels` map takes (garamsh/mvmd#364).
- **mke2fs.** `image/e2fsprogs/build.sh` downloads the pinned e2fsprogs tarball, fails unless its SHA-256 is the pinned one, unpacks it, configures an out-of-tree build and builds the libraries and `mke2fs` only (no other tool of the package), then strips it and fails unless `file` reads it as statically linked. `LDFLAGS=-static` links it against the host's `libc.a`; libuuid and libblkid are the tree's own (`--enable-libuuid --enable-libblkid`), so no system copy is linked. NLS, `fuse2fs`, `debugfs`, `e2image`, `resize2fs`, `e4defrag`, `uuidd`, the initrd helper and the shared-library forms are switched off, since mke2fs links none of them or needs none of them to format a disk ([ADR 0011](./adr/0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md)). The build paths are mapped away with `-ffile-prefix-map` and the build id is dropped, so the same inputs give the same bytes whatever the directory. A build whose inputs (the pin, the script, `image/build.env`) match the last one is skipped, by a stamp beside the output.
- **gaon.** `image/gaon/build.sh` fetches the pinned commit with git (`git init`, `fetch --depth 1` of that object name, `checkout`) and fails unless `HEAD` is that object name, then builds `node-agent/cmd/gaon-node-agent`, `apiserver/cmd/gaon-apiserver`, `scheduler/cmd/gaon-scheduler` and `controllers/cmd/gaon-controllers` with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -buildvcs=false -ldflags='-s -w'`, and fails unless `file` reads each as statically linked. The same script, from the same checkout, builds `gaon-cli/cmd/gaon` with the same flags into `gaon/gaon`; it is a test input for the host, and `image/initramfs/build.sh` names the four services and takes nothing else from the directory, so the initramfs is the same with or without it. `GOTOOLCHAIN` is set to the toolchain line of gaon's `go.work` at that commit (`go1.26.11`), so the host's Go downloads it when it is older and the bytes do not depend on the host's version. A build whose inputs match the last one is skipped, by a stamp beside the output.
- **etcd.** `image/etcd/build.sh` does the same for etcd: it fetches the commit of v3.6.16, checks `HEAD`, builds the `server` module's main package (the repository's root is a library) with `GOTOOLCHAIN` from `server/go.mod` (`go1.26.10`), fails unless the binary is static and `etcd --version` reports `3.6.16`, and installs it as `etcd`. Only the server is built, not `etcdctl` or `etcdutl`.
- **The initramfs.** `image/initramfs/build.sh` builds the programs, takes mke2fs from `image/e2fsprogs/build.sh`'s output and the gaon binaries and etcd from theirs, fails unless each is a static executable, and writes the archive with the kernel's own `usr/gen_init_cpio`, compiled from the pinned tarball. The guest files and `guest.json` are added at `/usr/lib/naru/guest/`, from the generated tail of the list. The archive is newc, in the order of `image/initramfs/initramfs.list` and that tail, every entry owned by 0:0 and stamped with `SOURCE_DATE_EPOCH` from `image/build.env`, then compressed with `gzip -9n`. **Size added by gaon and etcd** (measured on one build of this branch): the five binaries are 70,107,946 bytes uncompressed (etcd 27,226,274; gaon-apiserver 16,294,050; gaon-node-agent 12,927,138; gaon-scheduler 6,844,578; gaon-controllers 6,815,906) and 26,176,327 bytes when each is gzipped alone at level 9; the whole initramfs is 129,623,552 bytes uncompressed and `initramfs.cpio.gz` is 47,229,248 bytes. The initramfs without them was not built for comparison, so the compressed increase of the archive itself is not measured; the figures above bound it.
- **The disk.** `make disk` (which runs `make image` first) writes `build/image/naru.img` and `build/image/naru.qcow2` with `image/disk/build.sh` and `tooling/disk`. `naru.img` is a raw GPT disk of 1 MiB, one EFI system partition of at least 64 MiB, and 1 MiB. The partition is FAT32, label `NARUESP`, and starts at sector 2048 with a fixed GUID, is sized for two kernels (the larger of 64 MiB and two kernels with slack, a whole number of MiB), and holds the kernel as `\EFI\BOOT\BOOTX64.EFI`, the default slot. The trial slot, `\EFI\BOOT\TRIAL.EFI`, is absent from a built disk. `mkfs.fat` makes the empty volume, `sgdisk` the table, and `tooling/disk/internal/fat` writes the file; the builder reads it back and fails unless it is the input. `naru.qcow2` is `naru.img` converted by `qemu-img convert -O qcow2`, for Proxmox's `import_from`.
- **How the initramfs reaches the kernel.** The kernel is built with the EFI stub, `CONFIG_EFIVAR_FS` and a built-in command line, `console=ttyS0 panic=-1 loglevel=4`, with no `initrd=`: the stub concatenates every initrd it is named, so a slot with its own initramfs would also load another's. `image/kernel/build.sh` builds `bzImage.bare`; `image/kernel/embed.sh` sets `CONFIG_INITRAMFS_SOURCE` to `initramfs.cpio.gz`, links again and writes `bzImage`, so the bzImage depends on the initramfs and a slot is one file. An embedded archive replaces the kernel's default one, so `/dev/console` is a node in `initramfs.list`. This supersedes ADR 0007 item 1 and ADR 0004 item 2 ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)). `image/kernel/required.txt` fails the kernel build if any of these options is missing from the final configuration. The reasons and the kernel documents are in ADR 0007.
- **naru-init's version.** `make image` and `make release` pass `VERSION` (`git describe --tags --always`, or `VERSION=<name>`) to `image/initramfs/build.sh` as `NARU_VERSION`, which builds `naru-init` with `-ldflags -X main.buildVersion=<VERSION>`: `version()` in `init/cmd/naru-init/main.go` prefers it, so `GET /v1/version` and `naructl version` on a Node of a release report the release's tag. The string is the only thing the flag adds to the binary, so two builds of one `VERSION` stay byte-identical, and builds of two `VERSION`s differ in `naru-init` and so in the initramfs and the disks. Without `NARU_VERSION` the flag is left out and `version()` falls back as [init.md](./init.md) says.
- **Reproducibility.** `make image-repro` builds twice from empty build directories, the disk included, and fails unless `bzImage`, `e2fsprogs/mke2fs`, `etcd/etcd`, the four service binaries of `gaon/` (not the client `gaon/gaon`, which the image does not carry), `initramfs.cpio.gz`, `guest/guest.json` (which holds the SHA-256 of the guest kernel and both initrds), `naru.img` and `naru.qcow2` have equal SHA-256. It holds for one host toolchain and one `VERSION` (both builds of a run use the same one): the kernel build records the compiler's version, so a host with another gcc or Go builds other bytes.
- **Who moves the pins.** The kernel's pin is moved by the PM ([image/kernel/pin.env](../../image/kernel/pin.env)), and so are mvmd's ([image/initramfs/pin.env](../../image/initramfs/pin.env)) e2fsprogs's ([image/e2fsprogs/pin.env](../../image/e2fsprogs/pin.env)), gaon's ([image/gaon/pin.env](../../image/gaon/pin.env)) and etcd's ([image/etcd/pin.env](../../image/etcd/pin.env)); each names how. The pins of the gaon and etcd commits are bumped in a pull request that rebuilds the image and runs `make test-qemu`; the etcd pin moves with a release, gaon's with a commit whose docs the PM has read again for what boundaries.md and config.md claim.

## Booting a Node

- **Boot N Nodes: `make nodes N=3`** (default 2, at least 2). It builds the image and the disk, then boots N Nodes of the image under QEMU on one network and keeps them up until interrupted. Each Node has its own disks and console log under `build/nodes/node-<i>/`; the command prints a line per Node once that Node's stand-in has dialled its peer across the network. `tooling/qemu/cmd/naru-nodes` is the command.
- **Run the test: `make test-qemu`.** It builds the image and the disk, boots Nodes as the tests need, reads their serial consoles, and fails, never skips, when no test ran. The tests are `TestNode_*` in `tooling/qemu/tests`, built with `-tags qemu_real`.
- **QEMU** runs as the user with `-enable-kvm -cpu host`, laid out as a Proxmox guest is: the q35 machine under OVMF (`/usr/share/OVMF/OVMF_CODE_4M.fd` as read-only pflash unit 0, a per-Node copy of `/usr/share/OVMF/OVMF_VARS_4M.fd` as unit 1), a `virtio-scsi-pci` controller with `naru.img` (read-only, `bootindex=0`) and the data disk as `scsi-hd`, the NoCloud drive as a read-only `ide-cd` on the AHCI bus, and one virtio NIC (a Node of a gaon cluster that has the control plane has a second, see "The host path to gaon's API server" below); nothing needs root. There is no `-kernel`, `-initrd`, `-append` or `ip=`. The kernel's built-in command line carries `loglevel=4`, so kernel info messages do not split init's console lines, which the tests read; no test asserts a kernel line. A missing `naru.img` fails before QEMU starts, naming `make disk`.
- **The network** is QEMU's `-netdev socket` over a multicast group on the loopback, with a group port drawn at random per cluster so clusters on one host do not share a network. Each Node has its own MAC, `02:00:00:00:<i high byte>:<i low byte>`, and its `network-config` gives it `10.78.0.<i>/24` (the release's example for Proxmox gives other values, [Release assets](#release-assets)) on `eth0` with `10.78.0.254` as gateway and resolver (no machine has that address), which init applies before any service ([config.md](./config.md)). Machine networks are separate: Node i gives mvmd `network.ipv4_prefix` `10.77.<i>.0/24`, and `spec.network.forwarding` lists `ipv4`.
- **The drives** are built by `tooling/qemu/internal/node`. The NoCloud drive is a 4 MiB file, as Proxmox's is, holding an ISO 9660 volume labelled `cidata` with `user-data` (the Node's `naru.yaml`: its name, its services and the file `/run/mvmd/config.json`, mode `0600`, which is mvmd's JSON configuration), `meta-data` (`instance-id`) and `network-config`. `tooling/qemu/internal/iso9660` writes it, with a primary and a Joliet tree because the kernel reads `user-data` through Joliet; no genisoimage, xorriso or root is needed. The data disk is made with `/sbin/mkfs.ext4 -d`, which fills an ext4 image from a directory without mounting it, owned by root: labelled `NARUDATA`, 2 GiB sparse, with the `verity` feature, holding only the test inputs under `inputs/` (no guest file: the image carries those), so it is the same for every Node (etcd creates `/var/lib/naru/etcd` on it at its first start, beside `mvmd` (mvmd's `state_dir`) and `inputs`); `naru.yaml` mounts it at `/var/lib/naru`, and the mvmd service's `-config` names the file init wrote under `/run/mvmd`, so init knows nothing of mvmd's configuration. The data disk is where the inputs go because init mounts the NoCloud drive and that disk and no other.
- **The inputs** are staged by `tooling/qemu/internal/fixture` from build outputs and hard-linked into each data disk: the test-only `naru-registry` and `naru-probe`, and an OCI registry directory holding one image and its TLS authority. They are test inputs and not image contents. gaon's CLI is not staged: the gaon Machine test runs it on the host from `$NARU_IMAGE_DIR/gaon/gaon` (`build/image/gaon/gaon`, built by `image/gaon/build.sh`). The guest kernel and initrds are not staged: `tooling/qemu/internal/guest` reads `build/image/guest/guest.json`, and mvmd's configuration (`naructl`'s, for a gaon Node, which reads the same manifest, and `node.Config.MvmdJSON` for the stand-in Nodes) names the paths and SHA-256 in it, with every declared kernel written to the Firecracker section's `kernels` map and `default_kernel` (the form mvmd reads at the pinned commit; it refuses the single `kernel` and `kernel_sha256` there), and the default kernel alone written to the `conversion` section, which keeps one `kernel` and `kernel_sha256`.
- **The services** of every Node of a cluster without gaon, in order, are `mvmd` (the Firecracker driver, `SSL_CERT_FILE` naming the registry's authority); `registry`, which serves the image over TLS on `127.0.0.1:5000` and is how mvmd pulls; `standin`, which logs the file system type of `/var/lib/naru`, dials mvmd's Unix socket until it accepts, and dials the stand-in of the next Node (Node i dials Node i+1, the last dials the first) on TCP 7000 until it accepts; and `control`, a stand-in marked `controlPlane: true`. Node 1 has `spec.controlPlane: true`, so only it starts `control`; every other Node's init logs that it skips it. Node 1 also runs `probe` in the restart test.
- **`naru-cluster`** boots the same Nodes from a release's assets for a harness outside this repository, with gaon binaries the harness supplies and a `cluster.json` it reads; [harness.md](./harness.md) is its contract. `make test-harness` runs it as a harness does, from a directory outside the checkout, in its own target so that `make test-qemu` stays the length it is.
- **gaon's services.** A cluster started with `ClusterSpec.Gaon` (the Nodes' user-data is written by `naructl`, which owns this layout: `naructl/internal/layout`, [ADR 0015](./adr/0015-naructl-is-the-single-owner-of-the-gaon-node-layout-and-tooling-qemu-runs-it-as-a-binary.md); the tests build it from the checkout and `naru-cluster` takes it from the release; the QEMU extras are flags: `--serving-address 127.0.0.1`, `--extra-nic`, `--binary`, `--disable`) (the gaon tests; `make nodes` and the other tests do not set it) replaces the services above, after `mvmd` and `registry`, with gaon's, so every Node runs `mvmd` and `registry`, because the scheduler may bind a Machine to any Node and that Node's mvmd pulls the image from `127.0.0.1:5000`. The gaon services follow in this file order: `etcd` (`--data-dir /var/lib/naru/etcd`, TLS on both ports with `--client-cert-auth` and `--peer-client-cert-auth` from the pairs `etcd-server` and `etcd-peer`; one member on `https://127.0.0.1:2379` and `:2380`, or with `--member` flags the static cluster of the members' addresses on 2379 and 2380, [ADR 0024](./adr/0024-the-control-plane-is-three-etcd-members-with-tls-on-both-ports-and-a-virtual-address-held-by-naru-vip-behind-a-fence-on-etcds-ports.md)), preceded by `fence` (`/bin/naru-fence -allow <members>,<virtual address>`, which rejects other sources to ports 2379 and 2380 with a TCP reset; kernel options `CONFIG_NFT_REJECT` and `CONFIG_NFT_REJECT_IPV4`) and followed after the API server by `vip` (`/bin/naru-vip`) when there are several members, `gaon-apiserver` (`--listen 0.0.0.0:6443`, `--etcd-endpoints` with its own member's `https://` URL, `--etcd-ca-file`, `--etcd-cert-file`, `--etcd-key-file`, `--tls-client-ca`, `--tls-cert`, `--tls-key`, and with a token cluster `--bootstrap-token-file /run/gaon/bootstrap-tokens`), `gaon-scheduler` and `gaon-controllers` (each `--api <root>` and its own `--tls-*` files; the controllers also `--signing-cert /run/gaon/ca.pem --signing-key /run/gaon/ca.key` there), each marked `controlPlane: true` and so started only on node-1, then `gaon-node-agent` on every Node (`--api-server <root>`, `--node-name`, `--mvmd-socket`, `--tls-ca`, and `--tls-cert` and `--tls-key`, or in a token cluster `--bootstrap-token-file /run/gaon/bootstrap-token --cert-dir /var/lib/naru/gaon-node-agent`). `<root>` is `https://10.78.0.1:6443/apis/compute.gaon.garam.sh/v1alpha1`. They are argv and files, no environment variable. Each starts after what it dials, but init waits for none: the API server exits when etcd does not answer and init restarts it after the backoff, and the Node Agent and the others retry, so the order is a courtesy and init is unchanged ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)). The flags are the ones `apiserver.md`, `node-agent.md` and the services' `main.go` name at the gaon commit above.
- **The certificates** are issued per cluster by `naructl` (`gen ca`, `gen client`, `gen node`; ECDSA P-256, a CA valid ten years and certificates one year, so a test cluster's lasts longer than its run), from a CA the QEMU tests and `naru-cluster` make in the cluster's directory (`naru-cluster` removes the CA's directory once the last Node's user-data is written, and copies the CA's certificate beside the client pair): the API server's serving certificate with the IP SANs of the API server's address and `127.0.0.1`, an agent certificate per Node with the Node's name as CN (a pair issued by `naructl` in a cluster with `ClusterSpec.BootPKI` false, by a signing request with a bootstrap token in one with it true), client certificates for the scheduler (`gaon-scheduler`) and the controllers (`gaon-controllers`) and the test host's (`naru-test-host`, from `gen client`), which the QEMU tests give to gaon's CLI (`tooling/qemu/internal/gaoncli`) and to their API reads. With `BootPKI` false every Node carries its pairs as files (`--pairs-as-files`). The release's code writes a CA's key into node-1's user-data, as "Keys the release publishes" below says.
- **The host path to gaon's API server.** node-1 of a gaon cluster has a second NIC: `-netdev user,id=net1,restrict=on,hostfwd=tcp:127.0.0.1:<port>-10.0.2.15:6443` and a `virtio-net-pci` with MAC `02:00:00:01:<i high byte>:<i low byte>`, given `10.0.2.15/24` and no gateway by node-1's `network-config` (`eth1`), so the default route stays on `eth0`. `<port>` is a free port of the loopback chosen per cluster. The test host reaches the API server at `127.0.0.1:<port>` over mutual TLS with the test host's client certificate; the serving certificate names `127.0.0.1`. `restrict=on` leaves the guest no route to the host's network, except for the time test's node-1 (`HostReach`), which leaves out `restrict=on` so that it reaches an SNTP server on the host at `10.0.2.2`; the NIC has no gateway, so its default route stays on `eth0`. This is a stable part of the QEMU layout that gaon's end-to-end test (garamsh/gaon#9) can rely on: the second NIC's address, the forward's guest port `6443`, and the `127.0.0.1` SAN. A Node with this NIC configures two interfaces, so the shared judge's `interfaces=1` holds only for the Nodes of the other tests.
- **The host path to a Node's API.** A cluster started with `ClusterSpec.NodeAPI` (with `Gaon`; the Node API tests, [ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md)) has `naructl gen api-ca` write the Node API's authority in the cluster's CA directory before any Node's user-data, so every Node's user-data carries `spec.api` (a client CA, and a serving pair naming the Node's address, `127.0.0.1` and any serving address). node-1's second NIC then has a second forward, `hostfwd=tcp:127.0.0.1:<apiport>-10.0.2.15:50000`, in the same `-netdev` as the first; `<apiport>` is another free port of the loopback. `naructl gen api-client` writes three client files under `<dir>/api-client/` for `127.0.0.1:<apiport>`: `admin.yaml`, `reader.yaml`, and `foreign.yaml`, which is the admin's with the certificate and key of an admin of a second authority made for the purpose (the server's certificate stays trusted, so the file is refused by the Node and not by the client). The authorities' keys are removed with the CA directory once the last Node's user-data is written. The tests run the `naructl` built from the checkout on the host with `--config <file>`. A cluster without `NodeAPI` has no `spec.api`: that is the form v0.3.0 wrote.

## Judging serial logs

- **`make judge-serial NODE1=<log> NODE2=<log>`** reads the serial logs of two Nodes, node-1 first, and exits 0 only when both show what the QEMU tests assert. `tooling/qemu/cmd/naru-judge` is the command. It exits 1 and prints a `FAIL <node>: <expectation>: no line with <fragments>` line for each expectation not met, and 2 when a log cannot be read or an argument is missing. It prints per Node the log's size, the number of re-printed blocks, the largest `dropped` a block reported, and how many expectations were met of how many.
- **`-node-api listening|off`** (`make judge-serial JUDGE_NODE_API=<listening|off>`) also judges, on both Nodes, init's line `the Node API is listening` and no `the Node API is off` line, or the reverse. Left out, those lines are not judged, so the log of a release before v0.4.0, which has neither, passes. The test user-data of v0.4.0 has no `spec.api`, so its Nodes show `off`.
- **The expectations** are, for each Node: init accepted the configuration under the name `naru-<name>`, configured one interface (the judge requires no count of nameservers: Proxmox's network gives two, the QEMU network one, and `TestNode_*` assert that one as a check of their own), remounted the root read-only, started `mvmd`, `standin` and `registry`, and the stand-in logged the data disk mounted as ext4 (init logs nothing of that mount, so a gaon Node shows no such line and the judge does not ask for one of it); mvmd's socket accepts connections; the stand-in reached its peer. node-1 started `control` and skipped nothing; node-2 skipped `control` and never started it. With `-gaon` (`make judge-serial JUDGE_GAON=1 JUDGE_NARUCTL=<naructl> …`, `-naructl` naming a `naructl` binary, which prints the services with `naructl topology` and is the judge's only list of them, [ADR 0019](./adr/0019-the-gaon-topology-and-a-nodes-credential-mode-are-defined-once-in-naructls-layout-and-the-harness-reads-the-topology-from-naructl-topology.md)) the services expected are the ones of a Node of the test-only user-data, at this writing: `mvmd` and `registry` on both, `gaon-node-agent` on both, and on node-1 `etcd`, `gaon-apiserver`, `gaon-scheduler` and `gaon-controllers` started and nothing skipped, on node-2 those three skipped (init logs the skip of each control-plane service) and never started; the stand-in, the peer check and the probe are not expected, and each Node configures one interface, as a Proxmox Node does by default (a QEMU gaon cluster's node-1 configures two: `-node1-interfaces <n>`, which `make judge-serial` passes from `JUDGE_NODE1_INTERFACES`, sets node-1's count, and node-2's stays one). With `-gaon -pki` (`JUDGE_PKI=1`), node-1's log (a control-plane Node that issued its pairs from `spec.pki`, [ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)) is also judged on init's issuing: `certificate issued` for `apiserver`, `scheduler`, `controllers` and `agent`, and `authority written`, each before the first `started` line of a service, and no `certificate renewal failed`; a log that shows none fails. Without `-pki` no issuing is expected, and `-pki` and `-node1-interfaces` without `-gaon` exit 2. Without `-gaon`, node-1's log has each of the twelve `PROBE <check> ok` lines, `PROBE finished`, no `PROBE` line with `fail`, and init's restart of `mvmd`. Each is one line holding its fragments in order, which is the match `TestNode_*` make.
- **The log may be a raw capture.** The judge takes out terminal escape sequences and other control characters, ends a line at CR, LF or CR LF, accepts a capture that starts in the middle of a line, removes the markers of init's re-prints, and judges a line present once however many times a block repeats it. A log in which init dropped lines (`dropped` above 0) may lack an early line; the failure names the line, and the summary shows `dropped`.
- **The logs of a run of `make nodes`** are `build/nodes/node-<i>/console.log`; `naru-nodes -probe` runs the probe on node-1.

## Release assets

- **`make release`** (version from `git describe --tags --always`, or `VERSION=<name>`; it is also the version `naru-init` reports, [naru-init's version](#building-the-image)) builds the image and the disk and writes into `build/release/`: `naru-<version>.qcow2` (the boot disk, byte for byte `build/image/naru.qcow2`), `naru-upgrade-<version>.tar` (the upgrade bundle: `kernel.efi`, the release's `bzImage`, and `manifest.json` with the version and the kernel's size and SHA-256; a tar with no timestamps, byte-reproducible, [ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)), `naru-data-<version>.qcow2`, `naru-guest-<version>.json` (a copy of `guest.json`: the names and SHA-256 of the guest kernel and initrds inside the boot disk's initramfs), `naru-inputs-<version>.json` (the Firecracker digest the Nodes' mvmd configuration names and the reference of the test image, which [`naru-cluster`](./harness.md) reads), `naructl-<version>-linux-amd64` (the operator's tool, a static binary built by `make release` and the one that writes the two files below; [config.md](./config.md#operator-tooling-naructl)), `naru-node-1.test.yaml`, `naru-node-2.test.yaml` and `SHA256SUMS` of the eight. The two `.test.yaml` files are **test-only** user-data: they carry private keys, [below](#release-assets). `tooling/qemu/cmd/naru-release` is the command; it prints each asset's digest and size.
- **The data disk** is the one the tests give every Node, converted to qcow2: ext4 with the `verity` feature, label `NARUDATA`, 4096-byte blocks, **2 GiB virtual**, holding `inputs/` and nothing of a Node: the OCI registry directory and its TLS authority, `naru-probe` and `naru-registry`. 2 GiB is the size the QEMU tests run the probe's Machine on (a 256 MiB root disk and mvmd's state); the qcow2 file is about 63 MiB because the unused space is not stored. Both Nodes attach their own copy, found by label (`scsi1` on Proxmox), since mvmd's state is written to it.
- **Reproducibility.** The boot disk is the output of `make disk`, which `make image-repro` shows reproducible. A second `make release` of the same tree gives the same boot disk and the same guest manifest, and **not the same data disk and not the same user-data**. On the data disk the registry's TLS authority, certificate and key (`inputs/registry/ca.pem`, `cert.pem`, `key.pem`) are generated anew for every build, and they are the only files that differ. In `naru-node-<n>.test.yaml` the CA (certificate and key) and the bootstrap tokens are generated anew for every build, and the files under `/run/gaon/` and node-1's `spec.pki` are the only content that differs: the text of every other field is the same. The file system's UUID, directory hash seed and clock, and the files' times, are fixed. It holds for one host's `mke2fs`.
- **The test-only user-data** is the `naru.yaml` of a gaon Node, written by `naructl gen token` and `naructl gen node` (the code that writes the QEMU tests' gaon Nodes) with the Proxmox values as parameters, named `naru-node-<n>.test.yaml`: the `.test` says that it carries private keys and is for a throwaway deployment. node-1 is 192.168.0.40, MAC `02:00:00:00:03:E9`, `controlPlane: true`, and runs `mvmd`, `registry`, `etcd`, `gaon-apiserver`, `gaon-scheduler`, `gaon-controllers` and `gaon-node-agent`; node-2 is 192.168.0.61, MAC `02:00:00:00:03:F4`, and runs `mvmd`, `registry` and `gaon-node-agent`, and init logs that it skips the three control-plane services. The stand-ins (`standin`, `control`) and the probe are not in it: they check init and mvmd, which gaon's services now exercise on the same Nodes, and a deployed Node has no use for them; the QEMU tests that name them still run them. node-1 carries the CA in `spec.pki` and init issues the API server's serving certificate (naming 192.168.0.40), the scheduler's and the controllers' pairs at boot; both Nodes carry `ca.pem` and a bootstrap token in `spec.files` under `/run/gaon/`, and each Node Agent is issued its pair by a signing request. The CA comes from `naructl gen ca` in a directory removed when the build has written the files (and the Node Agents on both Nodes dial `https://192.168.0.40:6443`). mvmd's configuration is the file `/run/mvmd/config.json` in `spec.files`, with `network.ipv4_prefix` `10.200.1.0/24` for node-1 and `10.200.2.0/24` for node-2, and the gateway and resolver the first address of the prefix. Each file passes the other Node as a peer (`gen node --peer`): node-1 routes `10.200.2.0/24` via 192.168.0.61 and node-2 routes `10.200.1.0/24` via 192.168.0.40 in `spec.network.routes`, and each lists the other's prefix in mvmd's `network.no_masquerade` ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)). The gateway 192.168.0.1 and the resolvers 1.1.1.1 and 8.8.8.8 are not in the user-data: they are Proxmox's network-config, which the cloud-init drive of each VM provides. The data disk's `inputs/` paths in the files are the ones the tests use, so the files and the disk go together: the registry's image digest in the yaml is the one the data disk's registry serves, and the Node Agent of each Node reaches the API server on node-1's address with no host forward.
- **Keys the release publishes.** The release's test CA's private key **is published**, in `naru-node-1.test.yaml`: `spec.pki` carries the authority with its `key`, and init writes it to `/run/gaon/ca.key` (`0600`) for the controllers to sign with ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md), which supersedes ADR 0015 item 3's "no CA key"). The CA is made by `naructl gen ca` in a temporary directory during `make release`, which is removed; it is generated for each build, is trusted only by that deployment, and the release notes mark it test-only like the registry's authority. An operator's CA is never written into any asset. Both files hold a bootstrap token (`/run/gaon/bootstrap-token`, `0600`) and node-1's also the list of both (`/run/gaon/bootstrap-tokens`). node-1's pairs for the API server, scheduler and controllers are issued by init on the Node, so no entry of `spec.files` holds a private key; a Node Agent's key is made on its Node by the agent. No asset holds a client pair for an operator; a deployer makes a CA, user-data and a client pair of their own with the release's `naructl` ([config.md](./config.md#operator-tooling-naructl)). The data disk holds the registry's authority key (`inputs/registry/key.pem`), as before. Each yaml is written with mode `0600`. All of these are readable by anyone who can read the public GitHub Release; the files are for a deployment that nothing depends on.
- **What the build checks.** `make release` fails unless every service binary of each yaml is on the data disk (read with `debugfs`) or installed by `image/initramfs/initramfs.list`. The tests of the release parse each file with `naru-init -validate`, init's own parser, and check the addresses, the roles, mvmd's prefix and the services, that the serving certificate init will issue for the API server names 192.168.0.40, that node-1's authority is the `ca.pem` of both files and its key is the CA's, that both Nodes carry a token of gaon's form and node-1 lists both, and that node-2 carries no authority and no key.

## Release workflow

[`.github/workflows/release.yml`](../../.github/workflows/release.yml) publishes the release assets as a GitHub Release (the owner's decision 5 on garamsh/naru#14: distribution through a naru GitHub Release, which aurora pins by URL and digest).

- **Trigger.** A push of a tag `v*`, or `workflow_dispatch` with the `tag` of an existing tag, to repeat a run. A repeat edits the release of that tag and replaces its files. A tag whose name contains `-` (`v0.1.0-rc.1`) is published with `--prerelease --latest=false` on both the create and the edit path, so it is a pre-release and never the latest release; any other tag is published as before ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)).
- **Build job** (`ubuntu-24.04`, read-only token). It checks out the tag, records the commit, installs what [the host needs](#what-the-host-needs) lists for the build, the disk and the release (the kernel's build dependencies, e2fsprogs with `mke2fs -d` and `debugfs`, dosfstools, gdisk and qemu-utils; the static mke2fs build needs only the compiler, `libc.a` and `strip` that `build-essential` brings), fetches the pinned mvmd checkout alone (`image/mvmd-checkout.sh build/initramfs/mvmd`), installs the Rust toolchain that mvmd's `rust-toolchain.toml` names with the runner's rustup, then runs `make release VERSION=<tag>`, which builds the image, so mvmd's Rust initrds are built after the toolchain is installed. The kernel builds clear `MAKEFLAGS`, so a `VERSION` given to `make` does not reach the kernel's own make. It boots no QEMU: `make test-qemu` is not part of it. It uploads `build/release/` as a workflow artifact.
- **Publish job** (`contents: write`, the only one). It checks the nine files against `SHA256SUMS`, writes the release notes and runs `gh release create` (or `edit` and `upload --clobber` when the release exists), with the `gh` the runner has. The notes name the commit built, say what the release carries beyond v0.3.0 (the Node API, `naructl` as its client, `naru-init` reporting the tag) and that the test user-data has no `spec.api`, with the commands that enable it (`naructl gen api-ca`, `gen node` from the same CA directory, `gen api-client`; v0.3.0-form user-data boots unchanged and logs that the Node API is off), say that the data disk carries a test-only registry TLS authority including its private key (trusted only by the mvmd on the Node; the registry listens on 127.0.0.1), say that the two `.test.yaml` files are test-only and carry the private keys of gaon's serving and client pairs (the CA's key is published nowhere), say that the data disk is not byte-reproducible and why, and state how the release relates to a workstation build. The notes end with each asset's name and SHA-256, one line per asset, taken from the `SHA256SUMS` of the same build that is attached beside them (garamsh/aurora#749, criterion 3), so that a consumer pins a digest without downloading the file.
- **Release bytes and a workstation build.** The boot disk is `make disk`'s output, shown byte-identical across two clean builds on one workstation by `make image-repro`. The release's boot disk is built on the runner with Ubuntu 24.04's compiler and tools; its equality with a workstation's build of the same commit has not been checked, so aurora pins the digest of the published asset. The data disk differs between any two builds (see Release assets).
- **Caches.** The Go module cache, keyed on every `go.sum`, which the checksum database makes content-addressed. Nothing else is cached: the kernels, the initramfs, the guest initrds and the disks are built from the pinned sources on every run.
- **Pins and movers.** Each action is pinned by full commit SHA, with its version in a comment: `actions/checkout` v7.0.1, `actions/setup-go` v7.0.0, `actions/upload-artifact` v7.0.2, `actions/download-artifact` v8.0.2. The PM moves them, in a pull request that reads the action's current release and the GitHub Advisory Database, when an advisory is published for one and at each Go minor release; no bot proposes the bumps. The runner label `ubuntu-24.04` cannot be pinned: it names its version, the first step of the build job prints the image version, OS release and compiler it resolved to, and the PM moves it when GitHub retires the label. The Rust channel is mvmd's, pinned in its checkout; the Ubuntu packages are not pinned, and the run records only the compiler version and `mke2fs`'s.
- **Not verified before merge.** The workflow has not run; its run time is not measured. The kernel build and mvmd's two guest initrds (each built twice by mvmd's Makefile) are the long steps.

## What the host needs

- Linux x86_64 with `/dev/kvm` readable and writable by the user. The Nodes run Firecracker inside QEMU, which needs nested KVM: `/sys/module/kvm_intel/parameters/nested` or `/sys/module/kvm_amd/parameters/nested` reads `Y` or `1`. The tests were run on a host where `kvm_amd` reads `1`.
- To build: bash, curl, tar, xz, gzip, git, file, gcc and the static C library (`libc.a`, in libc6-dev), strip (binutils), make, flex, bison, bc, perl, and the libelf and OpenSSL headers the kernel build asks for; and Go at the version `go.work` names (1.26, which the probe's use of mvmd's `lib/runtimeapi` needs), which Go's toolchain download supplies. `make image` also needs what mvmd's `make guest-initrd converter-initrd` needs: the Rust toolchain that mvmd's `rust-toolchain.toml` names, installed by rustup for the user.
- To build the disk: `/sbin/mkfs.fat` (dosfstools), `/sbin/sgdisk` (gdisk) and `qemu-img`. `make release` also needs `/sbin/debugfs`. To boot it: the 4 MiB OVMF files named above (the Debian `ovmf` package).
- To boot: `qemu-system-x86_64` (with the `ide-cd`, `scsi-hd`, `virtio-scsi-pci` and `virtio-net-pci` devices), and `/sbin/mkfs.ext4` (e2fsprogs 1.43 or later for `-d`), which makes the data disk. The mkfs.ext4 mvmd runs is the image's own and needs nothing of the host.
- Network access for the first build: cdn.kernel.org, github.com, and the Go module proxy.

## Pinned dependencies

`init/go.mod` is covered in [init.md](./init.md). `tooling/qemu/go.mod`, `tooling/probe/go.mod` and `tooling/disk/go.mod` pin their modules (`tooling/disk` requires only `github.com/stretchr/testify`, at the version `tooling/qemu` pins); `go.sum` and the Go checksum database fix what each version means. The PM moves them: the PM reviews the pins when an advisory is published for one of them and at each Go minor release, and bumps the module in a pull request. No dependency bot is configured (`.github/` holds no `dependabot.yml`). The probe's `github.com/garamsh/mvmd/lib/runtimeapi` version is a pseudo-version of mvmd commit `d189133bba8d842d2bcb20046f39fe03161efeb1`, the commit `MVMD_COMMIT` names in [image/initramfs/pin.env](../../image/initramfs/pin.env), and moves with it in the pull request that moves the pin; the restart test runs this probe against the mvmd of the pinned commit.

## Open questions

- **Installer.** How an image reaches a Node's disk is not decided.
- **A/B upgrade.** The disk, the bundle and the boot behaviour are decided ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)); the writer of the trial slot and of the boot entry, the health decision, the promotion call and how a bundle reaches a Node are not.
- **Signing.** How an image, a kernel and a configuration are signed and verified is not decided.
- **Disk layout.** The boot disk's slots are decided (ADR 0020); how an installed Node's other disks are laid out, and where the system lives other than as an initramfs, are not decided. A disk of v0.4.0 or earlier is recreated once.
- **Memory of the guest files.** They are in the tmpfs root, about 20.3 MiB ([ADR 0010](./adr/0010-the-guest-kernel-and-initrds-are-image-components-built-at-the-pinned-mvmd-commit.md)); whether a Node should hold them elsewhere is not decided.
- **Selecting a guest kernel.** mvmd offers every kernel of `guest.json` to a Machine by name (garamsh/mvmd#364); no gaon Machine names one yet (garamsh/gaon#59), and no test in this repository creates a Machine with a kernel other than the default.
- **How the other mvmd obligations are met.** The capabilities' grant and the nftables ownership are not decided; they wait under [boundaries.md](./boundaries.md) §Open questions. The cgroup placement of supervisors is decided: [init.md](./init.md) §What init requires of mvmd's placement.
