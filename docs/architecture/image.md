# Image

What the P0 image holds, where its inputs come from, and how a Node boots it.

Claims about garamsh/mvmd hold at commit `cfe57fb9f9bfbd7ec8e24b54915656030f1e2b64`; they promise nothing about later versions.

## Current decisions

- **P0 is done when a QEMU VM boots the image and init, as PID 1, starts and supervises the services the configuration names.** The services are mvmd, gaon's Node Agent and optionally gaon's control plane.
- **One boot form.** The kernel and initramfs boot from a UEFI disk image, `naru.img`, which is the form Proxmox attaches ([ADR 0007](./adr/0007-the-proxmox-boot-form-is-a-uefi-disk-image-whose-efi-stub-kernel-loads-the-initramfs-from-the-esp.md)); the QEMU tests boot it, and none passes `-kernel` or `-initrd`. There is no installer and no disk layout for the system. The system is the initramfs, which init copies to a tmpfs root at start and remounts read-only before it starts the first service ([Booting a Node](#booting-a-node)).
- **Three drives are attached.** The NoCloud drive (label `cidata`) carries the Node's configuration and network ([config.md](./config.md), [ADR 0008](./adr/0008-a-node-reads-its-configuration-and-network-from-a-cloud-init-nocloud-drive.md)). The boot disk is `naru.img`. The data disk holds mvmd's state directory and the test inputs, formatted ext4 with the `verity` feature.
- **Host kernel.** kernel.org longterm 6.18.63, built by naru from the release tarball with naru's configuration, the version and the tarball's sha256 pinned in `image/kernel/`. It meets the conditions table of [ADR 0006](./adr/0006-the-host-kernel-is-built-from-the-pinned-longterm-6-18-tarball-and-the-image-inputs-live-in-image.md).
- **Non-Go inputs** are `image/kernel/` (configuration, pin and the build script), `image/initramfs/` (pin, the entry list and the build script) and `image/disk/` (the disk and partition GUIDs and the build script); `image/build.env` fixes the environment both scripts build in.
- **Binaries in the initramfs:**
  - naru-init as `/init`.
  - mvmd and mvmd-supervisor, built with Go (`CGO_ENABLED=0`) from the mvmd commit pinned in `image/initramfs/pin.env`, `cfe57fb9f9bfbd7ec8e24b54915656030f1e2b64`, fetched with git into the build directory.
  - Firecracker, from the release that mvmd's `tooling/firecracker/fetch.sh` pins, verified by that pin. The script is run from the pinned checkout.
  - `naru-standin`, the stand-in service of the P0 test (see [Booting a Node](#booting-a-node)). gaon's binaries are built from a pinned gaon commit once gaon ships them, and arrive by a pin bump.
  - Nothing is built or run in a container. There is no shell and no busybox.
- **Not in the P0 image:** the guest kernel, and mvmd's guest-agent and converter initrds. They are needed only to run a Machine, and the tests put them on the data disk ([Booting a Node](#booting-a-node)).
- **Forwarding is set by init**, not by mvmd ([config.md](./config.md)).

## Building the image

- `make image` writes `build/image/bzImage` and `build/image/initramfs.cpio.gz`, and for the tests of Machines `vmlinux` (the guest kernel) and `inputs.env` (mvmd's names for it and for Firecracker, with their digests). `build/` is not tracked.
- **The kernel.** `image/kernel/build.sh` downloads the pinned tarball, fails unless its SHA-256 is the pinned one, merges `image/kernel/naru.config` over the x86_64 `defconfig` with the kernel's `merge_config.sh`, runs `olddefconfig`, and then fails unless every line of `image/kernel/required.txt` matches a line of the final `.config`: kconfig drops an option whose dependencies are unmet without failing, so the file the build uses is what is checked. The unpacked source and the object directory are emptied before each build.
- **The initramfs.** `image/initramfs/build.sh` builds the programs, fails unless each is a static executable, and writes the archive with the kernel's own `usr/gen_init_cpio`, compiled from the pinned tarball. The archive is newc, in the order of `image/initramfs/initramfs.list`, every entry owned by 0:0 and stamped with `SOURCE_DATE_EPOCH` from `image/build.env`, then compressed with `gzip -9n`.
- **The disk.** `make disk` (which runs `make image` first) writes `build/image/naru.img` and `build/image/naru.qcow2` with `image/disk/build.sh` and `tooling/disk`. `naru.img` is a raw GPT disk of 1 MiB, one EFI system partition of at least 64 MiB, and 1 MiB. The partition is FAT32, label `NARUESP`, and holds the kernel as `\EFI\BOOT\BOOTX64.EFI` and the initramfs as `\INITRD.GZ`. `mkfs.fat` makes the empty volume, `sgdisk` the table, and `tooling/disk/internal/fat` writes the two files; the builder reads them back and fails unless they are the inputs. `naru.qcow2` is `naru.img` converted by `qemu-img convert -O qcow2`, for Proxmox's `import_from`.
- **How the initramfs reaches the kernel.** The kernel is built with the EFI stub and a built-in command line, `console=ttyS0 panic=-1 loglevel=4 initrd=/INITRD.GZ`; the stub loads `\INITRD.GZ` from the volume it was started from. The initramfs is not embedded, so the bzImage does not depend on it. `image/kernel/required.txt` fails the kernel build if any of these options is missing from the final configuration. The reasons and the kernel documents are in ADR 0007.
- **Reproducibility.** `make image-repro` builds twice from empty build directories, the disk included, and fails unless `bzImage`, `initramfs.cpio.gz`, `naru.img` and `naru.qcow2` have equal SHA-256. It holds for one host toolchain: the kernel build records the compiler's version, so a host with another gcc or Go builds other bytes.
- **Who moves the pins.** The kernel's pin is moved by the PM ([image/kernel/pin.env](../../image/kernel/pin.env)), and so is mvmd's ([image/initramfs/pin.env](../../image/initramfs/pin.env)); both name how.

## Booting a Node

- **Boot N Nodes: `make nodes N=3`** (default 2, at least 2). It builds the image, the disk and the guest inputs, then boots N Nodes of the image under QEMU on one network and keeps them up until interrupted. Each Node has its own disks and console log under `build/nodes/node-<i>/`; the command prints a line per Node once that Node's stand-in has dialled its peer across the network. `tooling/qemu/cmd/naru-nodes` is the command.
- **Run the test: `make test-qemu`.** It builds the image, the guest inputs and the disk, boots Nodes as the tests need, reads their serial consoles, and fails, never skips, when no test ran. The tests are `TestNode_*` in `tooling/qemu/tests`, built with `-tags qemu_real`. `make guest-inputs` alone builds the two guest initrds into `build/guest`.
- **QEMU** runs as the user with `-enable-kvm -cpu host`, laid out as a Proxmox guest is: the q35 machine under OVMF (`/usr/share/OVMF/OVMF_CODE_4M.fd` as read-only pflash unit 0, a per-Node copy of `/usr/share/OVMF/OVMF_VARS_4M.fd` as unit 1), a `virtio-scsi-pci` controller with `naru.img` (read-only, `bootindex=0`) and the data disk as `scsi-hd`, the NoCloud drive as a read-only `ide-cd` on the AHCI bus, and one virtio NIC; nothing needs root. There is no `-kernel`, `-initrd`, `-append` or `ip=`. The kernel's built-in command line carries `loglevel=4`, so kernel info messages do not split init's console lines, which the tests read; no test asserts a kernel line. A missing `naru.img` fails before QEMU starts, naming `make disk`.
- **The network** is QEMU's `-netdev socket` over a multicast group on the loopback, with a group port drawn at random per cluster so clusters on one host do not share a network. Each Node has its own MAC, `02:00:00:00:<i high byte>:<i low byte>`, and its `network-config` gives it `10.78.0.<i>/24` (the release's example for Proxmox gives other values, [Release assets](#release-assets)) on `eth0` with `10.78.0.254` as gateway and resolver (no machine has that address), which init applies before any service ([config.md](./config.md)). Machine networks are separate: Node i gives mvmd `network.ipv4_prefix` `10.77.<i>.0/24`, and `spec.network.forwarding` lists `ipv4`.
- **The drives** are built by `tooling/qemu/internal/node`. The NoCloud drive is a 4 MiB file, as Proxmox's is, holding an ISO 9660 volume labelled `cidata` with `user-data` (the Node's `naru.yaml`: its name, its services and the file `/run/mvmd/config.json`, mode `0600`, which is mvmd's JSON configuration), `meta-data` (`instance-id`) and `network-config`. `tooling/qemu/internal/iso9660` writes it, with a primary and a Joliet tree because the kernel reads `user-data` through Joliet; no genisoimage, xorriso or root is needed. The data disk is made with `/sbin/mkfs.ext4 -d`, which fills an ext4 image from a directory without mounting it, owned by root: labelled `NARUDATA`, 2 GiB sparse, with the `verity` feature, holding only the test inputs under `inputs/`, so it is the same for every Node; `naru.yaml` mounts it at `/var/lib/mvmd`, and the mvmd service's `-config` names the file init wrote under `/run/mvmd`, so init knows nothing of mvmd's configuration. The data disk is where the inputs go because init mounts the NoCloud drive and that disk and no other.
- **The inputs** are staged by `tooling/qemu/internal/fixture` from build outputs and hard-linked into each data disk: the guest kernel and the two guest initrds, which `image/guest/build.sh` builds from the pinned mvmd checkout and verifies against the digests of `image/guest/pin.env`; the test-only `naru-registry` and `naru-probe`; and an OCI registry directory holding one image and its TLS authority. They are test inputs and not image contents.
- **The services** of every Node, in order, are `mvmd` (the Firecracker driver, `SSL_CERT_FILE` naming the registry's authority); `registry`, which serves the image over TLS on `127.0.0.1:5000` and is how mvmd pulls; `standin`, which logs the file system type of `/var/lib/mvmd`, dials mvmd's Unix socket until it accepts, and dials the stand-in of the next Node (Node i dials Node i+1, the last dials the first) on TCP 7000 until it accepts; and `control`, a stand-in marked `controlPlane: true`. Node 1 has `spec.controlPlane: true`, so only it starts `control`; every other Node's init logs that it skips it. Node 1 also runs `probe` in the restart test.
- **What the tests assert**, each on the console. `TestNode_UEFIDiskBootsToInitAndStartsItsServices`: on each of two Nodes init's `configuration accepted` with `node=naru-<name>`, `network configured` with one interface and one nameserver, the data disk mounted, and `started` for `mvmd` and `standin`. `TestNode_ABrokenNetworkConfigRefusesTheBoot`: a Node whose `network-config` address is not an address logs `boot refused; no further service will start` and starts no service. `TestNode_TwoNodesRunTheirServicesAndReachEachOther`: on each of two Nodes init's `configuration accepted`, `network configured`, `started` for `mvmd`, `registry` and `standin`, the data disk mounted as ext4, `socket accepts connections` for `/run/mvmd.sock`, and `peer accepts connections`, which is the check across the network, over the addresses of the Nodes' `network-config`. `TestNode_ControlPlaneServicesStartOnlyOnTheControlPlaneNode`: node-1 logs `started` for `control`; node-2 logs the skip and never `started`. `TestNode_MachineSurvivesMvmdRestart`: the probe, a static Go program using mvmd's `lib/runtimeapi`, arms the fencing deadline, pulls the image, starts a Machine, waits until mvmd reports it running, kills mvmd, and checks that init restarted mvmd, that the supervisor is the same live process, and that mvmd reports the Machine running again. It prints `PROBE <check> ok|fail <detail>` and `PROBE finished`; the test fails on any `fail`, on a missing line, and after a timeout. `TestNode_AConsoleReaderThatAttachesLateSeesTheWholeLog`: node-1's console shows init's first re-print, `NARU-LOG-BEGIN seq=1` to `NARU-LOG-END seq=1`, and the block holds the line `configuration accepted` and the line that started `mvmd` ([init.md](./init.md)). Waits are on conditions, never on fixed sleeps. The expectations of the first four tests and of the restart test are one list, `tooling/qemu/internal/judge`, which `TestNode_*` wait for on a live console and `make judge-serial` checks on a captured one ([Judging serial logs](#judging-serial-logs)).
- **What the image needed for this**, found by booting it: the kernel option `CONFIG_CFS_BANDWIDTH` (mvmd writes `cpu.max`), and init leaving the initramfs's rootfs for a tmpfs copy of it before it mounts anything (`linux.LeaveRootfs`), because the kernel refuses `pivot_root` from the rootfs and mvmd's supervisor pivots into a root of its own for each VMM. Init then remounts that copy read-only once its mount points exist (`Host.SealRoot`), and every test passes with the root read-only.
- **mvmd runs `mkfs.ext4`** to format a Machine's disk, and the image has none. The test stages the host's `mke2fs`, its loader and its libraries on the data disk and a static launcher, `tooling/qemu/cmd/naru-mkfs`, as `mkfs.ext4`, which `disk.mkfs` names. A Node that is not a test needs a statically linked `mkfs.ext4` in its image; which is not decided.

## Judging serial logs

- **`make judge-serial NODE1=<log> NODE2=<log>`** reads the serial logs of two Nodes, node-1 first, and exits 0 only when both show what the QEMU tests assert. `tooling/qemu/cmd/naru-judge` is the command. It exits 1 and prints a `FAIL <node>: <expectation>: no line with <fragments>` line for each expectation not met, and 2 when a log cannot be read or an argument is missing. It prints per Node the log's size, the number of re-printed blocks, the largest `dropped` a block reported, and how many expectations were met of how many.
- **The expectations** are, for each Node: init accepted the configuration under the name `naru-<name>`, configured one interface and one nameserver, remounted the root read-only, mounted the data disk as ext4, started `mvmd`, `standin` and `registry`; mvmd's socket accepts connections; the stand-in reached its peer. node-1 started `control` and skipped nothing; node-2 skipped `control` and never started it. node-1's log has each of the twelve `PROBE <check> ok` lines, `PROBE finished`, no `PROBE` line with `fail`, and init's restart of `mvmd`. Each is one line holding its fragments in order, which is the match `TestNode_*` make.
- **The log may be a raw capture.** The judge takes out terminal escape sequences and other control characters, ends a line at CR, LF or CR LF, accepts a capture that starts in the middle of a line, removes the markers of init's re-prints, and judges a line present once however many times a block repeats it. A log in which init dropped lines (`dropped` above 0) may lack an early line; the failure names the line, and the summary shows `dropped`.
- **The logs of a run of `make nodes`** are `build/nodes/node-<i>/console.log`; `naru-nodes -probe` runs the probe on node-1.

## Release assets

- **`make release`** (version from `git describe --tags --always`, or `VERSION=<name>`) builds the disk and the guest inputs and writes into `build/release/`: `naru-<version>.qcow2` (the boot disk, byte for byte `build/image/naru.qcow2`), `naru-data-<version>.qcow2`, `naru-node-1.yaml`, `naru-node-2.yaml` and `SHA256SUMS` of the four. `tooling/qemu/cmd/naru-release` is the command; it prints each asset's digest and size.
- **The data disk** is the one the tests give every Node, converted to qcow2: ext4 with the `verity` feature, label `NARUDATA`, 4096-byte blocks, **2 GiB virtual**, holding `inputs/` and nothing of a Node: the guest kernel and the two guest initrds, the OCI registry directory and its TLS authority, `naru-probe`, `naru-registry`, and `mkfs.ext4` with the staged `mke2fs`, loader and libraries. 2 GiB is the size the QEMU tests run the probe's Machine on (a 256 MiB root disk and mvmd's state); the qcow2 file is about 63 MiB because the unused space is not stored. Both Nodes attach their own copy, found by label (`scsi1` on Proxmox), since mvmd's state is written to it.
- **Reproducibility.** The boot disk is the output of `make disk`, which `make image-repro` shows reproducible. A second `make release` of the same tree gives the same boot disk and the same `naru-node-*.yaml`, and **not the same data disk**: the registry's TLS authority, certificate and key (`inputs/registry/ca.pem`, `cert.pem`, `key.pem`) are generated anew for every build, and they are the only files that differ. The file system's UUID, directory hash seed and clock, and the files' times, are fixed. It holds for one host's `mke2fs`.
- **The example user-data** is the `naru.yaml` the tests give a Node, made by the same code (`node.Config.NaruYAML`) with the Proxmox values as parameters. node-1 is 192.168.0.40, MAC `02:00:00:00:03:E9`, `controlPlane: true`, runs `control` and the probe; node-2 is 192.168.0.61, MAC `02:00:00:00:03:F4`. Each stand-in listens on its Node's address and dials the other's on TCP 7000. mvmd's configuration is the file `/run/mvmd/config.json` in `spec.files`, with `network.ipv4_prefix` `10.200.1.0/24` for node-1 and `10.200.2.0/24` for node-2, and the gateway and resolver the first address of the prefix. The gateway 192.168.0.1 and the resolvers 1.1.1.1 and 8.8.8.8 are not in the user-data: they are Proxmox's network-config, which the cloud-init drive of each VM provides. The data disk's `inputs/` paths in the files are the ones the tests use, so the files and the disk go together: the registry's image digest in `naru-node-1.yaml` is the one the data disk's registry serves.
- **What the build checks.** `make release` fails unless every service binary of each yaml is on the data disk (read with `debugfs`) or installed by `image/initramfs/initramfs.list`. The tests of the release parse each file with `naru-init -validate`, init's own parser, and check the addresses, the roles, mvmd's prefix and the services against the QEMU Nodes' file.

## What the host needs

- Linux x86_64 with `/dev/kvm` readable and writable by the user. The Nodes run Firecracker inside QEMU, which needs nested KVM: `/sys/module/kvm_intel/parameters/nested` or `/sys/module/kvm_amd/parameters/nested` reads `Y` or `1`. The tests were run on a host where `kvm_amd` reads `1`.
- To build: bash, curl, tar, xz, gzip, git, file, gcc, make, flex, bison, bc, perl, and the libelf and OpenSSL headers the kernel build asks for; zstd, which mvmd's fetch.sh unpacks the guest kernel with; and Go at the version `go.work` names (1.26, which the probe's use of mvmd's `lib/runtimeapi` needs), which Go's toolchain download supplies. `make guest-inputs` also needs what mvmd's `make guest-initrd converter-initrd` needs: the Rust toolchain that mvmd's `rust-toolchain.toml` names, installed by rustup for the user.
- To build the disk: `/sbin/mkfs.fat` (dosfstools), `/sbin/sgdisk` (gdisk) and `qemu-img`. `make release` also needs `/sbin/debugfs`. To boot it: the 4 MiB OVMF files named above (the Debian `ovmf` package).
- To boot: `qemu-system-x86_64` (with the `ide-cd`, `scsi-hd`, `virtio-scsi-pci` and `virtio-net-pci` devices), `/sbin/mkfs.ext4` (e2fsprogs 1.43 or later for `-d`), and a dynamically linked host `mke2fs` with `ldd` and its loader, which the test stages for mvmd.
- Network access for the first build: cdn.kernel.org, github.com, and the Go module proxy.

## Pinned dependencies

`init/go.mod` is covered in [init.md](./init.md). `tooling/qemu/go.mod`, `tooling/probe/go.mod` and `tooling/disk/go.mod` pin their modules (`tooling/disk` requires only `github.com/stretchr/testify`, at the version `tooling/qemu` pins); `go.sum` and the Go checksum database fix what each version means. The PM moves them: the PM reviews the pins when an advisory is published for one of them and at each Go minor release, and bumps the module in a pull request. No dependency bot is configured (`.github/` holds no `dependabot.yml`). The probe's `github.com/garamsh/mvmd/lib/runtimeapi` version is a pseudo-version of the commit `MVMD_COMMIT` names in [image/initramfs/pin.env](../../image/initramfs/pin.env), and moves with it.

## Open questions

- **Installer.** How an image reaches a Node's disk is not decided.
- **A/B upgrade.** How a Node upgrades and rolls back is not decided.
- **Signing.** How an image, a kernel and a configuration are signed and verified is not decided.
- **Disk layout.** Partitions of an installed Node, and where the system lives other than as an initramfs, are not decided.
- **The guest artifacts.** Which guest kernel and which guest-agent and converter initrds a Node carries is not decided; P0 omits them from the image, and the tests supply them.
- **mkfs.ext4 in the image.** mvmd needs one to format a Machine's disk; the test ships the host's.
- **How the other mvmd obligations are met.** The capabilities' grant and the nftables ownership are not decided; they wait under [boundaries.md](./boundaries.md) §Open questions. The cgroup placement of supervisors is decided: [init.md](./init.md) §What init requires of mvmd's placement.
