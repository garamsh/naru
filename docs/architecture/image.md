# Image

What the P0 image holds, where its inputs come from, and how a Node boots it.

Claims about garamsh/mvmd hold at commit `b1a60cd649673a6db5fa72ca8cc23f088fd83639` (the PM moved the pin there for aurora#811 from `191326aca748a0e6e365578016ab87455107164e`, which it had for garamsh/naru#110; the claims about mvmd were read at `d189133bba8d842d2bcb20046f39fe03161efeb1` and not read again at the new commit), and claims about garamsh/gaon at `c2b42f91724cae39a4f6824517c278150cf4695f`; they promise nothing about later versions, except that the gaon flags of the control plane (`--etcd-*-file`, the `https://` endpoints) were read at `f431811565beb905ac859a78b126a47a734fdb27`, an ancestor of the pin `d69c5b0fdf05d5d8905fadbe78437890b22e69a7` ([ADR 0024](./adr/0024-the-control-plane-is-three-etcd-members-with-tls-on-both-ports-and-a-virtual-address-held-by-naru-vip-behind-a-fence-on-etcds-ports.md)). Claims about etcd hold for etcd-io/etcd v3.6.16, commit `0b065e61c679ea81f6862bb24c9815f7fc673966`. The claims about the QEMU tests, the release's user-data and the keys it publishes were checked against the code and the runs of this branch, not against the pinned commits alone.

## Current decisions

- **P0 is done when a QEMU VM boots the image and init, as PID 1, starts and supervises the services the configuration names.** The services are mvmd, gaon's Node Agent and optionally gaon's control plane.
- **One boot form.** The kernel and initramfs boot from a UEFI disk image, `naru.img`, which is the form Proxmox attaches ([ADR 0007](./adr/0007-the-proxmox-boot-form-is-a-uefi-disk-image-whose-efi-stub-kernel-loads-the-initramfs-from-the-esp.md)); the QEMU tests boot it, and none passes `-kernel` or `-initrd`. The disk has two slots for a kernel with its initramfs embedded and a trial slot is reached once by `BootNext` ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)). There is no installer. The system is the initramfs, which init copies to a tmpfs root at start and remounts read-only before it starts the first service ([Booting a Node](#booting-a-node)).
- **Three drives are attached.** The NoCloud drive (label `cidata`) carries the Node's configuration and network ([config.md](./config.md), [ADR 0008](./adr/0008-a-node-reads-its-configuration-and-network-from-a-cloud-init-nocloud-drive.md)). The boot disk is `naru.img`. The data disk holds mvmd's state directory, etcd's data directory and the test inputs, formatted ext4 with the `verity` feature.
- **Host kernel.** kernel.org longterm 6.18.63, built by naru from the release tarball with naru's configuration, the version and the tarball's sha256 pinned in `image/pkgs/kernel/`. It meets the conditions table of [ADR 0006](./adr/0006-the-host-kernel-is-built-from-the-pinned-longterm-6-18-tarball-and-the-image-inputs-live-in-image.md). It has `CONFIG_WIREGUARD=y` and `CONFIG_NFT_COUNTER=y` for hostd's tunnel and its counted rules ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md)); not verified by a build when this was written.
- **Guest kernel and initrds.** The image carries the guest kernel `naru`, the Guest Agent's initrd and the converter's initrd, which a Machine boots on, under `/usr/lib/naru/guest/` (`kernels/naru/vmlinux`, `guest-initrd.cpio`, `converter-initrd.cpio`), with `guest.json` there naming each by its path and SHA-256 ([ADR 0010](./adr/0010-the-guest-kernel-and-initrds-are-image-components-built-at-the-pinned-mvmd-commit.md)). The kernel is built by naru from the host kernel's pinned tarball with its own configuration; the initrds are built by mvmd's Makefile at the pinned commit and checked against `image/pkgs/guest-initrds/pin.env`. mvmd's configuration names these paths and digests, read from `guest.json`.
- **The guest form.** The image also carries a Node's own kernel and initramfs as a boot set mvmd knows by name, `naru-node` ([ADR 0034](./adr/0034-a-node-boots-as-a-microvm-from-a-guest-kernel-and-initramfs-the-image-carries-as-a-boot-set.md)): `/usr/lib/naru/guest/boot-sets/naru-node/vmlinux`, a PVH kernel for Firecracker and Cloud Hypervisor (virtio over PCI and MMIO, no UEFI, no ESP, no built-in command line), and `initrd.cpio.gz`, the Node's initramfs, which has a list of its own (`image/pkgs/initramfs-node/initramfs.list`, [ADR 0054](./adr/0054-the-image-is-split-into-image-host-and-image-node-with-what-both-carry-in-image-common-and-the-nodes-initramfs-has-its-own-list.md)). `boot-sets.json` beside them names both by path and SHA-256, in the shape of the `boot_sets` of mvmd's driver configuration. It is a file of its own and not a key of `guest.json`, whose readers refuse a key they do not know.
- **Non-Go inputs** are under `image/`: `image/pkgs/` holds every package, each a Dockerfile and a `pin.env` (a pin file, a kernel configuration, a `required.txt` or an entry list where the package has one) and the bake graph that ties them together ([ADR 0075](./adr/0075-the-images-packages-are-built-by-buildkit-from-one-bake-graph-against-a-musl-toolchain-built-from-source-and-assembled-by-tooling-disk.md), [The package graph](#the-package-graph)); `image/host/disk/` holds the disk and partition GUIDs and the script that writes the disk with `tooling/disk`; `image/builder/` is the builder ([The builder](#the-builder)); and `image/build.env` and `image/repro.sh` sit directly under `image/` ([ADR 0054](./adr/0054-the-image-is-split-into-image-host-and-image-node-with-what-both-carry-in-image-common-and-the-nodes-initramfs-has-its-own-list.md), whose folders `image/host/`, `image/node/` and `image/common/` the packages replaced).
  - The packages: `toolchain`, `util-linux`, `e2fsprogs`, `xfsprogs` with `liburcu` and `libinih`, `nftables` with `libmnl`, `libnftnl` and `jansson`, `cacert`, `libseccomp`, the Go programs (`naru`, `extension`, `gaon`, `mvmd`, `etcd`, `kubernetes`, `containerd`, `cni`, `ecr-login` and `rolesanywhere`), the kernels (`kernel-host`, `kernel-node`, `kernel-guest-naru` and the `bzImage` packages), the guest initrds (`guest-initrds`) and the two initramfs archives (`initramfs-host`, `initramfs-node`). The kernel's pin and `naru.config` are in `image/pkgs/kernel/`, with the host's `required.txt` in `host/`, the Node's overlay in `node/` and the guest kernel's in `guest-naru/`.
- **The host image carries the Node runtime.** The boot disk's own Node form (ADRs 0007 and 0031) runs from the host initramfs, so the host initramfs list (`image/pkgs/initramfs-host/initramfs.list`) names Kubernetes, containerd, runc, the CNI plugins and etcd as well. What would remove them is recorded in ADR 0054.
- **Binaries in the initramfs:**
  - naru-init as `/init`: `host/cmd/naru-init` in the host image, and `node/cmd/naru-init` in the node initrd ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md)).
  - `naru-signer` and `naru-orchd` are not in the initramfs: they are in the `naru-orch` system extension (the item after the next) ([ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md), which supersedes [ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md) item 1's placement).
  - mvmd and mvmd-supervisor, built with Go (`CGO_ENABLED=0`) from the mvmd commit pinned in `image/pkgs/mvmd/pin.env`, `b1a60cd649673a6db5fa72ca8cc23f088fd83639`, fetched with git into the build directory.
- **The `naru-orch` system extension** is `build/image/extensions/naru-orch.sqfs`, built by the package `image/pkgs/extension`: a squashfs (zstd, `mksquashfs -reproducible`, one processor, fixed times) of `/bin/naru-orchd`, `/bin/naru-signer` (built with Go, `CGO_ENABLED=0`) and `/manifest.json` (`name`, naru `version`, `services`), and `naru-orch.json` beside it (`name`, `version`, `sha256`, `services`). The kernel has `CONFIG_SQUASHFS` and `CONFIG_SQUASHFS_ZSTD` (`image/pkgs/kernel/naru.config`, so the Node's kernel has them too) and `CONFIG_BLK_DEV_LOOP`, which the host's `required.txt` checks. The release carries both files as `naru-orch-ext-<tag>.sqfs` and `naru-orch-ext-<tag>.json`; `make release` refuses a description that does not state the image's digest and the release's version, and the release workflow installs `squashfs-tools`. `make image-repro` compares the extension's digest. The host's upgrade bundle carries the extension as the member `extensions/naru-orch.sqfs` after `manifest.json`, which lists it ([ADR 0084](./adr/0084-an-upgrade-bundle-carries-the-extensions-the-hosts-configuration-names-and-an-entry-without-a-digest-is-resolved-by-init-to-the-image-built-for-its-version.md)).
  - Firecracker, from the release that mvmd's `tooling/firecracker/fetch.sh` pins (v1.17.0 at the pinned commit), verified by that pin. The script is run from the pinned checkout as `fetch.sh --firecracker-only`, which downloads the Firecracker release tarball and verifies its digest and the binary's, and requests nothing from the Kata Containers release, writes no `vmlinux`, and writes an `inputs.env` that names only `MVMD_FIRECRACKER` and `MVMD_FIRECRACKER_SHA256`. It is still the only source of the Firecracker binary at that commit: mvmd's `make guest-initrd` and `make converter-initrd` fetch nothing and are unchanged between `3b37892f303a4d4dbd8e5360906d0f9c036b562e` and the pinned commit.
  - `mkfs.ext4`, mke2fs statically linked from the e2fsprogs release pinned in `image/pkgs/e2fsprogs/pin.env` ([ADR 0011](./adr/0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md)), installed as `/bin/mkfs.ext4`, the path mvmd's `disk.mkfs` names. It is the package `image/pkgs/e2fsprogs`, linked against musl.
  - `mkfs.xfs`, statically linked from the xfsprogs release pinned in `image/pkgs/xfsprogs/pin.env`, installed as `/bin/mkfs.xfs`; init runs it on a blank `spec.storage` disk ([ADR 0027](./adr/0027-a-node-offers-an-extra-disk-as-xfs-storage-for-mvmds-disks-formatted-when-blank-mounted-hardened-and-grown-at-boot.md)).
  - `gaon-node-agent`, `gaon-apiserver`, `gaon-scheduler` and `gaon-controllers`, built with Go (`CGO_ENABLED=0`, `-trimpath`) from the gaon commit pinned in `image/pkgs/gaon/pin.env`, `d69c5b0fdf05d5d8905fadbe78437890b22e69a7`, fetched with git into the build directory ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)).

## Building the image

- `make image` writes `build/image/bzImage` (the kernel with the initramfs embedded), `build/image/bzImage.bare` (the kernel before it), `build/image/initramfs.cpio.gz`, `inputs.env` (mvmd's name for Firecracker and its SHA-256, which the tests read) and `build/image/guest/`, which holds the guest files the initramfs carries and `guest.json`, `build/image/gaon/` (the four gaon binaries, and `gaon`, gaon's command line client, which the QEMU tests run on the host and the initramfs does not carry) `build/image/etcd/etcd`, `node-initrd.cpio.gz`, `boot-sets.json`, `extensions/`, `k8s/` and `regtools/` (what `image/pkgs/layout.sh` places). `build/` is not tracked.
- **The kernel.** `image/pkgs/kernel/Dockerfile` (the `kernel-host` target) unpacks the pinned tarball after `fetch.sh` has checked its SHA-256, merges `image/pkgs/kernel/naru.config` over the x86_64 `defconfig` with the kernel's `merge_config.sh`, runs `olddefconfig`, and then fails unless every line of `image/pkgs/kernel/host/required.txt` matches a line of the final `.config`: kconfig drops an option whose dependencies are unmet without failing, so the file the build uses is what is checked. The package holds `bzImage.bare` and the final `kernel.config`.
- **The guest files.** The same Dockerfile builds the guest kernel `naru` (`kernel-guest-naru`: the host kernel's tarball, `image/pkgs/kernel/guest-naru/naru.config` merged over x86_64 `tinyconfig`, `olddefconfig`, then a failure unless every line of its `required.txt` matches the final `.config`, with a line for each condition of mvmd's guest.md §Kernel conditions, `CONFIG_VMGENID` and `CONFIG_ACPI` among them, and the uncompressed ELF `vmlinux`, everything built in) and the Node's kernel (`kernel-node`: `image/pkgs/kernel/naru.config` merged over x86_64 `defconfig` first, so the guest Node holds what a host Node does for Kubernetes, then `image/pkgs/kernel/node/naru.config`: PVH, `VIRTIO_MMIO`, no EFI, no built-in command line, the i8042 and AT keyboard drivers and the ACPI button for the stop request, WireGuard, and the same check of `required.txt`). The package `guest-initrds` builds the two initrds with mvmd's `make guest-initrd converter-initrd` at the pinned commit and fails unless each has the SHA-256 of `image/pkgs/guest-initrds/pin.env`. `initramfs-host` writes `guest.json`: `kernels` (name to `{path, sha256}`), `default_kernel`, `guest_initrd` and `converter_initrd`, the paths being the ones inside the image. A kernel name is 1 to 63 characters of `[a-z0-9-]`, the form mvmd's `kernels` map takes (garamsh/mvmd#364). The Node's kernel is written to `boot-sets/<name>/vmlinux`, the name being the `GUEST_BOOT_SET` of `image/pkgs/initramfs-host/boot-set.env`.
- **mke2fs.** `image/pkgs/e2fsprogs/Dockerfile` fetches the pinned tarball with `image/pkgs/fetch.sh` (SHA-256 checked), builds the libraries and `mke2fs` only with `-static` against musl, and installs it through `install-bin.sh` (strip, static, no distribution compiler, no iconv). libuuid and libblkid are the tree's own (`--enable-libuuid --enable-libblkid`). NLS, `fuse2fs`, `debugfs`, `e2image`, `resize2fs`, `e4defrag`, `uuidd`, the initrd helper and the shared-library forms are switched off ([ADR 0011](./adr/0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md)). The build paths are mapped away with `-ffile-prefix-map`.
- **gaon.** `image/pkgs/gaon/Dockerfile` fetches the pinned commit with `gitfetch.sh` (`git init`, `fetch --depth 1` of that object name, `checkout`, and a failure unless `HEAD` is that object name), then builds `node-agent/cmd/gaon-node-agent`, `apiserver/cmd/gaon-apiserver`, `scheduler/cmd/gaon-scheduler`, `controllers/cmd/gaon-controllers` and `gaon-cli/cmd/gaon` with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -buildvcs=false -ldflags='-s -w'`. `gaon`, the command line client, is a test input for the host: `initramfs-host` names the four services and takes nothing else from the package, so the initramfs is the same with or without it. `GOTOOLCHAIN` is the toolchain line of gaon's `go.work` at that commit (`go1.26.11`).
- **etcd.** `image/pkgs/etcd/Dockerfile` does the same for etcd: it fetches the commit of v3.6.16, checks `HEAD`, builds the `server` module's main package (the repository's root is a library) with `GOTOOLCHAIN` from `server/go.mod` (`go1.26.10`), fails unless the binary is static, and installs it as `/usr/bin/etcd`. Only the server is built, not `etcdctl` or `etcdutl`.
- **The credential helpers and the bundle.** The packages `ecr-login` and `rolesanywhere` do for their commits what `etcd` does for etcd (`HEAD` checked against the pin, `GOWORK=off`, the pinned Go toolchain, a check that the result is static); the package `cacert` downloads the pinned bundle and fails unless its SHA-256 is the pinned one, and the initramfs packages append the `TEST_ROOT` file (the `testroot` named context of the bake file, empty for a release) to it as `ca-certificates.crt`.
- **mkfs.xfs.** `image/pkgs/xfsprogs/Dockerfile` builds `mkfs.xfs` only with `-all-static` against musl, with libuuid and libblkid from the util-linux package, and userspace-rcu and inih from their packages, each installed into the toolchain's sysroot by the Dockerfile's `COPY --from`. NLS and every other tool of xfsprogs are off ([ADR 0027](./adr/0027-a-node-offers-an-extra-disk-as-xfs-storage-for-mvmds-disks-formatted-when-blank-mounted-hardened-and-grown-at-boot.md)). util-linux has one pin, `image/pkgs/util-linux/pin.env`.
- **The initramfs.** `image/pkgs/initramfs-host/Dockerfile` builds `naru-init` (with the image's version, below) and takes the other programs from the packages by named context: mke2fs, mkfs.xfs, nft, mount and umount from theirs, the gaon binaries and etcd, the two helpers and the bundle, fails unless each is a static executable, and writes the archive with the kernel's own `usr/gen_init_cpio`, the target `gen-init-cpio` of the kernel Dockerfile compiled from the pinned tarball. The guest files and `guest.json` are added at `/usr/lib/naru/guest/` by `assemble.sh`, from the generated tail of the list. The archive is newc, in the order of `image/pkgs/initramfs-host/initramfs.list` and that tail, every entry owned by 0:0 and stamped with `SOURCE_DATE_EPOCH` from `image/build.env`, then compressed with `gzip -9n`. `image/pkgs/initramfs-node/Dockerfile` builds the Node's initramfs from `image/pkgs/initramfs-node/initramfs.list` with the same tool and writes `node-initrd.cpio.gz`; `initramfs-host` puts that initrd, the Node's kernel and `boot-sets.json` in the host initramfs under `/usr/lib/naru/guest/boot-sets/`, and also leaves `boot-sets.json` in its package. The dependency order is the kernels, the Node's initramfs, the host initramfs ([ADR 0054](./adr/0054-the-image-is-split-into-image-host-and-image-node-with-what-both-carry-in-image-common-and-the-nodes-initramfs-has-its-own-list.md)). `image/pkgs/layout.sh` then places the unpacked packages as `build/image/` (below).
- **The disk.** `make disk` (which runs `make image` first) writes `build/image/naru.img` and `build/image/naru.qcow2` with `image/host/disk/build.sh` and `tooling/disk`. `naru.img` is a raw GPT disk of 1 MiB, one EFI system partition of at least 1 GiB, and 1 MiB. The partition is FAT32, label `NARUESP`, and starts at sector 2048 with a fixed GUID, is sized for two slots each of twice the kernel (the larger of 1 GiB and four kernels with 8 MiB of slack, a whole number of MiB), so that a Node installed from the image can take an upgrade to a kernel twice the size of its own ([ADR 0037](./adr/0037-the-esp-has-room-for-a-trial-kernel-twice-the-size-of-the-one-it-was-built-with-and-a-release-refuses-a-kernel-the-previous-image-cannot-take.md)), and holds the kernel as `\EFI\BOOT\BOOTX64.EFI`, the default slot. The trial slot, `\EFI\BOOT\TRIAL.EFI`, is absent from a built disk. `mkfs.fat` makes the empty volume, `sgdisk` the table, and `tooling/disk/internal/fat` writes the file; the builder reads it back and fails unless it is the input. `naru.qcow2` is `naru.img` converted by `qemu-img convert -O qcow2`, for Proxmox's `import_from`.
- **How the initramfs reaches the kernel.** The kernel is built with the EFI stub, `CONFIG_EFIVAR_FS` and a built-in command line, `console=ttyS0 panic=-1 loglevel=4`, with no `initrd=`: the stub concatenates every initrd it is named, so a slot with its own initramfs would also load another's. the `kernel-host` package holds `bzImage.bare`; the `bzImage` package sets `CONFIG_INITRAMFS_SOURCE` to the `initramfs-host` package's `initramfs.cpio.gz`, links again and writes `bzImage`, so the bzImage depends on the initramfs and a slot is one file. An embedded archive replaces the kernel's default one, so `/dev/console` is a node in the initramfs list. This supersedes ADR 0007 item 1 and ADR 0004 item 2 ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)). `image/pkgs/kernel/host/required.txt` fails the kernel build if any of these options is missing from the final configuration. The reasons and the kernel documents are in ADR 0007.
- **naru-init's version.** `make image` and `make release` pass `VERSION` (`git describe --tags --always`, or `VERSION=<name>`) as `NARU_VERSION` to the initramfs packages, which builds `naru-init` with `-ldflags -X github.com/garamsh/naru/lib/init/run.buildVersion=<VERSION>`: `version()` in `lib/init/run/run.go` prefers it, so `GET /v1/version` and `naructl version` on a Node of a release report the release's tag. The string is the only thing the flag adds to the binary, so two builds of one `VERSION` stay byte-identical, and builds of two `VERSION`s differ in `naru-init` and so in the initramfs and the disks. `build.sh` and both initramfs Dockerfiles refuse to build without `NARU_VERSION`, so a built image always carries a version; the fallback of `version()` ([init.md](./init.md)) is for a binary built by hand.
- **Reproducibility.** See [The builder](#the-builder): the image is built in one pinned container, and `make image-repro` compares the `SHA256SUMS` of two builds.
- **Who moves the pins.** The kernel's pin is moved by the PM ([image/pkgs/kernel/pin.env](../../image/pkgs/kernel/pin.env)), and so are mvmd's ([image/pkgs/mvmd/pin.env](../../image/pkgs/mvmd/pin.env)) e2fsprogs's ([image/pkgs/e2fsprogs/pin.env](../../image/pkgs/e2fsprogs/pin.env)), xfsprogs's ([image/pkgs/xfsprogs/pin.env](../../image/pkgs/xfsprogs/pin.env)) and the toolchain's ([image/pkgs/toolchain/pin.env](../../image/pkgs/toolchain/pin.env)), gaon's ([image/pkgs/gaon/pin.env](../../image/pkgs/gaon/pin.env)) and etcd's ([image/pkgs/etcd/pin.env](../../image/pkgs/etcd/pin.env)); each names how. The pins of the gaon and etcd commits are bumped in a pull request that rebuilds the image and runs `make test-qemu`; the etcd pin moves with a release, gaon's with a commit whose docs the PM has read again for what boundaries.md and config.md claim.

## Booting a Node

- **Boot N Nodes: `make nodes N=3`** (default 2, at least 2). It builds the image and the disk, then boots N Nodes of the image under QEMU on one network and keeps them up until interrupted. Each Node has its own disks and console log under `build/nodes/node-<i>/`; the command prints a line per Node once that Node's stand-in has dialled its peer across the network. `tooling/qemu/cmd/naru-nodes` is the command.
- **Run the test: `make test-qemu`.** It makes a throwaway root (`naru-testroot`), builds the image and the disk with it as `TEST_ROOT`, boots Nodes as the tests need, reads their serial consoles, and fails, never skips, when no test ran. The tests are `TestNode_*` in `tooling/qemu/tests`, built with `-tags qemu_real`.
- **QEMU** runs as the user with `-enable-kvm -cpu host`, laid out as a Proxmox guest is: the q35 machine under OVMF (`/usr/share/OVMF/OVMF_CODE_4M.fd` as read-only pflash unit 0, a per-Node copy of `/usr/share/OVMF/OVMF_VARS_4M.fd` as unit 1), a `virtio-scsi-pci` controller with `naru.img` (read-only, `bootindex=0`) and the data disk as `scsi-hd`, the NoCloud drive as a read-only `ide-cd` on the AHCI bus, and one virtio NIC (a Node of a gaon cluster that has the control plane has a second, see "The host path to gaon's API server" below); nothing needs root. There is no `-kernel`, `-initrd`, `-append` or `ip=`. The kernel's built-in command line carries `loglevel=4`, so kernel info messages do not split init's console lines, which the tests read; no test asserts a kernel line. A missing `naru.img` fails before QEMU starts, naming `make disk`.
- **The network** is QEMU's `-netdev socket` over a multicast group on the loopback, with a group port drawn at random per cluster so clusters on one host do not share a network. Each Node has its own MAC, `02:00:00:00:<i high byte>:<i low byte>`, and its `network-config` gives it `10.78.0.<i>/24` (the release's example for Proxmox gives other values, [Release assets](#release-assets)) on `eth0` with `10.78.0.254` as gateway and resolver (no machine has that address), which init applies before any service ([config.md](./config.md)). Machine networks are separate: Node i gives mvmd `network.ipv4_prefix` `10.77.<i>.0/24`, and `spec.network.forwarding` lists `ipv4`.
- **The drives** are built by `tooling/qemu/internal/node`. The NoCloud drive is a 4 MiB file, as Proxmox's is, holding an ISO 9660 volume labelled `cidata` with `user-data` (the Node's `naru.yaml`: its name, its services and the file `/run/mvmd/config.json`, mode `0600`, which is mvmd's JSON configuration), `meta-data` (`instance-id`) and `network-config`. `tooling/qemu/internal/iso9660` writes it, with a primary and a Joliet tree because the kernel reads `user-data` through Joliet; no genisoimage, xorriso or root is needed. The data disk is made with `/sbin/mkfs.ext4 -d`, which fills an ext4 image from a directory without mounting it, owned by root: labelled `NARUDATA`, 2 GiB sparse, with the `verity` feature, holding only the test inputs under `inputs/` (no guest file: the image carries those), so it is the same for every Node (etcd creates `/var/lib/naru/etcd` on it at its first start, beside `mvmd` (mvmd's `state_dir`) and `inputs`); `naru.yaml` mounts it at `/var/lib/naru`, and the mvmd service's `-config` names the file init wrote under `/run/mvmd`, so init knows nothing of mvmd's configuration. The data disk is where the inputs go because init mounts the NoCloud drive and that disk and no other.
- **The inputs** are staged by `tooling/qemu/internal/fixture` from build outputs and hard-linked into each data disk: the test-only `naru-registry` and `naru-probe`, and an OCI registry directory holding one image and its TLS authority. They are test inputs and not image contents. gaon's CLI is not staged: the gaon Machine test runs it on the host from `$NARU_IMAGE_DIR/gaon/gaon` (`build/image/gaon/gaon`, built by the package `image/pkgs/gaon`). The guest kernel and initrds are not staged: `tooling/qemu/internal/guest` reads `build/image/guest/guest.json`, and mvmd's configuration (`naructl`'s, for a gaon Node, which reads the same manifest, and `node.Config.MvmdJSON` for the stand-in Nodes) names the paths and SHA-256 in it, with every declared kernel written to the Firecracker section's `kernels` map and `default_kernel` (the form mvmd reads at the pinned commit; it refuses the single `kernel` and `kernel_sha256` there), and the default kernel alone written to the `conversion` section, which keeps one `kernel` and `kernel_sha256`.
- **The services** of every Node of a cluster without gaon, in order, are `mvmd` (the Firecracker driver, whose registry section names the files init writes from a `spec.registries` entry that carries the registry's authority, [ADR 0026](./adr/0026-a-node-takes-registry-credentials-and-trust-as-configuration-an-ecr-credential-comes-from-iam-roles-anywhere-and-an-agent-pair-without-the-required-organization-is-set-aside.md)); `registry`, which serves the image over TLS on `127.0.0.1:5000` and is how mvmd pulls; `standin`, which logs the file system type of `/var/lib/naru`, dials mvmd's Unix socket until it accepts, and dials the stand-in of the next Node (Node i dials Node i+1, the last dials the first) on TCP 7000 until it accepts; and `control`, a stand-in marked `controlPlane: true`. Node 1 has `spec.controlPlane: true`, so only it starts `control`; every other Node's init logs that it skips it. Node 1 also runs `probe` in the restart test.
- **`naru-cluster`** boots the same Nodes from a release's assets for a harness outside this repository, with gaon binaries the harness supplies and a `cluster.json` it reads; [harness.md](./harness.md) is its contract. `make test-harness` runs it as a harness does, from a directory outside the checkout (with `RELEASE=<dir>`, the directory's `naru-cluster-<version>-linux-amd64` after a `SHA256SUMS` check, and no build), in its own target so that `make test-qemu` stays the length it is.
- **gaon's services.** A cluster started with `ClusterSpec.Gaon` (the Nodes' user-data is written by `naructl`, which owns this layout: `lib/layout`, [ADR 0015](./adr/0015-naructl-is-the-single-owner-of-the-gaon-node-layout-and-tooling-qemu-runs-it-as-a-binary.md); the tests build it from the checkout and `naru-cluster` takes it from the release; the QEMU extras are flags: `--serving-address 127.0.0.1`, `--extra-nic`, `--binary`, `--disable`) (the gaon tests; `make nodes` and the other tests do not set it) replaces the services above, after `mvmd` and `registry`, with gaon's, so every Node runs `mvmd` and `registry`, because the scheduler may bind a Machine to any Node and that Node's mvmd pulls the image from `127.0.0.1:5000`. They are argv and files, no environment variable. Each starts after what it dials, but init waits for none: the API server exits when etcd does not answer and init restarts it after the backoff, and the Node Agent and the others retry, so the order is a courtesy and init is unchanged ([ADR 0012](./adr/0012-gaon-runs-on-the-nodes-with-etcd-on-the-data-disk-carried-certificates-and-a-host-forward-to-the-api-server.md)). The flags are the ones `apiserver.md`, `node-agent.md` and the services' `main.go` name at the gaon commit above.

Init then remounts that copy read-only once its mount points exist (`Host.SealRoot`), and every test passes with the root read-only.
- **What the storage tests assert** (`tooling/qemu/tests/storage_test.go`; one Node with a blank sparse extra disk, the data disk and the extra disk both virtio-blk so that the kernel names them `/dev/vda` and `/dev/vdb` in the order attached, the extra disk named by `spec.storage` at `/dev/vdb` and mounted at `wire.MvmdStorageMount`; `naru-storageprobe` reports on the mount, and every 2 s how many disks, snapshots and run directories it holds): a blank disk is formatted as XFS, mounted, and a FICLONE copy of a file in it succeeds; after a reboot the marker the probe wrote is kept and the console has no formatted line; a disk the test enlarges between boots is grown by init at the next boot, and the probe reports the larger file system; and a Node rebooted with its data disk and extra disk attached in the other order finds the extra disk by its label, at `/dev/vda`, and keeps its marker ([ADR 0032](./adr/0032-a-storage-disk-is-found-by-the-xfs-label-init-gives-it-and-device-names-only-a-blank-disk.md)). The kernel options the disk needs are `XFS_FS`, the device mapper, `BLK_DEV_LOOP` and `BLK_DEV_NBD`, and `XFS_ONLINE_SCRUB` is off. `TestNode_AStorageDiskHoldsMvmdsDisksSnapshotsAndRunDirectoriesWhileAMicroVMIsCreatedSnapshotAndResumed` runs the host Node with such a disk, creates a microVM through the host API, snapshots it and resumes the snapshot: mvmd lists both Running, and the probe counts the microVM's disk and run directory, then the snapshot, on the storage disk ([ADR 0073](./adr/0073-mvmds-disks-snapshots-and-run-directories-are-on-the-first-storage-disk-through-links-while-its-state-directory-stays-on-the-data-disk.md)).
- **mvmd runs `mkfs.ext4`** to format a Machine's disk, and the image carries it: `/bin/mkfs.ext4`, a statically linked mke2fs built from the pinned e2fsprogs release ([ADR 0011](./adr/0011-mkfs-ext4-is-a-static-mke2fs-built-from-the-pinned-e2fsprogs-release-and-installed-in-the-image.md)). The mvmd configuration of the QEMU Nodes and of the release's user-data names that path in `disk.mkfs` (`layout.MkfsPath` in `naructl`), and the data disk carries no mke2fs, loader, library or launcher. mvmd runs it with `-q -F -U <uuid> <path>` and no `-t` (`daemon/internal/diskfile/disk.go` line 344 at commit d189133bba8d842d2bcb20046f39fe03161efeb1), so mke2fs takes the file system type only from the name it is run as; with no `/etc/mke2fs.conf` in the image it uses the defaults built into it.

## Judging serial logs

- **`make judge-serial NODE1=<log> NODE2=<log>`** reads the serial logs of two Nodes, node-1 first, and exits 0 only when both show what the QEMU tests assert. `tooling/qemu/cmd/naru-judge` is the command. It exits 1 and prints a `FAIL <node>: <expectation>: no line with <fragments>` line for each expectation not met, and 2 when a log cannot be read or an argument is missing. It prints per Node the log's size, the number of re-printed blocks, the largest `dropped` a block reported, and how many expectations were met of how many.
- **`-node-api listening|off`** (`make judge-serial JUDGE_NODE_API=<listening|off>`) also judges, on both Nodes, init's line `the Node API is listening` and no `the Node API is off` line, or the reverse. Left out, those lines are not judged, so the log of a release before v0.4.0, which has neither, passes. The test user-data of v0.4.0 has no `spec.api`, so its Nodes show `off`.
- **The expectations** are, for each Node: init accepted the configuration under the name `naru-<name>`, configured one interface (the judge requires no count of nameservers: Proxmox's network gives two, the QEMU network one, and `TestNode_*` assert that one as a check of their own), remounted the root read-only, started `mvmd`, `standin` and `registry`, and the stand-in logged the data disk mounted as ext4 (init logs nothing of that mount, so a gaon Node shows no such line and the judge does not ask for one of it); mvmd's socket accepts connections; the stand-in reached its peer. node-1 started `control` and skipped nothing; node-2 skipped `control` and never started it. With `-gaon` (`make judge-serial JUDGE_GAON=1 JUDGE_NARUCTL=<naructl> …`, `-naructl` naming a `naructl` binary, which prints the services with `naructl topology` and is the judge's only list of them, [ADR 0019](./adr/0019-the-gaon-topology-and-a-nodes-credential-mode-are-defined-once-in-naructls-layout-and-the-harness-reads-the-topology-from-naructl-topology.md)) the services expected are the ones of a Node of the test-only user-data, at this writing: `mvmd` and `registry` on both, `gaon-node-agent` on both, and on node-1 `etcd`, `gaon-apiserver`, `gaon-scheduler` and `gaon-controllers` started and nothing skipped, on node-2 those three skipped (init logs the skip of each control-plane service) and never started; the stand-in, the peer check and the probe are not expected, and each Node configures one interface, as a Proxmox Node does by default (a QEMU gaon cluster's node-1 configures two: `-node1-interfaces <n>`, which `make judge-serial` passes from `JUDGE_NODE1_INTERFACES`, sets node-1's count, and node-2's stays one). With `-gaon -pki` (`JUDGE_PKI=1`), node-1's log (a control-plane Node that issued its pairs from `spec.pki`, [ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)) is also judged on init's issuing: `certificate issued` for `apiserver`, `scheduler`, `controllers` and `agent`, and `authority written`, each before the first `started` line of a service, and no `certificate renewal failed`; a log that shows none fails. Without `-pki` no issuing is expected, and `-pki` and `-node1-interfaces` without `-gaon` exit 2. Without `-gaon`, node-1's log has each of the twelve `PROBE <check> ok` lines, `PROBE finished`, no `PROBE` line with `fail`, and init's restart of `mvmd`. Each is one line holding its fragments in order, which is the match `TestNode_*` make.
- **The log may be a raw capture.** The judge takes out terminal escape sequences and other control characters, ends a line at CR, LF or CR LF, accepts a capture that starts in the middle of a line, removes the markers of init's re-prints, and judges a line present once however many times a block repeats it. A log in which init dropped lines (`dropped` above 0) may lack an early line; the failure names the line, and the summary shows `dropped`.
- **The logs of a run of `make nodes`** are `build/nodes/node-<i>/console.log`; `naru-nodes -probe` runs the probe on node-1.

- **`make image-upgrade`** builds, after `make image`, the two kernels the upgrade tests put on a Node ([ADR 0025](./adr/0025-an-upgrade-is-a-bundle-posted-to-v1-upgrade-which-init-writes-to-the-trial-slot-and-the-trial-boot-promotes-when-healthy-and-rolls-back-when-not.md)), into `build/upgrade/next/bzImage` and `build/upgrade/refuse/bzImage`, by building the `upgrade` group of the bake file: the initramfs and `bzImage` packages again with another `NARU_VERSION` (`initramfs-host-next`, `bzImage-next`). `next` is the tree with the version `<VERSION>-next`. `refuse` has the version `<VERSION>-refuse` and a naru-init whose `dataDiskLabel` is stamped `naru67-absent` by the `-X` flag of `REFUSE_LDFLAGS` in the bake file (`initramfs-host-refuse`, `bzImage-refuse`), so that it finds no data disk and its boot is refused, with a configuration drive and without one. `make test-qemu` depends on it and gives the tests the directory as `NARU_UPGRADE_DIR`.
- **What the upgrade tests assert** (`tooling/qemu/tests/upgrade_test.go`; one Node running gaon with the Node API, on a copy of the boot disk with its ESP writable; QEMU runs with `-no-reboot`, so each time it ends the test starts it again). `TestNode_UpgradeReplacesTheKernelOfARunningNodeAndKeepsItWhenItIsHealthyWithItsDataIntact`: `naructl upgrade` sends the `next` bundle; the Node reports the new version, `default` as its slot and `promoted` as the outcome; the boot ID differs; the store revision and `store.yaml` on the data disk are as before; a power cycle boots the new version from the default slot. `TestNode_UpgradeToAKernelThatRefusesIsRolledBackByTheNodeToTheVersionBefore`: the same with the `refuse` bundle; with nothing done to the Node, it comes back on the old version, reports `rolled back` with a reason that begins with init's `the boot sequence refused: ` and a new boot ID, and `store.yaml` is as before. `TestNode_UpgradeIsRefusedByTheNodeWith422WhenAnExtensionEntryHasNoImageForTheBundlesVersion`: with `spec.extensions` naming the stored extension built for the running version, `naructl upgrade` of the `next` bundle prints the Node's 422 naming the extension and ADR 0055, and the Node is not rebooted. The release's own promise, that a host installed from one release upgrades in place to the next, is backed by `make test-release-upgrade FROM=<dir> TO=<dir>`, run before each release on the previous release and the candidate (no workflow step runs it): `TestRelease_AHostInstalledFromOneReleaseUpgradesInPlaceToTheNextAndKeepsItsData` boots the host disk of the release in `FROM` with the user-data of that release's own `naructl`, writes data, sends the bundle of the release in `TO` with `TO`'s `naructl`, and requires the version, slot `default`, an outcome naming the promotion, `store.yaml` as before and `GET /v1/services` answering. `make test-qemu` does not run it.

## Release assets

- **`make release`** (version from `git describe --tags --always`, or `VERSION=<name>`; it is also the version `naru-init` reports, [naru-init's version](#building-the-image)) builds the image and the disk and writes into `build/release/`: `naru-host-<version>.qcow2` (the boot disk of the host artifact, byte for byte `build/image/naru.qcow2`; releases up to `v0.1.0-dev.8` name it `naru-<version>.qcow2`, [ADR 0056](./adr/0056-the-hosts-release-assets-are-named-naru-host-the-boot-disk-naru-host-version-qcow2-and-the-upgrade-bundle-naru-host-upgrade-version-tar.md)), `naru-host-upgrade-<version>.tar` (the upgrade bundle, `naru-upgrade-<version>.tar` up to `v0.1.0-dev.8`: `kernel.efi`, the release's `bzImage`, and `manifest.json` with the version, the kernel's size and SHA-256, and the size of the image's ESP (`esp.bytes`); a tar with no timestamps, byte-reproducible, [ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)), `naru-node-kernel-<version>` (the guest form's `naru-node` kernel), `naru-node-initramfs-<version>` (`node-initrd.cpio.gz`) and `naru-node-<version>.json` (the Node boot set's manifest, [below](#the-node-boot-set-manifest)), `naru-data-<version>.qcow2`, `naru-guest-<version>.json` (a copy of `guest.json`: the names and SHA-256 of the guest kernel and initrds inside the boot disk's initramfs), `naru-inputs-<version>.json` (the Firecracker digest the Nodes' mvmd configuration names and the reference of the test image, which [`naru-cluster`](./harness.md) reads), `naru-orch-ext-<version>.sqfs` and `naru-orch-ext-<version>.json` (the `naru-orch` system extension and its description, whose `sha256` an operator writes into `spec.extensions`, [ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)), `naructl-<version>-linux-amd64` (the operator's tool, a static binary built by `make release` and the one that writes the two files below; [config.md](./config.md#operator-tooling-naructl)), `naru-cluster-<version>-linux-amd64` (the harness's command, a static binary built by `make release` with `gobuild` like `naructl`; [harness.md](./harness.md), [ADR 0074](./adr/0074-naru-cluster-is-a-release-asset-and-a-harness-downloads-it-and-checks-it-against-sha256sums.md)), `naru-node-1.test.yaml`, `naru-node-2.test.yaml`, `naru-sbom-<version>.spdx.json` and `naru-sources-<version>.tar` (the Integrity of a release bullet below) and `SHA256SUMS` of the other sixteen: seventeen files. The release workflow adds an eighteenth, `SHA256SUMS.sigstore.json`, which signs `SHA256SUMS` and so is not listed in it. The two `.test.yaml` files are **test-only** user-data: they carry private keys, [below](#release-assets). `tooling/qemu/cmd/naru-release` is the command; it prints each asset's digest and size, and with `-notes-figures <file>` (`make release` passes `build/release-figures.env`, outside `build/release/` because every file there is an asset) writes `ESP_BYTES` (the boot disk's ESP) and `LARGEST_UPGRADE_KERNEL_BYTES` (the largest kernel a Node installed from this image can take as an in-place upgrade: the ESP's room for a trial kernel beside this release's own, ADR 0037) for the release notes. Before the long steps it refuses a kernel that would not fit the trial slot of a Node installed from the previous release's image: `PREV_MANIFEST=<path>` names that release's `manifest.json` (the release workflow takes it from the previous release's bundle), `RECREATE=1` lets the release through and its notes then say that earlier Nodes are recreated, and with no `PREV_MANIFEST` nothing is checked and the command says so (ADR 0037).
- **The data disk** is the one the tests give every Node, converted to qcow2: ext4 with the `verity` feature, label `NARUDATA`, 4096-byte blocks, **2 GiB virtual**, holding `inputs/` and nothing of a Node: the OCI registry directory and its TLS authority, `naru-probe` and `naru-registry`. 2 GiB is the size the QEMU tests run the probe's Machine on (a 256 MiB root disk and mvmd's state); the qcow2 file is about 63 MiB because the unused space is not stored. Both Nodes attach their own copy, found by label (`scsi1` on Proxmox), since mvmd's state is written to it.
- **Reproducibility.** A second `make release` of the same commit in the same builder gives the same `SHA256SUMS` for every asset but one: **the data disk**. The registry's TLS authority, certificate and key on the data disk (`inputs/registry/ca.pem`, `cert.pem`, `key.pem`) derive from the version and `SOURCE_DATE_EPOCH` like the test CA, so that the user-data's `ca=` names the authority the disk serves; the data disk is nevertheless left out of the comparison. The test user-data is reproducible: its CA (certificate and key) and bootstrap tokens derive from the version and `SOURCE_DATE_EPOCH` ([ADR 0078](./adr/0078-the-releases-test-user-data-derives-its-authority-and-tokens-from-the-version-so-only-the-data-disk-differs-between-builds.md)). The file system's UUID, directory hash seed and clock, and the files' times, are fixed. `image/repro.sh` leaves the data disk out and compares the rest, the SBOM and the sources tar among them; [The builder](#the-builder) says what was measured. The release workflow leaves the same asset out when it compares a new build with a published release (`internal/release.ByDesignPattern`, the same expression as `repro.sh`'s `skip`, which a test reads from the file).
- **Integrity of a release.** [ADR 0076](./adr/0076-a-tag-publishes-once-and-a-release-is-signed-attested-and-carries-an-sbom-and-the-corresponding-source.md) decides all of it; `docs/operate/verify-a-release.md` is the consumer's side.
  - **The SBOM** `naru-sbom-<version>.spdx.json` is SPDX 2.3 JSON written by `naru-release`. It has one package for every pin under `image/` (name, version, download location, SHA-256 of the tarball or the repository and commit, and the SPDX licence expression of the pin's `<NAME>_LICENSE` line) and, for every Go binary the release ships (those in the host and Node initramfs archives, among them `naru-init`, gaon, etcd, the Kubernetes programs and mvmd's Go helpers; the same programs as laid out under the image's `gaon`, `etcd`, `k8s` and `regtools` directories; `naru-orchd` and `naru-signer` of the `naru` package; `naructl` and `naru-cluster`), a package with the binary's SHA-256 and a `DEPENDS_ON` relationship to each module in its build information. `naru-release` fails on a pin without a `_LICENSE` line. The only time in it is `SOURCE_DATE_EPOCH`.
  - **The sources tar** `naru-sources-<version>.tar` holds `naru-source.tar` (a `git archive` of the built commit, which `make source-archive` writes on the host) and `sources/<tarball>`, the exact upstream tarball of every pin whose licence expression names a GPL, LGPL or AGPL licence. Every tarball is fetched from the pin's URL when `naru-release` runs (the packages' tarballs live only inside BuildKit, so none is on the host), with a timeout and three tries for each, and its SHA-256 must be the pin's, or the build fails. Two pins whose tarballs have the same name fail the build. The pins are the only source: the SBOM does not list Firecracker, which `tooling/firecracker/fetch.sh` of mvmd's commit downloads (see ADR 0076). Its members are sorted, owned by no one and dated `SOURCE_DATE_EPOCH`.
  - **The signature** `SHA256SUMS.sigstore.json` is a cosign bundle made keyless by the release workflow, and every asset `SHA256SUMS` lists has a build provenance attestation in the repository.
- **The test-only user-data** is the `naru.yaml` of a gaon Node, written by `naructl gen token` and `naructl gen node` (the code that writes the QEMU tests' gaon Nodes) with the Proxmox values as parameters, named `naru-node-<n>.test.yaml`: the `.test` says that it carries private keys and is for a throwaway deployment. node-1 is 192.168.0.40, MAC `02:00:00:00:03:E9`, `controlPlane: true`, and runs `mvmd`, `registry`, `etcd`, `gaon-apiserver`, `gaon-scheduler`, `gaon-controllers` and `gaon-node-agent`; node-2 is 192.168.0.61, MAC `02:00:00:00:03:F4`, and runs `mvmd`, `registry` and `gaon-node-agent`, and init logs that it skips the three control-plane services. The stand-ins (`standin`, `control`) and the probe are not in it: they check init and mvmd, which gaon's services now exercise on the same Nodes, and a deployed Node has no use for them; the QEMU tests that name them still run them. node-1 carries the CA in `spec.pki` and init issues the API server's serving certificate (naming 192.168.0.40), the scheduler's and the controllers' pairs at boot; both Nodes carry `ca.pem` and a bootstrap token in `spec.files` under `/run/gaon/`, and each Node Agent is issued its pair by a signing request. The CA comes from a directory the release's code derives from the version (`internal/release/testpki.go`) in the layout of `naructl gen ca` and `gen token`, removed when the build has written the files (and the Node Agents on both Nodes dial `https://192.168.0.40:6443`). mvmd's configuration is the file `/run/mvmd/config.json` in `spec.files`, with `network.ipv4_prefix` `10.200.1.0/24` for node-1 and `10.200.2.0/24` for node-2, and the gateway and resolver the first address of the prefix. Each file passes the other Node as a peer (`gen node --peer`): node-1 routes `10.200.2.0/24` via 192.168.0.61 and node-2 routes `10.200.1.0/24` via 192.168.0.40 in `spec.network.routes`, and each lists the other's prefix in mvmd's `network.no_masquerade` ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)). The gateway 192.168.0.1 and the resolvers 1.1.1.1 and 8.8.8.8 are not in the user-data: they are Proxmox's network-config, which the cloud-init drive of each VM provides. The data disk's `inputs/` paths in the files are the ones the tests use, so the files and the disk go together: the registry's image digest in the yaml is the one the data disk's registry serves, and the Node Agent of each Node reaches the API server on node-1's address with no host forward.
- **Keys the release publishes.** The release's test CA's private key **is published**, in `naru-node-1.test.yaml`: `spec.pki` carries the authority with its `key`, and init writes it to `/run/gaon/ca.key` (`0600`) for the controllers to sign with ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md), which supersedes ADR 0015 item 3's "no CA key"). The CA is derived from the release's version in a temporary directory during `make release` (ADR 0078), which is removed; two builds of one commit derive the same one, and it is trusted only by that deployment, and the release notes mark it test-only like the registry's authority. An operator's CA is never written into any asset. Both files hold a bootstrap token (`/run/gaon/bootstrap-token`, `0600`) and node-1's also the list of both (`/run/gaon/bootstrap-tokens`). node-1's pairs for the API server, scheduler and controllers are issued by init on the Node, so no entry of `spec.files` holds a private key; a Node Agent's key is made on its Node by the agent. No asset holds a client pair for an operator; a deployer makes a CA, user-data and a client pair of their own with the release's `naructl` ([config.md](./config.md#operator-tooling-naructl)). The data disk holds the registry's authority key (`inputs/registry/key.pem`), as before. Each yaml is written with mode `0600`. All of these are readable by anyone who can read the public GitHub Release; the files are for a deployment that nothing depends on.
- **What the build checks.** `make release` fails unless every service binary of each yaml is on the data disk (read with `debugfs`) or installed by `image/pkgs/initramfs-host/initramfs.list`. The tests of the release parse each file with `naru-init -validate`, init's own parser, and check the addresses, the roles, mvmd's prefix and the services, that the serving certificate init will issue for the API server names 192.168.0.40, that node-1's authority is the `ca.pem` of both files and its key is the CA's, that both Nodes carry a token of gaon's form and node-1 lists both, and that node-2 carries no authority and no key.

### The Node boot set manifest

`naru-node-<version>.json` is the contract between `naru-release`, which writes it, and `naructl host boot-set add`, which reads it (each defines its own struct: units do not import each other). Fields: `name` (the name mvmd offers the set under: `naru-node-` and the version in lower case with each character outside `a-z`, `0-9` and `-` replaced by `-`, so `v0.4.0` is `naru-node-v0-4-0`; the release refuses a name over 63 characters), `version` (the tag as it is), and `kernel` and `initramfs`, each `{file, sha256, bytes}`, where `file` is the name of the asset beside the manifest (`naru-node-kernel-<version>`, `naru-node-initramfs-<version>`). naructl refuses a `file` that is not a plain file name, and sends the two digests to the host API, whose mvmd checks the files against them ([host.md](./host.md), [ADR 0046](./adr/0046-the-host-api-adds-and-removes-a-boot-set-on-a-running-host-through-mvmds-runtime-api-and-a-release-carries-the-node-boot-set-as-a-kernel-an-initramfs-and-a-manifest.md)).

## Release workflow

[`.github/workflows/release.yml`](../../.github/workflows/release.yml) publishes the release assets as a GitHub Release (the owner's decision 5 on garamsh/naru#14: distribution through a naru GitHub Release, which aurora pins by URL and digest).

- **Trigger.** A push of a tag `v*`, or `workflow_dispatch` with the `tag` of an existing tag, to repeat a run. A tag publishes once: a run for a tag whose release exists compares `SHA256SUMS`, uploads nothing when they agree and fails when they do not (below). A tag whose name contains `-` (`v0.1.0-rc.1`) is published with `--prerelease --latest=false`, so it is a pre-release and never the latest release; any other tag is published as before ([ADR 0016](./adr/0016-a-nodes-agent-gets-its-pair-from-a-signing-request-with-a-bootstrap-token-and-the-release-publishes-a-test-ca-key.md)).
- **Build job** (`ubuntu-24.04`, read-only token). It checks out the tag, records the commit, runs `make ci` (the repository's own checks, with the Go that `go.work` names), then `make release VERSION=<tag>`, which starts the builder container: the image is built from `image/builder/Dockerfile` and must have the digest of `image/builder/builder.env`, so nothing is installed on the runner for the build, and mvmd's checkout and Rust toolchain come inside the container. It records the builder's identity (Docker's version and the image's config digest) in the log. The kernel builds clear `MAKEFLAGS`, so a `VERSION` given to `make` does not reach the kernel's own make. It boots no QEMU: `make test-qemu` is not part of it. It uploads `build/release/` as a workflow artifact.
- **Publish job** (`contents: write`, `id-token: write` and `attestations: write`; the only job with them). It checks out the tag, checks the seventeen files against `SHA256SUMS`, and then, if the tag has a release, downloads that release's `SHA256SUMS` and runs `naru-release compare` against the new one: a release with no `SHA256SUMS`, an asset the two disagree on or one that only one lists (the by-design assets apart) fails the job and names it, and a release that lacks an asset its `SHA256SUMS` lists fails it too, the fix being to delete a release nobody has used. When the two agree the job ends there: it uploads, signs and attests nothing, and does not edit the notes. Otherwise it writes the release notes, signs `SHA256SUMS` with cosign (`sign-blob`, keyless, bundle `SHA256SUMS.sigstore.json`), attests the provenance of every asset `SHA256SUMS` lists (`subject-checksums`) and runs `gh release create` with the eighteen files and `--verify-tag`; it never edits or overwrites a release. The notes name the commit built, say what they describe (the assets, how to use and verify them; the Node API in a sentence, `naructl` as its client, `naru-init` reporting the tag) and name every asset, including the SBOM, the sources tar and the signature bundle, give the three commands that verify a release, say that a second run for the tag changes nothing, say that the test user-data has no `spec.api` and carries private keys, with the commands that enable the API (`naructl gen api-ca --ca-dir`, `gen node --ca-dir` from the same CA directory, `gen api-client`; a Node whose user-data has no `spec.api` logs that the Node API is off), say that the data disk carries a test-only registry TLS authority including its private key (trusted only by the mvmd on the Node; the registry listens on 127.0.0.1), say that the two `.test.yaml` files are test-only and carry the private keys of gaon's serving and client pairs (the CA's key is published nowhere), say that the data disk is not byte-reproducible and why, say how to add the Node boot set to a host (`naructl host boot-set add`) and state the boot disk's ESP size and the largest in-place upgrade kernel, which the build job reads from `build/release-figures.env` into job outputs, and state how the release relates to a workstation build. The notes end with each asset's name and SHA-256, one line per asset, taken from the `SHA256SUMS` of the same build that is attached beside them (garamsh/aurora#749, criterion 3), so that a consumer pins a digest without downloading the file.
- **Release bytes and a workstation build.** The runner builds in the same builder image as a workstation, so the release's reproducible assets are meant to equal a workstation build of the same commit; [The builder](#the-builder) records the comparison. The data disk differs between any two builds (see Release assets), so aurora pins the digest of the published asset.
- **Caches.** The Go module cache of the runner's `make ci`, keyed on every `go.sum`, which the checksum database makes content-addressed. The build caches nothing between runs: the container is built or loaded fresh, and the kernels, the initramfs, the guest initrds and the disks are built from the pinned sources on every run.
- **Pins and movers.** Each action is pinned by full commit SHA, with its version in a comment: `actions/checkout` v7.0.1, `actions/setup-go` v7.0.0, `actions/upload-artifact` v7.0.2, `actions/download-artifact` v8.0.2, `sigstore/cosign-installer` v4.1.3, `actions/attest-build-provenance` v4.2.2; cosign itself is pinned by version in the installer's input (v3.1.4). The PM moves them, in a pull request that reads the action's current release and the GitHub Advisory Database, when an advisory is published for one and at each Go minor release; no bot proposes the bumps. The runner label `ubuntu-24.04` cannot be pinned: it names its version, and the PM moves it when GitHub retires the label; it no longer affects the release's bytes, which come from the builder. The builder's pins ([The builder](#the-builder)) are moved by the PM in a pull request that rebuilds the image and carries the new `builder.env`.
- **Not verified before merge.** The run time of the build in the container on a runner is not measured here beyond [The builder](#the-builder)'s comparison run. The kernel build and mvmd's two guest initrds (each built twice by mvmd's Makefile) are the long steps.

## The builder

`make image`, `make image-upgrade`, `make disk` and `make release` run inside one container, [ADR 0063](./adr/0063-the-image-is-built-inside-one-digest-pinned-builder-container-whose-toolchains-are-pinned-and-the-stage-2-direction-is-a-musl-toolchain-with-buildkit-built-packages.md). The public targets call `image/builder/run.sh make in-builder-<target>`, and the `in-builder-*` targets hold the recipes the scripts of `image/` run.

- **The Dockerfile.** [image/builder/Dockerfile](../../image/builder/Dockerfile) starts from `ubuntu@sha256:2198e4c6...` (Ubuntu 24.04, by digest), points apt at `snapshot.ubuntu.com` at one fixed time, installs every package at an exact version, installs Go 1.26.11 from its tarball after checking the SHA-256, and installs `rustup-init` 1.29.3 after checking its SHA-256. It deletes the apt and dpkg logs and the ldconfig cache, which differ between builds.
- **The config digest.** The builder is built with `docker buildx build` in a BuildKit container of the image `BUILDKIT_IMAGE` in `builder.env` (pinned by digest, so a daemon without the containerd image store builds it too), from `SOURCE_DATE_EPOCH` and `rewrite-timestamp=true`, exported as a docker archive that every daemon loads, so two builds of the Dockerfile give one image. [image/builder/builder.env](../../image/builder/builder.env) names the image's config digest, and `run.sh` builds the image when `naru-builder:<digest>` is absent and fails unless the result has that digest. Two `--no-cache` builds on the workstation gave one manifest digest, `sha256:50e9de7b...9d41a`, and the config digest in `builder.env`.
- **What `run.sh` runs.** `docker run --rm --init` as the calling user, the repository at `/naru`, `HOME` and the Go and Cargo caches under `/naru/build/cache`, `NARU_BUILDER` set to the config digest. `DOCKER=podman` is expected to work, with the same command line, and is untested: Podman is not installed on the workstation that built this.
- **Go.** The builder's Go, `go1.26.11`, is `GOTOOLCHAIN` in the container and builds naructl, naru-cluster and tooling/disk; the programs of the image are built in the packages, from the same Go release installed in their builder stage. A project whose pinned source names its own release builds with it, and the Go command downloads that release and checks it against the checksum database: containerd and runc and the CNI plugins (the `go` line of their `go.mod`), etcd (the `toolchain` line of `server/go.mod`), Kubernetes (its `.go-version`), gaon (the `toolchain` line of its `go.work`) and aws_signing_helper (`GO_TOOLCHAIN` in its `pin.env`, `go1.27.3`). `install-go.sh <release> <binary> <dest>` in `image/pkgs/` runs `go version -m` on each shipped Go binary, each package passing `NARU_GO_VERSION` or the release it exported, and fails the build unless the binary names it. [ADR 0063](./adr/0063-the-image-is-built-inside-one-digest-pinned-builder-container-whose-toolchains-are-pinned-and-the-stage-2-direction-is-a-musl-toolchain-with-buildkit-built-packages.md) records why the projects are not rebuilt with the builder's Go.
- **The NSS gate is gone.** glibc's warning for a static link that calls `getpwnam`, `getaddrinfo` or `dlopen` had a script (`nss_gate`) and an allow list for the one program that linked statically with cgo. The packages of `image/pkgs/` link musl, which prints no such warning, and the Go programs are built with `CGO_ENABLED=0` but for aws_signing_helper, which links statically against musl with cgo ([ADR 0075 erratum](./adr/0075-the-images-packages-are-built-by-buildkit-from-one-bake-graph-against-a-musl-toolchain-built-from-source-and-assembled-by-tooling-disk.md)).
- **No stamp.** A package of `image/pkgs/` has no stamp: BuildKit's cache is its stamp, and `make image-repro` builds the packages with `--no-cache`.
- **What it measured.** `make image-repro` builds the packages twice with `--no-cache` and runs `make release` twice in the builder, into `build/repro/1` and `build/repro/2`, and `image/repro.sh` compares the manifest digest of every package and the two `SHA256SUMS`. On 2026-11-15 on the workstation, 10 of the 13 assets had the same SHA-256 in both builds (the host disk, the upgrade bundle, the Node kernel, initramfs and manifest, the guest manifest, the inputs file, the orch extension and its manifest, naructl); the data disk and the two test user-data files differed. The test user-data files have been reproducible since [ADR 0078](./adr/0078-the-releases-test-user-data-derives-its-authority-and-tokens-from-the-version-so-only-the-data-disk-differs-between-builds.md); the data disk differs in every build, by design (Release assets).
- **The two machines.** The release workflow ran on tag `v0.0.0-craft-178.5` on a GitHub-hosted `ubuntu-24.04` runner (run 43698831849, `make ci` then `make release`). The runner built the builder with the manifest digest `sha256:50e9de7b...9d41a` and the config digest `sha256:ace58aed...3b7d` the workstation has. `make image-repro REFERENCE=<the run's SHA256SUMS> VERSION=v0.0.0-craft-178.5` built the same commit on the workstation and found 10 of the 13 assets with the same SHA-256 as the runner's; the data disk and the two test user-data files differed (the user-data files then; see above). The test release and its tag were deleted afterwards. The release carries no signature of `SHA256SUMS`: signing is [#188](https://github.com/garamsh/naru/issues/188).

## The package graph

[ADR 0075](./adr/0075-the-images-packages-are-built-by-buildkit-from-one-bake-graph-against-a-musl-toolchain-built-from-source-and-assembled-by-tooling-disk.md) moves the non-Go packages out of the builder's compiler. `image/pkgs/docker-bake.hcl` is the graph; each target is `image/pkgs/<name>/Dockerfile` with a `pin.env`, and a dependency is a named context (`target:toolchain`). `make image`, `make image-upgrade`, `make disk` and `make release` run `image/pkgs/build.sh build/pkgs` on the host first, because it needs the Docker daemon with `buildx`, and then the builder container.

- **The build.** `build.sh` creates (or reuses) a `docker-container` buildx builder of the pinned `BUILDKIT_IMAGE`, runs `docker buildx bake` with provenance and SBOM off, and exports each package as `build/pkgs/<name>.tar`, an uncompressed OCI image with timestamps rewritten to `SOURCE_DATE_EPOCH`. The first target, the builder, is the stage 0 of every package; its config digest is checked against `BUILDER_CONFIG_DIGEST` and its tar is then removed.
- **The toolchain.** `image/pkgs/toolchain` builds binutils, the kernel's UAPI headers, musl's headers, a C-only gcc, libgcc and musl itself into `/toolchain`, target `x86_64-linux-musl`, from tarballs pinned by SHA-256 in its `pin.env` (provenance in the ADR). Every other package's Dockerfile starts from it and sets `CC` to its compiler.
- **A package** is a Dockerfile whose last stage is `FROM scratch` with only its installed files: programs under `/usr/bin` or `/usr/sbin`, libraries and headers under `/usr/lib` and `/usr/include`, the bundle at `/etc/ssl/certs`. A library goes into the next package's sysroot by `COPY --from`.
- **What every program passes.** `image/pkgs/install-bin.sh` strips a linked program and fails the build unless it is statically linked, names no Ubuntu compiler in `.comment`, and shows no `iconv` symbol in `nm` (the CVE statement of the ADR).
- **Reading a package.** `naru-pkg` (`tooling/disk/cmd/naru-pkg`) unpacks a package's tar into a directory and prints a package's manifest digest; `image/pkgs/layout.sh` unpacks the packages `make image` needs into `build/pkgroot/` and places them as `build/image/` (`bzImage`, `bzImage.bare`, `initramfs.cpio.gz`, `node-initrd.cpio.gz`, `boot-sets.json`, `inputs.env`, `guest/`, `extensions/`, and the directories `gaon/`, `etcd/`, `k8s/` and `regtools/` of programs the tests and the release take).
- **Every part of the image is a package.** The Go programs, the kernels, the guest, the initramfs archives and the extension were the last `build.sh` files; they were converted in phase B ([ADR 0075](./adr/0075-the-images-packages-are-built-by-buildkit-from-one-bake-graph-against-a-musl-toolchain-built-from-source-and-assembled-by-tooling-disk.md) item 9). The repository's root `.dockerignore` narrows the `src` context to the Go workspace, and `build.sh` takes the version from `NARU_VERSION`.

## What the host needs

- Linux x86_64 with `/dev/kvm` readable and writable by the user. The Nodes run Firecracker inside QEMU, which needs nested KVM: `/sys/module/kvm_intel/parameters/nested` or `/sys/module/kvm_amd/parameters/nested` reads `Y` or `1`. The tests were run on a host where `kvm_amd` reads `1`.
- To build: Docker with a daemon the user can reach (Podman, `DOCKER=podman`, is expected to work and is untested), and network access; the compiler, Go, Rust, the kernel's build dependencies, the squashfs, dosfstools, gdisk and qemu tools are in the builder container, not on the host ([The builder](#the-builder)). `make ci` needs Go at the version `go.work` names.
- To boot it: the 4 MiB OVMF files named above (the Debian `ovmf` package).
- To boot: `qemu-system-x86_64` (with the `ide-cd`, `scsi-hd`, `virtio-scsi-pci` and `virtio-net-pci` devices), and `/sbin/mkfs.ext4` (e2fsprogs 1.43 or later for `-d`), which makes the data disk. The mkfs.ext4 mvmd runs is the image's own and needs nothing of the host.
- Network access for the first build: cdn.kernel.org, github.com, mirrors.kernel.org, static.rust-lang.org, go.dev, snapshot.ubuntu.com (only to build the builder image) and the Go module proxy.

## Pinned dependencies

`lib/init/go.mod` is covered in [init.md](./init.md). `tooling/qemu/go.mod`, `tooling/probe/go.mod` and `tooling/disk/go.mod` pin their modules (`tooling/disk` requires only `github.com/stretchr/testify`, at the version `tooling/qemu` pins); `go.sum` and the Go checksum database fix what each version means. The PM moves them: the PM reviews the pins when an advisory is published for one of them and at each Go minor release, and bumps the module in a pull request. No dependency bot is configured (`.github/` holds no `dependabot.yml`). The probe's `github.com/garamsh/mvmd/lib/runtimeapi` version is a pseudo-version of mvmd commit `b1a60cd649673a6db5fa72ca8cc23f088fd83639`, the commit `MVMD_COMMIT` names; it moved with the pin, in the pull request that moved it for aurora#811; the restart test runs this probe against the mvmd of the pinned commit.

## Open questions

- **Cloud-controller-manager add-on.** [ADR 0085](./adr/0085-a-service-of-type-loadbalancer-is-fulfilled-by-a-naru-cloud-controller-manager-that-asks-orch-for-an-address-from-a-pool-one-host-announces-it-on-the-lan-and-forwards-it-to-the-nodes-nodeports.md) (accepted) adds `naru-ccm` as an add-on of ADR 0083's mechanism; the kubelet flag it needs is `lib/layout`'s.

- **Cluster add-ons.** [ADR 0083](./adr/0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) decides that the image carries CoreDNS, a local-volume provisioner and the manifests that run them, pinned by digest; none is built yet, and the packages, the initramfs lists and this file follow in the pull requests that build them (garamsh/naru#264).
- **NetworkPolicy enforcement.** [ADR 0086](./adr/0086-kubernetes-networkpolicy-is-enforced-on-every-cluster-by-kube-network-policies-an-init-service-over-the-bridge-pod-network-that-a-cluster-setting-turns-off.md) decides that the image carries kube-network-policies as an init service before the kubelet and three kernel options; none is built yet, and the package, the Node's topology and this file follow in the pull request that builds them (garamsh/naru#266).
- **Installer.** How an image reaches a Node's disk is not decided.
- **A/B upgrade.** The disk, the bundle and the boot behaviour are decided ([ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md)), and so are the writer of the trial slot and of the boot entry, the health decision, the promotion and how a bundle reaches a Node ([ADR 0025](./adr/0025-an-upgrade-is-a-bundle-posted-to-v1-upgrade-which-init-writes-to-the-trial-slot-and-the-trial-boot-promotes-when-healthy-and-rolls-back-when-not.md)). What is not decided: a health check that a service defines, an operator's confirmation before promotion, and an upgrade of the ESP's other files.
- **Signing.** How an image, a kernel and a configuration are signed and verified is not decided.
- **Disk layout.** The boot disk's slots are decided (ADR 0020); how an installed Node's other disks are laid out, and where the system lives other than as an initramfs, are not decided. A disk of v0.4.0 or earlier is recreated once.
- **Memory of the guest files.** They are in the tmpfs root, about 20.3 MiB ([ADR 0010](./adr/0010-the-guest-kernel-and-initrds-are-image-components-built-at-the-pinned-mvmd-commit.md)); whether a Node should hold them elsewhere is not decided.
- **Selecting a guest kernel.** mvmd offers every kernel of `guest.json` to a Machine by name (garamsh/mvmd#364); no gaon Machine names one yet (garamsh/gaon#59), and no test in this repository creates a Machine with a kernel other than the default.
- **How the other mvmd obligations are met.** The capabilities' grant and the nftables ownership are not decided; they wait under [boundaries.md](./boundaries.md) §Open questions. The cgroup placement of supervisors is decided: [init.md](./init.md) §What init requires of mvmd's placement.
