# Init

What naru's init does as PID 1 of a Node: how it boots, starts, supervises and stops the services, and what it requires of them.

Claims about garamsh/mvmd hold at commit `1b08e5e04273b8839f66d9e154bf96086fbc3d23`; they promise nothing about later versions.

## Current decisions

- **Unit.** Init is the library module `lib/init`, whose package `lib/init/run` is the body of PID 1. Two thin binaries call it, `host/cmd/naru-init` and `node/cmd/naru-init`, each a static binary (`CGO_ENABLED=0`), since the image has no libc (ADR 0004, ADR 0039); the host image installs the first as `/init` and the node initrd carries the second as its `/init` (ADR 0039, [ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md)). It refuses to run unless it is PID 1, except as `naru-init -validate <file>`, which parses the file as `naru.yaml` with the parser init uses at boot, prints the Node's name and service count, and exits 0, or names the refusal and exits 1; the release's tests use it.
- **Init sets no hostname.** The kernel's hostname stays `(none)`. Every consumer is given the Node's `metadata.name` by a flag or a file, which `lib/layout` writes: `naru-hostd --host-id` (`lib/layout/host.go`), `--node-name` for gaon's Node Agent (`lib/layout/layout.go`), `--hostname-override` for kubelet and kube-proxy (`lib/layout/kubernetes.go`) and `--name` for orch's etcd (`lib/init/config/daemons.go`). Those flags are what each program takes on any host, so no workaround stands in for a missing step. `naru-hostd` falls back to `os.Hostname()` only when `--host-id` is absent, and the layout always passes it. Decided in garamsh/naru#195: a hostname would add a step no program asks for. The decision changes if a service must read the kernel's hostname, and then init sets it from `metadata.name` right after step 3.
- **Boot order.** Init does these in order, and stops at the first that fails:
  1. leaves the initramfs's rootfs: copies the initramfs to a tmpfs, moves that tmpfs over `/` and chroots into it, the copy keeping each file's owner, mode with its set-user-ID, set-group-ID and sticky bits, extended attributes and hard links (a socket or FIFO is not copied) (the kernel refuses `pivot_root` from the rootfs, which mvmd's supervisor does for each VMM), then makes `/` and the mounts under it shared, so every mount made later is, which a container's `Bidirectional` volume needs and mvmd's supervisor undoes in its own namespace before its `pivot_root` ([ADR 0090](./adr/0090-a-volume-is-made-where-its-disk-is-by-a-provisioner-per-node-a-disk-the-node-uses-is-never-handed-out-and-an-operator-frees-a-retained-disk-by-deleting-its-volume.md));
  2. mounts `/proc`, `/sys`, `/dev` (devtmpfs), `/dev/pts`, `/run` (tmpfs), `/tmp` (tmpfs) and `/sys/fs/cgroup` (cgroup2), and makes Ctrl-Alt-Del deliver SIGINT to init;
  3. finds the block device whose ISO 9660 label is `cidata`, mounts it read-only, and parses `user-data` as `naru.yaml` and `network-config` ([config.md](./config.md)); when no disk has that label, init takes the seedless path in the next item instead ([ADR 0072](./adr/0072-an-admitted-host-boots-from-its-stored-configuration-and-network-with-no-seed-attached.md));
  4. applies the network: sets `lo` up, then sets each link of the configuration up, adds its address and the default route through netlink, writes `/run/naru/resolv.conf`, and logs `network configured`; a DHCPv4 interface gets all of that from a lease instead, and a Node whose drive has no `network-config` runs DHCPv4 on the first Ethernet link with a carrier ([ADR 0058](./adr/0058-a-host-boots-from-a-join-form-that-names-an-orch-and-an-enrollment-key-and-init-applies-the-configuration-hostd-brings-back.md));
  5. finds, checks and mounts the data disk (for a join form, first formatting the first blank disk that is not the boot disk when no disk is labelled `NARUDATA`), then chooses the effective configuration (the next item); steps 1 to 5 act on the base, the `user-data`, and steps 6 to 14 on the effective configuration;
  6. starts the Node API, when the effective configuration has `spec.api`: it opens the listener on `spec.api.listen` and logs `the Node API is listening`, or logs `the Node API is off` and serves nothing when there is no `spec.api`; a listener that cannot be opened (an address in use, a serving pair that does not load, a `spec.api.keyFile` that cannot be read) is a refusal;
  7. turns on forwarding for the families `spec.network.forwarding` names;
  8. installs the routes `spec.network.routes` lists, each a static IPv4 route to `to` through `via` (a replace, so a route already there is not an error); a route the kernel refuses is logged at error level, with the route and the reason, and the boot goes on;
  9. writes the files `spec.files` lists;
  9a. writes the registry files `spec.registries` and `spec.aws` give, as `/run/naru/registry/credentials.json` (mode `0600`, always) and `/run/naru/registry/ca.pem` (every host's CA in one file, mode `0644`, while some registry has one) ([ADR 0026](./adr/0026-a-node-takes-registry-credentials-and-trust-as-configuration-an-ecr-credential-comes-from-iam-roles-anywhere-and-an-agent-pair-without-the-required-organization-is-set-aside.md)), and makes mvmd's `HOME`, `/run/naru/registry/home`, with mode `0700` ([ADR 0029](./adr/0029-aws-credentials-is-a-service-serving-the-instance-metadata-endpoint-to-mvmd.md));
  9a2. mounts the system extensions `spec.extensions` lists, each read-only at `/usr/lib/naru/extensions/<name>` (`extension mounted`): for each name, init mounts the one entry whose stored image was built for init's own version (entries for other versions, or not stored, are logged and skipped), checks the digest as it reads the file, attaches it to a loop device and mounts it, and reads its manifest again from the mount; no entry for init's version, two of them, a digest that does not hold or a manifest that disagrees is a refusal ([ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)); an entry with no `sha256` takes the one stored image of its name built for init's version, and a bundle brings those images and init drops the ones built for another version ([ADR 0084](./adr/0084-an-upgrade-bundle-carries-the-extensions-the-hosts-configuration-names-and-an-entry-without-a-digest-is-resolved-by-init-to-the-image-built-for-its-version.md));
  9b. prepares the disks `spec.storage` lists ([ADR 0027](./adr/0027-a-node-offers-an-extra-disk-as-xfs-storage-for-mvmds-disks-formatted-when-blank-mounted-hardened-and-grown-at-boot.md)): for each, init finds the disk (an entry given by `device` or by `serial` first by the XFS labelled with its `name`, wherever the kernel put it, and by the device, or by the one disk whose sysfs serial matches, only when there is none: a serial that matches no disk is waited for and one that matches two finds none and formats nothing, [ADR 0079](./adr/0079-a-blank-storage-disk-is-named-by-its-serial-number-which-init-reads-from-sysfs-and-the-xfs-label-takes-over-after-the-first-boot.md); [ADR 0032](./adr/0032-a-storage-disk-is-found-by-the-xfs-label-init-gives-it-and-device-names-only-a-blank-disk.md)), formats it as XFS with reflinks (`storage disk formatted as XFS`) only when it is blank (one rule for this and the data disk, [ADR 0070](./adr/0070-shared-constants-are-defined-once-in-the-leaf-module-lib-wire-one-rule-says-when-a-disk-is-blank-and-a-test-parses-what-the-layout-writes.md): its first MiB and its last MiB are all zero, so no partition table, no file system and no backup GPT), never one that holds an XFS file system or anything else (an XFS labelled otherwise than the entry's `name` at its `device`, and the data disk there, are left alone) (data only past the first MiB is not seen, and such a disk is formatted), mounts it at its mount point with `nodev,nosuid,noexec` and `prjquota` (`storage disk mounted`; the project quotas are what `naru-volumes` limits a local volume with, [ADR 0083](./adr/0083-a-control-plane-node-applies-pinned-cluster-add-ons-from-its-image-with-an-init-service-and-every-node-imports-their-images-so-coredns-and-a-local-volume-provisioner-run-by-default.md) item 8: XFS counts the blocks of a disk that was mounted without them at the first mount with them, so the first mount of a blank disk, which init has just formatted, counts nothing, and a disk that held data is counted for a time that grows with its inodes; that time has not been measured, and no boot step waits for it beyond the mount call itself), and grows the file system to the device when the device is larger (`storage file system grown`); a disk mounted at `wire.MvmdStorageMount` (the first of `gen node --storage`) also gets `disks/`, `snapshots/` and `disk-snapshots/` directories of mode `0700` that mvmd's state directory links to (`mvmd's disks, snapshots and disk snapshots linked into storage`): an empty directory there, as an earlier release left, is replaced by the link (user-data written by an earlier `naructl` still names the old mount point, so init does not link, and mvmd keeps refusing until new user-data is applied), a link that is right stays, a directory that holds entries has each moved into the storage target first (copied under a temporary name, fsynced, renamed, then removed from the data disk, so an interruption leaves it whole in one place and the next boot finishes it; `storage entry moved from mvmd's state directory`), and an entry whose name is taken there with other content, or a link to elsewhere, is logged at error level with both paths and that mvmd will refuse to start ([ADR 0073](./adr/0073-mvmds-disks-snapshots-and-run-directories-are-on-the-first-storage-disk-through-links-while-its-state-directory-stays-on-the-data-disk.md)); a disk that is missing, whose first MiB holds something else, or whose mount point already holds files is logged at error level, with the reason, and the boot goes on;
  10. sets the clock from `spec.time` when the effective configuration has it, within 10 s, and logs `time synchronised`; with no `spec.time` it uses the time servers (option 42) of the DHCPv4 lease, port 123, and when the lease named none it logs `time is not synchronised: the configuration has no spec.time and the lease named no time server`, and when no server answers it logs a warning and goes on;
  11. issues the certificates `spec.pki` lists, when it lists any, with the Node's addresses as the network gave them, which are those of `network-config` or the DHCPv4 lease's;
  12. prepares the cgroup tree;
  13. remounts `/` read-only (`MS_REMOUNT|MS_RDONLY`), by which time every mount point exists, and logs `root remounted read-only`;
  14. starts each service in file order, first setting aside a kept agent pair whose certificate lacks the service's `keptPair` Organization (renamed to `<file>.o-less`, logged `kept pair set aside`, never a refusal of the boot), leaving out one marked `controlPlane` on a Node whose `spec.controlPlane` is false. A service that names `restartOnChange` is stopped and started again, with no backoff, when the SHA-256 of one of those files (checked every 5 seconds) is not what it was at its start (`a watched file changed, restarting`); one that names `logFiles` has the lines appended to them copied to its console source, from where it started ([ADR 0029](./adr/0029-aws-credentials-is-a-service-serving-the-instance-metadata-endpoint-to-mvmd.md)).
- **A boot with no seed.** When no NoCloud drive is attached (after the wait for a disk), init does not format and does not parse a base ([ADR 0072](./adr/0072-an-admitted-host-boots-from-its-stored-configuration-and-network-with-no-seed-attached.md)):
  - it finds the data disk by the default label `NARUDATA` and mounts it at `/var/lib/naru` (`lib/wire`); a Node whose data disk has another label needs its seed;
  - it runs the stored configuration, which has no base to compare its digest with, and brings the network up from the `network-config` stored beside it (`network-config` in the store's directory), which every boot that has a seed writes;
  - it refuses, naming both reasons, when the disk cannot be mounted, when there is no stored configuration or it does not validate, and when no `network-config` was stored: a host that last booted before init stored it must boot once with its seed attached before the seed is detached;
  - a seed attached again wins, under the digest rule of step 5, and its `network-config` is stored again.
- **Init runs a DHCPv4 client** (`lib/init/dhcp4`, [ADR 0058](./adr/0058-a-host-boots-from-a-join-form-that-names-an-orch-and-an-enrollment-key-and-init-applies-the-configuration-hostd-brings-back.md)), over a raw packet socket and a UDP socket, with no libc.
  - **Exchange.** DISCOVER, OFFER, REQUEST, ACK; an offer without a subnet mask, server identifier or lease time is ignored; after a NAK the client waits and starts again; requests are retransmitted with a doubling timeout, 4 s to 64 s.
  - **Boot.** With no `network-config` init picks the first Ethernet link with a carrier, bringing Ethernet links up and waiting up to 30 s for one. A boot that gets no lease within 90 s is refused.
  - **Lease.** Init adds the leased address, the default route when the lease has a router, and writes the nameservers (option 6) to `/run/naru/resolv.conf`; a `nameserver` entry in `network-config` wins over option 6. The lease's address is the Node's address for `spec.pki` and for every other reader, through one accessor.
  - **Renewal.** For as long as the boot lasts: at T1 (the server's option 58, else half the lease) a unicast renewal to the server, at T2 (option 59, else 7/8) a broadcast rebind, and at expiry the address and the default route are removed, a warning is logged and the client starts again. A new address replaces the old; the certificates issued at boot are not issued again for it.
- **A join form is a whole configuration init derives** ([ADR 0058](./adr/0058-a-host-boots-from-a-join-form-that-names-an-orch-and-an-enrollment-key-and-init-applies-the-configuration-hostd-brings-back.md)). `spec.join` (`orch.url`, `orch.caSHA256`, `enrollKey`) alone makes init derive the data disk, the key file and the service `naru-hostd` in join mode.
  - **Data disk.** The disk whose ext4 label is `NARUDATA`; else the first blank whole disk other than the boot disk (the disk holding the partition with PARTUUID `cb4162e7-9d1e-48df-b937-f5792071b950`), which init formats and labels; else the boot is refused. A disk is blank when it has no partition table and no file system signature in its first and last MiB.
  - **Service.** `naru-hostd --join` with `--orch-url`, `--orch-ca-sha256`, `--enroll-key /run/naru-hostd/enroll.key` (a derived file, mode `0600`, root-owned), `--host-key /var/lib/naru/hostd/host.key` and `--join-config /var/lib/naru/join/config.yaml`. It has restart policy `on-failure`: no restart after an exit with status 0, a restart with backoff after any other exit.
  - **Handoff.** When the service exits with status 0 and `/var/lib/naru/join/config.yaml` exists, init applies it as a whole configuration in `reboot` mode through the apply engine, removes the file, logs `join configuration applied revision=<n>` and reboots. A configuration with `spec.signer`, `spec.orch` or `spec.join`, one that does not parse or one the engine refuses is logged as `join configuration refused` with the reason, the file is renamed `config.yaml.refused`, and the service is not started again before the next boot. On the next boot the stored revision stays in force, because its base digest is the join form's.
  - **Apply.** While the running configuration is a join form, an apply may set `metadata.name` and `spec.dataDisk`, which are otherwise never changed.
- **A service may run as another user.** `spec.services[].user` (`uid`, `gid`, `groups`) is the credential of the child, set at its start; `dirs` (`path`, `mode`, `uid`, `gid`) are made, chmodded and chowned before it starts; `setup` is a list of steps (`args`, `unless`), each the service's own binary run to completion as the service's user before the service starts, in order. A step is skipped while any path of its `unless` exists, and one that fails stops the start of that service like any failed start. A step ends when the service is stopped, or when it has run for 5 minutes, and its cgroup is killed then, so a step that waits for a peer that is not there does not keep `StopAll`, and so a power-off, from returning; the start then fails like any failed one. `spec.files[].owner` (`uid`, `gid`) is applied to the file and compared by an apply, so a change of owner rewrites the file. ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md))
- **Init runs orch and the signer from their sections.** Their binaries are in the `naru-orch` system extension, `/usr/lib/naru/extensions/naru-orch/bin/naru-orchd` and `.../naru-signer`, so a Node that sets `spec.signer` or `spec.orch` must list that extension in `spec.extensions` ([ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)). Parsing derives the services `naru-signer` (user 6001, directory `/var/lib/naru/signer` 0700, socket in `/run/naru-signer`) from `spec.signer` and `naru-orchd` (user 6002 with the supplementary group 6001, directory `/var/lib/naru/orch` 0700) from `spec.orch`, with their files, in `/run/naru-signer` and `/run/naru-orchd`, and the setup steps of the signer: `init` for a bootstrap, `join-key` then `join` for a replica. It gives orchd its own pair as the pair it presents to the hosts (`--host-client-cert`, `--host-client-key`) and, when `spec.orch.hostCA` is set, the file `/run/naru-orchd/host-ca.crt` (0644, restarts orch) as `--host-ca`. With `spec.orch.restore` it gives orchd `--restore`; with `spec.orch.join`, a running member's client URL, it gives orchd `--join <url>` and `--initial-cluster-state=existing` and no `--initial-cluster`, since the member takes the initial cluster from the cluster it joins, so a section with `join` has no `initialCluster` and no `restore`. It adds the flags to `naru-hostd` that `spec.host.network` and `spec.host.orch` give, and the file `/run/naru-hostd/enroll.key` (0600, root's). All of it is derived again at each parse and removed when its section goes. ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md))
- **Init serves metrics** when `spec.metrics.listen` is set: Prometheus text at `/metrics` on that address, port 9100, with `naru_init_service_state{service,state}` and `naru_init_service_restarts{service}`. The same address is given to hostd (9101), orch (9102) and the signer (9103) as `--metrics-addr`. An apply that changes the listener needs a reboot. ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md))
- **The root is read-only when the first service starts.** The system is never written after init's seal; a service writes only to the mounts above (`/run`, `/tmp`, the data disk). A refusal to remount stops every service like any other refusal.
- **The Node API checks revocation** when `spec.api.revocationPublicKey` is set: it refuses a client certificate on the signed list at the handshake, reading the list from the local signer socket (`spec.signer`) or orch's `GET /v1/crl` (`spec.host.orch`), keeping the last verified list at `<data>/api/crl.json`, and refusing every client when the list is missing or older than `spec.api.revocationMaxAge` (default 10 minutes) ([ADR 0062](./adr/0062-every-naru-tls-peer-is-checked-against-the-signed-revocation-list-by-one-verifier-in-lib-identity-and-fails-closed-when-the-list-is-older-than-its-max-age.md)). A reload changes the key and the max age and keeps the source; a key with no source is refused. Without the key it logs `no spec.api.revocationPublicKey` at start and checks the client CA only. `/metrics` carries `naru_init_revocation_list_age_seconds`, `_seq` and `_fetch_error`.
- **A refusal stops every service.** A root that cannot be left (step 1) and pseudo file systems that cannot be mounted (step 2) are refusals too: init is then in a half-deleted root or without `/proc`, so it logs `boot refused; nothing is started` with the reason and starts nothing, not even the network, and waits for a signal to power off or reboot (the kernel panics if PID 1 exits). A configuration or network-config that does not parse or fails validation, a network that cannot be applied, a file that cannot be written, a certificate that cannot be issued (a clock no server could set is not a refusal), a data disk that is refused, a system extension that cannot be mounted, a Node API that cannot listen, a forwarding setting that cannot be written and a cgroup tree that cannot be built and a root that cannot be remounted read-only each stop the sequence before the first service starts. Init logs the reason, with the field named for a configuration error, to the console and stays up, so the reason stays readable and the Node can still be powered off by signal. It starts no service afterwards, but a host's maintenance-mode hostd. Services that started before the refusal keep running and are supervised, and the certificates init issued for them are still renewed. A route the kernel refuses (step 8) is not a refusal, nor is a storage disk that cannot be prepared (step 9b), nor is a clock no server could set. A refusal after step 6 leaves the Node API serving, read-only: `GET` answers from the configuration chosen at step 5 and the services' state, and `POST /v1/config` answers 500, because the apply engine exists only once the boot has finished. A refusal at or before step 6 leaves no API.
- **A host's refusal enters maintenance mode, and a reset is carried out after the data disk mounts** ([ADR 0082](./adr/0082-a-host-resets-its-store-its-data-disk-or-both-through-post-v1-reset-at-its-next-boot-and-a-refused-host-serves-maintenance-mode-to-operators-under-orchs-host-ca.md)). When a host's boot is refused, init starts a derived `naru-hostd --maintenance` if it has an anchor (orch's URL and the SHA-256 of its host CA from the seed, or the stored `config/maintenance.json`) and a revocation key, and it logs why when it does not; this is the one service a refusal starts. After the data disk mounts, init reads and removes `config/reset.json` and carries out its scope (`store`, `data`, `all`). A Node, which has no such call, is replaced, not reset.
- **The effective configuration is stored, and chosen at boot.** The `user-data` is revision 0. After the data disk mounts, init reads `/var/lib/naru/config/store.yaml` (`revision`, `baseSha256`, `config`) and uses the stored configuration when `baseSha256` equals the SHA-256 of the current `user-data` and `config` validates as `naru.yaml` does. Otherwise it uses the `user-data`, logs `stored configuration discarded; running the base as revision 0` with the reason (the base changed, or the stored configuration is not valid), and stores the base as revision 0; a failure to store it is logged and does not stop the boot. A store that exists and cannot be read (an I/O error, not a missing file) is kept: init logs `stored configuration kept; running the base as revision 0 for this boot and storing nothing` with the error, runs the `user-data` for that boot and writes nothing, so a transient read failure does not cost the operator's revisions. Until the store can be read again an apply is refused: the store's save re-reads first and, on an unreadable store, writes nothing, so the apply is a 503 that changes nothing and says a reboot or repair of the data disk is needed. A Node with no store runs its `user-data` and writes none. The store is written to a temporary file in its directory, synced, renamed over `store.yaml`, and the directory is synced ([ADR 0018](./adr/0018-a-nodes-configuration-is-a-base-and-numbered-revisions-stored-on-the-data-disk-and-changed-by-merge-patch.md)).
- **Init applies a configuration change on a running Node** through one engine (`lib/init/apply`), which takes a revision, a merge patch or a whole configuration, a mode (`no-reboot`, `staged` or `reboot`) and `dryRun`, and returns the new revision and the actions, or an error of one of three kinds: stale revision (409), invalid (422, naming the field) or failed (500). Applies are serialised by one lock. The steps:
  1. The engine merges the patch into the stored configuration (RFC 7386, with `spec.services` merged by `name`, `spec.files` by `path`, `spec.storage` by `name`, `spec.network.routes` by `to`, `spec.registries` by `host`, `spec.extensions` by `sha256` and `spec.pki.authorities` and `spec.pki.certificates` by `name`: a new key is appended, `$patch: delete` removes an element and names a missing one as an error, and every other list is replaced whole), validates the result as `naru.yaml` is, and refuses a change to a field of the never class, or of the reboot-only class in `no-reboot` mode, and any `REDACTED` that stands where the stored value was not `REDACTED` in a place of the table of private material (below). `staged` stores a reboot-only change and acts on nothing, and `reboot` does the same and then has the caller reboot the Node (the result says so, and a dry run only lists the `reboot node` action); later `no-reboot` applies plan against the running configuration, so they refuse while the stored configuration differs from it in a reboot-only field.
  2. A `dryRun` returns the actions and writes nothing.
  3. The store is written before any live action. A store that cannot be written is a 500 with no action taken.
  4. The live actions, in this order: `delete-route` for each route whose `to` is gone and `add-route` for each route whose `to` is new or whose `via` changed (a changed `via` is one `add-route`, which replaces the route; both run before any file or certificate step, and the target is the prefix); `write-file` for each file whose path is new or whose `mode` or `content` changed; `write-registries` once when the files `spec.registries` and `spec.aws` give differ (the target is `spec.registries`); `issue-certificate` for each certificate that is new or changed (its `restart` included), which the issuer signs again at once and places like a renewal, without the renewal's restart; `forget-certificate` for each deleted certificate, which gives the issuer the new spec so it stops renewing it and restarts nothing; `sync-time` when `spec.time` is added or its servers change, which has init ask the servers at once, and `stop-time-sync` when `spec.time` is removed, after which init asks none and leaves the clock where it is (both run first in the plan, before any file or certificate); `reload-api` when `spec.api` changed; `stop` for a removed service, or one no longer started on this Node; `start` for an added one; `restart` for a changed one; and `restart` for each service a changed file or certificate names, unless it was already started or restarted in this apply. An unchanged service is not touched. A failed action is a 500 naming the actions done and the one that failed: nothing is rolled back, the revision stays stored, and the next apply merges into the stored configuration and plans its actions against the configuration that last applied in full, so it repeats the actions that failed.
  5. `spec.pki` renewals and applies share the issuer's lock, which covers its state and every write of a certificate and key, so a renewal and an issue at the same time take turns and neither's write is lost. A renewal after an issue finds the certificate not due.
  The engine is built in `lib/init/run` once the boot has finished, holds the effective configuration, and is what `POST /v1/config` calls ([ADR 0018](./adr/0018-a-nodes-configuration-is-a-base-and-numbered-revisions-stored-on-the-data-disk-and-changed-by-merge-patch.md)).
- **Init serves the Node API** from the package `lib/init/api`, in init's own process: HTTPS with JSON on `spec.api.listen` (`0.0.0.0:50000` when it names none), TLS 1.3 only, with the serving pair `spec.api.certificate` and `spec.api.key` and a client certificate required and verified against `spec.api.clientCA`. A client whose certificate another authority signed fails the handshake; handshake failures are not logged, so a client that cannot complete one cannot fill the kept console log. The client's role is the highest of the Organizations of its certificate: `naru:admin` may read and apply, `naru:reader` may only read, and any other certificate gets 403 on every endpoint. A request other than a `GET` needs `naru:admin`. The endpoints, in the shapes of [ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md):
  - `GET /v1/version`: the version, the kernel's boot ID (`/proc/sys/kernel/random/boot_id`), the uptime in seconds, the `slot` of the kernel running (`trial` from a trial boot until it is promoted, otherwise `default`) and, once an upgrade has ended, `lastUpgrade` (`from`, `to`, `result`, `reason`, `time`). The version is the release's `VERSION` when the image build gave it (the `initramfs-host` and `initramfs-node` packages of `image/pkgs/` build `naru-init` with `-ldflags -X github.com/garamsh/naru/lib/init/run.buildVersion=$NARU_VERSION`, which `make image` and `make release` set from `VERSION`, a tag such as `v0.1.0-dev.5` for a release), else the module version or the commit init was built from, and `devel` when the binary carries none of them.
  - `GET /v1/services`: each service of the effective configuration, in file order, with `state` (`running`, `backoff`, `exited` or `stopped`: `exited` is a service that ended with status 0 under restart policy `on-failure` and is not started again, and `stopped` one init does not supervise), `pid` (0 unless running), `restarts` and `startedAt`; a configured service init does not supervise is `stopped`. A service init supervises that the configuration does not name follows them. A service that runs from a system extension also has `extension`, the extension's name, and the empty string otherwise.
  - `GET /v1/extensions` (`naru:reader`): every stored extension image, ordered by SHA-256, with `name`, `version`, `services` (from its manifest), `size` and `mounted` with `mountPoint` ([ADR 0055](./adr/0055-orch-and-the-signer-are-delivered-as-a-system-extension-a-squashfs-image-init-mounts-read-only.md)). `PUT /v1/extensions/{sha256}` (`naru:admin`) stores the body, which must be an image whose SHA-256 is the path's and whose `/manifest.json` is valid (`400` for a digest or an image that does not hold, `413` for a body over the store's bound), and `DELETE /v1/extensions/{sha256}` removes an image that is not mounted (`409` when it is, `404` when none is stored). A Node without a store answers `501`. Both are served on a Node whose boot was refused, so that a missing image can be delivered.
  - `/v1/signer/{path}` (`naru:admin`, any method): forwarded to `/v1/{path}` of the signer's unix socket, `/run/naru-signer/signer.sock`, as the signer's own request (its `Host`, the request's `Content-Type` and `X-Naru-Request` and no other header), with the body streamed up to 1 MiB (`413` over it, `400` for a path that is not clean) and the signer's status, `Content-Type` and body returned unchanged. A Node with no `spec.signer` answers `404`, a socket that cannot be dialled `503`, another failure of the exchange `502`. init signs nothing and adds nothing the signer trusts, and logs no body ([ADR 0057](./adr/0057-an-operator-reaches-the-signer-through-the-node-apis-admin-role-which-forwards-v1-signer-to-the-signers-unix-socket-and-adds-no-authority.md)).
  - `GET /v1/services/{name}/logs`: the service's kept lines as `text/plain`, and with `follow=true` the response stays open and each line is written as it is kept, until the client closes it. An unknown name is 404.
  - `GET /v1/time`: `configured` and the `servers`, `synchronised` (a synchronisation has succeeded since boot or since `spec.time` was last changed), `lastSync` (`at`, `server`, `offsetSeconds` as measured before the correction, `delaySeconds`, `correction` `step` or `slew`) once there is one, and `lastError` with `lastAttemptAt` while the latest attempt found no server. Readers may call it.
  - `GET /v1/config`: the revision and the configuration, with `REDACTED` in place of every string the allow-list does not show; a field that is empty is not redacted. The allow-list is one map in `lib/init/apply` of the places shown in clear (a YAML path, `[]` for a list element), and both the redaction and the refusal of a placeholder read it, so a place is hidden and refused together, and a field the configuration gains later is hidden until it is listed. Only strings are replaced; a number or a boolean cannot hold a key. A file's `content` is shown only when group and other can read the file. The places hidden today are: `spec.api.key`, each `spec.pki.authorities[].key`, the `content` of each `spec.files` entry that gives group and other no read, each `spec.registries[].credential.password`, `spec.host.orch.enrollKey` and `spec.join.enrollKey`. A configuration taken from this endpoint and applied back is therefore refused (422, naming the places) and changes no secret. The configuration is returned as the document with a top-level `status` beside `spec`: `version`, `bootId`, `slot` and `lastUpgrade` as `GET /v1/version` gives them, the `revision`, and `services`, each with `name`, `state` and `restarts` as `GET /v1/services` gives them. `status` is observed and never declared: it is in no stored configuration, and an apply whose patch or `config` names it is 422 with `fields: ["status"]` before the engine is consulted. A boot ID that cannot be read is 500, as for `GET /v1/version` ([ADR 0047](./adr/0047-a-nodes-state-is-served-as-a-status-block-of-its-configuration-document-an-apply-naming-it-is-refused-and-a-node-has-no-login-path-and-no-port-its-configuration-does-not-name.md)).
  - `POST /v1/config`: the apply engine's request and result. A stale revision is 409 with the stored `revision`, an invalid request 422 with `fields`, a failed live action 500 with the `revision` stored, the `actions` taken and the `failed` one, and a store that cannot be written 500; a body that is not an apply request (not JSON, an unknown field, no `revision`) is 400. Every refusal body carries `error`.
  An apply that changes `spec.api` makes the `reload-api` action swap the serving pair and `clientCA` for the next handshake, on the same listener; a connection already open keeps what it was made with. A pair that does not load leaves the old one in place and fails the action. Each request is logged once, with a `trace_id` init makes for it (init has no tracer), and a handler that panics is answered with 500.
- **The kept log is attributed per service.** Each service's pipe is copied to a writer of the console that tags the lines it completes with the service's name, and every kept line has a number that is never reused. The block the console re-prints is the lines in order, unchanged ([ADR 0009](./adr/0009-init-re-prints-the-console-log-at-a-fixed-interval-between-numbered-markers.md)). A service's lines are those kept since boot and not dropped for the bound, so `GET /v1/services/{name}/logs` returns no line the re-print has dropped. Lines init writes itself have no service.
- **Disks are found by label.** Init reads each device in `/sys/class/block` itself and does not use `blkid`: the data disk by its ext4 superblock (magic `0xEF53` at offset 1080, label at 1144), the NoCloud drive by the volume label of its ISO 9660 primary descriptor (32 bytes at byte 40 of sector 16, `cidata` in either case). A disk that has not appeared when it is first looked for is waited for, up to 10 s. A storage disk is found by the GPT partition name or XFS label a `spec.storage` entry's `label` gives, or, for a `device` or a `serial`, by the XFS label init gave the disk, the path or the serial (read from `/sys/class/block/<dev>/serial`, `device/vpd_pg80` or `device/wwid`) being used only when no such XFS exists and the disk is blank; the image has no udev to give it a stable name, and the kernel's own names change between boots.
- **The network is applied before any service.** A link is found by MAC address, else by name, and waited for up to 10 s. Init does not rename links. It runs a DHCPv4 client for a link whose `network-config` says `dhcp4` and for a Node with no `network-config` (the DHCPv4 client below). The resolvers are in `/run/naru/resolv.conf` and `/etc/resolv.conf` is a link to it, so the read-only root holds what services read. `/run/naru` is init's: a `spec.files` path may not be under it.
- **`spec.host` reaches `naru-hostd` as a file.** Parsing (`lib/init/config`) derives `/run/naru-hostd/host.json` from `spec.host` and puts it among `spec.files`, so a change of region or labels is one `write-file` step with no restart and no reboot; init starts no service of its own for it, and `naru-hostd` is an ordinary entry of `spec.services` that naructl writes ([ADR 0028](./adr/0028-naru-hostd-serves-a-host-api-over-mutual-tls-from-its-own-authority-and-creates-microvms-through-mvmds-runtime-api.md)).
- **init tells `naru-hostd` its version, slot and last upgrade in a file.** init writes `/run/naru-hostd/init.json` (the body of `hostapi.NaruInfo`: `version`, `slot`, and `lastUpgrade` once an upgrade has ended; init marshals that type, so the file has no second definition) once the data disk is mounted (where an earlier boot's upgrade outcome is kept), and again each time an upgrade ends (`upgrade.Config.Changed`, called after the outcome is recorded and the slot is set), atomically. `naru-hostd` reads it on each `GET /v1/host` ([host.md](./host.md)), because it holds no client file of the Node API's authority. A write that fails is logged and the boot goes on.
- **`spec.files` are written before any service starts**, under `/run`, with the mode the file gives, creating parent directories and refusing an existing file. A file changed by an apply is written to a temporary file beside it and renamed over it.
- **The clock is set from `spec.time` over SNTP.** Init asks the `host[:port]` servers in order (port 123 by default), over UDP, and uses the first that answers, each given 3 s and the first synchronisation at boot 10 s in all. It steps the clock when the offset is 128 ms or more either way and slews it (`adjtimex`) below that, then asks again every 300 s, or after 60 s when no server answered. The first successful synchronisation since boot steps by any offset, because the RTC may be years wrong; after it a step of 1 h or more (`timesync.StepBound`) either way is refused: the clock is left alone, the next server is asked, and when none steps the attempt fails with `ErrStepTooLarge`, which `GET /v1/time` shows as `lastError` and init logs at each retry; a reboot is the cure. Each step is reported to the certificate issuer ([ADR 0065](./adr/0065-a-step-of-the-clock-has-init-judge-every-certificate-against-the-new-time-and-a-step-of-an-hour-or-more-is-refused-once-the-clock-has-been-set.md)). It checks each reply (the origin timestamp equals what it sent, server mode, a stratum of 1 to 15, no alarm) and does not discipline the clock's frequency or compare servers ([ADR 0021](./adr/0021-init-keeps-time-from-spec-time-servers-over-sntp.md)).
- **`spec.pki` certificates are issued before any service starts, and renewed.** Init writes each authority's certificate, and its key only where the authority names a `keyPath`, then issues each certificate with a new ECDSA P-256 key made on the Node, writing the key mode `0600` and the certificate mode `0644` under `/run`, never to the data disk, and logs `authority written` and `certificate issued`. A certificate is valid for its `validity`, 720 h when it names none, and never past the authority's own expiry (init logs `authority expires soon` when the authority caps it); it is refused when that leaves under 1 h. The clock is the Node's wall clock at boot, set from `spec.time` just before when the Node has it, and otherwise what an emulated RTC gives a Node under Proxmox or QEMU. When two thirds of the life it was issued for has passed, init issues it again with a new key, writes the new key and certificate beside the old ones and renames them over, the key first, putting the old key back if the certificate's rename fails, and logs `certificate renewed`. After every renewal of a pass it restarts each service they name, once: stops it, kills what is left in its cgroup and starts it again with the same configuration. A service that is not running is not started by it. When the clock is stepped, init also renews at once each certificate that is not valid at the new time (expired by a forward step, not yet begun after a backward one) and works out again when the others are due; the renewal times are wall-clock, so a step moves them with the validity ([ADR 0065](./adr/0065-a-step-of-the-clock-has-init-judge-every-certificate-against-the-new-time-and-a-step-of-an-hour-or-more-is-refused-once-the-clock-has-been-set.md)). A renewal that fails is logged as `certificate renewal failed` and retried after a minute, and restarts nothing until it succeeds. A certificate that cannot be issued at boot stops the sequence like any other refusal, and when a later step refuses, init still renews what it issued, for the services that already started ([ADR 0013](./adr/0013-init-issues-certificates-at-boot-from-a-ca-carried-in-spec-pki-and-renews-them.md)).
- **A blank data disk is formatted only when `spec.dataDisk.formatBlank` asks.** A guest Node's host cannot format the data disk it gives it, so with `formatBlank: true` (which needs `label`, the label the file system gets) init formats, before step 5's mount, the one blank whole disk (its first and last MiB all zero) as ext4 with the `verity` feature and a 4096-byte block, using the image's `mkfs.ext4`, and logs `data disk formatted as ext4`. It uses the blank test of `spec.storage` (`isBlankDisk`), one rule for both. A disk labelled so already is left as it is, a disk that holds anything is never formatted, and two blank disks with none labelled so are an error, which refuses like a data disk that cannot be found: init does not guess. Without `formatBlank`, no Node formats the data disk, as before ([ADR 0034](./adr/0034-a-node-boots-as-a-microvm-from-a-guest-kernel-and-initramfs-the-image-carries-as-a-boot-set.md)).
- **The data disk is a precondition of every service.** Init mounts it with `nosuid,nodev` only if its superblock is ext4 and has the `verity` feature (`ro_compat` bit `0x8000`). Otherwise it refuses, says which check failed, and starts no service. The check is made on every boot, before the mount, so mvmd is never started on a disk without `verity`, which mvmd would refuse to start on (mvmd ADR 0008, as [ADR 0003](./adr/0003-naru-deploys-and-supervises-mvmd-builds-both-kernels-and-carries-mvmds-deployment-constraints.md) records it).
- **The data file system is grown to its disk at boot** ([ADR 0088](./adr/0088-orch-compacts-defragments-and-bounds-its-etcd-by-a-share-of-the-data-disk-drops-events-by-age-removes-a-member-that-stays-out-for-it-to-rejoin-empty-and-init-grows-the-data-file-system-to-its-disk.md)). After the mount, init reads the ext4 superblock and, when the device is larger than the file system, issues `EXT4_IOC_RESIZE_FS` on the mount point (`data disk file system grown`). A refusal is logged (`data disk not grown`) and the boot continues.
- **Every service runs in a cgroup of its own.** The hierarchy under the cgroup v2 root is:

  ```
  /sys/fs/cgroup                 cpu, cpuset, hugetlb, memory and pids enabled for children
  /sys/fs/cgroup/naru            the same
  /sys/fs/cgroup/naru/<service>  one leaf per service
  /sys/fs/cgroup/naru/detached   reserved, empty; processes a service places outside its own
  /sys/fs/cgroup/naru/kubernetes reserved, empty, the same controllers enabled for children; the kubelet's Pod cgroups (ADR 0031)
  ```

  A service is created in its leaf (`CLONE_INTO_CGROUP`), so it is never outside it. `detached` and `kubernetes` are reserved service names.
- **Stop touches only the leaf.** Init sends the service SIGTERM, gives it 5 s, then writes `cgroup.kill` in its leaf, waits for `cgroup.procs` to empty and removes the leaf. After every exit, init kills what the exit left in the leaf, so a restart starts from an empty cgroup. A process the service moved to another cgroup is in none of these and survives its stop and restart; it is killed at the Node's shutdown (see Signals). The real-cgroup test of that is `make test-cgroup`.
- **Restart backoff.** A service that exits, or that cannot be started, is started again after 1 s, doubling per consecutive exit up to 30 s. A run of 60 s or longer resets the delay to 1 s. A stop ends the wait.
- **Routes.** `spec.network.routes` are static IPv4 routes, installed through netlink with protocol `RTPROT_STATIC` and no link named, so the kernel picks the one that reaches `via`; validation refuses a `to` that is not a canonical IPv4 prefix, the default route, a `via` that is not a unicast IPv4 address or is inside `to`, and a `to` listed twice. They are in the live class of ADR 0018, and `spec.network.forwarding` is the only reboot-only field of `spec.network` ([ADR 0023](./adr/0023-spec-network-routes-are-static-ipv4-routes-init-applies-live.md)).
- **Forwarding.** Init writes `1` to `/proc/sys/net/ipv4/ip_forward` and `/proc/sys/net/ipv6/conf/all/forwarding` for the families named, before any service starts ([config.md](./config.md)).
- **Reaping.** One reaper owns `wait4(-1)` on SIGCHLD and reports the exit of each child init starts, so an exit is never lost to an orphan's reaping. Every child init starts goes through `Reaper.Spawn`, directly or through `Reaper.Exec` and `Reaper.Output`, which run a program to completion and return its status: the services, their setup steps and `mkfs`. No code in init waits on a pid of its own (`exec.Cmd.Wait`, `CombinedOutput`), because the reaper may have collected the child first and the wait would fail with ECHILD, reporting a program that succeeded as failed. Every other child, orphans reparented to init included, is collected.
- **A service's environment is what the file gives it.** Init passes no variable of its own, runs the service in a new session, and gives it a pipe as standard output and error, which init copies to the console (see the next item).
- **The console log is kept and re-printed.** From before its first mount, init keeps every line it logs and every line its services write, and every 30 s writes the newest of them that fit in 16 KiB again in one block ([ADR 0036](./adr/0036-a-re-print-carries-at-most-the-newest-16-kib-of-the-console-log-and-the-api-servers-liveness-probe-is-a-tls-request-that-it-can-answer.md): the serial port costs the guest time per byte, and a whole 1 MiB log stalled a Node): `NARU-LOG-BEGIN seq=<n> lines=<k> dropped=<d>`, the lines, then `NARU-LOG-END seq=<n>`, with `seq` rising from 1 and `dropped` the number of lines since boot the block does not carry. A reader that attaches late therefore has the newest 16 KiB within 30 s, and the rest through `naructl logs`. The kept lines are bounded at 1 MiB, and a line over 4096 bytes is kept as several; past the bound the oldest lines are dropped from the kept lines. Kernel messages are not kept. A reader of the log treats each line as possibly repeated ([ADR 0009](./adr/0009-init-re-prints-the-console-log-at-a-fixed-interval-between-numbered-markers.md)). **No writer waits on the console device** ([ADR 0030](./adr/0030-no-writer-of-the-console-waits-on-the-console-device-one-goroutine-writes-it-from-a-bounded-queue-and-a-loss-is-counted-on-the-device.md)): one goroutine writes the device from a queue of at most 256 KiB of live output, and the mutex guards only the kept lines and the queue. Output that does not fit is kept but not written to the device, and a re-print is copied from the kept lines and queued as one block, or skipped, without using a sequence number, while the previous block is unwritten. The device then gets a line `NARU-CONSOLE dropped=<bytes> skipped=<re-prints>` with what it was not given since the last such line, never inside a block. Init waits at most 2 s for the queue before it reboots or powers off.
- **`POST /v1/reboot`** (`naru:admin`, no body) answers `202` with `{"actions":[{"action":"reboot","target":"node"}]}` and is served on a Node whose boot was refused. A `POST /v1/config` in `reboot` mode answers `200` as the other modes do. For either, the handler sets `Connection: close`, writes and flushes the reply, and only then calls the reboot `lib/init/run` gave the API, which returns at once. From then on a request that is not a `GET` is answered `503` (`the Node is rebooting`), so no apply starts a service after the stop; a request already past that check is not stopped by it ([ADR 0022](./adr/0022-a-node-is-rebooted-through-the-node-api-by-post-v1-reboot-or-the-reboot-apply-mode-and-init-answers-before-it-stops.md)).
- **An upgrade is carried out by init** from the package `lib/init/upgrade` ([ADR 0025](./adr/0025-an-upgrade-is-a-bundle-posted-to-v1-upgrade-which-init-writes-to-the-trial-slot-and-the-trial-boot-promotes-when-healthy-and-rolls-back-when-not.md)). `POST /v1/upgrade` (`naru:admin`; the body is the bundle of [ADR 0020](./adr/0020-a-node-boots-one-kernel-file-per-slot-of-the-esp-with-the-initramfs-embedded-and-a-trial-slot-is-reached-once-by-bootnext.md), the query parameter `sha256` its expected SHA-256) finds the ESP by its partition GUID, mounts it only while it writes, streams the kernel into `TRIAL.EFI` up to 4 GiB while hashing the body, checks the digest and the manifest's kernel size and SHA-256, `fsync`s the file and its directory, writes `/var/lib/naru/upgrade/pending.json`, `Boot0100` and `BootNext=0100`, answers `202` and reboots as `POST /v1/reboot` does. A bundle that is wrong is `400`, one over the cap `413`, an upgrade that cannot start now `409`; none touches `BOOTX64.EFI` or the variables, and a partial `TRIAL.EFI` is removed. At start init mounts `efivarfs` and reads `BootCurrent`: `0x0100` is a trial boot. After the boot sequence a trial boot is judged: a refused boot gives up at once, recording `the boot sequence refused: ` and the refusal on one line, cut to 300 bytes as maintenance mode's reason is (`boot.Reason`); a trial that gives up leaves its reason in `TRIAL.WHY` beside `TRIAL.EFI` on the ESP, not on the data disk, which a refused boot may lack, and the default boot that follows reads it and removes it with the trial slot ([ADR 0091](./adr/0091-a-trial-boot-that-gives-up-leaves-its-reason-in-a-file-beside-the-trial-slot-on-the-esp.md)); otherwise, when every service started has run 30 s without a restart (a service in state `exited` counts as having run: a clean one-shot does not hold a trial back, [ADR 0025](./adr/0025-an-upgrade-is-a-bundle-posted-to-v1-upgrade-which-init-writes-to-the-trial-slot-and-the-trial-boot-promotes-when-healthy-and-rolls-back-when-not.md) Errata), init renames `TRIAL.EFI` to `BOOTX64.EFI`, `fsync`s the directory, deletes `Boot0100`, records `promoted` in `last.json` and logs `upgrade promoted`; when that has not happened 180 s after init started, or the rename fails, init records the reason and reboots without promoting. A default boot that finds `TRIAL.EFI` or `Boot0100` removes them, records `rolled back` with the reason and logs `upgrade rolled back`. That reason is `lastUpgrade.reason` of `GET /v1/version`, and `naructl upgrade --status` prints it. `POST /v1/upgrade` also refuses with `422` (`upgrade.ErrExtensions`), after it has read the manifest and before it arms the slot (the partial `TRIAL.EFI` is removed), when the stored configuration's `spec.extensions` names an extension of which the Node stores no image built for the bundle's version (`upgrade.MissingExtensions`), naming the extension, since the trial boot would refuse; the bundle's `extensions/<name>.sqfs` members for the extensions the configuration names are staged in the store before the trial is armed ([ADR 0084](./adr/0084-an-upgrade-bundle-carries-the-extensions-the-hosts-configuration-names-and-an-entry-without-a-digest-is-resolved-by-init-to-the-image-built-for-its-version.md)).
- **Signals.** SIGTERM stops every service, then, in this order: closes the Node API, kills the processes in `naru/detached`, unmounts the system extensions, the storage disks (last mounted first) and the data disk, syncs and powers off. Each unmount that fails is logged at error level (`unmount at shutdown failed`, with the kind and the mount point) and the rest go on; each that succeeds is logged `unmounted at shutdown`. SIGINT does the same and reboots. Init ignores SIGHUP, SIGQUIT and SIGABRT, which Go would end the process on and so panic the kernel; every other signal it does not act on is caught by Go's runtime with no action taken. Init makes the kernel's Ctrl-Alt-Del a SIGINT (`reboot(CAD_OFF)`, a warning if refused), so the stop request mvmd sends a Firecracker guest takes this path. A reboot the Node API accepted is a SIGINT sent to init's own signal channel, so there is one stop path.

## What init requires of mvmd's placement

mvmd places its supervisors outside its own cgroup, so that stopping mvmd does not stop a running microVM (mvmd `runtime.md` §Fencing; mvmd ADR 0003 §Placement; mvmd ADR 0015). Read at the commit above, in `daemon/internal/supervision/supervision.go`, `supervision/cgroup.go` and `app/config.go`:

- `supervision.cgroup` is an absolute cgroup v2 directory in which mvmd starts each supervisor. mvmd opens it and does not create it, so it must exist when mvmd starts. If it is empty, the supervisors stay in mvmd's cgroup, which `cgroup.kill` on mvmd's leaf then kills with it.
- `supervision.vmm_cgroup` defaults to `/sys/fs/cgroup/mvmd-vmm`. mvmd creates it, writes `+cpu +memory +pids` to its `cgroup.subtree_control`, and makes one cgroup per VMM under it. That needs the three controllers enabled in the root's `subtree_control`.

What init provides, and what the Node's configuration must carry:

- Init creates `/sys/fs/cgroup/naru/detached` and enables the three controllers at the root and in `naru/`. mvmd's default VMM parent then works, and `detached` is outside mvmd's leaf `/sys/fs/cgroup/naru/mvmd`.
- The mvmd service's configuration must set `supervision.cgroup` to `/sys/fs/cgroup/naru/detached`. Init does not write mvmd's configuration (naru knows no service's internals, [config.md](./config.md)), so the Node's `naru.yaml` passes it in the service's `args` or `env`, or in a file of `spec.files` the service's `-config` names.
- mvmd's VMM cgroups go under `supervision.vmm_cgroup`, whose default is `/sys/fs/cgroup/mvmd-vmm` (`DefaultVMMCgroup` in `daemon/internal/supervision/supervision.go`, at the commit above). That is under the root, whose controllers init enables, so the Node's configuration leaves `supervision.vmm_cgroup` at its default.
- A host kernel built with `CONFIG_RT_GROUP_SCHED` needs the supervisors in the root cgroup (mvmd ADR 0015). Init does not provide that: it runs every service in `naru/`. Whether the P0 kernel is built with the option is [image.md](./image.md)'s to decide.

## Pinned dependencies

`lib/init/go.mod` pins `go.yaml.in/yaml/v4`, `github.com/vishvananda/netlink` (the netlink client, with `github.com/vishvananda/netns` and `golang.org/x/sys` beneath it), `golang.org/x/net` (its `bpf` package, for the DHCP client's socket filter in `lib/init/linux`), `github.com/prometheus/client_golang` (the `naru_init_*` metrics, `lib/init/run`) and `github.com/stretchr/testify`; `go.sum` and the Go checksum database fix what each version means. The PM moves them: the PM reviews the pins when an advisory is published for one of them and at each Go minor release, and bumps the module in a pull request. No dependency bot is configured (`.github/` holds no `dependabot.yml`).

## Open questions

- **Verifying the P0 kernel's options.** Whether the image's kernel has `CONFIG_RT_GROUP_SCHED` off and cgroup v2 with the three controllers on is checked by the QEMU test of the image, not by init.
- **Boot and PID 1 behaviour.** Init's behaviour as PID 1 (mounts, console, power-off, reboot) is covered by the QEMU test of the image, not by `make test`; the unmounts of a shutdown by `tests/shutdown_test.go`, which reboots a Node with a mounted extension and reads the console.
- **A failed service.** A service that keeps failing is restarted at 30 s forever; whether init gives up is not decided. A Node reports it: `GET /v1/services` gives each service's state and restart count ([ADR 0017](./adr/0017-the-node-api-is-served-by-init-over-mutual-tls-from-its-own-authority-and-naructl-is-its-client.md)).
