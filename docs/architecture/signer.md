# Signer

What `naru-signer` is: the one process that holds the keys of naru's authorities and issues certificates, so that no other process, orch included, can make an identity. It is the first of garamsh/aurora#811's A2 to A5 built; the roles, the revocation list, the admission statement and the encrypted files it uses are `lib/identity`'s ([README](../../lib/identity/README.md)).

## Current decisions

- **`naru-signer` is a binary of the `host/` module,** with its code in `host/internal/signer` and its composition in `host/cmd/naru-signer`. It imports `lib/identity` and no other unit. The image carries it as `/bin/naru-signer` ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md)).
- **Its directory holds every key and is private.** `--dir` (default `/var/lib/naru/signer`) must be mode 0700 and owned by the user the signer runs as, or it refuses to start. Each file is 0600; a key file with a wider mode, or a directory with some of the authorities and not all, is refused at start.
- **What `init` makes.** The host, operator and orch authorities (ECDSA P-256, ten years), the revocation key (Ed25519), the first root certificate for a certificate request the caller supplies, and the empty revocation list at sequence 1. It records the recovery key's public half and writes the revocation key's public half as a PKIX PEM (`--revocation-public-key`), which orch verifies the list with. A directory that holds authorities is not initialised again.
- **Roles and who may do what.**

  | Call | root | operator | reader, automation, orch, host |
  | --- | --- | --- | --- |
  | `POST /v1/operator` (issue operator, reader or automation) | yes | 403 | 403 |
  | `POST /v1/orch` (issue orch) | yes | 403 | 403 |
  | `POST /v1/revoke` | yes | yes, except a serial that is root's: 403 | 403 |
  | `POST /v1/crl` | the revocation key's signature on the list is the authentication: no role, no request envelope | | |
  | `GET /v1/bundle`, `POST /v1/restore`, `POST /v1/replicate` | yes | 403 | 403 |
  | `POST /v1/host` | the statement must be an operator's or root's | | |
  | `POST /v1/reissue-root` | the recovery key's signature on the request is the authentication: no role, no certificate | | |

- **Where it listens.** HTTP on a unix socket (`--socket`, mode `--socket-mode`, default 0660); the group that may reach it is the deployment's. `GET /v1/crl` (the signed revocation list) and `GET /v1/ca` (the three authority certificates and the revocation key's public half) answer anyone who reaches the socket. `GET /v1/bundle` carries its signed request in the header `X-Naru-Request`, base64. With `--peer-listen`, a TLS 1.3 listener serves `POST /v1/replicate` and nothing else.
- **Authentication is by signature.** A request is the signed envelope of `lib/identity` (`SignRequest`, `VerifyRequest`): action, expiry, body, the caller's certificate. The signer checks the chain against the operator authority for client authentication, the revocation list, the signature, the action and the expiry, then the role. `identity.Authenticate` and `VerifyRequest` are the authenticator seam: authorisation reads only the `Identity` they return.
- **Host certificates.** `POST /v1/host` takes an admission statement and the host's certificate request. The signer runs `VerifyAdmission` itself, requires the SHA-256 of the request's public key to equal the statement's `hostKeySHA256`, and issues CN=hostID, OU host, server and client authentication, one year, with the issue logged (host ID, serial, key hash, the operator's name and serial). A host ID is a name: letters, digits, `.`, `_`, `-`, at most 128.
- **Other certificates** carry one year. An orch certificate also carries the DNS names and IP addresses of the certificate request, which root authorised by signing the request. Operator, reader and automation certificates carry client authentication only; host and orch carry both. Root is made only by `init`.
- **Revocation.** A revoke adds a serial, signs the list again with the next sequence number and writes it before the signer uses it. A serial already on the list changes nothing. The signer records the role of every serial it issues in `issued.json` of its directory (0600, written before the certificate is handed out, carried by the bundle), and a revoke of a serial recorded as root's needs root. A serial the signer has no record of, one issued before the record existed, is not protected.
- **Replicas share one list.** `POST /v1/crl` takes a signed list and answers with the list the signer holds afterwards; the revocation key must have signed it, else 403. The list also carries the nonces of the reissue requests taken, each with its request's expiry, and a nonce past its expiry is dropped at the next signing. A list that adds no serial and no live nonce to the signer's own changes nothing. A list with a higher sequence whose serials and live nonces are a superset of the signer's own is adopted and written. Lists that each hold a serial or a live nonce the other lacks are merged and signed again at the higher sequence plus one. A signer that has taken a list this way is peered (an empty `peered` file in its directory) and refuses `reissue-root` until it has taken one within 30 seconds, as it does after a restart until the next push; a signer never pushed to is alone. ([ADR 0052](./adr/0052-a-reissue-nonce-is-signed-into-the-revocation-list-so-orchs-sync-carries-it-to-every-signer-and-a-peered-signer-refuses-a-reissue-until-it-has-taken-the-list-lately.md)) Orch carries the lists between the signers ([orch.md](./orch.md)); each signer's own sequence still rises by its own revokes, so two signers that merge independently sign different lists at the same sequence, and the next sync merges those again until they agree.
- **Bundle and restore.** `GET /v1/bundle` returns every authority key sealed to the recovery key's X25519 public half. `POST /v1/restore` fills a blank directory from a bundle, the path of the recovery key's file and the path of its passphrase file, and root's authorisation signed for the SHA-256 of that bundle; the authorisation is verified against the bundle's own authorities. The certificates issued before the loss verify against the restored authorities. The recovery key is made outside the signer and never enters its directory.
- **Reissuing root.** `POST /v1/reissue-root` is for the holder of the recovery key who has lost root's person file. Its request is signed with the recovery key's Ed25519 half and carries the certificate request of the new root key, an expiry of at most ten minutes ahead and a random nonce; the signer verifies it against the recovery key's public half, refuses a nonce on its revocation list that has not expired, so a captured request is taken once, and refuses with 409 a peered signer (see Replicas share one list) that has not taken a list in the last 30 seconds. It then signs the list once, at the next sequence, with the nonce and its expiry and every serial `issued.json` records as root's, and issues the new root (CN root, OU root, one year) under the operator authority. The signer logs the new serial and key hash, the hash of the recovery key's public half, the nonce and the revoked serials. The revocation and the nonce reach another signer by the list sync, and that signer refuses the old root and the replayed request from then on. A root serial with no record is not revoked by it. ([ADR 0051](./adr/0051-the-recovery-key-signs-a-once-only-request-for-a-new-root-certificate-and-the-signer-revokes-every-root-serial-it-recorded.md), nonce and sync: [ADR 0052](./adr/0052-a-reissue-nonce-is-signed-into-the-revocation-list-so-orchs-sync-carries-it-to-every-signer-and-a-peered-signer-refuses-a-reissue-until-it-has-taken-the-list-lately.md))
- **Replication.** A blank signer's `join-key` makes an ephemeral X25519 key; root signs an authorisation for its host ID and that key; `join` posts it to a running signer's peer listener, pinned to the orch authority, and receives the bundle sealed to the ephemeral key. The peer listener's serving certificate is signed by the orch authority in memory with no key on disk. The new signer verifies root's authorisation against what it received before it writes, and removes the ephemeral key.
- **No authority key leaves the directory unencrypted.** The bundle and the replication answer are sealed; the operator's key is in its encrypted person file; the recovery key is encrypted. A test scans a bootstrap's temporary root for private keys outside the directory.
- **`naructl operator add|revoke`** signs a request with the person file given by `--admin` (opened with `--passphrase-file`) and sends it to the socket; `add` takes the certificate request by path and writes the issued certificate.

- **Deployment.** A Node runs it from `spec.signer` ([config.md](./config.md)): init runs `naru-signer serve` as user and group 6001 with `--dir=/var/lib/naru/signer` (0700, owned by 6001) and its socket `/run/naru-signer/signer.sock`, whose group is 6001; orch's user is 6002 with 6001 as a supplementary group, so it reaches the socket and cannot read the directory. A `bootstrap` makes init run `naru-signer init` once, while the directory has no `recovery-public.json`. A `replica` makes it run `join-key` at the first start, printing the public join key (base64 of the 32 bytes) on the console, and, once root has authorised the key for the host ID `metadata.name`, `join` against `replica.join.peer` pinned to `replica.join.peerCA`; neither runs again once the directory holds authorities. A signer whose directory holds no authority serves its socket alone, so that `restore` reaches it, and ends once the directory holds them, so init starts it again with every listener: the peer listener signs its serving certificate with an authority the blank signer did not have. ([ADR 0040](./adr/0040-naru-signer-alone-holds-the-authority-keys-in-a-private-directory-and-issues-certificates-over-a-unix-socket-against-signed-requests-and-a-recovery-key-opens-the-bundle-that-restores-them.md) item 9 has the restore fill a blank directory, which a signer that refuses to serve it could not do.) `--metrics-addr` serves `naru_signer_http_requests_total` by listener, method and code. ([ADR 0050](./adr/0050-the-image-carries-orch-and-the-signer-and-init-runs-them-as-separate-users-from-spec-orch-spec-signer-and-spec-metrics.md))
### Making and using identities with naructl

- **`naructl operator request`** writes a new ECDSA key (0600, never printed) and the certificate request for it; `--der` writes the DER that `naru-signer init --root-csr` reads. **`naructl operator person`** joins that key and its issued certificate into the encrypted person file, and removes the plain key.
- **`naructl orch csr`** does the same for orch, with the DNS names and IP addresses its certificate serves; **`naructl orch issue`** has the signer issue orch's certificate with root's person file.
- **`naructl signer authorise-replica`** signs root's authorisation for a host's signer and its join key; **`bundle`** writes the authorities sealed to the recovery key; **`restore`** fills a blank signer from that bundle. These three are root's.
- **`naructl signer reissue-root`** is the recovery key's, for a lost root person file: `--recovery-key` and `--passphrase-file` are local files, the key is opened on that machine and signs the request, and `--csr` (from `naructl operator request`), `--socket` and `--out` name the request, the signer and the certificate written. `naructl operator person` joins the certificate with the request's key.

## Why

- **A separate process with a private directory** is what keeps orch from minting identities: orch asks, and the signer verifies a signature orch cannot make. ([ADR 0040](./adr/0040-naru-signer-alone-holds-the-authority-keys-in-a-private-directory-and-issues-certificates-over-a-unix-socket-against-signed-requests-and-a-recovery-key-opens-the-bundle-that-restores-them.md))
- **The threat model** is orch, and any other user of the machine, reading the keys. That orch's user cannot read the directory is enforced by ownership at deployment (the user `naru-signer`, the directory 0700), and is stated as such; the signer checks the directory's mode and owner and cannot check how orch is run.
- **Accepted risks:** a signed request can be replayed until it expires, except a reissue of root, whose nonce is on the revocation list every signer takes (a replay on a second signer during the sync interval after the first use still succeeds when its caller reaches that signer's socket, because a push is no proof that orch made it); a root serial the signer has no record of is not revoked by a reissue; an operator can revoke any serial the signer has no record of as root's, and the recovery key reissues root; anyone who reaches the socket may push a list the revocation key signed, which is a replay of an older list at worst and never removes a serial; a host certificate lasts a year with no renewal and no subject alternative name; the bundle and the recovery key are the one recovery path; the join is TLS with server authentication, and the binding of root's authorisation to the ephemeral key is its client authentication.
- **The operator's key is a file behind `crypto.Signer`,** so a hardware key replaces the file without a change to a caller.

## Open questions

- **aurora#811 A4 is not built:** `naructl login` with a second factor and short-lived certificates, re-confirmation of dangerous actions, passkeys, hardware keys and single sign-on.
- **Renewal of a host certificate,** and a subject alternative name for it.
