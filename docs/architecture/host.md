# Host API

What `naru-hostd` is: the service that creates, shows and destroys microVMs on a Node through mvmd's local runtime API, and what it asks of the Node's configuration. This is the interface a control plane above the Node (garamsh/aurora) calls; gaon's own Node Agent is a separate caller of the same mvmd.

## Current decisions

- **`naru-hostd` is a unit.** It is the module `host/`, with one binary, `cmd/naru-hostd`. The image carries it as `/bin/naru-hostd`. A Node runs it only when its configuration has `spec.host`; naructl writes the service into `spec.services` then, after mvmd, and init supervises it like any other service ([ADR 0028](./adr/0028-naru-hostd-serves-a-host-api-over-mutual-tls-from-its-own-authority-and-creates-microvms-through-mvmds-runtime-api.md)).
- **Where it listens.** HTTPS over mutual TLS 1.3 on `0.0.0.0:7443`. The client's certificate must verify against `--client-ca`; the role is the client certificate's Organization, the highest of those it carries (`naru:host-provisioner` is `provisioner`, `naru:host-reader` is `reader`), or, for a certificate whose one OrganizationalUnit is a role of `lib/identity`, `provisioner` for `orch` (the pair naru-signer issues to orch), `root` and `operator`, `reader` for `reader` and `automation` ([ADR 0080](./adr/0080-a-seed-joined-host-accepts-an-operator-certificate-the-signer-issued-and-takes-its-role-from-the-certificates-organizational-unit.md)), and a certificate with none of these is refused with 403. `--client-ca` is a bundle: the host authority, and the authority orch's certificate chains to where orch reaches this host. The authority is the host authority, `<ca-dir>/host/ca.pem`, which is neither gaon's CA nor the Node API's.
- **Leader token.** A mutating call (any method but GET and HEAD) from the orch leader carries `X-Naru-Leader-Token`. After the role check, hostd refuses a token lower than the highest it has seen with 409 and the code `stale-leader-token`; a higher token is written to `--leader-token-file` (default `/var/lib/naru/hostd/leader-token`) with `lib/atomicfile` before the call runs. A call without the header is an operator's and is not checked; a header that is not a positive integer is 400 ([ADR 0071](./adr/0071-an-orch-leader-fences-its-etcd-writes-and-its-host-calls-with-the-revision-of-its-election-key-and-a-host-refuses-a-lower-token.md)).
- **What each role may do.**

  | `GET /v1/microvms`, `GET /v1/microvms/{name}` | yes | yes |
  | `POST /v1/microvms` | 403 | yes |
  | `POST /v1/microvms/{name}/stop`, `POST /v1/microvms/{name}/start` | 403 | yes |
  | `DELETE /v1/microvms/{name}` | 403 | yes |
  | `GET /v1/microvms/{name}/fence`, `GET /v1/snapshots`, `GET /v1/snapshots/{name}` | yes | yes |
  | `POST /v1/microvms/{name}/fence`, `POST /v1/microvms/{name}/snapshot` | 403 | yes |
  | `POST /v1/snapshots/{name}/resume`, `DELETE /v1/snapshots/{name}` | 403 | yes |
  | `GET /v1/networks`, `GET /v1/networks/{name}`, `GET /v1/peers`, `GET /v1/tunnel` | yes | yes |
  | `PUT /v1/networks/{name}`, `DELETE /v1/networks/{name}`, `PUT /v1/peers` | 403 | yes |
  | `POST /v1/boot-sets`, `DELETE /v1/boot-sets/{name}` | 403 | yes |
  | `POST /v1/reset` | 403 | yes |
  | `GET /v1/maintenance` (maintenance mode only) | yes | yes |
  | `PUT /v1/identity` | 403 | yes |

- **Reset and maintenance mode** ([ADR 0082](./adr/0082-a-host-resets-its-store-its-data-disk-or-both-through-post-v1-reset-at-its-next-boot-and-a-refused-host-serves-maintenance-mode-to-operators-under-orchs-host-ca.md)). `POST /v1/reset` takes `scope` (`store`, `data` or `all`) and `confirm`, which must equal the host's ID (`--host-id`, else the common name of `host.crt` beside `--host-key`, else the hostname; `GET /v1/host` returns it as `hostId`), and answers 202. hostd writes `/var/lib/naru/config/reset.json` (`--reset-marker`), reboots the host after 1 s, and init carries the reset out after it mounts the data disk: `store` removes the stored configuration, `data` everything but `config/`, `all` blanks and re-formats the disk. For `data` and `all` it answers 409 `revoked-pair` while the pair `--cert` names is revoked. With `--maintenance`, which init passes on a refused boot, hostd serves only `GET /v1/maintenance` and `POST /v1/reset`, to client certificates under orch's host CA, whose authority it takes from orch by the fingerprint `--orch-ca-sha256` and whose revocation it checks with `--revocation-public-key`; with no list, it refuses every client. A host that never enrolled is unreachable there. A Node is replaced, not reset. `naructl reset --scope --confirm` is the client.
- **`GET /v1/host`** returns `region`, `labels`, the Node's `capacity` and what is `free` (CPU, memory and state disk; CPU and memory of running Machines are subtracted), and mvmd's `version` and `driver`. Region and labels are read from `/run/naru-hostd/host.json` on every request, so a changed label shows at the next request.
- **`spec.host`** is `region` (a DNS label) and `labels` (Kubernetes label keys and values, at most 64). Parsing derives the file `/run/naru-hostd/host.json` from it as an entry of `spec.files`, so the apply engine writes it when `spec.host` changes and no service restarts: a label change is live ([config.md](./config.md), [init.md](./init.md)). An entry the user wrote at that path is replaced by the derived one.
- **`POST /v1/microvms`** takes `name` (a DNS label, which is mvmd's Machine ID), `image` (`repository@sha256:<digest>`), `cpu`, `memory` and `rootDiskBytes` (bytes), `disks` (`name`, `sizeBytes`, `readOnly`) and `networkPolicy` (`egress` and `ingress` rules of `prefix`, `protocol` and `ports`). It pulls the image, creates the disks as `<name>.<disk>`, creates the Machine and starts it, and answers 201 with the microVM. `env` and `command` are refused with 422: mvmd at the pinned commit has neither field.
- **The OS form** of `POST /v1/microvms` makes a microVM that boots a boot set mvmd offers, with no image and no root disk. It takes `name`, `cpu`, `memory`, `bootSet`, `cmdline` (optional), `seed` (the user-data, base64), `dataDisk` (bytes), `podPrefix` (optional, an IPv4 prefix of /16 to /32, routed to the Machine) and `networkPolicy`, and none of the image form's `image`, `rootDiskBytes`, `disks`, `env` and `command`: a request that mixes them is 422. hostd creates the data disk `<name>.data` with no file system (blank, for init to format, [init.md](./init.md)), then the Machine, then the seed disk `<name>.seed` (a NoCloud volume labelled `cidata` of `user-data`, `meta-data` and a version 1 `network-config` with the address mvmd gave the Machine, its netmask and the gateway), attaches the seed read-only, and starts the Machine. A volume over 1 MiB, mvmd's limit for a disk's contents, is 422 on `seed`. A failure before the start deletes what this request made, the Machine too once it exists, and not a disk or Machine of another request; a failed start leaves the Machine, and the same request starts it. The gateway is the flag `--machine-gateway`, which naructl sets to the first address of the Node's Machine prefix; without it an OS-form request is 501 ([ADR 0035](./adr/0035-the-host-api-creates-a-microvm-of-an-os-form-from-a-boot-set-with-a-data-disk-and-a-nocloud-seed-and-the-iso-9660-writer-is-a-library-module.md)).
- **A POST is idempotent by name, without state in hostd.** A request that names a Machine mvmd holds is compared with what mvmd recorded (image digest or boot set, command line, routed prefixes, restart on boot, CPU, memory, root disk size, disk sizes, network policy, and for the OS form the read-only seed; the seed's contents are not compared): the same request answers 200 with the same microVM, and a different one answers 409. A Machine that an interrupted request left Created or Stopped is started again.
- **`POST /v1/microvms/{name}/stop` and `.../start`** stop and start the Machine and answer 200 with the microVM as it is after. A stop of a microVM that is not running, and a start of one that is running, answer 200 without a call to mvmd; a name mvmd does not hold is 404, and a start mvmd refuses in the Machine's state is 409 ([ADR 0038](./adr/0038-the-host-api-stops-and-starts-a-microvm-and-restart-on-boot-brings-a-microvm-back-after-its-host-restarts-and-naructl-takes-the-os-forms-flags.md)).
- **`restartOnBoot`** is a field of `POST /v1/microvms`, true for the OS form and false for the image form when absent, passed to mvmd's `restart_on_boot` and shown in the microVM; a repeated request with another value is 409. After the host restarts, mvmd starts a Machine with it that was running, or being started, and had no stop since; a microVM stopped through the API stays stopped. A restart that fails leaves the Machine stopped, and mvmd's reason (it begins "the restart after the host's boot changed failed") is the microVM's `failure`; neither mvmd nor hostd retries ([ADR 0038](./adr/0038-the-host-api-stops-and-starts-a-microvm-and-restart-on-boot-brings-a-microvm-back-after-its-host-restarts-and-naructl-takes-the-os-forms-flags.md)).
- **`--metrics-addr`** makes hostd serve `/metrics` over plain HTTP on that address, from `lib/metrics`, and serve none when it is empty (the default). It exposes `naru_hostd_requests_total` by `route` (the route pattern, `none` for a request no route answered, a refusal for the role among them) and `code`, and `naru_hostd_microvms` by `state`, read from mvmd on each scrape; a scrape that cannot list the Machines exposes no `naru_hostd_microvms` series. Bind it to an address only the scraper reaches: it carries no authentication.
- **`fenced`** is a field of `POST /v1/microvms`, passed to mvmd's `fenced` and shown in the microVM. A fenced microVM is created and not started, an identical repeat does not start it either, and a repeat with another value is 409. `POST /v1/microvms/{name}/fence` takes `lengthSeconds` (1 to 86400) and `renewal` (above 0) and renews that microVM's own fence; `GET` on the path shows `phase` (`notArmed`, `armed`, `expired`), `lengthSeconds`, `remainingSeconds` and `renewal`. A start of a fenced microVM that is not armed is 409. The microVM shows `fenceLapsedAt` once its fence has lapsed, and `failure` carries mvmd's reason, which begins "the Machine's own fence lapsed". The caller renews the fence of a microVM; hostd renews none ([ADR 0043](./adr/0043-the-host-api-snapshots-and-resumes-a-microvm-gives-it-a-fence-of-its-own-and-its-types-and-client-are-the-module-lib-hostapi.md)).
- **Snapshots.** `POST /v1/microvms/{name}/snapshot` takes `name`, the snapshot's, and answers 201 with it; the microVM stays as it was, and one that mvmd cannot snapshot (not running, an OS form) is 409. `GET /v1/snapshots` and `GET /v1/snapshots/{name}` show them, `DELETE /v1/snapshots/{name}` deletes one (204, also when absent). `POST /v1/snapshots/{name}/resume` takes `name`, `networkPolicy`, `podPrefix` and `network` and makes a new running microVM, as mvmd restores a snapshot into a Machine of its own; a snapshot the host cannot restore is 409 with mvmd's reason ([ADR 0043](./adr/0043-the-host-api-snapshots-and-resumes-a-microvm-gives-it-a-fence-of-its-own-and-its-types-and-client-are-the-module-lib-hostapi.md)).
- **`DELETE /v1/microvms/{name}`** stops the Machine, deletes it and its disks that no snapshot lists, and answers 204. A name mvmd does not hold answers 404 after removing the unattached disks that carry the name's prefix and that no snapshot lists, so a retry finishes what an interrupted delete left. `DELETE /v1/snapshots/{name}` also deletes the snapshot's disks that no other snapshot lists and no Machine holds, so a snapshot stays resumable after its source is deleted ([ADR 0048](./adr/0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md)).
- **`POST /v1/boot-sets`** adds a boot set to the running host, with no reboot, through mvmd's `AddBootSet`. The body is `multipart/form-data`, read as a stream, with three parts in this order: `boot-set` (JSON `{name, kernelSha256, initramfsSha256}`, at most 4 KiB; `name` matches `[a-z0-9-]{1,63}` and each digest is 64 hexadecimal characters), `kernel` and `initramfs` (each at most 1 GiB; the request is bounded to 15 minutes). mvmd checks each file's SHA-256 as it receives it. It answers 200 with the request echoed, also for the same name and digests again; 409 for the name with other digests; 422 for an invalid request or a file whose SHA-256 is not the one named; 400 for a body that is not these parts in this order; 413 for a file over the limit. **`DELETE /v1/boot-sets/{name}`** removes the set and answers 204, also for a set mvmd does not hold; it is 409 while a Machine names the set ([ADR 0046](./adr/0046-the-host-api-adds-and-removes-a-boot-set-on-a-running-host-through-mvmds-runtime-api-and-a-release-carries-the-node-boot-set-as-a-kernel-an-initramfs-and-a-manifest.md)).
- **`PUT /v1/identity`** replaces the pair the host reports to orch with, for a rotation ([ADR 0077](./adr/0077-the-signer-rotates-a-hosts-pair-with-the-old-serial-revoked-registers-offline-pairs-by-serial-and-hostd-refuses-a-revoked-key.md)). The body is JSON `{certificate, key}` in PEM (64 KiB at most, unknown fields 400). The certificate must be for the host's own ID and unexpired and the key an ECDSA key, else 422. The host heartbeats to orch with the pair first and writes nothing when orch refuses (502); otherwise it writes the key and the certificate beside `--host-key`, each atomically, uses the pair from the next heartbeat, stores it as `serving.pem` beside `--host-key` (0600, one atomic rename) and presents it as the serving certificate from the next handshake (`tls.Config.GetCertificate`, no restart), and answers 200 with the serial in hex. A host not enrolled with orch is 409. It changes no trust of the host API's clients.
- **Its own key.** At start and every minute, `naru-hostd` serves, at start, the stored `serving.pem` when it is not on the list, else `--cert`, `--key` when that is not on the list, and else logs its file, subject and serial and exits 1 without serving; every minute it checks the pair it serves and the one beside `--host-key` and exits 1 on a revoked one. A wiped data disk loses `serving.pem`. A list not yet had is logged and the check retried. ([ADR 0077](./adr/0077-the-signer-rotates-a-hosts-pair-with-the-old-serial-revoked-registers-offline-pairs-by-serial-and-hostd-refuses-a-revoked-key.md))
- **Revocation.** `naru-hostd` refuses a client whose certificate chain holds a revoked serial, at the TLS handshake, through `lib/identity`'s `PeerCheck` ([ADR 0062](./adr/0062-every-naru-tls-peer-is-checked-against-the-signed-revocation-list-by-one-verifier-in-lib-identity-and-fails-closed-when-the-list-is-older-than-its-max-age.md)). With `--revocation-public-key` it reads the signed list from the signer socket (`--revocation-signer-socket`, a Node with `spec.signer`) or from orch's `GET /v1/crl` (`spec.host.orch`), keeps the last verified list in `--revocation-file` (`/var/lib/naru/hostd/crl.json`), seeds it from `--revocation-seed` (`spec.host.revocationList`, delivered at admission), and refuses every client when it has no list or the list is older than `--revocation-max-age` (default 10 minutes; `spec.host.revocationMaxAge`, 1 minute to 24 hours). A list with a lower `seq` than the one held is refused. Without the key nothing is checked and `naru-hostd` logs that at start. `/metrics` carries `naru_hostd_revocation_list_age_seconds`, `_seq` and `_fetch_error`. `spec.host.revocationPublicKey` is a PKIX PEM; `lib/layout` writes it for a host that joined from a seed and for a Node that has both orch and a signer.
- **Errors** are JSON `{"error": "..."}`: 404 not found, 409 conflict or precondition, 422 invalid request, 503 mvmd unavailable, 504 mvmd timed out, 502 any other mvmd failure. A call to mvmd that ends at its deadline is 504 whether the context ended it or mvmd answered with the gRPC code `DeadlineExceeded`; the client of `host/internal/mvmd` returns both as `context.DeadlineExceeded`.
- **Shutdown drains.** On SIGTERM or SIGINT hostd stops accepting connections, lets the requests in flight finish for up to 30 seconds (`api.DrainTimeout`), closes the connections of any still running, and exits 0. A connection made after the signal is refused.
- **An undo does not depend on the request.** What a failed `POST /v1/microvms` or resume removes (the Machine it stopped and deleted when the network refused it, the disks it made) is removed with a context of its own, bounded to 30 seconds and not cancelled with the request, since the request may have failed by being cancelled.
- **Fencing.** mvmd starts no Machine without an armed fencing deadline. `naru-hostd` renews it (length 10 minutes, every minute, retried after 5 s), with a number above mvmd's last, read from `InspectDeadline` at start and again after a failed renewal.
- **A seed-joined host's certificate names only its host ID.** The serving certificate of a host that joined from an install seed has one DNS name, `h-<id>`, and no IP address, because the address comes from DHCP and can change within the certificate's year. An operator reaches such a host by its address with `--server-name h-<id>` on any naructl command that calls the host API or the Node API: naructl dials `--endpoint` and verifies the certificate against that name instead of the address, with the same authority as the only root. No IP SAN is added.
- **Keys.** naructl issues the serving pair and writes it into `spec.files` (`/run/naru-hostd/tls.crt`, `tls.key` at `0600`, and `client-ca.crt`), as it does for the Node API. The host authority's key stays with the operator and is in no Node's user-data. The pair is valid one year and is not renewed.
- **Networks.** With `--management-prefix`, a host holds virtual networks, each a name, one prefix (the Pod and routed space) and a set of members, declared by `PUT /v1/networks/{name}` (`prefix`, optional `apiEndpoint` inside it, `remoteMembers`: the CIDRs of the network's microVMs on other hosts) and deleted by `DELETE`. A microVM is created on one with `network` in `POST /v1/microvms`, and so is a resume (`POST /v1/snapshots/{name}/resume`); its address is whatever mvmd gave it, and its `podPrefix` must be inside the prefix (422). `GET` of a microVM shows its `network` and `podPrefix`. hostd writes the nftables table `inet naru` and replaces it whole on each change: one set per network holds its prefix, its members and its remote members, and the forward chain drops by default and accepts a network's traffic inside its set, to its egress interface, and management's to the network's API endpoint. A network to another network's set and to the management prefix is dropped and counted by a rule of its own, and so is a packet from a tap whose source is no local member's, which counts only what mvmd lets pass: the ingress chain mvmd keeps for each tap (`table netdev mvmd`) has the policy drop and accepts IPv4 from the Machine's own address only, so a forged source is dropped there first and hostd's counter is the second layer. The input chain drops and counts a new connection from a tap, or from a network's set arriving by the tunnel, to any address of the host. Two networks on a host may share the Machine prefix. Without the flag these calls are 501 ([ADR 0048](./adr/0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md), which supersedes parts of [ADR 0045](./adr/0045-each-network-of-a-host-is-closed-by-default-by-an-nftables-table-hostd-writes-and-wireguard-carries-the-networks-between-hosts.md)).
- **The tunnel.** With `--tunnel`, hostd creates the WireGuard interface and its private key (`/var/lib/naru/hostd/wg.key`, mode 0600, generated at the first start, never returned or logged). `GET /v1/tunnel` shows the public key, the listen port and the host's Machine prefixes. `PUT /v1/peers` replaces the peers: public key, endpoint, and the prefixes the peer holds, which are its allowed IPs and the routes through the interface. hostd runs no `wg` ([ADR 0048](./adr/0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md)).
- **A declaration that changes nothing is not applied.** Orch declares its networks and peers again every few seconds; when the state a call makes equals the state the host holds, whatever the order of its lists, hostd runs no `nft` and writes no file, so the counters of the table's drop rules are not reset by it.
- **Members follow mvmd's machines.** At start, before the API serves, and then every 30 seconds, hostd lists mvmd's machines and drops each member whose address no machine holds, so a machine that mvmd lost or that was deleted while hostd was down leaves no address in a network's set for another network's microVM to inherit. A pass that cannot list the machines changes nothing and is logged.
- **A change commits whole or not at all.** The ruleset is one `nft -f` transaction. When the tunnel refuses the peers after it, or the state file cannot be written, hostd applies the previous state again, and the error names the step that failed; when that fails too, the error says so and the next change is applied even if it equals the state held. A prefix wider than /8 (a `/0` among them) in `remoteMembers` or a peer's `prefixes` is 422. hostd writes the table by exec'ing `nft` and the Node's fence uses google/nftables: the table is generated text pinned by golden files and read back with `nft list table inet naru`, and the fence has three rules.
- **The state of networks, members and peers** is the file `/var/lib/naru/hostd/networks.json` (`--networks-state`, mode 0600), written after each applied change by a temporary file and a rename. At start hostd applies it, or the empty table when there is none, before the API serves, so a restarted host forwards what it did and nothing more ([ADR 0048](./adr/0048-a-network-is-a-set-of-members-hostd-makes-its-own-tunnel-and-keeps-its-state-in-a-file-and-a-snapshot-keeps-the-disks-it-needs.md)).
- **`lib/hostapi`** holds the host API's request and response types and a Go client for it, which `host/` serves and `orch` calls. mvmd is pinned at b1a60cd in hostd's `go.mod`; the image's pin moves separately ([ADR 0043](./adr/0043-the-host-api-snapshots-and-resumes-a-microvm-gives-it-a-fence-of-its-own-and-its-types-and-client-are-the-module-lib-hostapi.md)).
- **`naructl`** is the client, with a client file (`--config`) or, for a seed-joined host, the person file of `naructl operator add` (`--identity --passphrase-file --host-ca --endpoint [--server-name]`, [ADR 0080](./adr/0080-a-seed-joined-host-accepts-an-operator-certificate-the-signer-issued-and-takes-its-role-from-the-certificates-organizational-unit.md)): `gen host-ca`, `gen host-client --role provisioner|reader`, `gen node --host-region --host-label`, `host`, and `microvm create|get|list|stop|start|delete|snapshot|fence get|fence renew`, `snapshot list|get|delete|resume`, `host network put|get|list|delete`, `host peers get|set`, `host tunnel` and `host boot-set add <naru-node-<tag>.json>|remove <name>` (the files the manifest names are read from beside it) ([config.md](./config.md)).

- **`naru-hostd --join`** ([ADR 0059](./adr/0059-orch-admits-a-host-that-boots-from-an-install-seed-allocates-its-machine-prefix-and-builds-its-configuration-from-one-fleet-profile.md)) runs the enrollment agent alone, for a host that booted from an install seed: `--join --orch-url --orch-ca-sha256 --enroll-key /run/naru-hostd/enroll.key --host-key /var/lib/naru/hostd/host.key --join-config /var/lib/naru/join/config.yaml`. The host ID is `h-` and the first 16 hex digits of the SHA-256 of the DER of its public key. It reports its hardware (read from `/proc` and `/sys`: each disk's size, model and partition count; hostd calls no disk blank, which is init's check of the join form alone) and its address, prints the pairing code, and on admission writes the configuration it is handed (0600, atomically) and its certificate, then exits 0 for init to apply the configuration. A run that finds the certificate and the configuration already written exits 0 at once.

## Rationale

- [ADR 0082](./adr/0082-a-host-resets-its-store-its-data-disk-or-both-through-post-v1-reset-at-its-next-boot-and-a-refused-host-serves-maintenance-mode-to-operators-under-orchs-host-ca.md): the reset, its scopes, the marker, and maintenance mode with its trust anchor.
- [ADR 0080](./adr/0080-a-seed-joined-host-accepts-an-operator-certificate-the-signer-issued-and-takes-its-role-from-the-certificates-organizational-unit.md): the operator credential a seed-joined host accepts, the roles of the signer's units, and the `--identity` form.
- [ADR 0071](./adr/0071-an-orch-leader-fences-its-etcd-writes-and-its-host-calls-with-the-revision-of-its-election-key-and-a-host-refuses-a-lower-token.md): the leader token, the header, the refusal and the file that keeps the highest token.

## Open questions

- **The tap prefix.** The tap name prefix is not reported by mvmd.
- **Inspecting one snapshot.** mvmd has no such call; hostd lists them all and picks one.

- **`env` and `command`.** The issue asks for them; mvmd's runtime API at the pinned commit has no such fields, and hostd refuses them. They are added when the pin moves to a commit that has them.
- **A crash between the Machine and its seed.** The Machine stays Created with no seed and a repeat of the request is 409; the operator deletes it.
- **Removing `spec.host`.** The apply engine removes no file, so the derived file stays on the Node's tmpfs until the next boot; the service keeps running until it is removed from `spec.services`.
- **Renewing the serving pair.** It is valid one year, as the Node API's is, and no one renews it.
- **Sharing mvmd with gaon's Node Agent.** Both renew mvmd's one fencing deadline. hostd re-reads the deadline after a failure, so the two converge, and what the Node Agent does under that is gaon's to say.
